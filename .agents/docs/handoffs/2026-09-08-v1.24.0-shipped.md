## The one thing that matters for whoever picks this up

**The feature has never been used.** It shipped inert and is still inert:

```
lan_allow_host=0   lan_allow_published_ports=0
STYRMAN-IN: -j DROP only        STYRMAN-FWD: 6 DROPs, 0 allowance rules
```

Two things named in the gate report as unproven remain unproven, and no
amount of desk-checking will change that:

1. **No LAN allowance has ever been applied by the v4 script on real
   hardware.** Every firewall test is either the unshare namespace or a
   no-marker run against live chains.
2. **The published-port path has never been exercised live.** The
   `integration.sh` assertions exist and skip.

Both are blocked behind the opt-in, and the opt-in is blocked behind sshd.

## Blocked: the sshd precondition

`install.sh --lan-allow-host 1` refuses on this host because sshd accepts
password authentication — R12, now enforced in code rather than documented
and hoped for. The five-step hardening sequence is in `deploy/remote.md`.

**The open question is which public key the operator's own client uses.**
`~/.ssh/id_ed25519.pub` on this host is the HOST's key; if the operator SSHes
in from another machine with a different key and hardening happens without
adding it, they are locked out. Get that key (or confirmation of console
access) before touching `/etc/ssh`.

Note also: on 2026-09-08 the auto-mode classifier denied
`sudo bash deploy/firewall/install.sh --lan-allow-host 1` twice, including a
natural variation, so the opt-in was never actually attempted against the
gate. The operator can run it directly or add a Bash permission rule.

## What the gate cost, and the two lessons worth keeping

Sixteen findings across three review rounds — eleven fixed, one deleted by
design, four subsumed. In each of the three rounds the previous round's fixes
introduced the next round's worst defect.

1. **The best fix was deletion, twice.** The credential latch removed a
   question that had no reliable answer (net −53 lines); the rewritten sshd
   gate stopped trying to evaluate `Match` blocks and refuses on "cannot
   tell". Both are shorter than what they replaced. When a second round of
   findings lands on the same mechanism, ask what the mechanism is for.
2. **The mechanical gate proves the tree builds, not that it is correct.**
   `verify-commit.sh` and every suite were green before all three rounds and
   caught none of the sixteen.

## Corrections carried forward

- **`dc5bad4`'s commit message contains a false claim** ("install.sh --dry-run
  reaches the end on both opt-in paths"). It was verified only under `sudo`,
  where sshd is on PATH; as non-root it exited 1 with empty output. The
  commit is pushed and cannot be amended — the correction is in the gate
  report.
- **A `Monitor` armed on the production deploy emitted nothing for 15
  minutes** across a deploy that had already succeeded, so it would have been
  silent on a failure too. The live state was established by looking.
- The brokered SSH key does not open this host (no `authorized_keys` for
  either account); what `LAN_ALLOW_HOST=1` opens is sshd with password auth
  plus `%sudo NOPASSWD:ALL`. ADR-066 records this.
