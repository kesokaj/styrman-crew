## Root cause (FAIL)

Two independent problems surfaced by Tier 4 e2e, both first exercised in this range (v1.19.1..d24fe40):

1. **Files panel regression.** In the self-hosted e2e server, a freshly created project's Files → Project scope shows "Empty directory" even though the project workspace demonstrably has content (screenshot `/tmp/styrman-shots/04-files.png`, captured mid-run, shows the terminal having already run `git init`-backed commands, `mkdir subdir`, and `echo hi > subdir/nested.txt`, while the right-hand Files panel simultaneously reads "Project" / "Empty directory"). Every downstream file-explorer and editor-pane check cascades from this single failure. The only commit in range touching file-listing path resolution is `cd11dd0` ("harness replacement phase 3: … tenant-confined roots for every path below a mounted home (BUG-002, BUG-003)"), which reworked `internal/files.go` to open per-tenant roots via `os.Root` under `HomesDir/<u>` and `StateDir/projects/<u>`. Tier 2 integration checks for file listing still pass (they exercise the API directly against a differently-provisioned isolated server), so this looks like a gap between the integration fixture and the real project-creation/mount path the e2e browser flow exercises — not something integration.sh's existing checks catch. Needs a `bug` diagnosis pass with the e2e server's own logs (not captured here: `web/e2e/run.sh`'s `cleanup()` trap deletes the isolated `STATE` dir, including `server.log`, on exit, before this failure could be inspected server-side).
2. **Git clone path.** `failed clone still leaves a git repo (R13)` got an empty file listing (`no .git in workspace: []`) and the follow-on `successful clone fills the workspace` timed out at 180s. Given (1), these are plausibly the same underlying file-listing/mount problem rather than two separate clone regressions, but that is not confirmed — the clone itself may also be failing (no network egress check was done for the "successful clone" case, though the test's own OFFLINE-detection path was not triggered, so it did not classify this as a SKIP).
3. **`web/dist` non-reproducibility.** `web/e2e/run.sh` rebuilds `web/dist` in the live working tree before starting; after the run, `web/src/lib/../dist/client/_shell.html` differs byte-for-byte from the committed version (same size, different bytes) even though `deploy/verify-commit.sh` had certified freshness against the same commit minutes earlier in an isolated worktree. Something in the build (a timestamp, non-deterministic ordering, or environment-dependent embed) is not content-addressed the way `verify-commit.sh`'s check assumes. Not fixed here; flagged for `bug` review.
