**Design note on scenario (h):** before settling on `chattr +i`, I verified empirically
(`<scratch>/mvtest/`) that the task's alternative suggestion — "a directory in its place" at the
destination path — does **not** actually make the install fail: `mv -f "<dst>.new.$$" "<dst>"`
when `<dst>` already exists as a directory silently moves the temp file *inside* that directory
(`<dst>/<dst>.new.$$`) rather than erroring, so `atomic_install()` would wrongly report success
without the file actually landing at `<dst>`. This is worth flagging as a latent robustness gap
(not a new regression — pre-existing in the reviewed code, low severity: it would require the
destination path to already be a directory, which nothing in the ADR-052-validated ownership/mode
checks rules out but which is an unusual environment state) but it is out of scope to fix here per
the verifier's remit; noting it for the record. `chattr +i` on the unit dir was used instead and is
a reliable, unambiguous install-time failure (`install: cannot create regular file ...: Operation
not permitted`), matching the task brief's other suggested method.
