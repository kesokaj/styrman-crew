## Honest summary

Three of the four items are exercised (two via existing/expanded e2e checks, one via a direct
root hand-run consistent with this script's established, non-automatable verification
convention). The fourth — the new `upload()`/`evictUploaded()` logic in `FileExplorer.tsx` — is
genuinely new client-side branching (success vs. failure eviction, base-name extraction, `?? []`
null-guard, `inDir()` joining) with **no test anywhere touching it**. This is exactly the class
of change the Definition of Done exists to catch: changed code with no covering test. Per the
verifier mandate ("no exceptions, no softening"), this is a blocking FAIL — regardless of the
fact that round 2's own coverage table listed the pre-refactor version of this same code path
("finding 6") as an accepted, documented residual. That earlier acceptance does not carry
forward as a waiver: the code changed again in this round, and it is still untested.

**What is missing, concretely:** a Playwright check in `web/e2e/run.mjs` that (a) uploads a file
whose name collides with one already open in a pane and asserts the pane is evicted using the
server's reported `saved` name, and (b) forces an upload failure (e.g., into a managed/blocked
dir) and asserts eviction still happens using the locally-known dropped file names. Absent that
— or an equivalent Go/integration-level test if the maintainers decide the client behavior is
better asserted there — this gap remains open.
