## Root cause (FAIL)

`internal/netpolicy/netpolicy.go` (this change set) bumped
`MinScriptVersion` from 3 to 4 — `Availability()` now rejects any root status
reporting `version` below 4 as "outdated" (fail-closed, by design: a script
that hasn't converged to the version implementing ADR-066 must not report a
LAN allowance the server can't trust).

`.agents/docs/testing/styrman/integration.sh` was itself touched by this
change set (43 lines, part of `git diff --stat`), but only in the
`STYRMAN_IT_LIVE_LAN` opt-in block at the tail of the file (host-allowance and
published-port live checks, correctly gated off by default). The **crafted
root status the non-live "local network (ADR-065)" section writes to fake out
`Availability()`** was left at the old literal — three occurrences of
`version=3` (lines 273, 280, 420) — never bumped to 4 alongside
`MinScriptVersion`. `web/e2e/run.mjs`'s equivalent crafted status, touched by
the same commit set, WAS correctly updated to `version=4` (confirmed by
reading it), which is why the e2e run's LAN checks (already reported 89/0/2)
were not affected — this is specifically an integration.sh omission, not a
server-side regression.

Effect, traced against the script's own logic: with `version=3` on disk,
`Availability()` always returns `ok=false`, so:
- `PUT .../network {lanAccess:true}` never leaves "the reconciler can't act
  on this yet" — it can accept the intent (marker + spool trigger get
  written) but `lanState` can never advance to `pending`/`on` because
  `Derive()` also gates on `Availability()`. Five checks in the "local
  network (ADR-065)" section fail as a direct result: "enable accepted with a
  fresh status → pending, never on", "marker projected for root", "spool
  trigger dropped", "project list carries lanState", "root reporting it
  applied → on".
- Later, the "stop + delete" section's re-enable-before-delete step
  (`curl -fsS -X PUT ${API}/api/projects/${ID}/network -d
  '{"lanAccess":true}' -o /dev/null`, line 422) hits the same stale-version
  status file, and this call is NOT wrapped in `|| true`. `curl -fsS` prints
  `curl: (22) The requested URL returned error: 503` and returns nonzero;
  under `set -euo pipefail` the script aborts on the spot. The cleanup trap
  still runs (containers were torn down), but the five checks queued after
  that line never execute at all: "marker present before the delete",
  "delete removed the LAN marker with the record", "container gone (async
  delete)", "workspace wiped", "project gone from API". `ABORTED` stays at
  its initial `1` because the trailing `ABORTED=0` is never reached — the
  script's own convention for "this run does not vouch for its late-arriving
  checks."

Fix is a documentation/test-fixture change only (no server code implicated):
bump the three `version=3` literals in
`.agents/docs/testing/styrman/integration.sh` (lines 273, 280, 420) to
`version=4`, matching `internal/netpolicy/netpolicy.go`'s `MinScriptVersion`
and `web/e2e/run.mjs`'s already-correct fixture. Per this dispatch's scope
("Do not edit source, tests, or any doc other than your own log"), that edit
was not made here — reported, not fixed.

The 3 unrelated "shell skel" FAILs ("seeded .bash_exports carries the new
GOPATH", "login shell resolves GOPATH to $HOME/.go", "$HOME/.go/bin joins
PATH once it exists") are pre-existing and NOT caused by this change set: the
runtime image used (`styrman-runtime:test`, built 2026-09-04T08:22 per
`docker inspect`) predates commit `fe00412` ("GOPATH is $HOME/.go in the
seeded skel"), and ADR-066's diff touches nothing under `image/`. These are
an environment-staleness gap (an out-of-date pinned test image), not a defect
in the commits under review — flagged here so they are not conflated with the
ADR-066 root cause above, but they are a real FAIL of this run's counts
nonetheless and the runtime image should be rebuilt before the next
integration run.
