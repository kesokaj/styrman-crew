## Verdict: FINDINGS

The read deadline works as tested. `acquireSlot` (explorer.go:487-489) now
sets a 30 s read deadline beside the 30 s write deadline, so a PUT or POST
whose body never arrives loses its editor slot at the deadline.
`TestASlowBodyReleasesItsSlotAtTheReadDeadline` drives that through
`s.Routes()`, the same handler `cmd/styrman/main.go:170` serves.

It does not do what its comment and the change entry claim. The pool is still
8 slots server-wide with no per-user share. One signed-in user can re-send 8
body-less PUTs every 30 s, hold every slot all the time, and keep every other
tenant's editor open, save, format and check on 429. The deadline bounds each
REQUEST, not the user. The reviewer's medium is narrowed (from "8 idle
connections" to "a trivial loop"), not closed.

There is also a latent hazard. `acquireSlot` is shared, so the history search,
the transcript read and the file read (body-less GETs) now get a read deadline
too. On a GET, net/http is already waiting on the connection when the handler
runs, and the deadline's expiry cancels the context of the whole CONNECTION.
Today that is harmless only because the write deadline is set a few ns earlier
to the same 30 s, which forces the connection closed.

No secrets, no new input parsing, no auth change, no crypto, no dependency
change.

## Findings
- **[medium / confidence: high]** `internal/httpapi/explorer.go:472-477`
  (comment), `:481-495` (`acquireSlot`), `:455-460` and
  `internal/httpapi/server.go:189-190` (the 8-slot `fileSlots` pool, shared by
  all users), `.agents/docs/changes/2026-10-05-1643-v1.42.3-read-deadline.md:10-13`.
  - **The claim:** the deadline stops "a client trickling 8 bodies" from
    locking "all tenants out of the editor".
  - **What it does:** each request now holds a slot for at most about 30 s
    and then releases it. writeFile, formatFile and checkFile all take the
    slot before decoding the body (explorer.go:274-286, format.go:61-78,
    check.go:338-355). Nothing stops the same user taking the slot straight
    back.
  - **How it is still exploitable:** a signed-in user sends
    `PUT .../file` with `Content-Length: 1048576` and no body (exactly the
    test's request) and sends another whenever one ends. That user holds
    8 of 8 slots continuously, at a cost of 8 requests per 30 s. Legitimate
    requests arriving in the gaps race a client that retries at once.
  - **Impact:** other tenants are locked out of the editor's file
    operations. No data is lost: the reviewer traced that a 429 on save
    keeps the buffer dirty.
  - **Prior acceptance:** this is the shape of the server-wide-pool class the
    operator accepted as low for search and read (preflight v1.42.2 row 3, as
    the reviewer cites it). The editor case was rated medium because the hold
    was indefinite; now it is merely repeatable. The operator decides whether
    that acceptance extends to the editor's pool.
  - **Remediation:** give each user a share of `fileSlots`: a
    `map[username]int` under a mutex, at most 2 of the 8 per user, 429
    beyond that. Standard library only. Correct the comment and the change
    entry so they no longer claim the lockout is closed.
- **[low / confidence: medium]** `internal/httpapi/explorer.go:487-489`,
  reached by three body-less GET handlers: `readFile` (:78-81),
  `searchHistory` (:512-516) and `readHistory` (:548-552).
  - **Mechanism** (go1.25.0 `net/http/server.go` on this host):
    - For a request without a body, the server starts a background read
      BEFORE the handler runs, and clears the deadline first (:2095-2099,
      :687-699).
    - `(*response).SetReadDeadline` sets the deadline on the connection
      itself (:499-500), so that pending read picks it up.
    - When the deadline expires and the read was not aborted,
      `handleReadErrorLocked` cancels the CONNECTION context (:729-732,
      :769-776). That context is created once per connection (:2012-2013)
      and is the parent of every request's context on it.
  - **(a) Undescribed effect:** on these GETs the read deadline also cancels
    `r.Context()` at 30 s, which ends `history.Search` (:516). The comment at
    :472-476 says the deadline bounds sending a BODY. api.md:192-193 names
    only the write deadline for search and read.
  - **(b) Canceled context on a reused connection:** the connection context
    stays canceled for every later request on that keep-alive connection, and
    the ingress reuses upstream connections across users. This cannot happen
    today. The write deadline is set a few ns earlier in the same call (:488)
    to the same 30 s, so a handler still running at the read deadline cannot
    flush its response: the `finishRequest` write fails and the connection is
    closed, not reused.
  - **(c) Address leak, blocked by the same ordering:** `writeErr`
    (server.go:1405) echoes errors verbatim. Called from explorer.go:286-287,
    format.go:78 and check.go:355, it would send the raw `*net.OpError` text
    of a body-read timeout ("read tcp <server>-><ingress>: i/o timeout") to
    the client. Today that response is never delivered.
  - **The unstated invariant:** (b) and (c) stay closed only while
    `historyWriteTimeout <= slotReadTimeout`. Nothing states or tests that.
    The new test itself runs with a 30 s write deadline and a 1 s read
    deadline, the unsafe order.
  - **Remediation:** set the read deadline only on requests that carry a
    body (pass `r` in and skip when `r.Body == http.NoBody`), or document the
    ordering and pin it with a test. Replace the echoed decode error with a
    fixed "cannot read request body".
  - **Basis:** not run (read-only dispatch). Read from the local go1.25.0
    source; production builds with golang:1.25.13
    (deploy/Dockerfile.server:9), not compared. Assumes the ingress-to-server
    hop is HTTP/1.1.
- **[low / confidence: high]** `internal/httpapi/write_deadline_test.go:76-89`
  (`TestASlowBodyReleasesItsSlotAtTheReadDeadline`).
  - **Gap:** the test checks that the slot was taken and later freed. It
    never checks that the slot was HELD until about the deadline. writeFile
    takes the slot before `scopeFor` (explorer.go:274-281). A future change
    that fails the request before the body decode would release the slot
    within microseconds, and this test would still pass without the deadline
    doing anything.
  - **Evidence today:** the only proof that the test catches a missing
    deadline is the author's one mutation run (change entry: "still held 8 s
    later").
  - **Not covered:** `/format` and `/check` (same order: format.go:61-78,
    check.go:338-355), and the body-less GET effect in finding 2.
  - **Remediation:** assert the slot is still held at about
    0.8 × `slotReadTimeout`, and run the same check against format and check.
