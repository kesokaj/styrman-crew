## Status: COMPLETE

## Verdict: FINDINGS

The worst problem is new and comes from the fix itself. `oom_score_adj: -1000` is inherited by every process the server forks. It does not apply only to the server binary. Among those children is the host-side `git rev-parse` that `internal/gitrepo` runs against every tenant's guest-writable workspace at every server boot (`cmd/styrman/main.go:296-315`). I measured its memory on this host, with the same hardening flags and env as `gitrepo.go`. Its RSS scales with the size of the repo's `.git/config`: a 12.9 MB config took 616 MiB (about 48×). So a config of about 1.3 GB, which any tenant can write into their own workspace, asks for more than dave's 62.4 GiB (no swap). Before 2ba3f79 that git process ran at adj 0 and was the kernel's first victim. At -1000 it cannot be killed. The kernel instead kills every other process on the host: the operator's sessions, dockerd, every tenant's VM. When nothing killable is left, it panics. dave runs `kernel.panic=0`, so the NUC then hangs until someone power-cycles it. Neither service has a memory limit (`Memory=0`), and ADR-084's stated guard ("its own health check and restart policy") does not exist.

Status of the earlier findings:
- **v1.42.0 finding 1** is only partly fixed. Server and Caddy no longer die first. But dockerd (-500) still dies before any VM below about half the host's memory, and systemd stops restarting it after 3 kills a minute. The "stop or resize a project" path ADR-084 promises then has no Docker behind it.
- **Finding 2** is fixed in the three living docs it named. The same argv form remains in the pre-existing fresh-host bring-up lines, and the closed plan still carries its line.
- **Addendum low 1** (`truncate`) is fixed, with a fail-open residue.
- **Addendum low 2** (reap bound) is fixed.
- No secrets in the range. The govulncheck and npm audit results are unchanged.

## Findings

- **[high / confidence: high (inheritance, measured amplification, measured host sysctls), medium (end-to-end; no OOM provoked on production)]**
  - **Where:** `deploy/docker-compose.yml:61`, `:157` (`oom_score_adj: -1000`, no `mem_limit`), `internal/gitrepo/gitrepo.go:40-52` (host-side `git` child), `cmd/styrman/main.go:296-315` (boot sweep: `IsRepo` → `rev-parse` on every workspace), `.agents/docs/architecture/DECISIONS.md:2866` (ADR-084 Consequences).
  - **The weakness: -1000 makes the platform's whole process tree unkillable, and a tenant controls the memory of one of its children.**
  - **Mechanism:**
    - `oom_score_adj` is copied on fork and kept across exec, so every child of `styrman-server` runs at -1000. `docker exec` processes in the container do too.
    - `gitrepo.git()` runs `git -C <workspace> … rev-parse --absolute-git-dir`. The workspace is bind-mounted into the tenant's VM with guest root, so `.git/config` is tenant-written. The `-c` overrides neutralise exec keys, but not size.
    - git loads the whole repo config into its config set.
  - **Measured on dave:**
    - Probe repo `.agents/scratch/sec-v1.42.1-git-config-probe` with gitrepo's exact `-c` list and `GIT_CONFIG_*` env, git 2.47.3:
      - 10k keys (109 KB): 10.9 MiB max RSS.
      - 1M keys (12.9 MB): 616 MiB max RSS.
    - Host: MemTotal 62.4 GiB, SwapTotal 0, `vm.overcommit_memory=1`, `vm.panic_on_oom=0`, `kernel.panic=0`.
    - Both containers have `HostConfig.Memory=0`.
  - **Scenario:**
    - A tenant writes a config of about 100M keys (about 1.3 GB) into their workspace's `.git/config`.
    - The next server start runs the boot sweep. That happens at every release deploy the auto-updater performs, starting with v1.42.1 itself. The sweep's 5-minute bound kills git only by deadline, and the memory runs out well before then.
    - Before 2ba3f79, git at adj 0 with the largest RSS was the kernel's first pick: git died, the sweep logged it, and the server continued.
    - Now the kernel kills, in order: every adj-0 process (operator shells and agent CLIs on dave, cron, updater ticks), then dockerd, then every tenant's VM by size, then containerd, virtiofsd and the shims.
    - The kernel then reports "Out of memory and no killable processes" and panics. With `kernel.panic=0` the host stays hung until power-cycled. All tenants are down.
    - The on-demand calls `internal/httpapi/provision.go:92`, `:155` were not traced. They may give the tenant a trigger without waiting for a restart.
  - **The same holds for the internet-facing ingress:**
    - Caddy, at -1000 and unlimited, holds the Docker socket (`docker-compose.yml:22-26`) and has no healthcheck (measured `Health=none`).
    - Any memory growth reachable without authentication (connections, buffering) now ends the same way instead of in a container restart.
    - Confidence that such growth is practical: low, not tested.
  - **ADR-084's guard is not real.** It says "a server that leaks memory is never killed by the kernel; its own health check and restart policy remain the guard".
    - Docker restart policies act only on exit, never on `unhealthy`.
    - Caddy has no health check at all.
    - The updater reads health only in its deploy wait (`deploy/update/styrman-update:917-927`).
  - **Remediation:**
    - (1) Use `oom_score_adj: -999`, not -1000.
      - It ties with the VMs, so the kernel compares RSS: a 16 MiB server or a 95 MiB Caddy is never chosen over a GiB-sized VM, but the largest -999 process, a ballooning child included, stays killable and `unless-stopped` restarts it.
      - ADR-084's "Rejected" list did not consider -999.
    - (2) Make host-side git cheaper to kill than its parent and refuse oversized input:
      - Raise the child's own adj. Raising needs no privilege: write `/proc/<pid>/oom_score_adj` after `Start`, or use `choom -n 1000 --`.
      - Cap its memory (`prlimit --as`).
      - Stat `.git/config` through the tenant root and refuse anything over a small bound before running git.
    - (3) Add `mem_limit` to both services, sized from measured peaks.
    - (4) Set `kernel.panic=<seconds>` in `host-setup.sh` so a panic reboots instead of hanging.
    - Tests:
      - a compose pin for the chosen adj and `mem_limit`;
      - a gitrepo test that plants an oversized `.git/config` and asserts the refusal;
      - a must-fail run of both.

- **[medium / confidence: high (measured adj, unit limits, live-restore), medium (kill order is computed from the kernel's `oom_badness`, not provoked)]**
  - **Where:** `.agents/docs/architecture/DECISIONS.md:2859-2866` (ADR-084 Decision, Rejected, Consequences), `deploy/docker-compose.yml:59-61`, `:156-157`.
  - **Finding 1 of the v1.42.0 review is only partly fixed:** the platform's Docker dependency still dies before the VMs.
  - **Measured on dave:**
    - dockerd (pid 843) runs at `oom_score_adj -500`, from docker.service `OOMScoreAdjust=-500`.
    - docker.service has `Restart=always`, `RestartUSec=2s`, `StartLimitBurst=3`, `StartLimitIntervalUSec=1min`.
    - Docker 29.7.2 runs with `LiveRestoreEnabled=true`.
    - containerd and every cloud-hypervisor and virtiofsd run at -999.
  - **Kill order:**
    - The kernel's score is RSS plus adj×totalpages/1000. So dockerd, with near-zero RSS at -500, outranks a VM at -999 unless that VM holds more than about 499/1000 of memory: roughly 31 GiB on dave.
    - Every adj-0 host process dies before either of them.
  - **Scenario:**
    - The v1.42.0 review's scenario, two whole-host projects running memory-heavy builds, splits memory so that neither VM passes about 31 GiB. Three VMs at about 20 GiB do the same.
    - The kernel kills the operator's processes, then dockerd. systemd restarts dockerd, and it is killed again.
    - After three kills in a minute systemd gives up, and dockerd stays down until `systemctl reset-failed docker`.
    - Live-restore keeps the VMs (and the pressure) running. The server is alive at -1000 but cannot stop, resize or start anything, because every orchestrator call needs dockerd.
    - Recovery still needs a host shell. That contradicts ADR-084's Consequences ("the platform stays reachable to stop or resize a project").
  - **Remediation:**
    - A host-setup drop-in for docker.service with `OOMScoreAdjust=-999`. dockerd's RSS is small, so on a tie the VMs go first. Add `StartLimitIntervalSec=0`.
    - Better: make the VMs the preferred victims, which is the half of the v1.42.0 remediation not taken.
      - ADR-084 rejected this because "the containerized server cannot reach" the shim.
      - But `host-setup.sh` already installs a root-owned host wrapper in the VMM's ancestry: `/usr/local/bin/containerd-shim-mvm-v2` (`deploy/lib/kata-config.sh`, BUG-089).
      - Raising its own adj before `exec` is unprivileged. Measure that the VMM keeps it (containerd may re-adjust shims).
    - Correct ADR-084's Consequences either way. Put the measured kill order in it.
