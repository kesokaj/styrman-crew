## Verdict: REQUEST CHANGES

The scripts themselves are in good shape — the previous round's high finding
(`GH_TOKEN` read through an unset `${STYRMAN_GH_TOKEN_FILE}` in a separate ssh
exec) is genuinely fixed, injection and secret-handling discipline matches
`styrman-ctl`, and `bash -n`/`shellcheck` are clean. The problem is the test
layer added with them: two of the eleven new tests only pass because the test
binary has **no controlling terminal**. Run `go test ./...` the way `AGENTS.md`
documents it, from the operator's own terminal, and
`TestGCPVMCreateNeedsYesWithoutTerminal` and
`TestGCPVMDeleteRefusesWithoutConfirm` go red — and the package hangs to its
timeout. Every green run cited for this change (the three verifier logs, the
prior review, my own first run) was made without a tty, so all of them
measured the other branch. That is the BUG-034/BUG-040 family the project's
own `verify-bare.md` rule exists for. Second: the one line the previous
round's high finding was about — `export GH_TOKEN` in `styrman-ctl`'s
`cmd_install` — has a test that passes with the export deleted.

## Findings

- **[high / confidence: high]** `internal/config/gcp_scripts_test.go:79-94`
  (`gcpRun`), reaching `:108-117` and `:161-179` — the child process inherits
  the test binary's controlling terminal, so `lib.sh`'s
  `has_tty() { ( : < /dev/tty ) 2>/dev/null; }` (`deploy/gcp/lib.sh:11`)
  returns **true** whenever `go test` is started from a terminal, and
  `vm.sh`'s `read -r -p … < /dev/tty` (`vm.sh:61`, `vm.sh:130`) is reached
  instead of the `die`/`return 2` branch the tests assert.
  Inputs and observed result (this machine, Go 1.27.1):
  - `go test ./internal/config/ -run 'GCP|StyrmanCtlInstallExportsToken'` → `ok 0.856s`
  - `script -qec "go test ./internal/config/ -run '^TestGCPVMCreateNeedsYesWithoutTerminal$' -count=1 -timeout 15s" /dev/null`
    → `--- FAIL: TestGCPVMCreateNeedsYesWithoutTerminal (0.01s)`
  - same for `^TestGCPVMDeleteRefusesWithoutConfirm$` → `--- FAIL (0.01s)`
  - `script -qec "go test ./internal/config/ -count=1 -timeout 90s" /dev/null`
    → `--- FAIL: TestGCPVMCreateNeedsYesWithoutTerminal` then
    `panic: test timed out after 1m30s` — the package never finishes.
  With a human at that terminal it is worse than a failure: `vm.sh` prompts
  on the operator's own tty and eats a line of their keystrokes.
  **Would a test catch it?** No — this *is* the test; the defect is that the
  suite's verdict depends on an ambient condition it never asserts.
  **Concrete fix:** detach the child in `gcpRun` —
  `cmd.SysProcAttr = &syscall.SysProcAttr{Setsid: true}` (a new session has no
  controlling terminal, so `/dev/tty` fails deterministically) — and, per
  `review-standards` §2, assert the condition holds: have the test also run
  the create path *with* a tty present (a `pty` pair, or a `STYRMAN_ASSUME_NO_TTY`
  knob) so both branches are exercised rather than one branch being reached by
  accident. The same treatment is owed to `ctlSetup`/`ctl` in
  `styrman_ctl_test.go`: the whole-package pty run above hangs past the two
  named failures, so at least one more test in that file prompts on a real
  terminal (not isolated here — see Not examined).

- **[medium / confidence: high]** `internal/config/styrman_ctl_test.go:896-925`
  (`TestStyrmanCtlInstallExportsTokenForHostSetup`) vs
  `deploy/styrman-ctl:457-461` — the test drives `install --dry-run`, so
  `run bash "${REPO}/deploy/host-setup.sh" --user …` (`styrman-ctl:462`) is only
  *echoed*; `host-setup.sh` never runs and its environment is never inspected.
  Every assertion in the test is about the **log line** (`"exported from
  --gh-token-file"`) and about strings *not* appearing. Delete
  `GH_TOKEN="$(tr -d '\n' < "${gh_token_file}")"; export GH_TOKEN` (line 459)
  and keep the `log` on line 460 and the test still passes — a test that
  cannot fail for the behaviour it names. This is precisely the line that
  repairs the previous round's high finding and the one BUG-071's `sed`
  restore corrupted once already, so it is the line that most needs a failing
  test. **Would `gcp_scripts_test.go` catch it?** No — it asserts only that
  `install.sh`'s plan carries `--gh-token-file "$HOME/.styrman-install/gh-token"`
  (`gcp_scripts_test.go:246`), which is true whatever `styrman-ctl` does with
  the flag. **Concrete fix:** in the `ctlSetup` fake-bin harness add a `bash`
  (or a `STYRMAN_HOST_SETUP` hook) fake that appends
  `host-setup GH_TOKEN_SET=${GH_TOKEN:+yes}` to `calls.log`, run `install`
  *without* `--dry-run` against the scratch prefix, and assert `GH_TOKEN_SET=yes`
  with `--gh-token-file` and `GH_TOKEN_SET=` without it — the value itself
  still never printed, as the existing sentinel check already enforces.

- **[medium / confidence: high]** `deploy/host-setup.sh:61-100` (the Kata step)
  — the R11 path this whole change exists to prove is still unverified on the
  only host that runs it. BUG-070's own record says "Verification of the fixed
  path on a fresh host is still pending", and the step is guarded by
  `[[ ! -x /opt/kata/bin/kata-runtime ]]`, so no re-run on the NUC can
  exercise it. There is no automated coverage either: `grep -n 'kata\|zstd'
  internal/config/*_test.go` finds only the unrelated `kata-runtime` version
  fake in `styrman_ctl_test.go:66`, and `deploy/verify-commit.sh` runs only
  `bash -n` over `host-setup.sh` (it was *not* added to the shellcheck line —
  a deliberate follow-up per the change entry's learning 4). The rule this
  same range adds, `.agents/rules/shared-path-learnings.md`, requires exactly
  this to be stated: "A change to such a step, or a release carrying one,
  states how the fresh-host path was exercised … or 'fresh-host path
  unexercised' in the gate report — never a green re-run on the NUC."
  Concrete failure scenario: `/preflight` cuts the release, the operator runs
  `deploy/gcp/install.sh --version <new>` against the VM, and a wrong asset
  name, a missing `digest` field in GitHub's API answer, or an `apt-get
  install zstd` on a host with stale apt lists takes the install down after
  Docker/KSM/firewall provisioning has already run — the same 10-20 minute
  loss BUG-070 recorded. **Would a test catch it?** No. **Concrete fix:** not
  a code change — the gate report for this release must carry the sentence the
  rule names, and the plan's Phase 2 box that completes the GCP bring-up is
  what converts it to "exercised".

- **[medium / confidence: medium]** `deploy/gcp/install.sh:141-147` vs the
  claim at `:149-151` ("Only a release the staged allowed_signers vouches for
  runs on the VM") — the existing-checkout branch runs
  `fetch --tags && git … checkout -q v${VERSION}`, and `git checkout <tag>`
  carries **unstaged modifications to tracked files** across when they merge
  cleanly, and never touches untracked files. `verify-tag` on line 153 vouches
  for the tag *object*, not for the working tree that `sudo ./deploy/styrman-ctl
  install` is then executed from on line 158. Concrete scenario: the VM
  described in the change entry already has `~/styrman-crew` cloned at v1.36.0;
  anything that writes into it between bring-ups (an interrupted run, a hand
  edit, an agent session on that box) survives the re-checkout and then runs as
  root with the signature check green. **Would a test catch it?** No —
  `TestGCPInstallPlan` asserts only the ordering `verify-tag` before
  `styrman-ctl install` (`:260`). **Concrete fix:** between checkout and
  verify-tag, require `git -C "$HOME/styrman-crew" status --porcelain` to be
  empty, or check out with `-f` plus `git clean -xdff` after printing what it
  would remove.

- **[low / confidence: high]** `deploy/gcp/vm.sh:145` (`ssh) vm_ssh "${ARGS[@]}"`)
  — the `ssh` verb is the one side-effecting path not wrapped in `run()`, so
  `deploy/gcp/vm.sh --dry-run ssh -- 'sudo reboot'` executes the command for
  real while the header on `vm.sh:15-17` promises a dry run "prints every
  command that would change something as '+ cmd' and runs none of them".
  That is the global read-only-mode rule ("a new side effect goes BELOW that
  mode's early returns; the test asserts the read-only mode does NOT perform
  it"). **Would a test catch it?** No — no test drives `vm.sh ssh` at all.
  **Concrete fix:** wrap the command form in `run` (safe: `install.sh` never
  passes `--dry-run` down to `vm.sh`, it gates at its own `run()`, so
  `DRY=0` inside the child still executes), and add a test asserting
  `--dry-run ssh -- CMD` reaches no fake gcloud.

- **[low / confidence: high]** `deploy/gcp/vm.sh:83` and `deploy/gcp/lib.sh:64-65`
  — both comments still say gcloud "adds this machine's key to **the project**
  on first use", but the same commit added `block-project-ssh-keys=TRUE` to
  `vm.sh:78`, which makes project-level keys inert on this instance (gcloud
  writes to instance metadata instead; the change entry records the live IAP
  ssh that proves the mechanism still works). Describing text next to a
  security-relevant flag that now says the opposite of what the flag does —
  the global describing-text rule. **Would a test catch it?** No.
  **Concrete fix:** "…adds this machine's key to the instance's metadata
  (project keys are blocked, `vm.sh:78`)".

## Criteria

1. **Dead code** — pass. The old `.tar.xz` + `.sha256sum` fetch is replaced,
   not commented out; `grep -rn 'tar.xz' deploy/` finds nothing live. The two
   `# shellcheck disable=SC2034` variables in `lib.sh` (`YES`, `GCP_REGION`)
   are genuinely read by `vm.sh`. No leftover debug output.
2. **Flow tracing** — fail, on findings 1, 2 and 4. Otherwise traced end to
   end and sound: `vm.sh` exit codes 0/1/2/3 → `install.sh:98-103`; `lib.sh`'s
   `run()` seam honoured by every mutating call in both scripts except the
   `ssh` verb (finding 5); the `EXIT INT TERM HUP` trap only fires the remote
   `rm -rf` once `STAGED=1`; `styrman-ctl`'s `private_file` accepts the staged
   token under `sudo` (owner = `SUDO_USER`, mode 600, parent 700) and the
   exported `GH_TOKEN` reaches `host-setup.sh:278`'s
   `--secret id=gh_token,env=GH_TOKEN` branch by inheritance through
   `run bash …`; `host-setup.sh`'s digest chain fails **closed** at every hop
   (`KATA_SHA256` → pinned constant → API `digest` → FATAL), which I checked
   against `set -euo pipefail` semantics on each `|| true` and `&&` list.
3. **Standards conformance** — pass on the automated gates (`bash -n`,
   `shellcheck -S warning` re-run bare here, exit 0; `verify-commit.sh` now
   covers `deploy/gcp/*.sh`). Fail on the describing-text rule: finding 6.
4. **Directory layout** — pass. `deploy/gcp/` sits beside `deploy/firewall/`
   and `deploy/update/`; the script test lives in `internal/config/` next to
   the existing `styrman_ctl_test.go` and reuses its `repoRoot(t)` rather than
   opening a parallel tree.
5. **Simplicity (DIY-except-security)** — pass. No new dependency; `python3`
   was already a hard requirement of `host-setup.sh`. No hand-rolled crypto or
   auth: the GitHub token travels as a file or a BuildKit `--secret`, integrity
   is `sha256sum` and `git verify-tag` (OpenSSH signatures via
   `gpg.ssh.allowedSignersFile`), the ssh transport is gcloud/IAP. Nothing in
   the diff implements a primitive or a protocol.
6. **Decoupling** — pass. `lib.sh`/`vm.sh`/`install.sh` compose through
   `vm.sh`'s CLI (`"${VM}" status`, `"${VM}" ssh --`), not through `lib.sh`

   `styrman-ctl` internal, only its flags.

## Outcome

1. **High**, `internal/config/gcp_scripts_test.go` (the harness lends the child its tty, so two tests never reached the branch they name and the package hung under a pty): **fixed**. `gcpRun` and `styrman_ctl_test.go`'s `ctl` now set `SysProcAttr{Setsid: true}`, so the child has no controlling terminal. Reproduced before the fix exactly as reported (`script -qec … /dev/null` → `--- FAIL: TestGCPVMCreateNeedsYesWithoutTerminal`, then `panic: test timed out`); after it, the same pty run is `ok … 6.2s`, and the no-tty run stays `ok`. That before/after on the real code is the must-fail evidence for this one.
2. **Medium**, `TestStyrmanCtlInstallExportsTokenForHostSetup` asserted only a log line: **fixed**. `styrman-ctl` gained `run_host_setup` (the real code path `cmd_install` calls) and a `__run-host-setup` test hook; the test runs it against a fake `host-setup.sh` under the test's temp root and asserts the token arrived in its ENVIRONMENT, that argv carries none of it, and that nothing printed it. Mutation: deleting the export → `host-setup.sh did not receive the token in its environment: GH_TOKEN=[<unset>]`; restored from a byte copy (`cmp` identical).
3. **Medium**, the Kata fresh-host path is unexercised and the new rule requires the gate report to say so: **stated**. The gate report's verification row and its "What was not checked" section say "fresh-host path unexercised" in as many words, and name the bring-up that exercises it immediately after this release. `versioning.md`'s release procedure gained that requirement as step 0.
4. **Medium**, `install.sh` re-install kept local modifications so `verify-tag` vouched for a tree that is not the tag: **fixed**. The existing-checkout path is now `fetch --tags && reset -q --hard v<VERSION> && clean -qfdx`.
5. **Low**, `--dry-run ssh` opened a real session: **fixed**. The `ssh` verb prints the planned `gcloud compute ssh …` line under `--dry-run` and connects to nothing; `TestGCPVMSSHDryRunRunsNothing` asserts both (red without the guard).
6. **Low**, describing text that outlived `block-project-ssh-keys=TRUE`: **fixed** in `vm.sh`'s wait line and `lib.sh`'s `vm_ssh` comment, which now also states the argument-flattening the usage line implies.
