# Security review — v1.42.4 (v1.42.3..5a8afa1)   (2026-10-05)

Range reviewed: v1.42.3..5a8afa1

## Status: COMPLETE

## Verdict: FINDINGS

The worst problem is a body cap chosen from the end of the decoded path (medium). ADR-086's memory budget assumes `bodyCap()` gives each route its true body cap. It does not. `bodyCap` (`internal/httpapi/budget.go:136`) and the new body-deadline exemption (`budget.go:225`) look at the end of the DECODED `r.URL.Path`. A trailing wildcard holding an encoded slash, such as `{term}` = `x%2Fupload`, makes a small-JSON route look like an upload route. That route then gets the 512 MiB upload cap (`server.go:736`) and no 30 s body read deadline. Its reservation is clamped to the 256 MiB tenant share. `PATCH /api/projects/{project}/terminals/{term}` is reachable this way by any signed-in tenant on their own project: `updateTerminal` decodes the body before it checks `{term}`. The cookie rename for BUG-074/ADR-088, the non-admin cap (ADR-087) with its admin-only settings write, and the token-file checks hold up. Their details are under Checked.

## Findings

- **[medium / confidence: medium]** `internal/httpapi/budget.go:136-142` (`bodyCap`), `internal/httpapi/budget.go:225` (deadline exemption), `internal/httpapi/server.go:736` (csrfGuard's `MaxBytesReader`), reachable through `internal/httpapi/server.go:1294-1304` (`updateTerminal`).
  - **Weakness.** All three pick the body rules from a suffix of the decoded `r.URL.Path`. Go's ServeMux unescapes paths one segment at a time. Path cleaning keeps `%2f` (see `go doc net/http.ServeMux`, "For matching, both pattern paths and incoming request paths are unescaped segment by segment"). So `PATCH /api/projects/<own-uuid>/terminals/x%2Fupload` matches `PATCH /api/projects/{project}/terminals/{term}` with `term` = `x/upload`, and `r.URL.Path` ends in `/upload`.
  - **What that route then gets.**
    1. A body cap of 512 MiB instead of 1 MiB.
    2. A budget price of `defaultWeight + body(r)` (`budget.go:204`), clamped to the 256 MiB tenant share.
    3. No body read deadline.
  - **What the handler does.** `updateTerminal` passes `getProjectFor` (the caller's own project) and then runs `json.NewDecoder(r.Body).Decode` at `server.go:1304`, before it reads `{term}` at `:1312`. The decoder's buffer plus the decoded string can come to roughly 2-3x the body. That is about 1-1.5 GiB live against a 256 MiB reservation. Without the deadline, the tenant can also trickle the body and hold the reservation for as long as they like.
  - **Why it matters.** This breaks ADR-086's stated invariant ("no tenant's requests — and not all tenants' together — can build more ... request-body memory than the server's 4g cap can hold"). Two allowlisted accounts doing this at the same time plausibly push past `GOMEMLIMIT=3GiB` and the 4g cap. The server is then OOM-killed and every tenant's terminals drop.
  - **Old and new parts.** csrfGuard's suffix-based cap existed before this range; `bodyCap` only moved it. What is new: the budget's pricing and the deadline exemption depend on it, and the plan priced bodies "at most at csrfGuard's cap".
  - **Same weakness, smaller impact.** `x%2Ffile`, `x%2Fformat` and `x%2Fcheck` give the 8 MiB editor cap.
  - **Confidence is medium because two things are unverified:**
    1. That the vendored Caddy `reverse_proxy` forwards `%2F` unchanged. I believe it does by default; this review did not test it.
    2. The real peak memory of the decode.
  - **Fix.** Choose the cap and the deadline exemption from the MATCHED PATTERN. `budgetGuard` already has the pattern from `mux.Handler(r)`. Move the `MaxBytesReader` into `budgetGuard`, or pass the mux to csrfGuard, and key both on `POST /api/projects/{project}/upload` / `.../home/upload`, the two `/file` PUTs, `/format` and `/check`. At the least, match on `r.URL.EscapedPath()`.
  - **Tests to add.** Plant `/terminals/x%2Fupload` with a body over 1 MiB and expect 413. Trickle a body to the same path and expect 408. Each must fail without the fix.
- **[low / confidence: low]** `internal/membudget/membudget.go:61,104-111,124-140`.
  - **Weakness.** Every `Acquire` scans the whole waiter queue (`tenantWaiting`), and every release and every cancelled waiter rescans it (`dispatch`). All of this runs under the one budget mutex. Only the number of concurrent connections bounds the queue, and each waiter stays up to `budgetWait` (2 s).
  - **Scenario.** One authenticated tenant that keeps many concurrent requests queued makes admission and release for all tenants cost O(n) each under a global lock. That amplifies CPU, but each waiter is bounded at 2 s.
  - **Fix.** Cap the number of queued waiters per tenant: past a small number (for example 64), answer 503 at once. Or keep a per-tenant waiting count so that `tenantWaiting` is O(1).
- **[low / confidence: low]** `.agents/docs/deploy/remote.md:93-94`, `.agents/docs/specs/styrman/deploy.md:266-267`.
  - **Overstated claim.** The snippet's comment says a pre-existing `~/fine-grained-token` with a wider mode "never holds it readable" because the file is emptied and chmodded first. That holds for new opens only. A descriptor opened while the old mode allowed it can still read the token after the `chmod`. `: >` and `chmod` also follow a symlink at that path.
  - **Who can exploit it.** Only someone who could already open the operator's file earlier. This is a residual, not a practical path.
  - **Fix.** `rm -f ~/fine-grained-token` first, then create it with `set -C` (noclobber) under `umask 077`.
  - **Token handling itself is sound.** `read -rsp` keeps the token off the terminal and out of history. `printf` is a builtin, so the token never appears in argv.
  - **Related, fails closed.** In this range, `sudo test -s` treats a whitespace-only installed token as installed. The updater's `token_file_ok` then refuses that file by name, so it fails closed. The coordinator reports a later working-tree change to `grep -q '[^[:space:]]'`; that change is outside this range and was not reviewed.

## Checked

That covers `token_file_ok` (`deploy/update/styrman-update`) and `require_token_file` (`deploy/styrman-ctl`), which both use `tr -d '[:space:]'` into a command substitution, and the `__check-token-file` hook. The hook is gated on `STYRMAN_UPDATE_TEST=1` and uses the caller's own uid as the trust bar, so it grants nothing.
  - A symlinked token file is still refused, because the `find -perm /077` check sees the link's 0777 mode.
- **Injection / input parsing.**
  - The `run.sh` screenshot `rm -rf` is guarded by a `/tmp/styrman-shots-*` glob, and in `[[ == ]]` a `*` also matches `/` and `..`. Here that is safe: `SHOTS` only ever comes from `mktemp -d` (`web/e2e/run.sh:134`).
  - The web changes render server values as JSX text only; there is no `dangerouslySetInnerHTML`. The cap inputs strip non-digits, and the server validates them.
  - `files.List`'s byte bound (`internal/files/files.go`) is correct and still lists through the confined root.
  - The `uncharged()` predicates cannot be reached by an `/api/` route: the first escaped segment decides them.
  - `body()` cannot over-price a forged Content-Length (`TestBodyPricingIsCapped`).
  - The claim that the deadline clears at EOF matches go1.25's `startBackgroundRead` / `body.readLocked` and is pinned by `TestTheBodyDeadlineEndsWithTheBody`.
- **Authz/authn.**
  - `PATCH /api/settings/runtime` checks `requireAdmin` before decoding the body. A member's PATCH returns 403, pinned by `resources_cap_test.go:170`.
  - The cap is applied on every start path: `runOptsFor` is the only builder, and all five `EnsureRunning` callers use it (network.go:230, resources.go:333, server.go:353/1014/1209).
  - Admin status is always taken from the project's owner, because `getProjectFor` is owner-scoped. The network toggle resolves the owner the same way.
  - A failed host read fails the start; a project never starts uncapped.
  - `IsAdminUsername` cannot be ambiguous: `slugCollision` is enforced in both `New` and `Add`.
  - The `ownerIsAdmin` DevAddr branch matters only when the dev listener is configured, which production compose does not do. It names `AllowedEmails[0]`, an environment admin.
  - `GET /api/settings` now returns the cap values to every user. That is not sensitive: the same values appear in the user's own dialog.
  - Coverage gap: the cap is exercised only by unit tests. The e2e and Tier 2 servers run `STYRMAN_AUTH=none` (everyone is admin), as the plan's Scope says.
- **Cookies (BUG-074 / ADR-088).** Checked against caddy-security v1.1.64 and go-authcrunch v1.1.41 in the module cache:

  - No other Set-Cookie name exists in that plugin version. The IdP identity-token cookie is not enabled by the generator.
  - The authz policy's `set access_token cookie name` replaces the list (`caddyfile_authz_misc.go:88`, `gatekeeper.go:135-137`). The validator matches exact names (`validator/sources.go:137-138`), so legacy and parent-deployment cookies no longer authorize.
  - The server's own guest proxy deletes the whole `Cookie` header (`internal/httpapi/proxy.go:177-182`), so the rename does not regress it.
  - The prefix is a derivable namespace, not a secret, and that is correct.
  - The gatekeeper now also accepts a `<prefix>_access_token` header or query name. ADR-088 records this, and `access_token` was already accepted.
- **Crypto.** `crypto/sha256` is used, as designed, to derive a non-secret cookie namespace. That is not hand-rolled crypto. No auth, session or JWT code is hand-written in this range; the portal stays caddy-security.

## Outcome   (main, 2026-10-05)

1. medium, encoded slash buys the upload cap and skips the read deadline — **fixed**: `budgetGuard` now applies the body cap (`bodyCap`) and the upload exemption from the MATCHED mux pattern, never the decoded path; csrfGuard no longer caps bodies itself. `TestAnEncodedSlashDoesNotBuyTheUploadCap` (`PATCH …/terminals/x%2Fupload` and `x%2Ffile` with a 2 MiB body → 400 "request body too large"); red with the cap keyed on `r.URL.Path` again (mutation run). `TestCheckAndFormatGetTheLargeBodyLimit` now drives `budgetGuard` on the real patterns. The suffix-on-path shape predates this range (csrfGuard since v1.x); the range added the deadline exemption on the same shape.
2. low, waiter queue scanned under the mutex — **left**: waiters are bounded by in-flight connections and expire after `budgetWait` (2 s); REQUIREMENTS.md caps users at 5. A per-tenant waiter cap would add a refusal path for a cost not measured.
3. low, token snippet fd/symlink — **fixed**: both snippets `rm -f` the name, then create it under `set -C` (O_EXCL) with umask 077; exercised on a scratch HOME where a 644 file pre-existed: the result is a 600 regular file holding only the new token.

Outcome addendum (main, 2026-10-05): finding 1's deadline half is now pinned too — `TestAnEncodedSlashDoesNotBuyTheUploadDeadlineExemption` (review `2026-10-05-review-5a8afa1-07f5517.md`, finding 1).
