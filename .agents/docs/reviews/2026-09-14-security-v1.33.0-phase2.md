## Verdict: FINDINGS

Nothing in this diff is exploitable and nothing here weakens the product; the change
closes a finding this repo has carried since the 2026-09-01 audit (item 9) and
re-raised on 2026-09-14 (`reviews/2026-09-14-security-wsboot-attach.md:75`). The
worst problem is **operational, and it points the wrong way**: the escape hatch the
change documents, `STYRMAN_ALLOW_IP_FORWARD`, is not reachable on the production
deploy path at all — `deploy/docker-compose.yml` passes an explicit `environment:`
allowlist and the variable appears nowhere under `deploy/` — while the failure it
guards is wired into the updater's automatic rollback. If a host ever trips the
guard, the server exits 1, the health check times out, and the updater rolls back to
the **previous version, which has no guard and runs with forwarding on**, latching
the failed tag so later ticks do not retry. The fail-closed direction is right; the
recovery story around it is thin and the one diagnostic line lives in the logs of a
container the rollback just replaced.

On the central question asked — is `/proc/sys/net/ipv4/ip_forward` the right
observable — the answer is **yes for IPv4, and the "misconfigured host" bypasses do
not apply.** Details under "Observable correctness" below; it is a pass, recorded
because it is the load-bearing claim of the change.

## Findings

- **[medium / confidence: high]** `deploy/docker-compose.yml:84-110` with
  `cmd/styrman/main.go:46` and `.agents/docs/specs/styrman/api.md:266` — **the
  documented override cannot be set on the deploy path it is documented for.** The
  `styrman` service enumerates every variable it receives in an explicit
  `environment:` list (the same deliberate allowlist pattern the file's own comment
  defends for caddy at :30). `STYRMAN_ALLOW_IP_FORWARD` is in none of it:
  `grep -rn ALLOW_IP_FORWARD deploy/` returns nothing (rc=1), and
  `deploy/.env.example` has no row for it. An operator following `api.md`'s env
  table would put it in `deploy/.env` and it would have **no effect** — compose
  never forwards it. Now combine that with `specs/styrman/versioning.md:154-163`: a
  tag that does not report healthy inside `STYRMAN_UPDATE_HEALTH_TIMEOUT` (120s
  default) is rolled back automatically and latched in `${STATE_DIR}/failed-version`,
  not retried until `--force` or a newer tag. A host whose server container came up
  with `ip_forward=1` therefore lands on the previous, unguarded binary — R12
  unasserted and now also unlogged, because the `logger.Error` explaining why went
  out with the replaced container. The plan's risk note
  (`plans/2026-09-14-v1.33.0-close-out.md:216`) says the rollback risk is "mitigated
  by … the override knob"; that mitigation does not exist as shipped.
  **Remediation:** add `- STYRMAN_ALLOW_IP_FORWARD=${STYRMAN_ALLOW_IP_FORWARD:-}` to
  the `styrman` service's `environment:` list so the documented hatch works, or amend
  `api.md`'s row to state that it requires editing `docker-compose.yml` and is not
  settable from `.env`. Either is fine; shipping the current mismatch is not, because
  it is discovered only during an incident.

- **[low / confidence: high]** `internal/config/ipforward.go:11,26` and
  `deploy/docker-compose.yml:82-83` — **the assertion is IPv4-only and the compose
  sysctl matches it**, so `net.ipv6.conf.all.forwarding` is neither set nor read.
  Today this is inert rather than exploitable, and the reasons should be written down
  because they are all *contingent*: `createBridgeNetwork`
  (`internal/orchestrator/orchestrator.go:895-901`) is documented as the only place a
  styrman bridge is created and it never sets `EnableIPv6`, so project networks carry
  no IPv6 subnet; and the root firewall separately writes
  `net.ipv6.conf.<if>.disable_ipv6=1` plus mirrored `ip6tables` drops
  (`deploy/firewall/styrman-firewall.sh:98-116`). Note that firewall loop globs
  `/sys/class/net/sdb-*` only — an ADR-067 **LAN-mode `lan-<hash>` bridge is not
  covered by it**, so the IPv6 story for LAN projects rests entirely on Docker not
  configuring IPv6. **Remediation:** add `net.ipv6.conf.all.forwarding=0` to the
  compose `sysctls:` list and extend `IPForwardOff` to both, or — cheaper and
  acceptable — record in `ipforward.go`'s comment that IPv6 is out of scope
  *because* bridges are created IPv4-only, so whoever later sets `EnableIPv6` is
  forced to revisit this guard rather than inheriting a silent gap.

- **[low / confidence: high]** `cmd/styrman/main.go:38-54` and
  `deploy/docker-compose.yml:78-81` — **a boot-time deploy assertion is being
  described in language that reads as a runtime guarantee.** `net.ipv4.ip_forward`
  is writable at any time by anything holding `CAP_NET_ADMIN` in that netns. The
  server process itself cannot do it (it runs unprivileged as
  `${STYRMAN_UID}:${STYRMAN_GID}`), but the same container mounts
  `/var/run/docker.sock` read-write, and a Docker-API holder can enter that netns
  privileged and flip the bit after boot. That is **not a new escalation** — socket
  access is already host-root-equivalent and the compose file says so for caddy at
  :22-25 — but it does mean the check is a configuration assertion, not an enforced
  invariant, and a one-shot one at that. Separately, compose:80-81's "structurally
  incapable of being used as a cross-project router" is true only of the *kernel*
  path: the server is a userspace process on every project bridge and the port-preview
  proxy is by design a cross-project reachability path, gated by authz rather than by
  `ip_forward`. **Remediation:** say "kernel-level routing" in that comment and in
  `guide.md:278`, so no later reader treats `ip_forward=0` as the whole of R12's
  cross-project guarantee — R12's actual enforcement is Docker's unconditional
  per-bridge DROP plus the root firewall. (Per AGENTS.md: a description that
  outlives its behaviour is read as a guarantee.)

- **[low / confidence: medium]** `cmd/styrman/main.go:45-46` (the read-error branch)
  — **fail-open on an unreadable sysctl is broader than the rationale it cites.**
  `IPForwardOff` is correct in itself: it returns the fail-closed bool (`false` =
  "forwarding on") alongside the error, and its tests pin that an exact `"0"` is the
  only "off" reading, with `""`, `"1"`, `"2"` all treated as on. But main's first
  branch reduces *any* read failure to a single Warn, and the comment justifies it
  with "an exotic kernel must not take the service down over a missing file" —
  which argues only for the *missing* case. A file that is **present but unreadable**
  (a custom `--security-opt`, a masked or restricted `/proc`, a future rootfs
  mishap) is a misconfiguration, not an exotic kernel, and silently downgrades the
  guard. The practical opening is narrow — the path is a compile-time constant in
  the container's own `/proc`, never attacker-supplied, and Docker's default
  masked-paths set does not include it — hence low. **Remediation:** split the
  branch: `errors.Is(err, fs.ErrNotExist)` → Warn and continue, anything else →
  the same refusal as `ip_forward=1`.

## Observable correctness (the central question — pass, recorded)

Asked whether a misconfigured host can make the check pass while forwarding is
effectively on. For IPv4, no:

- **Netns scoping is right.** `net.ipv4.ip_forward` is per-network-namespace. The
  host's own `ip_forward=1` (which Docker requires) does not leak into the server
  container's netns, and conversely the container's `0` says nothing about the host —
  which is exactly the scope the guard wants, since the concern is the server's own
  netns routing between the bridges it joins.
- **`net.ipv4.conf.all.forwarding` cannot disagree with it.** They are the same
  kernel variable: the ipv4 sysctl table's `ip_forward` entry aliases the
  `devconf_all` FORWARDING slot. There is no "all says 1, ip_forward says 0" state.
- **Interfaces created later inherit the 0.** This matters more than it looks,
  because `EnsureSelfAttached` (`internal/orchestrator/orchestrator.go:619-674`) adds
  a *new* interface to the container's netns on every project join, long after
  compose applied the sysctl at container creation. Writing the `all` knob propagates
  to `conf.default.forwarding` as well as to every existing device
  (`inet_forward_change`), and a new in_dev is initialised from `default` — so the
  bridges joined at runtime come up with forwarding off.
- **The host firewall cannot produce a false pass.** `deploy/firewall/styrman-firewall.sh`
  operates in the host netns; its FORWARD/`DOCKER-USER` rules govern what the *host*
  forwards, and it cannot make the server container forward. `rp_filter` does not
  enable forwarding. The `-m physdev --physdev-is-bridged -j RETURN` exemption
  (`styrman-firewall.sh:74`) is what made the original 2026-09-01 finding matter —
  it would exempt both hops of a server-mediated route from the private-range DROPs —
  and it is still present, which is precisely why this guard is worth having.
- **Residual.** A per-interface write (`net.ipv4.conf.<if>.forwarding=1`) applied
  *after* the `all` write would defeat the reading, since forwarding is decided from
  the inbound device's own flag. Nothing in the deploy does this and it requires
  `CAP_NET_ADMIN` in that netns — i.e. the finding-3 precondition, not a separate
  one. Not worth code; worth knowing.

**Fail-closed posture:** correct in placement and ordering. The check sits after
`config.Load` and **before** `os.MkdirAll(cfg.StateDir…)`, so a refusal happens
before any filesystem side effect. It is correctly gated on `cfg.SelfContainer != ""`:
host-mode dev runs (integration.sh, `web/e2e/run.sh`, the loopback dev server) share
the host netns where Docker needs forwarding on and never attach to a bridge, so they
are exempt by construction rather than by an opt-out — no new way to skip the check.
The posture itself is right for a control whose violation voids R12; my objection is
finding 1, the recovery path around it, not the refusal.

## Outcome

- **1 [medium/high] override not passed through compose — FIXED.**
  `deploy/docker-compose.yml` now lists
  `STYRMAN_ALLOW_IP_FORWARD=${STYRMAN_ALLOW_IP_FORWARD:-}` under the
  server's `environment:` (a comment says what it is for);
  `STYRMAN_VERSION=x docker compose config --quiet` rc 0. The env-table row
  in `specs/styrman/api.md` now says the knob is set in `deploy/.env`, and
  names the consequence of a tripped guard: the updater's health check
  fails and rolls back to the previous version, the refusal being in that
  container's log — the fail-closed behaviour is intended and stays.
- **2 [low/high] IPv4-only assertion — REBUTTED, no change.** Project
  bridges are created without `EnableIPv6` (`createBridgeNetwork`), so no
  IPv6 route between them can exist whatever the sysctl says; asserting
  `net.ipv6.conf.all.forwarding` would add a knob for a path that does not
  exist. The firewall's `sdb-*`-only IPv6 loop on `lan-*` bridges is
  pre-existing and by ADR-067's design (LAN mode is a normal Docker
  container, matched by no styrman rule); noted, not changed here.
- **3 [low/medium] fail-open on any read error — FIXED.**
  `cmd/styrman/main.go`: a missing sysctl file (`errors.Is(err,
  fs.ErrNotExist)`) warns and continues; any other read error refuses like
  forwarding-on unless the override is set (then one Warn). Comment and
  the env-table row updated. `go build`/`go vet` rc 0.
