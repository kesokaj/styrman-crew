# Security review — harness channel, Phases 1-3 (567b81f..43dc991)   (2026-09-16)

Range reviewed: 567b81f..43dc991

**Tree state.** The working tree kept changing DURING this review and, by the end, carried

## Verdict: FINDINGS

Nothing in the range lets an unsigned or foreign-signed styrman-harness tag reach a
project VM: `harness_main` forces `REQUIRE_SIGNED=1` before the tag loop, tag names are
constrained to `^v[0-9]+\.[0-9]+\.[0-9]+$` by the `git tag -l` filter, and `verify_tag` is
the same hardened SSH-only, allowlist-pinned, empty-GNUPGHOME check the crew updater
already carried (last-armor-header comparison across all four of git's markers, root-owned
`allowed_signers`, annotated-tag requirement). The worst thing in the diff is on the SETUP
side instead: `styrman-ctl` reads `STYRMAN_HARNESS_ORIGIN` and `STYRMAN_HARNESS_REPO_DIR`
from the ambient environment, refuses neither in the production-seam guard that exists
twenty lines below them, and hands the origin straight to a root `git clone` WITHOUT the
plain-https validation that the crew clone's `https_origin()` applies with the comment "no
other transport (ext::, file://), no option-shaped value (security review)" — so the one
threat model this repo already wrote down (a poisoned env under `sudo -E`) is re-opened on
the new path. Second: the server's harness trust check gates only the CREATE of a
container's binds; a stopped project that already has them keeps them and re-resolves
`<dir>/current` on start even when the server has just REFUSED that channel as untrusted.
That second one is the worst problem STILL LIVE at the end of this review — the origin
validation and the seam guard landed in the working tree while the review ran.

## Answers to the dispatch's explicit questions

- **Unsigned / foreign-signed tag reaching a project:** no. `harness_main` sets
  `REQUIRE_SIGNED=1` (`styrman-update:374`) and the harness dispatch (`:563`) leaves before
  any crew-path use of the `update.env` opt-out, so the opt-out cannot reach it. `verify_tag`
  refuses a lightweight tag, refuses anything whose LAST signature armor header is not
  `-----BEGIN SSH SIGNATURE-----` (all four of git's markers matched, closing the
  decoy-in-the-tag-message path), refuses a missing / non-root-owned / group- or
  world-writable `allowed_signers`, and runs `verify-tag` with an empty scratch `GNUPGHOME`
  so a gpg dispatch finds no keyring. A tag below the installed version is refused and
  alarmed; a moved tag at the installed version is never re-exported without `--force`; the
  failed-tag latch stops a retry storm. `internal/config/styrman_harness_test.go` drives all
  of it end to end against a scratch origin (foreign key, lightweight tag, a symlink in the
  tree, the downgrade rule, the latch, `--check`, `--force`, and the production path
  refusing to run unelevated). Note by design, not a finding: the harness channel uses the
  SAME `/etc/styrman/allowed_signers` as crew releases, so one signing key now also decides
  what runs inside every project VM.
- **A project VM influencing the export or the mount:** not through the filesystem. A guest
  sees only its home and workspace binds plus the read-only channel; the content dir is
  root-owned 0755 beside `users/`/`projects/`, never under a mounted home, and both the
  script (`styrman-update:340-346`) and the server (`harness.go:64-96`) re-assert
  not-a-symlink, ownership and no group/world write on every run. The residuals are the two
  medium findings above (a guest with SYS_ADMIN remounting the ro bind; a refused channel
  still mounted into an already-created container).
- **Another host user:** no. Everything the channel writes is root-owned; the export's
  `find -type l` check (`:235`), the "current must be a symlink" check and the "resolves
  inside the content dir" check all hold. By design, not a finding: the server accepts a
  content dir owned by root OR by its own uid (`ownedAndPrivate`), and `/var/lib/styrman` is
  operator-owned, so the operator can substitute the whole channel — the operator already
  runs the server with the Docker socket, so that is the same trust domain.
- **Test mode on a production host:** no new door. The `harness` + `STYRMAN_UPDATE_TEST=1`
  entry point (`styrman-update:412-427`) runs before the `id -u -eq 0` gate, but
  `harness_test_guard` refuses `/`, `/etc*`, `/var/lib/styrman*`, `/opt*`, `/usr*`, `/root*`,
  `/run*` for all three paths AFTER `realpath -m` canonicalisation, signature verification
  stays forced on, `want_owner` becomes the invoking uid (still 0 when root runs it), and the
  smoke image must be named explicitly. The guard is a denylist, so a test run can still
  write into e.g. `/home/<op>` or `/srv` — but only with the invoker's own privileges and
  only `install -d` plus export files, so no boundary is crossed. `STYRMAN_DEPLOY_DIR` is not
  covered by the guard; on the harness path it is read-only (the `harness-builder` FROM line).
  `make-scratch-harness.sh` adds its own absolute-path and production-path refusal.
- **Token / helper leakage:** none found. The harness token is read by the helper at git's
  call time from `${HARNESS_GH_TOKEN_FILE}` — the command line carries the PATH, not the
  secret, so `ps` shows nothing; the file must be root-owned and not readable or writable
  beyond root (`styrman-update:358-363`). In `styrman-ctl` the token is a shell variable and
  a `printf` builtin redirect under `umask 077` into the root-only `CTL_TMPD` (0700, with an
  EXIT/INT/TERM/HUP trap), then `install -m 600 -o root -g root`; `ask … secret` uses
  `read -rs`; the ctl test asserts no token text appears in the plan. `GIT_CRED_ARGS` is
  reset to `-c credential.helper=` first, so an ambient root helper cannot answer for the
  fetch. Failure messages name the token PATH only, and the units' `Environment=` lines carry
  paths only. Residual, generic: if an operator ever embeds a token in the origin URL, git's
  fetch error text (`2>&1` into the journal) would carry it — the https+helper shape avoids it.
- **What the builder and smoke containers can reach:** the builder runs `go build` as the
  invoking uid with `/src` read-only, `/out` writable, `GOPROXY=off GOTOOLCHAIN=local
  CGO_ENABLED=0 HOME=/tmp`; the smoke runs the freshly built binary as uid 1000 with the
  export read-only and a scratch home writable. Both keep Docker's default network and
  default capabilities and both run through the root updater's Docker socket — finding 5.
- **What the guest can do with the read-only mounts:** read and execute them. The entrypoint
  runs `sh-agent install` from the mount as the project user; the guest cannot write the
  mount through ordinary filesystem calls (Tier 2 asserts that), and the remount question is
  finding 3. Nothing in the guest verifies the mounted content before executing it.
- **Injection through tag names / TAG / COMMIT / log lines:** constrained. Tag names pass
  `^v[0-9]+\.[0-9]+\.[0-9]+$` before any use; `INSTALLED` read back from `harness-version` is
  re-validated against the same regex; `COMMIT` is `git rev-parse` output, read back in the
  entrypoint as `head -c 40 … | tr -cd '0-9a-f'`; `TAG` as `head -c 64 … | tr -cd '[:print:]'`;
  both land in a double-quoted `log` string with no `eval`, and the stamp is written with the
  value as an ARGUMENT to `sh -c`, never interpolated. `EXPORT_ERR`/`SMOKE_ERR` carry
  build/smoke output through `tr -cd '[:print:]' | cut -c1-200` into `harness-refused`;
  `styrman-ctl status` re-filters with `printable` and escapes with `json_str` (python3
  `json.dumps`, or a `sed` fallback escaping `\` then `"`). Printable-but-quoted content can
  therefore reach the refusal line, but it is never re-parsed as shell.

## Outcome

Written by the main agent, 2026-09-16, in the commit that applies the findings; each code fix carries its test (the config and orchestrator packages and the whole module green after every edit).

- `deploy/styrman-ctl` `HARNESS_REPO_DIR`/`HARNESS_ORIGIN` overrides outside the test seam, origin unvalidated — fixed: both names join the `STYRMAN_CTL_TEST` seam list (refused as production knobs), and `setup_harness_channel` dies unless `HARNESS_ORIGIN` matches `^https://[a-z0-9.-]+/[A-Za-z0-9._/-]+$` before any clone or fetch; `TestStyrmanCtlUpdateSetupHarnessPlan` still passes (the default origin).
- `internal/orchestrator/orchestrator.go` refused channel + a container with the binds starts anyway — fixed: the recreate rule is one comparison, the binds a stopped container carries must equal what `harnessBinds` answers now, so a refused (or absent, or disabled) channel drops them and the project boots from the image; `TestEnsureRunningRecreatesAStoppedContainerToDropTheHarnessBindsWhenTheChannelIsUntrusted`; plan D26 supersedes the Interfaces clause; `deploy.md` server-side paragraph updated. The suggested per-project UI error is not taken: the WARN names the project and the reason, and the boot succeeds from the fallback.
- Kata host-side enforcement of the `:ro` binds — resolved by measurement, not by code: on this host (Kata 3.31.0, Docker 29.7.2) a guest root with `CAP_SYS_ADMIN` and AppArmor off can flip the guest mount to `rw` (`/proc/mounts` shows it) and a write still fails with "Read-only file system", a bind-remount trick fails the same way, and nothing lands in the host directory; the rw control (the same bind without `:ro`) accepts the write. Recorded as plan D27 and in `deploy.md`; Tier 2 repeats the probe on every run (`guest cannot write the channel even after remounting it rw`). No per-project copy and no guest-side manifest verification.
