## Verdict: APPROVE WITH NITS

I found no correctness or security defect in the code. The BUG-087 fix in `reloadCaddy` is right:
- A failed load hidden behind a 200 now returns a plain error, not `errAdminUnreachable`. `scanAndReload` then neither latches `lastCaddyfile` nor skips `noteReloadFailure`, so the existing 15 s retry chain runs. It resets `adminDown`, which is correct because the admin API did answer.
- `loadError` reads only caddy's `APIError` shape (`{"error": "<msg>"}`). Warnings alone, an empty body and a tail it cannot decode all count as success, so it cannot turn into a reload loop.
- I checked whether the 10 s client timeout, which now also covers reading the body, could cause endless reloads. It cannot: a retry that posts the same config gets caddy's "config is unchanged" success and latches.

The TerminalPane fix clears the queue only when the reconnect comes from a closed-for-good state, which is the scenario the security review named. Every exit from closed-for-good goes through `reconnectNow`, and an epoch bump or remount creates a new `outbox`, so I found no other path that replays the queue. The new e2e check stages that exact path. Its sentinel `ob-stale-82` matches only the command's output, never the echoed command text, which is the BUG-077 lesson. It runs on a throwaway page closed in a `finally`, which follows BUG-078 / the rule that an e2e check leaves the suite as it found it. The must-fail proof is recorded as `passed=96 failed=1` before the fix and `passed=97` after. Per that rule the pass mark is `failed=1`, and the README's Tier 4 count line went to 97 in the same commit.
