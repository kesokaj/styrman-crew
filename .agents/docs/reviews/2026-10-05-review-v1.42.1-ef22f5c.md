## Verdict: APPROVE WITH NITS

The code is sound. The semaphore releases its slot on every path. The new tests fail when the behaviour they name is removed, and the ADR edits stay within the append-only rule. The worst problem is in the docs. The new token instruction (`gh auth token | sudo install -D -m 600 /dev/stdin /etc/styrman/gh-token`) writes the operator's broad `gh` OAuth token, for good, into the file that the unattended root updater uses as its least-privilege, fine-grained token. On an existing host it also overwrites the token already there, and the guide this appears in (remote.md) is written for existing hosts. The leak through sudo's log is fixed, but a long-lived credential is now more exposed. Everything else is low.

## Findings

- **[medium / confidence: high]** `.agents/docs/deploy/remote.md:88`, `.agents/docs/specs/styrman/deploy.md:262`, `deploy/host-setup.sh:307` — `/etc/styrman/gh-token` is not a build-only file. It is the auto-updater's token (`deploy/update/styrman-update:559-578`, which also feeds it to git's credential helper for the deploy clone). The updater's own error text requires "a FINE-GRAINED GitHub token (this repo only, Contents: Read-only)" (`styrman-update:596`), and `verify-commit.sh:76` asks for the same. Before this change, the docs' `gh auth token` lived in GH_TOKEN for one host-setup run. The new line makes the operator's full-scope `gh` OAuth token (all repos, usually `repo`/`workflow`/`read:org`) a persistent root credential that every updater tick uses. remote.md frames this as the step to "run once, after deploying the next tag", which means on hosts that already have the file, so the pipe also replaces a correctly scoped token without warning. A smaller failure mode: without `pipefail`, a `gh auth token` that fails (not logged in, wrong account) gives an empty pipe. `install` then writes an empty 600 root file, which passes host-setup's owner/mode check (`host-setup.sh:304`) and the updater's check (`styrman-update:569-572`), and fails later as an auth error at download or fetch. Fix: guard the write with `[ -f /etc/styrman/gh-token ] ||` (or say "only on a host without the file"). Tell the operator to pipe a fine-grained token for both repos, not `gh auth token` (for example `sudo install -D -m 600 /dev/stdin /etc/styrman/gh-token < token-file`, or `styrman-ctl install --gh-token-file`). Refuse an empty file at the consumers' existing check (`-s`).
- **[low / confidence: medium]** `internal/httpapi/explorer.go:457-463` — the semaphore covers the whole server, not each tenant. One allowlisted user who keeps 4 searches in flight holds every slot. A worst-case search is 50 transcripts × about 144 ms ≈ 7 s (`history.go:109`, the measurement in the comment at `history.go:181-183`), and they can be re-issued in a loop. Meanwhile every other tenant's history search gets 429. This is availability only and the user count is ≤ 5, but it is cross-tenant interference against "each user fully isolated" (`REQUIREMENTS.md:11`). Fix: a per-user cap of 1–2 in front of the global 4. The memory bound itself is sound: one search holds one transcript at a time (`history.go:138-144`), about 4 MiB × 5 copies, roughly 100 MiB at 4 in flight.
- **[low / confidence: medium]** `internal/gitrepo/oom_test.go:55-76` — the test skips only when it cannot RAISE its score. Lowering the child to 0 is refused (EACCES) when the child's inherited `oom_score_adj_min` is above 0. That happens when the test runs under a process tree where a privileged ancestor set a positive score, for example a systemd unit with `OOMScoreAdjust=`. In that case `git()` only logs a warning, the child stays at 300, and the test goes red with a misleading message. Production is unaffected: raising from -999 to 0 needs no privilege. Fix: read `/proc/self/oom_score_adj` first and skip when it is above 0, and restore it in `t.Cleanup`. The premise that the raise is "irreversible" is wrong: an unprivileged process can lower its score back down to its own `oom_score_adj_min`.
- **[low / confidence: high]** `internal/config/compose_oom_test.go:63` — the GOMEMLIMIT check reads the whole file (`strings.Contains(string(src), …)`), while the other assertions are scoped to each service through `blocks`/`has`. A `- GOMEMLIMIT=3GiB` line moved into caddy's `environment:` (same 6-space indent) would still pass. Fix: track the 6-space `environment` items per service in the same parser and assert inside `blocks["styrman"]`.
- **[low / confidence: high]** `.agents/docs/specs/styrman/api.md:192` — the endpoint row for `GET …/history/search` lists its bounds but not the new 429 past 4 searches in flight server-wide. The global describing-text rule applies; this goes to `documentation`.

## Answers to the dispatch's questions

- **Semaphore:** non-blocking `select`/`default` gives 429 with no queueing. The slot is taken after `getProjectFor` and the query-length check, so an unauthenticated or invalid request cannot hold one. The release is `defer`red right after acquiring, so it runs on a normal return, an error return and a panic (net/http recovers per connection, after the defers have run). `history.Search` checks `ctx.Err()` per transcript, so a client that disconnects frees its slot within one transcript (about 150 ms). The channel is created in `New` (`server.go:263`), the only constructor (no other `&Server{` outside tests). A nil channel would turn every search into a 429, not a hang. 4 is a sane memory bound (see the finding above); the gap is fairness, not size. The test fills `cap(searchSlots)` directly and asserts 429, then that a freed slot works, then that a finished search gives its slot back. It discriminates: without the semaphore, the second request is 200.
- **UI on a 429:** `SidePanelHistory.tsx:38-46`. `request()` throws `ApiError` with the server's message, which is shown as an error toast ("too many history searches in progress — try again in a moment"). Earlier matches stay, and `searching` is cleared. Acceptable. Searches run on Enter only. A stale response is dropped on the client, but its server request is not aborted, so pressing Enter quickly several times uses this user's own slots (see the fairness finding).
- **GOMEMLIMIT=3GiB vs mem_limit 4g:** sound. Compose's `4g` is 4 GiB, which leaves 1 GiB for non-Go memory in the cgroup: stacks, cgo, the host-side git child and page cache, which is reclaimable. GOMEMLIMIT is soft, and Go caps GC CPU at about 50% near the limit. If git grows past the headroom, the in-cgroup OOM picks git (score 0) over the server (-999), as intended. The server's ENTRYPOINT is the binary itself (`Dockerfile.server:27`), so the variable reaches the runtime.
- **slog.Warn on a failed reset:** correct. It uses the default logger (gitrepo has no injected one), carries the error, and does not fail the git call. That matches ADR-085's statement that the cap still bounds git.
- **TestGitResetsItsChildsOOMScore leak / timing:** each package is its own test binary, so nothing leaks outside `internal/gitrepo`. Inside the package it is the last test in source order (gitrepo_test.go, then oom_test.go). Under `-count`/`-shuffle` the other three tests still hold: `TestSetOOMScoreAdjWritesTheChild` compares against 500, and the child reset 300→0 is allowed while min ≤ 0. Timing: `Start` returns after the child has exec'd, and the write follows within microseconds, so 0.3 s is generous. A miss would be a false red, never a false green. A poll loop in the fake would remove even that, but this is not a finding. Discrimination: removing the reset leaves the child at 300, and the test fails (the change entry reports it read 300).
- **TestReapSetupVMsStopsWhenThePassIsOutOfTime:** it discriminates. `ContainerRemove` never clears, so the first VM's `forceRemove` returns only on `rctx.Done()`. The loop then must return before inspecting the second VM. With the check at `orchestrator.go:1683-1686` removed, the second `ContainerInspect` is recorded (n = 2) and the test fails. The outcome is deterministic, with no race on the 100 ms bound. Not covered: the Warn line itself (preflight row 4 named "return and log"). The change entry claims only the return, which is accurate.
- **ADR-084 marker / ADR-085 amendment:** the only in-place edit is the status suffix on the ADR-084 heading (`DECISIONS.md:2855`), which the rule allows. The amendment is appended at the file's end as `### ADR-085 amendment 1`, which is append-only. There is no ADR index elsewhere that still says "Accepted". Note on the amendment's content (not a finding: the amendment itself defers adoption pending a measurement): containerd-style shims call `AdjustOOMScore` on themselves after start, which may overwrite a score a wrapper set before `exec`. The measurement it asks for should check this.
- **Stdin token instructions:** the flags are correct. `install -D -m 600 /dev/stdin <dst>` under sudo makes a root:root file with mode 0600, which passes `host-setup.sh:304`'s `stat -c %u` = 0 check and its `-perm /077` check. `-D` creates `/etc/styrman` with mode 0755 when it is missing, and `host-setup.sh:427-429` resets it to 700 later in the same run. sudo reads its password from the tty, so the pipe is fine. The trailing newline from `gh auth token` is harmless: every consumer reads the file through `$(cat …)`. The scope and overwrite problem is the medium finding above. The old `--preserve-env` and `sudo GH_TOKEN=` recommendations are gone from the living guides. The remaining hits are warnings against them, closed plans, and `deploy/README.md:36`, which mentions the bare form only as the one to avoid.
- **Preflight rows:** rows 2, 3, 4, 8 and 9 are answered. Row 6: the e2e line was relabelled "main page" (it documents the limit rather than reading other pages), and ADR-085's premise is corrected by the amendment. Row 1: the 429 and GOMEMLIMIT are done. The "streaming scan" the row also listed is not, and the change entry does not say it was dropped.
