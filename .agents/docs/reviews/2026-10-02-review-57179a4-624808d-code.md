## Status: COMPLETE

## Verdict: APPROVE WITH NITS

Nothing in the shipped code is broken. Both fixes are correct and complete. `GuestGoingAway` now answers as soon as the container is down while a lifecycle change still holds the lock. `status_ancestors_ok` accepts the production path (`/`, `/etc`, `/etc/styrman`) and refuses an ancestor that others can write unless it has the sticky bit. It is safe under `set -euo pipefail`, including for `/`. The one finding is in the tests. `trustedTempDir` makes only the leaf directory trusted, but the new walk checks every ancestor up to `/`. So the status tests now depend on where `TMPDIR` points. With `TMPDIR` under the project's own `.agents/scratch/` (0775 under this host's umask 002), six `TestStyrmanUpdateStatus*` tests fail. I reproduced this.

## Findings

- **[low / confidence: high]** `internal/config/styrman_update_status_test.go:88-98` (`trustedTempDir`, used by every write case): the helper chmods only the `t.TempDir()` leaf to 0755. The writer's new `status_ancestors_ok` walks every directory from `/` down. So each case passes only when every ancestor of `os.TempDir()` is owned by root or the caller and is not group- or world-writable without the sticky bit. That holds for the default `/tmp` (1777), but not for a `TMPDIR` under a group-writable tree. Reproduced: `TMPDIR=$PWD/.agents/scratch/rvtmp go test -run StyrmanUpdateStatus ./internal/config/` gave rc=1 with 6 FAILs: WritesTheSixValidatedFields, RefusesValuesOutsideItsSets, CarriesSinceAcrossAFailingStreak, WriteDirectoryTrust, ExitDecision, RefusesAWritableAncestor. `.agents/scratch` and its parents are `drwxrwxr-x`. The global rules make `.agents/scratch/` the place for temporary files, so a verifier that points `TMPDIR` there gets a false red. The only message it sees is the writer's generic `WARN: status not written`. The release gate is unaffected (`deploy/verify-commit.sh` does not set `TMPDIR` for `go test`). Fix: have `trustedTempDir` walk `filepath.Dir(d)` up to `/` with the same rule (owner 0 or `os.Getuid()`, no `022` bits unless sticky). On the first bad ancestor, call `t.Fatalf` and name that ancestor, or root the fixtures under a directory the test can prove trusted.

## Answers to the dispatch's questions

1. **Production path.** Accepted. `status_ancestors_ok` was extracted from the script with `sed` and run under `set -euo pipefail`, with `TRUST_UID=0`, against this host's real `/` (root 0755), `/etc` (root 0755) and `/etc/styrman` (root 0700). All three passed (`.agents/scratch/rv-anc.sh`). With 0700, `-perm /022` matches nothing. The walk only needs to stat `/etc/styrman`, and that works even unprivileged. The real tick runs as root (`TRUST_UID=0` at `deploy/update/styrman-update:394`; the unit has no `User=`). The unit pins the path to `/etc/styrman/status/updater.json`, so the walk covers `/`, `/etc` and `/etc/styrman`, and `status_dir_ok` covers `/etc/styrman/status`. That leaves no gap between the two checks.
2. **`IFS='/' read -ra` under strict mode.** Safe.
   - `IFS` is scoped to `read` alone. A here-string always ends in a newline, so `read` returns 0, and the call sits in an `if !` context anyway.
   - For `/`: `"${1#/}"` is empty, so `parts=()`. Bash 5.2 (this host) does not treat an empty `"${parts[@]}"` as unbound under `set -u` (that changed in 4.4). The loop then checks only `/`. A direct call on `/` outside any condition returned rc=0 under `set -e`.
   - For the directory's parent: `dirname "${dir}"` of a canonical absolute path is absolute with no trailing slash. `p="${p%/}/${c}"` builds `/`, `/etc`, `/etc/styrman` correctly.
   - A path with a newline would be cut at the first line, and the walk then fails closed (`[ -d ]` on a truncated path). In any case the path comes from a root-owned unit file.
3. **Can `waitInTheLoop`'s counts be reached without the wait?** No.
   - Every `ContainerInspect` is recorded by the fake. `plant` writes the map directly and records none.
   - `ListeningPorts` → `Status` is inspect #1, then the failed exec is `ContainerExecInspect` ≥1, and `GuestGoingAway`'s first `gone()` is inspect #2.
   - The caller holds the lock, so `TryLock` fails, and inspect #3 comes only after one `time.After(lifecycleRecheck)`.
   - Without a held lock the count would reach 3 with no wait (`gone`, `TryLock` succeeds, `gone`). Every caller of `waitInTheLoop` holds the lock first.
   - Side note, not a defect: against the pre-fix code (one `gone()` before the loop), these tests would fail at `waitInTheLoop`'s 5 s Fatal ("never reached the wait"), not at their own assertion. The new test still fails without the fix, but the message would name the wrong cause.
4. **Docker cost of a Status call on every tick.** This is real but bounded, and does not rise to a finding.
   - Each waiting request makes at most 10 `ContainerInspect` calls a second (local socket, about a millisecond each), and only while the lock is held and the guest is still the same running container. Before the fix, a waiter polled `TryLock` in memory and made no Docker calls.
   - A stop or toggle ends the wait when its container goes down, usually within seconds.
   - The Ports panel's `usePolled` never stacks requests (`web/src/lib/hooks.ts`), and `request()` aborts at 20 s (`web/src/lib/api.ts:376`). That gives at most one waiter per open panel, at most about 200 inspects per stall. The browser endpoint has the same shape.
   - The server sets no `WriteTimeout` (`cmd/styrman/main.go:168`). A non-browser client that never disconnects is therefore bounded only by how long the lock is held, about 90 s at the worst (a start's `waitReady`), so at most about 900 inspects.
   - Recommendation: name the bound in `GuestGoingAway`'s doc comment if desired. No change needed.
