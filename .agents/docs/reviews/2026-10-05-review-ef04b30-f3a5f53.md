## Findings
- **[medium / confidence: medium]** `internal/httpapi/explorer.go:455-461` — the write deadline is untested. `acquireSlot` ignores the `SetWriteDeadline` error, and httptest's recorder does not support deadlines, so no test reaches the line. Deleting it leaves every test green, while api.md claims "Search and read responses have a 30 s write deadline". Mitigation: production has no ResponseWriter wrapper (grep found none), so `http.NewResponseController` works there. I ran a scratch test (Go 1.24.4) showing that a deadline set in a handler does not poison the next request on the same keep-alive connection. Fix: one test with `httptest.NewServer` and a client that never reads a large transcript, asserting the slot is returned within about 30 s (shorten `historyWriteTimeout` through a var). Or reword api.md to say the deadline is not covered by a test.
- **[low / confidence: medium]** `internal/httpapi/explorer.go:442-446` with `web/src/routes/index.tsx:218` — the 8 read slots are shared by every tenant and by the dashboard `TerminalTail`, which polls `readHistory(..., 4096)` every 15 s per terminal. One tenant making 8 concurrent slow-reading requests for 4 MiB transcripts holds all 8 for up to 30 s, over and over. Every other user's tail and transcript view then gets 429. The tail ignores the error and keeps stale text, so the cost is a retryable, silent degradation, not a crash, the same trade-off already accepted for search. The tail's tiny reads (4 KiB) need no 30 MiB budget, so weighting by `bytes` would fix it. A follow-up, not a blocker.
- **[low / confidence: high]** `.agents/docs/deploy/remote.md:92-94`, `.agents/docs/specs/styrman/deploy.md:265-267` — `A && B && C || echo` parses as `((A && B && C) || echo)`. The guard `sudo test -e … ||` correctly skips everything when the token exists. The `echo "no token installed: … missing or empty"` also fires when `install` succeeded and only `shred -u` failed, which says "no token installed" when one is. The plaintext token then stays on disk with that message. `test -e` is evaluated under sudo, which is correct since `/etc/styrman` is 0700. Fix: `shred -u … || echo "token installed; delete ~/fine-grained-token by hand" >&2`, or a plain if/else. The two copies and the host-setup hint are otherwise consistent.

## Questions in the dispatch
- **Revert complete and correct?** Yes. `git diff ef22f5c f3a5f53 -- internal` shows only the read limit, the `acquireSlot` refactor and the test additions. `searchBusy` and `searchMu` appear nowhere in the code or live docs. The api.md search row no longer mentions "a search of the same user". The earlier review's UX regression (429 for a quick second Enter) is gone.
- **`acquireSlot` release.** The `defer func(){ <-sem }()` follows immediately after a successful acquire at both callers, with no panicking code between them, so it runs on normal return, error return and panic. A refused call takes no slot and the callers return before the defer. `writeErr` on 429 does not hold anything. The slot is held during `history.Read`/`Search` and the response write, which is intended. Scenario checked: `getProjectFor` and the `bytes` clamp happen before the acquire, so a 404 or bad request never takes a slot.
- **Deadline vs large legitimate responses.** The deadline is set at acquire, so it covers compute plus write. Worst-case search is about 7 s and a read of at most 4 MiB (about 30 MiB JSON-escaped) goes out as one Encode write, so a normal client has about 23 s or more. `json.Encoder` builds the whole value before writing, so memory is held either way. The SPA's own fetch aborts at 20 s (`api.ts` `AbortSignal.timeout(20000)`), below the server's 30 s, so the SPA never relies on the deadline. A slow reader behind Caddy applies backpressure, so the deadline fires.
- **UI on 429.** `request` turns the body into `ApiError(message, 429)`. `SidePanelHistory.open` renders `e.message` in the transcript pane ("too many transcripts being read at once — try again in a moment"), which is sensible. A search shows the toast. The tail swallows it. Nothing retries automatically in the panel, which is acceptable.
- **Can the test fail?** Yes. Without the `acquireSlot` call in `readHistory` the past-limit request returns 200 and the test fails. The slot-return assertion catches a missing `defer`. It first proves the idle read returns 200 (the condition holds), then fills the slots. It exercises only the 429 and release paths, not the deadline (see the medium finding). I ran `go test -race -count=1 -run History ./internal/httpapi`: ok. I ran no mutation.
