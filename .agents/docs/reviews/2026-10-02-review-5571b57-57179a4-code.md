Range reviewed: 5571b57..57179a4 (one commit, 57179a4; `web/dist/` excluded from reading, but checked to be rebuilt)

## Status: COMPLETE

## Verdict: APPROVE WITH NITS

Nothing in the range is broken in a way that blocks it. The `GuestGoingAway` rewrite is correct. No caller holds the project lock while calling it. Every caller passes a request ctx, so no request can hang without bound, and the code-review finding 1 case (a no-op lock holder) is now reported. The worst remaining problem is in the design. After a failed exec, the function waits for the whole lifecycle change instead of for the guest's state to change. A mode toggle holds the lock through stop, recreate and `waitReady` (up to 90 s). So a Ports poll whose scan the toggle killed is pinned for that whole time. The client aborts it at 20 s, and the server then returns BUG-088's `port scan exited 9` 500 to a closed connection. The second problem is that security finding 2 is marked "fixed", but the race it named still exists.

## Findings

- **[low / confidence: medium]** `internal/orchestrator/ports.go:143-151`: the wait loop re-checks only the lock and never the guest. `gone()` runs once before the loop and once after the lock is free. For a mode toggle, the lock is held from `pr.Stop` (`internal/httpapi/network.go:~206`) through `pr.EnsureRunning` (`:~228`, `waitReady` 90 s cap, `orchestrator.go:465/782`). The container already reads stopped seconds after the kill, but the scan request waits for the rest of the rebuild. The callers' clients bound it: `request()` defaults to `AbortSignal.timeout(20000)` (`web/src/lib/api.ts:376`). For a toggle that outlasts 20 s, ctx is cancelled, `GuestGoingAway` returns false, and `ListeningPorts` returns `port scan exited 9`. That is BUG-088's 500, now written to an aborted connection. Until then the panel shows stale ports (`usePolled` does not stack polls). The same wait pins a per-user browser relay slot (`internal/httpapi/browser.go:343-374`, acquired before `browserExec`). The fix is cheap: call `gone()` on each `lifecycleRecheck` tick inside the loop and return true as soon as it holds. Keep the final `gone()` after the lock for the no-op case. Add a test that flips `running=false` while the lock is STILL held and expects an answer before the unlock.
- **[low / confidence: high]** `deploy/update/styrman-update:115-125`: security finding 2 is marked **fixed** in `reviews/2026-10-02-security-v1.40.0-5571b57.md` Outcome, but the race it described is still there. The finding was a lower-privileged owner of an ANCESTOR who swaps a path component between `status_dir_ok` and `mktemp`/`mv`. The `realpath -m` comparison is a snapshot taken at check time just like `status_dir_ok`, so a swap after it still redirects root's write. Only the remediation's other option closes the race: walk every ancestor and require root-owned, not a symlink, not group/world-writable (`realBelow`'s shape). The finding also asked for a hook test that plants a non-root-owned ancestor, and none was added. The Outcome's "matching the state dir's rule" is also inaccurate: the state dir is canonicalized and refused under `/var/lib/styrman` and at top level (`:394-412`), and the status path gets neither check. Impact is still as the finding said: production pins `/etc/styrman/status/updater.json` under a root 0700 dir. Fix: either add the ancestor walk and its test, or change the Outcome to "partly fixed: symlinks and `..` at check time; the swap race remains, test-only paths".
- **[low / confidence: medium]** `internal/config/styrman_update_status_test.go:445` (the `"relative"` case) breaks review-standards § 8: a guard's absence must stay harmless. The hook runs with no `cmd.Dir` (`:46`), so `status/updater.json` resolves against the package directory, which is the real checkout. With the guard removed, on a checkout with umask 022 (`internal/config` 0755), the old code passes `status_dir_ok(".")`, creates `internal/config/status/` and writes `updater.json` into the tree. On this host `internal/config` is 0775, so the old code already WARNs. That makes this subcase unable to fail here, and it does not prove the new absolute-path rule (the Outcome rightly cites only the `..` and symlink cases). Fix: set `cmd.Dir` to a `t.TempDir()` for this case. Then assert that nothing appeared there, and assert the specific "is not an absolute path" WARN rather than the shared `WARN: status not written` prefix.
- **[low / confidence: medium]** `internal/orchestrator/ports_lifecycle_test.go:44-52` (`scanWhileLocked`): the test assumes the goroutine has failed its exec and is waiting within `3*lifecycleRecheck` (300 ms). Under load (e.g. `-race` on a busy host) it may not be there yet. For the stop and toggle tests, `change(fd)` then runs before the goroutine's first `Status`, and `ListeningPorts` answers `[]` through the not-running path, green without exercising the wait. It can never go falsely red, only falsely green. Fix: block on a signal that the exec has run before calling `change` (e.g. a channel or exec counter on `fakeDocker`), instead of sleeping.
- **[low / confidence: high]** Describing text not updated for the reversed claim "a held lock means the guest is going away". `internal/httpapi/browser.go:91-93` still lists "a lifecycle change in flight" as a case where the guest went away. `internal/httpapi/guestexec_test.go:63-65` documents the fake's `goingAway` as "a lifecycle change in flight (BUG-088)". `internal/orchestrator/ports.go:105-107` says a failure is real only "with no lifecycle change in flight", and a no-op change in flight now also leaves it real. Fix: reword each to "stopped or replaced, after any lifecycle change in flight has finished".
