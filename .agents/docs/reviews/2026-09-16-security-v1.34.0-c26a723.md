## Verdict: FINDINGS (three low; nothing tenant-exploitable — no security reason to hold v1.34.1)

Nothing in this range is reachable by a project user, across tenants, or from
the network. The change adds one Docker SDK method to a package-private seam
(`ContainerUpdate`, docker.go:24-34) and two call sites, both addressed by a
server-derived container name (`"styrman-" + <project UUID>`, and the store
re-validates every ID against a strict lowercase-UUIDv4 regex on load,
`internal/project/store.go:112,144`) or by the ID from an inspect the server
just made — so the seam reaches no container the pre-existing
`ContainerStop`/`ContainerStart`/`ContainerRemove` calls could not already stop
or destroy. Both call sites run under the same per-project lock
(`EnsureRunning` orchestrator.go:192-197, `Stop` :1163-1168), behind
owner-scoped handlers, and after the symlink guard `projectHomeIsReal` (:341),
which still precedes the switch it protects. The worst item on the record is a
measurement gap rather than a hole: on a **running** container moby forwards the
update's all-zero `Resources` into the runtime shim, and nothing in the repo
asserts that a live Kata guest's CPU/memory caps survive that call — those caps
being what keeps one project from starving the single shared host. Separately,
and outside the diff, `npm audit` in `web/` now reports one high advisory that
no previous gate has recorded, because previous gates skipped the tool when the
range had no `web/` path.

## Findings

- **[low / confidence: medium]** `internal/orchestrator/orchestrator.go:359` and `:1229` — the update carries an all-zero `container.Resources`, and for a **running** container moby passes the *caller's* resources (not the merged ones) into the runtime: `daemon.update` ends in `tsk.UpdateResources(ctx, toContainerdResources(hostConfig.Resources))` (moby v28.5.2, `daemon/update.go`). The *persisted* limits are safe, which I checked independently of the fix's own security row: `container/container_unix.go:248-325` copies each resource field only when non-zero, and `daemon/update_linux.go` maps an all-zero request to `nil` CPU, `nil` Memory, `nil` BlockIO with `getPidsLimit` → `nil` (`daemon/daemon_unix.go:125`), so the `NanoCPUs`/`Memory` a project VM is created with (orchestrator.go:1076-1079, from `STYRMAN_VCPUS`/`STYRMAN_MEMORY_MB`) stay in `HostConfig`. What is established nowhere in the repo is what `containerd-shim-kata-v2` does with an empty `LinuxResources` on a live sandbox — Kata sizes the guest from exactly these values. The in-code comment asserts "it does not touch the guest (probed on a Kata VM 2026-09-16)" and the changes entry records "Live probe on production host (docker update accepted with guest ready)", i.e. the probe established that the update is *accepted*, not that sizing is *unchanged*; the two new Tier 2 checks assert exit code, `RestartCount` and policy name only. Exploitable in principle as a noisy-neighbour/DoS lever: a project whose live caps were silently dropped can take more of the host than its tenant is allowed, and every other tenant shares that host. Strongly mitigated in practice — the running-container update happens either immediately before the VM is stopped (stop path, where sizing is moot) or, on the attach path, only when the inspected policy already disagrees, which for a running container means a stop that half-failed. Remediation, no new code and no dependency: add one Tier 2 assertion that `docker inspect -f '{{.HostConfig.NanoCpus}} {{.HostConfig.Memory}}' ${CN}` is unchanged across a Stop of a running project, and either one in-guest read of the memory cgroup limit after an attach that flips the policy, or record the Kata probe's exact command and output in the verification artifact so the comment's claim is evidence rather than assertion.
- **[low / confidence: high]** `internal/orchestrator/orchestrator.go:1229-1236` — the stop-path update is warn-only and a log line is its only signal. If the daemon or the Kata shim rejects it, moby rolls the persisted host config back to `unless-stopped` and styrman proceeds into the in-guest `kill -TERM 1` — straight back into BUG-063's race: one extra guest boot and, as observed live on 2026-09-16, a 35 s "Dead agent" hang ending in exit 255 (the dirty shutdown the graceful TERM exists to avoid). The code is honest about this and `TestStopProceedsWhenTheRestartPolicyUpdateFails` covers both failure branches, so this is a residual rather than a defect; it is recorded because the degraded mode is invisible above the log — `POST /api/projects/{id}/stop` still answers `200 {"state":"stopped"}` — and the only live detector is a Tier 2 check that does not run in production. Remediation if it recurs: re-assert the policy once after `waitStopped` and log at error level when it still reads `unless-stopped` with the container running, or surface the degraded stop in the project record.
- **[low / confidence: high]** `web/package-lock.json` (unchanged in this range; state of the release tree) — `npm audit` in `web/` exits 1 with **1 high**: `js-yaml` 4.0.0-4.3.1, GHSA-2883-xcg3-v3hh (`maxTotalMergeKeys` does not bound CPU for empty merge sources — a parser DoS), reached via `@tanstack/react-start@1.168.49 → @tanstack/start-plugin-core@1.171.39 → xmlbuilder2@4.0.3 → js-yaml@4.3.1`, and still present under `--omit=dev`. Not introduced here and not, on this evidence, exploitable: the path is a build-time Vite plugin, the only YAML parsed is the project's own, and the shipped bundle carries no js-yaml marker (`grep -rl 'YAMLException|unacceptable kind of an object to dump' web/dist/client` → no match, 2.5 MB tree). It is recorded because **no gate has ever recorded it**: `2026-09-16-security-v1.33.0-3743c29.md:261` and `…-preflight-v1.34.0-2.md:164` both say `npm audit` was "not applicable, no `web/` path in the range", so the advisory has been accumulating unseen. Remediation: run `npm audit` once per release regardless of range (it measures the tree, not the diff), and take the transitive bump when TanStack ships it — `npm audit fix` here would move a transitive pin, so it belongs in a web-touching change with the web trio run, not in this PATCH.
- **[low / confidence: low]** `.agents/docs/testing/2026-09-16-verify-release-v1.34.0.md` (and the same shape in the handoff) — guest boot-log text and `sh-agent status` output from a project VM are quoted verbatim into trail documents that later agents read as context. A project's guest output is tenant-influenced (the entrypoint's own hint lines interpolate the in-guest username, which is why the note filter matches the hint's wording rather than a word a username could carry, per the handoff's Key Decisions), so this is an instruction-injection channel from a tenant into an agent session running with the repo's standing `Bash` permission. In this range the quoted text is benign, it is inside fenced blocks, and it is labelled as observed output; no change is required for the release. Recorded so the channel is on the record: keep guest-derived text fenced and never reproduce it into an instruction position (a Next Steps line, a command to run), and prefer quoting the assertion that was checked over the raw line when the line contains guest-controlled substrings.

## Verified negatives (checked, not findings)

- **No new authz surface and no client-supplied identifier.** `stopProject` and `startProject` (`internal/httpapi/server.go:1120-1160`) resolve the project through `getProjectFor(r)` — owner-scoped, 404 on a foreign or unknown ID — before any orchestrator call; routes, middleware and the ingress-token/`X-Caddy-Email` guard are untouched. `ContainerUpdate` can never be pointed at `styrman-sys-setup-<other user>`, the server's own container or the ingress, because `config.ContainerName` (config.go:462) prefixes a store-validated UUID.
- **Every caller of the changed mechanism was enumerated** (project rule `mechanism-reaches-every-caller`): `EnsureRunning` is reached from `ensureFor` → `wsBoot` (the terminal-WS boot, server.go:261-306, wired into the bridge at :245 with `stillAuthorized`), the background create boot (:939), `startProject` (:1135) and the network-mode toggle (network.go:228); `Stop`/`stopLocked` from `stopProject` (:1155), the mode toggle (network.go:206) and the idle reaper (`stopIfIdle`). All are user- or reaper-initiated and owner-scoped; none polls, and none is anonymous. The port-preview proxy and the notifications poll do **not** reach either path.
- **No attach-path amplification.** The write is skipped when the inspect already shows the wanted policy (`insp.HostConfig == nil || insp.HostConfig.RestartPolicy.Name != want.Name`, :358), so the hottest path in the product — a terminal WebSocket reconnect on a running project — issues no daemon write at all. A nil `HostConfig` falls through to the write, the fail-safe direction. A persistently failing update retries once per attach: bounded, self-healing.
- **The ephemeral setup VM keeps `no`.** `EnsureSetup` (orchestrator.go:700-785) is a separate path with its own inspect/start and makes no `ContainerUpdate` call; only `ensureRunningLocked` writes `unless-stopped`, and it is never invoked for `config.SetupContainer(user)`. An abandoned onboarding VM still cannot survive a host reboot.
- **No guard reordered, no window opened.** `projectHomeIsReal(TenantDir(user), ProjectHome(user, project))` (:341) still precedes the `switch` (:344) and therefore the new write; the three recreate branches above it set `err = errdefs.NotFound(...)`, so no update is issued against a container about to be rebuilt. Stop and EnsureRunning take the same per-project lock, so the two writes cannot interleave (a concurrent Stop cannot have its `no` overwritten by an attach mid-stop).
- **`errdefs.IsNotFound(err) → return nil` in `stopLocked` is behaviour-preserving.** Before the change the same `nil` was reached through `ContainerStop`'s own NotFound check at the end of the function; `stopLocked` (orchestrator.go:1208-1245, read in full) holds no post-stop cleanup — the stopped marker, network and record handling all live in the callers (`stopMarked`, `stopIfIdle`) — so the early return skips nothing, and the marker set before the call still keeps the project stopped.
- **Tier 2 additions fail closed and inject nothing.** The suite's helper is `check(){ if eval "$2"; …}` (integration.sh:52), so quoting matters: both new checks interpolate only `${CN}` (`"styrman-${ID}"`, :97, where `ID` is the UUID the suite's own API call returned, extracted with `grep -oE '"id":"[0-9a-f-]{36}"'`) into a `docker inspect -f` template. A missing container makes `docker inspect` fail, the substitution yields the empty string, and `[ "" = '0 0 no' ]` is false — the check fails rather than passing vacuously.
- **Seam widening is bounded.** `dockerAPI` is package-private, its production implementation is `*client.Client`, and the fake's `ContainerUpdate` (fakedocker_test.go) mutates only its own map. The fake's new restart-manager simulation on the `kill -TERM 1` exec is test-only and cannot reach a host.
- **No secret disclosed in the trail.** The live verification record quotes the ingress-token header as the *variable* `$STYRMAN_INGRESS_TOKEN` inside a `docker exec … sh -c`, never its value; the `Good "git" signature … ED25519 key SHA256:5HpYQJjpG+…` line is a **public** signer fingerprint from the allowed-signers check; `~/.claude/.credentials.json` is named with its mode (0600) but no content. Project UUIDs and the operator's own email appear, neither of which is a capability on their own (access needs an authenticated, owner-matching session).
- **Observations, out of range, no action here**: `.claude/settings.json` is tracked with `{"permissions":{"allow":["Bash"]}}` (the operator's recorded standing permission, named in the handoff); the changes entry's "live probe on the production host" mutated a live container's restart policy, which the new attach path self-heals on the next attach.
