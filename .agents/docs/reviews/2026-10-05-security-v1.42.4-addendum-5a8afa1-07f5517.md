# Security review — v1.42.4 addendum 5a8afa1..07f5517   (2026-10-05)

## Status: COMPLETE

## Verdict: FINDINGS

The fix for the earlier finding 1 holds for the case it targeted. The body
cap and the upload deadline exemption now come from the matched mux pattern,
and `TestAnEncodedSlashDoesNotBuyTheUploadCap` passes. But the fix's own rule,
"keyed on the pattern, never the request path", is not applied to the line
just above it. `budgetGuard`'s tunnel early return, and `csrfGuard`'s
identical tunnel exemption, still classify a request by `path.Clean` of the
DECODED path. Cleaning the decoded path resolves dot segments that were
encoded inside a single escaped segment. So the property the dispatch asked
about does not hold: "every non-GET/HEAD request that reaches the mux gets a
MaxBytesReader". A request can read as a preview/link/shared/proxy tunnel to
both guards and still be routed to an API pattern. It then gets no body cap,
no budget charge, no body deadline and no Origin check.

This is the same decoded-versus-routed class as finding 1, and it predates
the range: 5a8afa1's csrfGuard ran the same exemption ahead of its cap. It
also contradicts the earlier review's Checked line "the `uncharged()`
predicates cannot be reached by an `/api/` route: the first escaped segment
decides them". The other parts of the range hold:
- Tunnels stay uncapped, as before.
- No handler of the API mux is reached without `budgetGuard`.
- The `updateRuntime` keep-semantics are behind `requireAdmin`.
- The token snippet does not leak the token.

## Findings
- **[medium / confidence: medium]** `internal/httpapi/budget.go:203` (`uncharged(path.Clean(r.URL.Path))`
  early return) and `internal/httpapi/server.go:719` (`csrfGuard`'s
  tunnel exemption, same predicate).
  - **Weakness.** Both decide "this is a tunnel" from the cleaned decoded
    path. The mux routes on the escaped path, where an encoded separator
    stays inside one wildcard segment. The finding-1 test relies on exactly
    this property. When the two disagree, the request skips:
    - `budgetGuard`'s `MaxBytesReader`, budget charge and `bodyDeadline`;
    - `csrfGuard`'s Origin check;

    and still reaches an API handler with a second wildcard. Both listeners
    set only `ReadHeaderTimeout` (`cmd/styrman/main.go:168-180`), so nothing
    else bounds that body in size or time.
  - **Reachable handler.** `updateTerminal` (`server.go:1290-1308`) resolves
    the caller's project, then runs `json.NewDecoder(r.Body).Decode`, and
    only then reads `{term}`.
  - **Impact.** In principle, an allowlisted tenant can make the shared
    server buffer an unbounded body. That is the cross-tenant OOM that
    ADR-086 and the earlier finding 1 exist to prevent; an OOM drops every
    tenant's terminals.
  - **Not a regression.** The same exemption sat ahead of csrfGuard's cap at
    5a8afa1.
  - **Confidence is medium.**
    - The server side follows by construction from the code paths cited
      here, and the stdlib routing is the property the finding-1 test
      already relies on.
    - Not verified: whether the Caddy ingress forwards such a path
      unchanged. That is the same open question as in the earlier review.
  - **CSRF.** I found no mutating handler where such a request still takes
    effect: the affected wildcard values fail their lookups in
    `updateTerminal`, `pauseTerminal`, `setShares` and `createLink`. Not
    every handler was traced.
  - **Unauthenticated callers.** `authGuard`'s link exemption (`auth.go:44`)
    uses the same predicate. A request it admits carries no identity, and
    `space()` refuses an empty username (`server.go:400-412`) before any
    body read in the handlers checked. Again, not every handler was traced.
  - **Remediation.** Decide tunnel status from the MATCHED PATTERN.
    - In `budgetGuard`, call `mux.Handler(r)` first. Take the early return
      only when the pattern is one of the tunnel registrations (`/p/…`,
      `/proxy/…`, `/link/…`, `/shared/…`).
    - `csrfGuard` and `authGuard` sit outside the mux. Either give them the
      mux, or refuse (400) a request whose cleaned decoded path and cleaned
      escaped path disagree on the tunnel prefix.
    - Tests that fail without the fix:
      1. An over-cap PATCH to a terminal whose `{term}` carries encoded
         separators and dot segments gets 400 "too large", or the refusal.
      2. The same request with a foreign `Origin` gets 403.
    - Also correct the earlier review's Checked line in its Outcome. Until
      the fix lands, `api.md` "Load limits" ("every API request that
      carries a body … must finish sending it within 30 s") has an
      undocumented exception.
- **[low / confidence: high]** `internal/httpapi/budget_test.go:183-201`
  (`TestTunnelsAreNotCharged`): covers only the budget charge, on a GET. No
  test pins the other half of the dispatch's question: that a tunnel's
  request body stays uncapped (preview apps' uploads). By reading, it does:
  both early returns (`budget.go:203`, `server.go:719`) come before the
  `MaxBytesReader`, the same as before the range. But moving the cap above
  the early return would leave every test green. Remediation: a POST over
  1 MiB to a `/link/…` or `/p/…/port/…` path through `n.h` reaches the
  tunnel handler unrefused.

## Checked
