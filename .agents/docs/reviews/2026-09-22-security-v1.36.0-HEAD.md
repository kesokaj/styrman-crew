# Security review — v1.37.0 release range (GCP Compute Engine target, ADR-075)   (2026-09-22)

Range reviewed: v1.36.0..2b84e94

## Status: COMPLETE

## Verdict: FINDINGS (no high; two medium)

The worst problem is not in the new shell code, which is careful: it is that the
new target is told to run on the **production host's own credentials**.
`.agents/docs/deploy/gcp.md` prerequisite 2 says the NUC's Cloudflare token and
Google OAuth client "can be reused", and the plan records a root pipeline that
copies `/etc/styrman/gh-token` and the live `/opt/styrman/deploy/.env` secrets
into `~/.config/styrman/gcp/`. The VM is designed to be disposable; the
credentials on it are not — a Cloudflare Zone:DNS:Edit token for `styrman.xyz`
can repoint `crew.styrman.xyz` and get a certificate for the production name.
Second: every document in the range asserts "no public port 22", but neither
script creates nor asserts a single firewall rule — port 22's exposure is
project state that is not in the repository, and BUG-069 records this very VM
being probed for root logins four minutes after boot.

Everything the dispatch flagged as blast radius was read and checks out: the
token never reaches an argv or a log; `sq()` produces correct POSIX
single-quote escaping (verified empirically on bash 5.2.37); every `GCP_*`,
`--user`, `--version` and origin value is regex-validated before it reaches a
gcloud argv or a remote shell string; the `--dry-run` seam prints paths, never
values, and the tests plant a sentinel and fail if it ever appears.

- **`block-project-ssh-keys=TRUE`** — `deploy/gcp/vm.sh:78`
  (`--metadata=enable-oslogin=FALSE,block-project-ssh-keys=TRUE`), asserted by

## Findings

- **[medium / confidence: high]** `.agents/docs/deploy/gcp.md:~"Prerequisites" item 2`
  + `.agents/docs/plans/2026-09-21-gcp-compute-engine-target.md` (the
  `sudo -n cat /etc/styrman/gh-token > gh-token` pipeline) — **the production
  host's live credentials are reused verbatim on a host declared disposable.**
  The three staged files carry the NUC's GitHub token (reads BOTH private
  repos, including `styrman-harness`, whose binary seeds every project home),
  the NUC's `CLOUDFLARE_API_TOKEN` (Zone:DNS:Edit on `styrman.xyz`) and the
  NUC's `GOOGLE_CLIENT_SECRET`, plus `ADMIN_EMAIL`/`STYRMAN_ALLOWED_EMAILS`.
  Exploitable in principle: the GCP VM runs untrusted agent workloads, a
  LAN-mode project reaches the host itself (AGENTS.md, ADR-067), and the same
  secrets also now sit in a second place on the operator's laptop. Anyone who
  reaches either copy can repoint `crew.styrman.xyz` at their own IP and
  obtain a valid certificate for the PRODUCTION name, and can read the harness
  source. Deleting the VM does not revoke anything.
  **Fix** (no new dependency — all three issuers support it): mint a separate
  fine-grained GitHub token, a separate Cloudflare token, and a second Google
  OAuth client for `auth.gcp.styrman.xyz`; replace gcp.md's "can be reused"
  with "must be separate, so the GCP host can be burned without touching
  crew.styrman.xyz", and note in the tear-down section that the GCP host's
  three credentials are revoked when the VM is deleted.

- **[medium / confidence: medium]** `deploy/gcp/vm.sh:71-78` and
  `deploy/gcp/vm.conf:18-20` — **"no public port 22" is a claim about project
  state that no code creates or asserts.** `create` passes `--tags=http,https`
  and nothing else; whether tcp:22 is reachable from `0.0.0.0/0` depends
  entirely on firewall rules already present in the target project, which are
  not in this repository. A GCP firewall rule with source `0.0.0.0/0` and *no
  target tags* — the shape of the auto-created `default-allow-ssh` on a
  default VPC — applies to every instance regardless of tags, so dropping the
  `ssh` tag does not close the port there. In `driven-eft-h4it` specifically
  the claim currently holds and was *verified live* (prior review Outcome item
  4: the only `0.0.0.0/0` allows are `allow-http`, `allow-https`,
  `allow-icmp`; the plan's Surfaces section lists this project's ssh rule as
  target-tagged). The finding is about the two cases this change explicitly
  invites: the operator's stated purpose is a **reusable** GCP deploy process
  ("for work later I will use gcp"), and in a fresh project on the default VPC
  the same `create` produces a world-open 22 while `vm.conf`, `gcp.md` and
  ADR-075 all state the opposite; and a rule change in this project restores
  the exposure with no signal, because the only check is a hand-run command in
  `gcp.md`'s Verify section. BUG-069 records what that looks like on this very
  instance — scanners attempting root logins four minutes after boot.
  **Fix** (gcloud + coreutils, no new dependency): after `instances create`,
  have `cmd_create` run
  `gcloud compute instances network-interfaces get-effective-firewalls "${GCP_INSTANCE}" …`
  and `die` (or `warn` loudly) when any ALLOW entry with source `0.0.0.0/0`
  covers tcp:22 — the same command `gcp.md`'s Verify section already names,
  promoted from a hand-run check to a gate, and the one place a second project
  would learn it must delete `default-allow-ssh`.

- **[low / confidence: medium]** `deploy/gcp/install.sh:153` — **`git verify-tag`
  is run inside a checkout the VM's login user can have pre-seeded, and
  repo-local config can subvert it.** The `-c gpg.ssh.allowedSignersFile=…`
  override pins the signers file, but `gpg.ssh.program` (default `ssh-keygen`)
  and `gpg.program` are ordinary config keys still read from
  `~/styrman-crew/.git/config`; a checkout left behind by an earlier run and
  edited to point `gpg.ssh.program` at a program that exits 0 would make
  `verify-tag` pass on any tag. The fresh-clone path is unaffected (git does
  not transfer config from a remote). Boundary note: the actor who can do this
  is the same login user whose `sudo` runs on the next line, so this is
  defence-in-depth, not a privilege crossing — but `gcp.md` and ADR-075 both
  state "before anything runs from the checkout, install.sh verifies the
  release tag's signature", which reads as a stronger guarantee than the
  re-install path gives.
  **Fix** (git only): add `-c gpg.format=ssh -c gpg.ssh.program=ssh-keygen` to
  the same `git … verify-tag` invocation, and extend
  `TestGCPInstallPlan`'s verify-line assertion to require them.

- **[low / confidence: high]** `deploy/gcp/install.sh:116-124` — **the staged
  secrets survive on the VM when the cleanup ssh cannot run, and the warning
  does not name the command to run.** `cleanup` best-efforts one
  `rm -rf "$HOME/.styrman-install"` over ssh and, on failure, prints
  "remove it by hand" with no command. Until then the production `.env`
  (`GOOGLE_CLIENT_SECRET`, `CLOUDFLARE_API_TOKEN`) and the GitHub token sit in
  the login user's home for the 10-20 minutes of the install. BUG-069 in this
  same range records an ssh outage on exactly this path, so "the cleanup ssh
  fails" is observed behaviour, not a hypothetical.
  **Fix** (bash only): retry the removal two or three times with the same
  `ssh_reachable` probe `lib.sh` already exports, and make the WARN print the
  literal recovery command
  (`deploy/gcp/vm.sh ssh -- 'rm -rf ~/.styrman-install'`) — the project's own
  `remote-check-names-transport-first.md` rule applied to the cleanup path.

- **[low / confidence: high]** `deploy/styrman-ctl:457-460` — **the token is read
  into the environment during `--dry-run` too, and stays exported for the rest
  of `cmd_install`.** The `if [ -n "${gh_token_file}" ]` block sits above the
  `run` seam, so a `--dry-run` also reads the secret file into the process;
  and after `run bash …/host-setup.sh` returns, `GH_TOKEN` remains exported
  for `docker build`, `docker compose up` and `setup_auto_update`, none of
  which need it (line 483's `--gh-token-file` branch wins over line 484's
  `GH_TOKEN` branch). Exposure is root-only (`/proc/<pid>/environ` is 0400
  owner), so this is hardening, not a live leak, and the `private_file` check
  running in dry-run is a *desirable* validation.
  **Fix** (bash only): `unset GH_TOKEN` on the line after the `host-setup.sh`
  call, so the widest-reaching secret in the install has the narrowest
  lifetime it can.

- **[low / confidence: high]** `deploy/host-setup.sh:78-88` — **the fallback
  "publisher digest" has the same trust root as the download it checks.** The
  asset and `assets[].digest` both come from `github.com` over TLS, so the API
  fallback catches transport/CDN corruption and nothing else; the comment
  ("The publisher's SHA256", "publisher digest") and
  `specs/styrman/deploy.md`'s rewritten Kata bullet read as an independent
  attestation. The default path is the genuinely pinned in-repo constant
  `KATA_SHA256_3_31_0` and is fine. Two practical notes: unauthenticated
  `api.github.com` is 60 requests/hour/IP, so a burst of fresh-host installs
  falls into the (correct) fail-closed branch with a confusing message; and
  `python3` absence also silently yields the fail-closed branch.
  **Fix** (no dependency — this is wording plus the pattern already in the
  file): keep one pinned constant per supported `KATA_VERSION`, and say in the
  comment and in `deploy.md` that the API digest is a transport check, not a
  publisher signature.

- **[low / confidence: medium]** `deploy/gcp/install.sh:69-72` — `--secrets-dir`
  refuses a symlink only at its **last** component (`[ -L "${SECRETS}" ]`), and
  `private_file`'s parent-mode check stats through symlinks, so a secrets
  directory reached through a symlinked parent is accepted with its real
  parent's mode unexamined. The operator supplies the path, so this is a
  robustness gap rather than an attack path.
  **Fix** (coreutils only): resolve once with `SECRETS="$(realpath -e -- "${SECRETS}")"`
  before the checks, and refuse when the resolved path differs from the given
  one under a non-default `--secrets-dir`.

- **[informational / confidence: high]** Dependency scan, recorded for the gate
  and **not introduced by this range** (`go.mod`, `go.sum`,
  `deploy/caddy/ingress/go.mod`, `web/package.json` and `web/package-lock.json`
  are untouched by `v1.36.0..2b84e94`). `govulncheck ./...` on both modules
  reports the same two, each **`Fixed in: N/A`** — no upgrade exists:
  `GO-2026-4887` and `GO-2026-4883` in
  `github.com/docker/docker@v28.5.2+incompatible`, reached from
  `internal/orchestrator` (`ContainerCreate`, `ContainerExecAttach`,
  `ContainerLogs`, `stdcopy.StdCopy`) and required directly by the ingress
  module. `npm audit --omit=dev` in `web/`: one high — `js-yaml 4.0.0-4.3.1`,
  GHSA-2883-xcg3-v3hh (`maxTotalMergeKeys` does not bound CPU on empty merge
  sources), `npm audit fix` available. Recommend taking the `js-yaml` bump in
  the next range and tracking the two docker advisories until upstream ships a
  fix, since no action is available today.

- **[low / confidence: high]** `deploy/gcp/lib.sh:66-73` — `vm_ssh` passes
  `--command="$*"`, flattening its arguments into one string the VM's login
  shell re-parses, while `vm.sh`'s usage advertises `ssh [-- CMD…]` (plural).
  `deploy/gcp/vm.sh ssh -- rm 'a b'` removes `a` and `b`. The prior review
  filed and **accepted** this ("every caller passes one string; documented on
  the function"), and `install.sh` does always hand it one pre-quoted string —
  but the usage line still promises word-safe arguments an operator does not
  get, and it is a seam that will silently turn a future caller's data into
  remote shell words.
  **Fix** (bash only; `sq()` already exists at `install.sh:137`): refuse more
  than one argument (`[ $# -le 1 ] || die`), or `sq` each argument before
  joining; either way make the usage line say "one command string".

- **[informational / confidence: high]** Trail accuracy, not a code defect:
  `.agents/docs/reviews/2026-09-21-review-gcp-compute-engine-target.md`'s
  `## Outcome` says its high finding was fixed by restoring
  `GH_TOKEN="$(cat "$HOME/.styrman-install/gh-token")"` on the install line.
  That was an intermediate state; the security review's fix **superseded** it
  the same day, and the shipped `install.sh:158` has no `GH_TOKEN=` at all
  (the round-3 verifier log records `grep -n 'GH_TOKEN=' deploy/gcp/install.sh`
  → rc 1). A future reader of that Outcome alone would hunt for a line that no
  longer exists, or re-introduce it. One sentence on that row pointing at the
  security review's Outcome item 1 closes it.

## Checked
- **Secrets** — No credential, token or key value anywhere in the diff. Every
  match for token/key/secret patterns is a placeholder or a deliberate test
  sentinel (`SENTINEL-abc`, `SENTINEL-cf`, `SENTINEL-ghtoken`,
  `ghp_SECRETTOKEN`, `AAAAC3NzaC1lZDI1NTE5AAAAIExample`), and both test files
  assert those sentinels never appear in any script output
  (`gcpRun` fails the test on `SENTINEL-`). No `.env`, `*.pem`, `*.key` or
  credential JSON in the range. The real weakness is credential *reuse*, not
  exposure — finding 1. Committed non-secret identifiers: GCP project
  `driven-eft-h4it` (`vm.conf:6`) and the VM's former public IP plus two
  scanner IPs in BUG-069 — targeting aids only, acceptable in a private repo.
- **Injection** — Two real boundaries, both sound. (a) gcloud argv:
  `load_gcp_env` (`lib.sh:28-46`) refuses any `vm.conf` key not matching
  `^GCP_[A-Z_]+$` before `printf -v` (so no arbitrary variable, and the
  `GCP_` prefix keeps `PATH`/`IFS` out of reach), then regex-validates every
  value that reaches a command line; values travel as array elements, never
  through a shell. `TestGCPVMRejectsBadNames` proves `GCP_INSTANCE='x;rm'`
  dies before any tool is called. (b) the remote shell strings in
  `install.sh:143,146,153,158`: `VERSION` (`^[0-9]+\.[0-9]+\.[0-9]+$`),
  `USER_NAME` (`^[a-z_][a-z0-9_-]{0,31}$`) and `ORIGIN`
  (`^https://[a-z0-9.-]+/[A-Za-z0-9._/-]+$`, after normalising scp/ssh forms)
  all exclude every shell metacharacter before interpolation. `sq()`
  (`install.sh:137`) was run standalone on this box (bash 5.2.37): it emits
  correct POSIX escaping — `a'b; rm -rf /` → `'a'\''b; rm -rf /'`, and the
  helper's own quotes survive — so the credential-helper snippet cannot break
  out of the remote command string. The helper snippet itself carries only
  `${STYRMAN_GH_TOKEN_FILE}`, escaped so the VM's shell (not install.sh)
  expands it, and `TestGCPInstallCloneHelperShape` asserts the token path is
  never interpolated into the snippet. `env_get`'s `grep -E "^$2="` uses only
  literal key names.
- **Authz/authn** — Nothing in this range touches the server's auth guard, the
  `X-Styrman-Ingress`/`X-Caddy-Email` pair, identity slugs, the user store or
  any endpoint; no Go source outside two new `_test.go` files changed. The
  trust decisions added are all install-time: `git verify-tag` against a staged
  `allowed_signers` (finding 3), `private_file`'s owner/mode/symlink checks on
  the three secret files (`install.sh:58-72`, mirroring `styrman-ctl`'s), and
  the pre-flight refusals (no VM / not running / ssh down / no `/dev/kvm` /
  loose or incomplete env), each with a test asserting that a refusal reached
  **no** tool and staged **no** file.
- **Crypto** — Nothing hand-rolled, nothing composed. The range uses
  `git verify-tag` (which dispatches to `ssh-keygen -Y verify` for SSH
  signatures) and `sha256sum`, both vetted tools used as designed; no cipher,
  MAC, KDF, RNG, token format, session or auth flow is implemented here. The
  one crypto-adjacent weakness is scope, not construction — finding 3.
- **Dependencies** — No dependency added or changed in the range (verified: the
  diff touches no manifest or lockfile in either Go module or in `web/`). New
  runtime requirement on the *target host* only: `zstd`, installed from Debian
  via apt when absent (`host-setup.sh`), and `python3`, already required by
  `install.sh:112` — both stdlib-equivalent choices for this job (`tar --zstd`
  needs the zstd binary; the release-API JSON has no coreutils parser, and
  `python3` avoids adding `jq`). `govulncheck`/`npm audit` results are in the
  informational finding above.
- **GCP surface** — Good, with one gap. `--no-service-account --no-scopes`
  (`vm.sh:76`) is the right call and is explicitly reasoned in ADR-075: a
  LAN-mode project reaches the metadata server, so there must be no token
  there to steal. Shielded VM fully on (secure-boot, vTPM, integrity
  monitoring). `enable-oslogin=FALSE` + `block-project-ssh-keys=TRUE` keeps
  project-wide metadata keys off the host. IAP tunnelling is the default for
  both ssh and scp (`SSH_ARGS`, `lib.sh:46`), asserted per-line by
  `TestGCPInstallPlan`; `GCP_SSH_VIA_IAP=0` is an explicit opt-in that the
  docs correctly tie to adding the `ssh` tag. Secrets travel as files by
  `gcloud compute scp` into a `install -d -m 700` directory and are `chmod
  600`-ed, never as env vars on any command line, and they are removed by a
  trap. No service-account key file anywhere. The gap is the firewall
  finding plus the credential-reuse finding above. One doc nit:
  `lib.sh:64-65` says gcloud "adds this machine's key to project metadata on
  first use", which `block-project-ssh-keys=TRUE` makes instance metadata;
  `gcp.md`'s Verify section already states it correctly. Carried forward from the prior review and still true: `gcloud compute ssh --quiet` generates a **passphraseless** `~/.ssh/google_compute_engine` key on the operator's machine on first use and pushes it to metadata — stock gcloud behaviour, noted rather than filed, but that key is what reaches this host.
- **Instruction-shaped text (new `.agents/rules/*.md`)** — Both read clean and
  neither tells a future agent to do anything unsafe.
  `remote-check-names-transport-first.md` actively encodes a security rule ("a
  management port is not exposed publicly when the platform offers a tunnel")
  and names the must-fail test that proves it.
  `shared-path-learnings.md` encodes "a download's checksum comes from
  something the publisher still publishes … never a sidecar file assumed to
  exist", which is the right lesson (see the `host-setup.sh:78-88` finding on how much that
  checksum is worth). The one piece of instruction-shaped text worth a second look is
  in the **plan**, not the rules: the recorded
  `umask 077; sudo -n grep …/opt/styrman/deploy/.env > env; sudo -n cat /etc/styrman/gh-token > gh-token; …`
  pipeline. It prints no value and sets `umask 077` first, so it is
  defensible, but it instructs a future agent to read the live production
  token files with passwordless sudo; it would be safer as an operator step in
  `gcp.md` written as a subshell `( umask 077; … )` so the umask cannot leak
  past the statement.

## Outcome

1. **Medium/high**, the NUC's live Cloudflare token, OAuth client secret and GitHub token reused verbatim on a host declared disposable: **accepted for this release, raised to the operator, and the guidance reversed in the docs**. `.agents/docs/deploy/gcp.md` no longer says the NUC's credentials "can be reused": it requires a separate OAuth client and a separate, zone-scoped Cloudflare token per host, with the reuse named as what it costs (a compromise of the disposable host can repoint the production name and obtain a certificate for it). The already-provisioned VM still holds the reused secrets; rotating them is an operator action, named in the handoff's Next Steps. Not a blocker: no high finding, and the host is not yet serving.
2. **Medium/medium**, "no public port 22" asserted by nothing: **fixed**. `deploy/gcp/lib.sh` gained `assert_no_public_ssh`, which `vm.sh create` runs BEFORE reserving or creating anything: it reads the project's firewall rules and refuses when any enabled ingress rule from `0.0.0.0/0` reaches this instance's tags (or carries none) on port 22, naming the rule; `GCP_ALLOW_PUBLIC_SSH=1` accepts the exposure with a warning. `TestGCPVMCreateRefusesPublicSSH` drives four must-fail shapes (a bare `tcp:22`, a `20-30` range, a portless `tcp`, an `all` rule on one of our tags) and six must-pass ones (empty, another tag's rule, web-only ports, an internal source range, a disabled rule, an egress rule), plus the override. Mutation: removing the call → `exposed project accepted: code 0`; restored from a byte copy.
3. **Low/medium**, `verify-tag` inside a VM-user-writable checkout: **fixed**. The command now pins `-c gpg.format=ssh -c gpg.ssh.program=ssh-keygen` alongside the allowed-signers file, and the checkout is reset hard to the tag before it runs (code review finding 4).
4. **Low**, staged secrets survive a failed cleanup and the WARN named no command: **fixed**. The warning now prints the exact `deploy/gcp/vm.sh ssh -- 'rm -rf "$HOME/.styrman-install"'` to run.
5. **Low**, `GH_TOKEN` read during `--dry-run`: **fixed**. `run_host_setup` reads the file only when not a dry run; the plan still states the export.
6. **Low**, the Kata digest shares a trust root with the download: **rebutted, as in the 2026-09-21 review**. The version every host installs is pinned to a constant in the script, matched against a same-day download; the API path serves an operator-chosen other version and still fails closed with no digest. `KATA_SHA256` pins it offline. A second trust root would need a publisher that offers one.
7. **Low**, `--secrets-dir`'s symlink check covers only the last component: **accepted**. The path is the operator's own home directory on their own machine; a hostile parent there is a compromise that this check cannot meaningfully narrow.
8. **Low**, `vm_ssh --command="$*"` flattening vs the `CMD…` usage line: **fixed as documentation** — `lib.sh`'s comment now states that every argument is flattened into one command string.
9. **Informational**, the 2026-09-21 code review's `## Outcome` describes an install line the security fix later superseded: **corrected** by an addendum in that report.
10. **Dependencies**: `GO-2026-4887` and `GO-2026-4883` in `github.com/docker/docker@v28.5.2+incompatible` are **Fixed in: N/A** upstream and pre-existing; `js-yaml` GHSA-2883-xcg3-v3hh in `web/` has a fix and is pre-existing. None is introduced by this range; all three are named in the gate report's "What was not checked" and left for a dependency task, since bumping the frontend at tag time would invalidate the verification this gate took.
