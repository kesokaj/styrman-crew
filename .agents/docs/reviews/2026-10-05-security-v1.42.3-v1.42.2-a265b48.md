# Security review — v1.42.3-v1.42.2-a265b48   (2026-10-05)

Range reviewed: v1.42.2..a265b48. The range has two commits: 34aabe8 (handoff)
and a265b48 (the v1.42.3 work). It touches 33 paths, all text according to
`git diff --numstat`.

## Status: COMPLETE

## Verdict: FINDINGS (2 medium, 3 low)

The worst problem is new in this range. The editor's file endpoints now share
8 `fileSlots` across the whole server, with no per-user share. Each slot is
taken before the request body is read, and no read deadline is ever set. So a
single tenant can hold all 8 slots, and while it does, every other tenant gets
a 429 on Open, Save, Format and Check:
- **For up to 30 s at a time, repeatable.** Send 8 `/check` requests and make
  the checker inside your own VM sleep. Do it again when they finish.
- **Possibly with no time limit.** Send 8 `PUT …/file` requests whose bodies
  arrive one byte at a time. Whether this works depends on Caddy's body-read
  default, which I did not verify.

Before this range, a slow editor request cost only its own memory. Gate row 3
(no per-user share, so other tenants get a 429) is still open, and it now
covers Save as well as history.

Second, the change entry claims "every memory-heavy endpoint bounded" and that
this "closes the last tenant crash-loop path under the 4g cap". That claim is
false:
- The git endpoints send up to 2 MiB of output that the guest controls. It is
  JSON-encoded in a single buffer, about 12 MiB once escaped. They have no slot
  and no write deadline.
- Directory listings, transcript listings and multipart uploads are not
  bounded either.
- Gate row 1 planned "one limiter for every heavy endpoint plus server
  timeouts". Only the four editor endpoints got it, and `cmd/styrman/main.go`
  is unchanged.

Of the fixes the range sets out to make:
- The editor bound itself works.
- The real-server deadline test is sound.
- The history-panel abort is in place.
- `host-setup.sh` now refuses an empty token file.
- The `.env` file is created with umask 077, then renamed into place.
- The e2e harness now refuses to run without `--base`, writes screenshots to a
  private directory, and refuses a status file outside its state dir.

The other lows are small leftovers from those fixes.

## Findings

- **[medium / confidence: high for the 30 s cycling variant; medium for the slow-body variant, which depends on Caddy's body-read default (not verified)]**
  `internal/httpapi/explorer.go:460-465,474-486` (fileConcurrency = 8,
  acquireSlot), `:77-81` (readFile), `:273-277` (writeFile),
  `internal/httpapi/format.go:61-64,109`, `internal/httpapi/check.go:338-341,381`,
  `cmd/styrman/main.go:168-172` (only `ReadHeaderTimeout`) — one tenant can
  lock every other tenant out of the editor.
  - **Weakness.**
    - The 8 slots are shared by the whole server; no user has a share of their
      own.
    - The slot is taken before the body is read (by design, see the comment at
      `:458-459`).
    - `acquireSlot` sets only a WRITE deadline, and there is no read deadline
      anywhere.
    - The `/format` and `/check` handlers run a command in the caller's own
      guest for up to 30 s (`format.go:109`, `check.go:381`). The tenant is
      root in that guest and decides what `shellcheck`, `gofmt` or `prettier`
      does.
  - **Scenario A (no dependency on Caddy).** Tenant A keeps 8
    `POST …/check` requests in flight. A's `shellcheck` is `sleep 29`. A sends
    a new batch as each one ends. Every other user's open, save, format and
    debounced check gets a 429 ("too many file operations in progress") for as
    long as A keeps this up.
  - **Scenario B.** A sends 8 `PUT …/file` requests whose body arrives one
    byte at a time.
    - Each holds its slot inside `json.NewDecoder(r.Body).Decode`
      (`explorer.go:286`) with no deadline at all.
    - Caddy's `reverse_proxy` streams request bodies to the upstream, and the
      generated config (`deploy/caddy/ingress/generator.go`) sets no
      `read_body` timeout.
    - Result: the editor stays locked for every user until A disconnects.
  - **New in this range.** Before it, the same requests held only their own
    memory. The gate's row 3 ("no per-user share") was about history. It is
    still open: the change entry says "The per-user server cap stays out".
    It now also covers Save.
  - **Remediation.**
    - Give each user a share inside the global 8 (for example at most 3). The
      editor needs one read, one check and one save at a time, and the client
      already aborts a superseded check.
    - Set a read deadline when the slot is taken
      (`http.NewResponseController(w).SetReadDeadline(...)`), so a body that
      never arrives frees the slot.
    - Optionally, take the slot after `scopeFor`/`gitContext`.
    - Tests, each failing without its fix:
      - User A at the cap gets a 429 while user B is still served.
      - On a real server, a request that sends its headers and only part of
        its body releases the slot when the read deadline fires.

- **[medium / confidence: medium — worked out from the code, not measured: production host, no load experiments]**
  `internal/httpapi/git.go:478-540` (gitDiff → `gitExec` → `guest.Exec`),
  `git.go:426,473,842` (`{"output": out}`), `internal/orchestrator/exec.go:32`
  (`maxExecOutput` 2 MiB), `internal/httpapi/server.go:1395-1399` (`writeJSON`
  encodes the whole body before `Write`), `internal/files/files.go:43`,
  `internal/history/history.go:64`, `internal/httpapi/explorer.go:329-384`
  (uploadFile) — memory-heavy endpoints are still unbounded. This contradicts
  `changes/2026-10-05-1637-v1.42.3-work.md:5,14-15`.
  - **Weakness: the git endpoints.** `GET …/git/diff` (and `?commit=`), and
    the `output` of stage, unstage, discard, commit, push, fetch, pull,
    checkout and stash, all return output the guest controls.
    - The output is capped at 2 MiB, then JSON-encoded in one buffer.
    - Control bytes and invalid UTF-8 escape to 6 bytes each, so about
      12–16 MiB stays held during the write.
    - There is no slot and no write deadline.
    - A tenant controls `git` in its own VM. It can also simply commit a
      2 MiB file of `\x01` bytes, which git does not treat as binary.
  - **Scenario.** About 250 `GET …/git/diff` requests that are never read
    (through Caddy, the backpressure reaches the server's write) hold about
    4 GiB. The server's 4g cap (ADR-085) OOM-kills it for every tenant. A
    repeat is a crash loop. This is the same class as gate row 1, on endpoints
    row 1 did not name.
  - **Same class, smaller:**
    - `GET …/files` and `…/home/files`: up to 5000 entries. A 255-byte name of
      control characters escapes to about 1.5 KiB, so about 8 MiB of JSON.
    - `GET …/history`: up to 5000 transcripts. Whether names are filtered was
      not verified.
    - `POST …/upload` and `…/home/upload`: Go's multipart reader keeps up to
      10 MiB of part headers in memory. They stay held while that part's body
      trickles in, with a 512 MiB body cap, no slot and no read deadline.
  - **Remediation.**
    - Do what the gate planned. Put every handler that returns or accepts
      more than about 1 MiB behind a limiter: the git verbs above, both file
      listings, the transcript listing and uploads. Each slot gets a read and
      a write deadline, plus the per-user share from the first finding.
    - Or shrink the buffers: a lower exec cap for output sent back as JSON,
      or send the diff as `text/plain` with no 6× escaping.
    - Record the open residual in the release entry. `changes/` is
      append-only.
  - **Route enumeration.** See `## Checked` → "Routes and buffers".

- **[low / confidence: high]** `.agents/docs/deploy/remote.md:90-98`,
  `.agents/docs/specs/styrman/deploy.md:263-271`, `deploy/update/styrman-update:559`
  (and onwards), `deploy/styrman-ctl` (`install --gh-token-file`) — the
  token-handling lows from gate row 4 are only half closed.
  - `(umask 077 && cat > ~/fine-grained-token)` sets the mode only when it
    creates the file. If a `~/fine-grained-token` already exists — for
    example from the previous snippet, created under the default umask — it
    keeps its wider mode while the token is written into it. Row 4's "the
    plaintext file's mode is not forced" still holds.
  - `cat` also shows the pasted token on screen, so it lands in the terminal's
    scrollback. Contrast `host-setup.sh:374-376`'s own `read -rs`, which
    avoids both.
  - The empty-file refusal was added to `host-setup.sh:313` only. A grep
    finds no `-s` test on the token file in `styrman-update` or `styrman-ctl`.
    The earlier addendum named all three callers (rule
    mechanism-reaches-every-caller).
  - **Remediation.** Use `rm -f ~/fine-grained-token` (or
    `install -m 600 /dev/null …`) before writing it, or the `read -rs` form.
    Add the `[ -s ]` refusal to the updater and to `styrman-ctl`.

- **[low / confidence: medium]** `web/e2e/run.mjs:30-37` and
  `web/e2e/run.sh:91-96` — the e2e harness fixes have three gaps.
  - **Status-file check.** It compares the strings without normalising them.
    `STYRMAN_UPDATE_STATUS_FILE=$STATE/../../x` passes `startsWith(st + "/")`,
    and `run.mjs:1483-1506` then writes that path and `rmSync`s it.
  - **Cleanup ownership.** The cleanup treats any `styrman-<uuid>` string in
    this run's server log as "ours".
    - That is broader than "containers this server created". The e2e server
      shares the host's Docker with production, and
      `orchestrator.go:643-668` walks every `sdb-` network on the host.
    - A log line naming a production container would let that project's
      network be removed, if it was created during the run. Whether such a
      line is ever logged was not verified.
    - In the fail-safe direction: if nothing is logged, the sweep removes
      nothing.
    - `grep -qx "${n#*-}"` uses the network name as a regex. Only principals
      with root-equivalent Docker access can name host networks, so this is
      a nit.
  - **Screenshots.** `$SHOTS` directories are never removed (`/tmp` is tmpfs
    on dave).
  - **Remediation.**
    - Run `path.resolve` (plus `realpath` on the state dir) before the prefix
      test.
    - Have `run.mjs` write the IDs it created (PID, BADID, OKID) to `$STATE`,
      sweep only those, and use `grep -qxF`.

- **[low / confidence: high]** `internal/httpapi/explorer.go:480`
  (the deadline is armed when the slot is taken), `format.go:109`,
  `check.go:381`, `changes/2026-10-05-1637-v1.42.3-work.md:17-19` — the
  write deadline starts before the work, and the entry's reason for skipping
  server timeouts is partly wrong.
  - **The deadline starts too early.** The 30 s write deadline starts before
    the body is read and before the guest command, which can itself take up
    to 30 s.
    - A Format or Check that takes longer than 30 s from upload to finish
      cannot send its result.
    - A `PUT …/file` whose 8 MiB body takes more than 30 s to upload (under
      about 2 Mbit/s) writes the file, but the client sees an error (Caddy
      returns 502). The UI then reports a failed save that actually
      succeeded.
    - This affects only the tenant's own requests; it is not a security
      boundary.
  - **The entry's reasoning.** It says "a global `WriteTimeout` would cut
    terminal WebSockets".
    - That is inaccurate: go1.25's `net/http` clears both deadlines on hijack
      (`$GOROOT/src/net/http/server.go:325`).
    - The conclusion still stands, because preview streams, long downloads
      and 512 MiB uploads would be cut.
  - **Remediation.** Re-arm the write deadline just before the response is
    written. Use the slot-time deadline as a READ deadline (first finding).

## Outcome
(main agent, 2026-10-05)
1. **Partly fixed, rest accepted (medium → bounded).** 2829e51 adds a 30 s read deadline to every slot holder, so a trickled body cannot hold a slot past it. A lockout is still possible: 8 slow `/check`s, or bodies re-sent every 30 s, give other tenants a retryable 429 on the editor. That is a bounded denial, not a crash. Per-tenant accounting is the follow-up, together with the history fairness items.
2. **Accepted and corrected (medium, NOT fixed).** The v1.42.3 work entry's claim that "every memory-heavy endpoint is bounded" is false. The git endpoints (up to 2 MiB of guest output, about 12–16 MiB JSON), the file and transcript listings, and multipart uploads are unbounded, the same crash-loop class open since v1.42.1's 4g cap. It is not new in this range. Bounding endpoints one by one keeps missing some, so the proposed fix is one central byte budget for building JSON responses and decoding bodies, as v1.42.4. The v1.42.3 release entry states this.
3. **Left: follow-up (low).** The token snippet's umask does not fix an existing file's mode, and the paste echoes; `styrman-update` and `styrman-ctl` do not refuse an empty token file.
