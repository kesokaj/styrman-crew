# Security review — v1.17.3 updater self-install + pinned-toolchain vulncheck   (2026-09-02)

Scope: working-tree diff on top of `c83ddba` (v1.17.2) — `deploy/update/styrman-update`
(+51, new `self_install()` called on the deploy-success and rollback-success paths),
`deploy/update/styrman-update.service` (+4, `STYRMAN_UPDATER_BIN` / `STYRMAN_UPDATER_UNIT_DIR`
pins), and the new `deploy/vulncheck.sh`. Blast radius followed outward: the whole trust chain
that decides which tree `self_install` copies from (`verify_tag`, the `REQUIRE_SIGNED` opt-out,
the rollback `trusted` path, the deploy-clone ownership asserts), the systemd unit that now
becomes self-mutable, `deploy/host-setup.sh` (the other installer of the same three files), and
the gate semantics of the vulncheck script. No Go, web or dist changes; concurrent docs edits
(`AGENTS.md`, `TODO.md`, `.agents/docs/**`) were scanned for secrets and carry none.

## Verdict: FINDINGS

Nothing here crosses a privilege boundary that was not already crossed — but the change moves the
updater from "deploys a container stack" to "rewrites its own root-run binary and its own systemd
unit on the host", and the guards did not follow it there. The worst of it: **with the documented
`STYRMAN_UPDATE_REQUIRE_SIGNED=0` opt-out engaged, an UNVERIFIED release's `styrman-update` and
units are installed to `/usr/local/bin` and `/etc/systemd/system` as root and `daemon-reload`ed**,
so an unsigned tag now buys host-level persistence outside the container stack *and* control of the
mechanism that would otherwise deliver its replacement — including whether signatures are checked
on the next tick. That is a real escalation of the opt-out's consequences (today the opt-out is
recoverable by turning it back on; after this change it is not), and the fix is one line: refuse to
self-install when `REQUIRE_SIGNED != 1`, exactly as the script already refuses to record a trusted
`deployed-sha` in an opt-out window. Everything else is defense-in-depth: the ADR-052 env pins are
the only root-supplied paths in this script with no validation at all, and `vulncheck.sh` does not
actually return govulncheck's exit status the way its header claims.

Answers to the four questions asked, up front:
1. **Unverified-tree install path: yes, exactly one** — the `REQUIRE_SIGNED=0` opt-out (F1).
   `--force` does **not** bypass verification (it only clears the failed-tag latch; `verify_tag`
   still runs on the main path), and the rollback's `trusted` skip is sound: `deployed-sha` is
   written *only* when `REQUIRE_SIGNED=1` and is shape-checked to 40 hex before use, so a SHA
   captured during an opt-out window can never be replayed as trusted.
2. **Unit install + `daemon-reload` lets a signed release rewrite its own hardening — yes, by
   design.** Threat-model delta: **no new capability**, one new consequence (F5).
3. **`sudo -E` env injection of the pins: yes, unvalidated** (F3) — root-only, so a foot-gun and a
   consistency gap rather than a boundary crossing, but it is the same class the `DOCKER_CONFIG`
   and `STATE_DIR` guards exist to close, and ADR-052 was written *because* of env-driven path
   aliasing in a privileged run.
4. **`vulncheck.sh` cannot be made to read as "clean" when it is not** — it is fail-closed in the
   direction that matters (no failure path yields exit 0), but its exit status is not govulncheck's
   and cannot distinguish "vulnerabilities found" from "docker/toolchain broke" (F6). Baseline
   re-run today and **confirmed**: both modules, exactly `GO-2026-4887` + `GO-2026-4883`
   (github.com/docker/docker@v28.5.2+incompatible, Fixed in: N/A, daemon-side moby AuthZ-plugin
   bypass and plugin-privilege off-by-one), **zero stdlib findings**.

## Findings

- **[high / confidence: high]** `deploy/update/styrman-update:364-395` (`self_install`) —
  `self_install` has no `REQUIRE_SIGNED` gate. With `STYRMAN_UPDATE_REQUIRE_SIGNED=0` set in
  `/etc/styrman/update.env`, `verify_tag()` returns 0 unconditionally, so **any** tag anyone can
  push is deployed and — once the health check passes — its `deploy/update/styrman-update`,
  `.service` and `.timer` are installed as root over the host copies and `systemctl daemon-reload`
  is run. Exploitable in principle by anyone who can push a `vX.Y.Z` tag to the private repo
  (account takeover, a future collaborator, a write-capable CI token) during an opt-out window.
  The opt-out already grants root code execution via `docker build`/`compose up` from the hostile
  checkout, so this is not a *new* privilege — what is new is **persistence and irrecoverability**:
  before this change the host's updater and units were `host-setup.sh` artifacts that no release
  could touch, so re-enabling signing and rolling back restored a clean control plane. After it,
  the attacker's updater is what runs on the next tick and it decides whether signatures are
  checked at all. Remediation (one line, first statement in `self_install`, mirroring the existing
  `deployed-sha` precedent at `:498-503`):
  `[ "${REQUIRE_SIGNED}" = "1" ] || { log "self-install skipped: signature checking is DISABLED — refusing to install host artifacts from an unverified tree"; return 0; }`

- **[medium / confidence: medium]** `deploy/update/styrman-update:369,371,379` — TOCTOU between
  verification and install: `self_install` copies from the **worktree** (`${DEPLOY_DIR}/deploy/update/*`),
  not from the verified git object, and the window between `git checkout --detach --force` and the
  call is the full duration of two docker builds plus the health wait (minutes). The script asserts
  `${DEPLOY_DIR}/.git` is root-owned and `deploy/.env` is root-owned + `0600`, but **never asserts
  the worktree's own mode** — a group/world-writable `/opt/styrman/deploy/update` (misconfigured
  clone, or a clone created outside `host-setup.sh`'s documented flow) lets a local unprivileged
  user swap the file after verification and have it installed root-owned `0755` into
  `/usr/local/bin`. The same tampering already poisons the built image, so the delta is again host
  persistence — but the fix is cheap: install from the verified object,
  `git show "HEAD:deploy/update/styrman-update"` into the temp file (immune to worktree writes), or
  at minimum assert `find "${DEPLOY_DIR}" -maxdepth 0 -perm /022` empty and `git diff --quiet HEAD -- deploy/update`
  before installing.

- **[low / confidence: high]** `deploy/update/styrman-update:362-363` +
  `deploy/update/styrman-update.service:11-14` — `STYRMAN_UPDATER_BIN` and
  `STYRMAN_UPDATER_UNIT_DIR` are consumed with **zero validation**: no `realpath` canonicalization,
  no prefix allowlist, no ownership/mode assertion on the destination directory. Every other
  root-supplied path in this script is guarded (`STATE_DIR` canonicalized + `/var/lib/styrman`
  refusal, `DOCKER_CONFIG` shape + root-owned + not-group-writable, `GH_TOKEN_FILE`,
  `ALLOWED_SIGNERS`, the clone, `deploy/.env`); these two are not. A hand-run inheriting a stale or
  hostile environment (`sudo -E styrman-update --force`, or the documented
  `sudo STYRMAN_...=... styrman-update` habit at `deploy/host-setup.sh:407` with one extra
  assignment) overwrites an arbitrary path with the updater script at mode `0755 root:root`, and
  writes two more files plus a `daemon-reload` into an arbitrary directory — e.g.
  `STYRMAN_UPDATER_BIN=/etc/cron.d/x`, or clobbering an existing system binary. Setting the env
  requires root already, so this is not a privilege escalation; it is the precise foot-gun class
  that produced the 2026-09-01 state-loss incident and ADR-052. Remediation: canonicalize with
  `realpath -m` and require `UPDATER_BIN` to be `/usr/local/bin/styrman-update` and `UNIT_DIR` to be
  `/etc/systemd/system` (an allowlist is defensible here — the unit is the only supported setter),
  or at minimum require both destination dirs to exist, be root-owned and not group/world-writable,
  and require `basename "${UPDATER_BIN}" = styrman-update`.

- **[low / confidence: medium]** `deploy/update/styrman-update:373,381` — predictable temp name
  `"${dst}.new.$$"` in the destination directory. On a stock host `/usr/local/bin` and
  `/etc/systemd/system` are `root:root 0755`, so no unprivileged process can pre-create the temp
  path and there is no race; the `mv -f` within the same directory is a correct atomic rename onto a
  new inode, and replacing a pre-existing symlink at the destination is handled correctly (rename
  replaces the link itself). But the script asserts none of that, and finding F3 means the
  destination directory is caller-chosen — so the two compound: a loose destination directory plus a
  guessable PID (the updater's PID is in the journal) makes the temp path a symlink-plant target,
  with `install(1)`'s follow-vs-unlink behaviour on a pre-existing symlink being the deciding detail.
  Remediation: `mktemp` inside the destination directory instead of `.$$`, and assert the directory
  is root-owned and not group/world-writable (fixing F3 largely subsumes this).

- **[low / confidence: high]** `deploy/update/styrman-update:372-385` — partial-install fails open
  and silent. Each component's failure branch does `return 0`, so a failed `install` of the script
  skips the units entirely, and a failed unit skips the remaining unit *and* the `daemon-reload`,
  while the deploy still reports `OK — vX is live` and the only trace is one `WARN` line in the
  journal. The most likely silent outcome is the worst one for this feature: the binary updates but
  `styrman-update.service` does not, so the `Environment=STYRMAN_UPDATER_*` pins never land and
  self-install is **permanently skipped from then on** with no alarm — i.e. the mechanism that
  delivers security fixes to the root-run updater fails closed-shut rather than loud. Not a
  vulnerability; a patch-delivery availability defect with security consequence. Remediation: do not
  `return` on a component failure — record it, continue, `daemon-reload` if anything changed, and
  make the final line name which components installed and which failed (and consider echoing that
  into the `OK — ... is live` line so it is visible without journal archaeology).

- **[low / confidence: high]** `deploy/update/styrman-update.service` (whole file, now
  self-mutable) — **accepted by design, recorded for the threat model.** Installing the units and
  running `daemon-reload` means a signed release can ship a `styrman-update.service` that drops
  `NoNewPrivileges` / `ProtectHome` / `RestrictSUIDSGID`, changes `ExecStart`, or adds an
  `ExecStartPre=`, and it takes effect on the next tick. This does **not** change the threat model
  against a hostile signed release: such a release already runs arbitrary code as root through
  `docker build` and `docker compose up` from its own checkout, and the unit's own comment says so
  ("a hostile release's payload runs in the DOCKER DAEMON, not in this cgroup — sandboxing this unit
  cannot contain it"). What it *does* change is recoverability — see F1 — and that the host's
  systemd configuration is now release-controlled state rather than a setup-time artifact. No code
  change requested beyond F1; record it in the ADR so the next reader does not mistake the unit
  hardening for a control that a release cannot reach.

- **[low / confidence: high]** `deploy/vulncheck.sh:16-33` — the header claims "Exit status is
  govulncheck's"; measured, it is not. `go run` collapses govulncheck's distinguishing exit 3 into
  its own exit 1 (observed: `exit status 3` printed to stderr, script exit `1`). So "called
  vulnerabilities found" (3), a failed image pull (125), a network/module-download failure and a
  read-only-mount failure are **all exit 1** and indistinguishable by status. The direction is
  fail-closed — no failure path produces exit 0, and `rc` is sticky across both modules, so a
  passing second module cannot mask a failing first — which is the property that matters, hence low
  severity. The practical hazard is the other way round: the *accepted* baseline is itself non-zero
  on every run (both docker/docker findings are CALLED, `Fixed in: N/A`), so a gate keyed on exit
  status is permanently red, and the realistic outcome is the status getting ignored — at which
  point a genuinely new finding looks exactly like the baseline. Remediation: capture the real
  status inside the container (`sh -c 'go run ...; echo $? > ...'` or `go build` the tool then run
  it), reserve exit 2 for infrastructure/tool failure vs 3 for findings, and — the durable fix —
  emit `-format json` and diff the OSV ID set against a checked-in baseline file so "same two
  accepted docker/docker findings" is exit 0 and any new ID is a hard fail.

- **[low / confidence: medium]** `deploy/vulncheck.sh:27` — the mount is the **whole repo root**
  (`-v "${ROOT}:/src:ro"`), which on this machine includes the gitignored `deploy/.env` (0600,
  ingress token + `STYRMAN_ALLOWED_EMAILS`). It is then readable by everything in that container,
  including the `govulncheck@v1.7.0` tool the script downloads and executes from the network at run
  time. Read-only, no known exfil path, and govulncheck does not read it — but handing a live
  credentials file to third-party code fetched at run time is gratuitous. Remediation: mask it,
  `-v /dev/null:/src/deploy/.env:ro` (and `/src/deploy/caddy/ingress/.env` if it ever exists), or
  mount only the module directories. Related, no action needed: module integrity *is* protected —
  `GOFLAGS=-mod=mod` does not disable `GOSUMDB`/`GONOSUMCHECK`, so the persistent
  `styrman-vulncheck-cache` volume is checksum-verified on fill; and the builder image comes from a
  version tag rather than a digest, which is deliberate (single source of truth with
  `Dockerfile.server`) and matches existing practice.

## Checked

- **Secrets** — none introduced. Diff (source + concurrent docs edits) scanned for
  `ghp_`/`github_pat_`/`AIza`/PEM headers/long base64: no hits. `self_install` logs only paths, never
  file contents; no new value is echoed. `deploy/.env` remains gitignored and is not committed; F7
  covers it being *mounted* into the vulncheck container.
- **Injection** — no shell interpolation of untrusted data added. `self_install`'s only variables
  are the two env pins and a fixed `for f in` literal list, all quoted; no `eval`, no unquoted
  expansion, no `sh -c` with interpolated data. `vulncheck.sh` interpolates `${ROOT}`, `${IMAGE}`
  (sed-extracted from a tracked Dockerfile, anchored regex, fail-closed when it does not match) and
  `${mod}` (two hardcoded literals) into a `sh -c` string — all developer-controlled, none reachable
  from external input. The path-injection surface that does exist is the unvalidated env pins (F3).
- **Authz/authn** — no HTTP surface touched. The authorization decision in scope is the tag
  signature check: `verify_tag` traced end to end (lightweight-tag refusal, last-armor-header check
  forcing the SSH verifier, allowlist ownership/mode assertion, fail-closed on a missing allowlist)
  and it is intact; `--force` does not bypass it; the rollback `trusted` skip is correctly fenced by
  `REQUIRE_SIGNED=1` at `deployed-sha` write time plus a 40-hex shape check at read time. The one
  gap is that `self_install` does not consult that decision at all (F1).
- **Crypto** — nothing hand-rolled. Signature verification is delegated to `git verify-tag` with
  `gpg.ssh.allowedSignersFile`; repo auth is a fine-grained GitHub token over TLS via a
  URL-scoped inline credential helper. No new primitive, no new session/JWT/password handling.
- **Dependencies** — no new runtime dependency. One new *tool* dependency, pinned:
  `golang.org/x/vuln/cmd/govulncheck@v1.7.0`, fetched inside the builder container and
  checksum-verified via the default sumdb; justified (stdlib has no equivalent, and it is the
  ecosystem-standard scanner). `deploy/vulncheck.sh` run twice today against
  `golang:1.25.13-trixie`: both modules report exactly `GO-2026-4887` and `GO-2026-4883`
  (github.com/docker/docker@v28.5.2+incompatible, Fixed in: N/A, daemon-side moby issues reached
  only via the docker *client* library) and **zero stdlib findings** — the host `go1.25.0`'s 31
  stdlib findings were toolchain artifacts, confirmed. Both accepted for this release: no fix
  exists upstream and the vulnerable code runs in the daemon, not in these binaries. `npm audit
  --omit=dev` in `web/`: **found 0 vulnerabilities**.

# Security review — v1.17.3 ROUND 2 (delta)   (2026-09-02)

Scope of this pass: the remediation delta only — `deploy/update/styrman-update` (`self_install`
rewritten: `REQUIRE_SIGNED` gate, `trusted_dir()`, `atomic_install()`, no-early-return partial
handling) and `deploy/vulncheck.sh` (`go install` + run, `GOTOOLCHAIN=local`, `/dev/null` shadow of
`deploy/.env`, `GOFLAGS` dropped). Re-traced: both `self_install` call sites, `REQUIRE_SIGNED`'s
full lifetime, the rollback `trusted` path, the target-validation chain, the orphan-cleanup glob,
and the container mount. No Go, `web/` or `dist/` changes in this round either. Concurrent doc edits
(`AGENTS.md`, `TODO.md`, `.agents/docs/**` incl. the new ADR-057) re-scanned for secrets: none.

## Verdict: FINDINGS

**The high (R1-F1) is CLOSED**, and closed correctly at the right layer. Two of the three low
findings on the target-injection/temp-file axis are closed, the partial-install defect is closed,
and both vulncheck findings are closed with measurement. What remains is the **medium R1-F2 —
`self_install` still copies from the mutable worktree rather than from the verified git object, and
the worktree's own mode is still never asserted** — which was not addressed in this round and is the
worst thing left on the record. It is not a regression and it is not reachable on a correctly
provisioned host (`host-setup.sh` clones as root into `/opt/styrman`), but it is now the only path
by which an unprivileged local user could get a file installed root-owned `0755` into
`/usr/local/bin`, and the fix remains cheap (`git show "HEAD:deploy/update/<f>"`, or a
`-perm /022` assert on `${DEPLOY_DIR}` and `${DEPLOY_DIR}/deploy/update`). Ship-blocking is the
reviewer's call, not mine; from the security side the high is gone and the residue is a medium with
a documented, bounded precondition.

## Round-2 status of every round-1 finding

- **R1-F1 (high) — CLOSED, verified by trace.** `styrman-update:384-391` now returns early with a
  log line when `REQUIRE_SIGNED != 1`, placed *before* any target resolution or file write.
  `REQUIRE_SIGNED` is written exactly twice in the whole script — the default `=1` at `:230` and the
  `/etc/styrman/update.env` opt-out read at `:239-240` — and is never reassigned thereafter (`grep`
  confirms `:264`, `:310`, `:388`, `:535` are all reads). It is therefore a single run-wide policy
  value, which makes **both** call sites covered by the one gate:
  - deploy-success path `:541` — `verify_tag "${LATEST}"` at `:312` is the only thing that let an
    unverified tag through, and the gate now refuses to act on that tree.
  - rollback-success path `:566` — the gate reads the *run's* policy value, not a per-deploy flag,
    so an opt-out run that falls into rollback also skips self-install. In the `REQUIRE_SIGNED=1`
    case the rollback ref is either `PREVIOUS_SHA` (written at `:535` **only** under
    `REQUIRE_SIGNED=1`, `rm -f`'d otherwise, and shape-checked to 40 hex at `:527`) or the previous
    tag, which `deploy` re-verifies. There is no reachable state where `self_install` runs against a
    tree this host has not verified. The `trusted` skip cannot be primed during an opt-out window.
  - Residual (accepted, no action): under `REQUIRE_SIGNED=1` a rollback self-installs an *older*
    verified updater — a signed downgrade of the host's control plane. That is the intended
    semantics ("the updater must match what is deployed") and every candidate is signer-allowlisted.
- **R1-F3 (low, `sudo -E` target injection) — CLOSED as a foot-gun-by-omission; bounded, not
  eliminated.** `:378-387`: both targets go through `realpath -m --`, `basename "${bin}"` must equal
  `styrman-update`, and `trusted_dir()` (`:366-368`) requires each destination directory to exist,
  be uid 0, and fail `find -maxdepth 0 -perm /022` — the identical bar `STATE_DIR`, `DOCKER_CONFIG`
  and `GH_TOKEN_FILE` already meet. Resolved targets are logged at `:388` before any write, so the
  journal records what was touched. Note `realpath -m` resolves the *final* component too, so a
  symlink at `/usr/local/bin/styrman-update` pointing elsewhere is followed and then re-judged by
  the basename pin and `trusted_dir` on the resolved parent — an attacker-owned or world-writable
  landing dir (`/tmp`, mode 1777) fails. **What a root operator can still do on purpose:** set
  `STYRMAN_UPDATER_BIN` to `<any root-owned, non-group/world-writable dir>/styrman-update` and get
  the updater written there `0755 root:root` — `/etc/cron.hourly/styrman-update` is the sharp
  example, since `run-parts` executes dot-free names; and set `STYRMAN_UPDATER_UNIT_DIR` to any such
  dir to get `styrman-update.service`/`.timer` at `0644` plus a `daemon-reload` (e.g. shadowing
  `/usr/lib/systemd/system`). Neither crosses a boundary — setting the env already requires root —
  and neither happens by accident any more: unset targets log-and-skip, a wrong basename or an
  untrusted dir log `WARN` and skip. Optional hardening if the operator wants the ADR-052 shape
  taken to its end: allowlist the two directories outright (`/usr/local/bin`, `/etc/systemd/system`),
  since the unit is the only supported setter.
- **R1-F4 (low, predictable `.new.$$` temp) — CLOSED.** `atomic_install` (`:371-377`) runs only
  after `trusted_dir()` has cleared the destination directory, so no unprivileged process can
  pre-create or symlink the temp path; `install -m … -o root -g root` then `mv -f` within the same
  directory is a correct same-filesystem rename onto a fresh inode (the running script keeps its old
  inode), and the failure branch cleans the temp up. The **orphan-cleanup glob is not abusable**:
  `rm -f "${dst}.new."*` is quoted up to the wildcard, is fenced to the same `trusted_dir`-cleared
  directory (so only root could have created a matching entry), `rm` does not follow symlinks — it
  unlinks the link itself, and an unmatched glob passes a literal through to `rm -f`, which is
  swallowed by `|| true`. A matching *directory* would make `rm` fail (no `-r`), also swallowed, and
  the subsequent install to `.new.$$` still succeeds. Concurrency is separately fenced by the
  existing `flock -n 9` on `/run/styrman-update.lock` (`:142-143`), so two runs cannot race each
  other's temps.
- **R1-F5 (low, self-mutable unit) — RE-STATED, accepted by design. For ADR-057:** installing the
  units and running `daemon-reload` means a signed release can ship a `styrman-update.service` that
  drops `NoNewPrivileges`/`ProtectHome`/`RestrictSUIDSGID`, rewrites `ExecStart`, or adds an
  `ExecStartPre=`, effective on the next tick. **No new capability:** a hostile *signed* release
  already executes arbitrary code as root through `docker build` and `docker compose up` from its
  own checkout, and the unit's own comment already concedes that sandboxing the unit cannot contain
  a payload that runs in the docker daemon's cgroup. **One new consequence:** the host's updater
  binary and its systemd configuration move from setup-time artifacts (`host-setup.sh`, untouchable
  by any release) to release-controlled state, so `/etc/styrman/allowed_signers` becomes the single
  trust root for the update *mechanism* as well as for the payload, and recovery from a hostile
  signed tag is no longer "re-enable signing and roll back" but a manual reinstall. The
  `REQUIRE_SIGNED=0` path never self-installs (R1-F1 fix), so the opt-out keeps the operator in
  manual control of the updater deliberately rather than by oversight. ADR-057 as drafted states
  this accurately; no correction requested.
- **R1-F6 (low, vulncheck exit status) — CLOSED for the property that mattered, measured.**
  `go install ${GOVULN} && govulncheck ./...` inside `sh -c` propagates govulncheck's own status:
  script re-run today, **`SCRIPT_EXIT=3`** with both modules reporting findings — the exit-3 signal
  the header promises is now real, and "vulnerabilities found" is distinguishable from a broken
  scan. `GOTOOLCHAIN=local` is present, so the scan can no longer silently auto-switch away from the
  image's Go. Two small residuals, both low/low and unchanged in severity: `rc=$?` inside the loop
  is **last-writer-wins, not sticky-max** — a first module exiting 3 followed by a second module
  failing infrastructure-wise (e.g. 1) reports 1, masking the finding as a broken scan; and the
  accepted baseline is still permanently non-zero, so a status-keyed gate stays red and the durable
  fix remains `-format json` diffed against a checked-in OSV-ID baseline.
- **R1-F7 (low, `deploy/.env` in the scan container) — CLOSED, verified empirically.** Confirmed
  with the exact probe: `docker run --rm -v "$PWD:/src:ro" -v /dev/null:/src/deploy/.env:ro
  golang:1.25.13-trixie wc -c /src/deploy/.env` → **`0 /src/deploy/.env`**, exit 0. The nested
  bind shadows the file inside the read-only repo mount, so the network-fetched `govulncheck` binary
  sees an empty file, not the ingress token / `STYRMAN_ALLOWED_EMAILS`. (No secret was printed in
  producing this evidence; only the byte count.) Residual, low/low: the shadow is a single hardcoded
  path — `deploy/caddy/ingress/.env` does not currently exist, but any future `*.env` under the repo
  root would be exposed again silently. Consider deriving the mask list from
  `git check-ignore` / a `*.env` scan, or mounting only the two module directories.

## New in round 2

- **[medium / confidence: medium] CARRIED FORWARD, still open** —
  `deploy/update/styrman-update:392-401` — R1-F2 was not addressed: `src="${DEPLOY_DIR}/deploy/update"`
  and the three files are read from the **worktree**, minutes after `git checkout --detach --force`
  and after two docker builds plus the health wait. The script asserts `${DEPLOY_DIR}/.git` is

  created outside `host-setup.sh`'s documented flow, or later `chmod`'d) therefore lets a local
  unprivileged user replace `deploy/update/styrman-update` after verification and have it installed

# Round 3 — security delta (2026-09-02)

Scope: only what changed since round 2 — `deploy/update/styrman-update` (`self_install` now sources
bytes from the git object at `HEAD` via `atomic_install <mode> <git-path> <dst>` + `differs()` +
`git cat-file -e`, `mv -fT`, orphan sweep hoisted ahead of all three targets) and
`deploy/vulncheck.sh` (worst-wins exit). Blast radius re-traced: what `git show HEAD:…` can be made
to return, the target-path validation, the sweep's glob, and the two paths that call `self_install`.

## Verdict: FINDINGS (the round-2 MEDIUM is CLOSED; two lows remain, one pre-existing)

The carried MEDIUM is **closed**. Installed bytes now come from the committed blob, and that is
verifiably immune to worktree tampering: measured in a scratch repo — with the worktree file
replaced (`HOSTILE`), a `.gitattributes` in HEAD binding `filter=evil diff=evil`, and
`filter.evil.smudge` / `diff.evil.textconv` configured, `git show HEAD:f.txt` still printed the
committed `CLEAN`. `git show <rev>:<path>` resolves `.git/HEAD` → commit → tree → blob and applies
**no** smudge filter, textconv or EOL conversion, and never reads the working tree or the index.
`HEAD` at the call site was set by `deploy()`'s `git checkout --detach --force <ref>`, where `ref`
is either a signature-verified tag or a 40-hex SHA this host verified when it first deployed it, and
`self_install` additionally returns early unless `REQUIRE_SIGNED=1`. So altering the installed bytes
now requires **write access to `${DEPLOY_DIR}/.git`** — objects, `refs/`, `HEAD` or `config` — which
is root-only on this host (`/opt/styrman` is `drwxr-xr-x root root`, and the tree was `chown -R
root:root`'d by `host-setup.sh:394`). Worktree edits are irrelevant: confirmed.

## Findings (round 3)

- **[low / confidence: high] PRE-EXISTING, now load-bearing** — `deploy/update/styrman-update:153-154`
  — the deploy-clone gate asserts only the **owner** of `${DEPLOY_DIR}/.git`
  (`stat -c %u … = 0`), never its **mode**, unlike every other root input in this script
  (`STATE_DIR`, `deploy/.env`, `gh-token`, `allowed_signers`, `DOCKER_CONFIG`, and the new
  `trusted_dir`, which all add `find -maxdepth 0 -perm /022` or `/077`). A root-owned but
  group/world-writable `.git` therefore passes. That is now the single trust root for the bytes
  written to `/usr/local/bin/styrman-update`; it was already the trust root for the code built and
  run as root (and for `core.hooksPath` in `.git/config`, which `git checkout` would execute as
  root), so this is a consistency/defence-in-depth gap rather than a new exposure — hence low.
  Remediation, one line beside the existing check:
  `[ -z "$(find "${DEPLOY_DIR}/.git" "${DEPLOY_DIR}" -maxdepth 0 -perm /022 2>/dev/null)" ] || fail …`.
- **[low / confidence: medium] NEW** — `deploy/update/styrman-update:198` (the `git()` wrapper) —
  the wrapper pins `safe.directory` and the credential helper but does not neutralise inherited
  `GIT_DIR` / `GIT_WORK_TREE` / `GIT_OBJECT_DIRECTORY` / `GIT_COMMON_DIR` / `GIT_CONFIG_GLOBAL`.
  Measured: `GIT_DIR=../other/.git git show HEAD:f.txt` printed the *other* repo's blob while the
  cwd repo was untouched — i.e. an inherited `GIT_DIR` redirects `verify_tag`, `deploy` and now the
  self-install source in one move, even though `[ -d "${DEPLOY_DIR}/.git" ]` still passes. Reachable
  only from a `sudo -E`-style hand-run carrying an attacker-chosen environment (the systemd unit and
  plain `sudo`'s `env_reset` both give a clean env), so it is bounded by the already-accepted
  "deliberate `sudo -E` misuse" residual — but the fix is free and removes the class:
  `unset GIT_DIR GIT_WORK_TREE GIT_COMMON_DIR GIT_INDEX_FILE GIT_OBJECT_DIRECTORY
  GIT_ALTERNATE_OBJECT_DIRECTORIES GIT_CONFIG_GLOBAL GIT_CONFIG_SYSTEM` near the top, or add
  `--git-dir="${DEPLOY_DIR}/.git"` to the wrapper. (`GIT_ALTERNATE_OBJECT_DIRECTORIES` alone cannot
  change what a given hash contains, so only the `GIT_DIR`/`GIT_COMMON_DIR` shape matters.)
- **[low / confidence: high] NEW, availability-only nit** — `deploy/update/styrman-update:413` (+ `:378`, `:385`)
  — the presence probe `git cat-file -e "HEAD:${src}/${f}"` succeeds for a **tree** as well as a
  blob (measured: `git cat-file -e HEAD:deploy/update` → exit 0, `-t` → `tree`), and `git show` on a
  tree path emits a directory listing (`tree HEAD:deploy/update` + filenames). If a future verified
  release ever turned one of those three paths into a directory, that listing would be installed
  `0755 root:root` over `/usr/local/bin/styrman-update` and brick the update channel until an
  operator intervenes. Source is signature-verified so this is self-inflicted, not attacker-driven;
  the cheap guard is `[ "$(git cat-file -t "HEAD:${src}/${f}")" = blob ]` in the same loop.

## Re-checks requested

- **Target validation** — unchanged by the refactor and still correct in order:
  `realpath -m --` canonicalises both env-supplied targets (so `//`, `..` and symlinked aliases
  cannot dodge the checks), the **basename of `UPDATER_BIN` is pinned** to `styrman-update`, then
  `trusted_dir` asserts both destination dirs exist, are uid 0 and are not `/022`. Only after all of
  that does anything get written or removed. The round-2 low stands verbatim: `UPDATER_UNIT_DIR` has
  no basename/allowlist constraint, so a root operator can still deliberately drop the two `0644`
  unit files into any root-owned directory and `daemon-reload` — root-only, deliberate, recorded.
- **Orphan sweep** — placement re-verified: it runs *after* `trusted_dir` cleared both directories
  and after the three-file presence probe, and *before* any `differs()`/`atomic_install`, covering
  all three names rather than only the ones that drift this run. `rm -f "${bin}.new."*` is safe:
  the variable part is quoted (no word splitting even with spaces in the path), only the `*` is
  glob, the glob is fenced to a directory unprivileged users cannot write, and a non-matching glob
  passes the literal to `rm -f`, which exits 0 silently (measured). No symlink-following risk: the
  targets are `<dst>.new.<pid>` regular files created by root in a root-only directory.
- **`mv -fT`** — measured: `mv -fT file dir` fails with `cannot overwrite directory` and leaves the
  source in place, so a directory at a target path now fails the install (and is reported by the
  `failed=1` path) instead of the file being swallowed inside it. `-T` is GNU coreutils; the target
  host is Debian, so this is fine.
- **`differs()` under `set -euo pipefail`** — called only in `if` conditions, so `-e` is suspended;
  with `pipefail`, a failing `git show` makes the pipeline non-zero → `differs` reports "differs" →
  `atomic_install` then fails on the same `git show` and is logged as a WARN with `failed=1`. Fails
  loud in the safe direction; the presence probe makes the case unreachable in practice.
- **`atomic_install`** — temp file is `<dst>.new.$$` inside a `trusted_dir`-asserted directory,
  `chmod`+`chown` before the rename, `mv -fT` gives a new inode so the running script's open inode
  is never modified in place, and every failure path `rm -f`s the temp and returns 1. Arguments are
  internal literals plus validated paths, all quoted. No injection surface.
- **`vulncheck.sh` worst-wins** — logic re-read: `0` never overwrites, `3` sets `rc` only from `0`,
  anything else (broken scan) always wins. `r` is reset to `0` each iteration and read as `${r:-0}`
  on the first, so a prior iteration's status cannot leak forward. No secret handling changed.

## Accepted residuals (re-stated, unchanged)

1. **Signed downgrade on rollback.** The rollback path calls `self_install` from the *previous*
   verified tree, so an attacker who can make a new release fail its health check (e.g. by killing
   `styrman-server` during the 120 s window) can force the host back to the previous updater,
   undoing a security fix inside `deploy/update/*`. Bounded: the tree is still one this host
   verified, `REQUIRE_SIGNED=1` is still required, the failed tag is latched, and the rollback is
   logged as `FATAL`. Accepted — it is inherent to having a rollback at all.
2. **`sudo -E` misuse is deliberate and bounded.** A root operator who exports
   `STYRMAN_UPDATER_BIN` / `STYRMAN_UPDATER_UNIT_DIR` / `STYRMAN_UPDATE_STATE_DIR` / `DOCKER_CONFIG`
   / `GIT_DIR` can aim this script at paths of their choosing. Every such path is still funnelled
   through canonicalisation, the `styrman-update` basename pin, and root-owned + not-`/022` asserts,
   and the actor already has root. Accepted; finding R3-2 above narrows it further for free.
3. **`GO-2026-4887` / `GO-2026-4883` in `github.com/docker/docker`** — daemon-side, `Fixed in: N/A`,
   reached only through the docker client library. Accepted for this release, unchanged.
