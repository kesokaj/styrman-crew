## Status: COMPLETE

## Verdict: APPROVE WITH NITS

Nothing is broken. The shared wait is race-free as written: `w.gone` is
written before `close(done)` and read only after a receive on it; a caller
can never park on a `done` that does not close (the only `Delete` of a key is
made by the goroutine that owns the stored value, in the same defer that
closes it, and a successor value can only be stored after that `Delete`); the
poller is bounded by its own `lifecycleWaitMax` context, and every Docker call
in it uses that context. The bash plain-set check behaves as a literal list in
both C and en_US.UTF-8 (hand-run below). The single finding is one low edge in
the shared wait's semantics: a request that joins a wait late gets the
remainder of the FIRST request's 20 s ceiling, not its own.

## Findings

- **[low / confidence: medium]** `internal/orchestrator/ports.go:150-163,185-189` —
  a request that joins an existing wait inherits that wait's deadline. The poller
  starts its `lifecycleWaitMax` clock when the FIRST parked request starts it
  (`context.WithTimeout(context.Background(), lifecycleWaitMax)` in
  `awaitLifecycle`), so a request that joins at t=19.9 s gets `false` at t=20 s
  and reports `port scan exited N` (500) even though its own context, and the
  per-request ceiling the code had at v1.41.0, would have kept it waiting up to
  20 s more. Concrete trigger: a lifecycle change that keeps the lock and the
  container "running" for more than 20 s (a slow stop under the lock), with a
  page polling `/ports` every few seconds. Every poll that joins late fails
  early, and the next poll starts a fresh wait. The failure is cosmetic and
  heals itself (a red Ports panel for one poll), so it is low. The doc comment
  ("ends at lifecycleWaitMax") is still literally true. Fix, if wanted: when
  the shared wait ends without an answer (`ctx.Done` in `awaitLifecycle`), a
  caller whose own `ctx` still has time loops back once and joins or starts a
  fresh wait. That keeps one poller per key and restores the per-request
  bound. No test covers a late joiner.

No other findings.

## Answers to the dispatch's questions

1. **Ordering of `w.gone` and `close(done)`.** Write at `ports.go:200`/`:205`,
   then `return`, then the deferred `Delete` + `close`. Readers read `w.gone`
   only in `case <-w.done`. This is a happens-before edge under the Go memory
   model. No data race.
2. **Can a `Delete`/`LoadOrStore` race strand a caller?** No. Interleavings:
   (a) a caller's `LoadOrStore` loads `w1` before the poller's `Delete`, and the
   following `close(w1.done)` answers it; (b) after `Delete`, `LoadOrStore`
   stores `w2` and starts a new poller. `Delete(k)` cannot remove `w2`: only
   `w1`'s poller deletes, once, and `w2` cannot exist in the map before that
   `Delete` has run. **Can two pollers run?** Only briefly. Between `w1`'s
   `Delete` and its `close`, a `w2` poller may already be running. That is
   harmless: `w1`'s poller has already decided and makes no more Docker calls.
   `CompareAndDelete(k, w)` would make (b) robust against a future second
   deleter. It is not needed today.
3. **Can the goroutine outlive something it must not, or leak?** It is bounded
   by `lifecycleWaitMax` plus at most one `Status` call, and that call runs on
   the same deadline context. It is not bounded by its callers. A single
   abandoned request now keeps one poller asking Docker for up to 20 s, where
   v1.41.0 stopped when the request's context ended. That costs at most one
   poller per (project, container), so it is no amplification, and it is the
   trade the security finding asked for. No finding. In tests, the poller left
   by `TestListeningPortsWaitIsBoundedByTheRequest` (its request leaves at
   400 ms while the lock is held) ends one tick after the test's deferred
   `l.Unlock`, and it touches only that test's own fake Docker.
4. **`lifecycleWaitMax` written by a test while a goroutine reads it.**
   `awaitLifecycle` reads it once, at goroutine start. The poller that
   `TestListeningPortsWaitIsBoundedByTheRequest` leaves behind reads it
   microseconds after the test's request starts. `TestListeningPortsWaitHasACeiling`
   (later in the file) writes it more than 400 ms later. I found no explicit
   happens-before edge from that poller back to the writer, but
   `go test -race -count=5 -run 'ListeningPorts|Ports' ./internal/orchestrator/`
   ran clean (rc=0, 0 `DATA RACE`). No observed failure, so this is not a
   finding. If it ever flags, the remedy is to read the ceiling in
   `GuestGoingAway` (the caller's goroutine) and pass it to `awaitLifecycle`.
5. **Keying by `key(user,project)+"\x00"+ContainerID`.** Sound. The answer
   (`guestGone`) depends only on `ran.ContainerID` (`now.ContainerID !=
   ran.ContainerID`), so two callers that saw different containers MUST NOT
   share a wait, and they do not. Callers that saw the same id are asking the
   identical question. `ran.State` is always `running` at both call sites
   (`ListeningPorts` returns before the exec otherwise, and so does
   `browser.go`). User slugs and UUIDs cannot contain NUL, so the separator
   cannot collide.
6. **Bash `${STATUS_FILE//[$plain]/}` under `set -euo pipefail`.** The `/`
   characters in `$plain` come from an expansion, so they cannot end the
   `${var//pat/rep}` pattern, which is split at parse time. The `-` sits last
   before `]`, so it is literal, and `.`/`_`/`/` are plain members. Hand-run
   with bash 5.2.37 under `LC_ALL=C` and `LC_ALL=en_US.UTF-8`:
   `/etc/styrman/status/updater.json` and `/x/A-Z_9.z/u` were accepted. The
   following were refused in both locales: a space, a newline, `é`, `ä`, `ẞ`,
   a fullwidth `ａ`, a raw `\xff` byte, `]`, `[`, `\`, `*`, `,`, and the empty
   string (also returned early by `[ -n "${STATUS_FILE}" ] || return 0`). The
   OLD regex `^/[A-Za-z0-9._/-]+$` accepted `/x/café/u` under en_US.UTF-8 and
   refused it under C. So the bug was real, and the new test's condition holds
   on this host. `/` alone now passes the plain check (the old `+` refused
   it), but the earlier `basename != updater.json` check refuses it first. No
   behaviour change. `shellcheck -S warning` is clean.

## Outcome
(Written by the main agent, 2026-10-03.)
- Finding 1 (low, a late joiner gets what is left of the first request's 20 s): **rebutted**. A shared wait ends without "gone" only when, for its whole 20 s, the project stayed the same running container while something held its lock. That holder is not taking the guest away: a stop or a rebuild makes `guestGone` true within a tick. So the failure a late joiner reports is the command's own, a few seconds sooner. The answer is the same one a fresh 20 s wait would give unless the guest goes away in exactly the remaining seconds. No re-join loop, which would add a branch for that window.
