# Security review — v1.38.0-gatefix   (2026-09-22)

## Status: COMPLETE

## Verdict: FINDINGS

Nothing in this delta blocks the v1.38.0 gate, and the fix for the prior
report's finding 1 is real. I probed the new `deploy/gcp/vm.sh` allowlist
directly in bash under the host locale (`en_US.UTF-8`) against sixteen
candidates: every metacharacter form is refused — `$(id)`, `;id`, a space, a
quote, a `/` inside the username, `..` traversal, `/./` prefix, a double
slash, a trailing space, a trailing newline, an embedded newline with a
second malicious line, a UTF-8 accented username, and a 33-character username
— while `/home/kesokaj/…` and a 32-character username still match. Bash's
`=~` uses POSIX ERE without `REG_NEWLINE`, so `$` anchors at end of string,
not before a newline; and glibc's `[a-z]` did **not** widen to uppercase or
accented characters under this UTF-8 locale, so the homoglyph route the brief
asked about is closed here too. The accepted set is exactly
`/home/<[a-z_][a-z0-9_-]{0,31}>/styrman-crew/deploy/styrman-ctl` plus three
literals — shell-safe by construction, and never leading with `-`, so no
option injection into `sudo` either. **No second `vm_ssh` round-trip
remains**: `grep -c vm_ssh deploy/gcp/vm.sh` is 3 at both b6e8f0d and
d2c1620, and `cmd_status` still makes exactly two calls (the probe at :115,
the `sudo … status` at :134).

**The web-build log cannot contain the harness token.** `deploy/verify-commit.sh:78`
runs `unset GH_TOKEN` before any build step; the token then lives only in the
unexported shell variable `BUILD_TOKEN` and is reintroduced as a per-command
assignment at :233 (`GH_TOKEN="${BUILD_TOKEN}" build_image …`). The npm block
at :140-149 therefore runs with no token in its environment, so neither the
log nor the printed tail can carry it. `LOGDIR` is a `mktemp -d` under
`${TMPDIR:-/tmp}` (mode 0700, unique, outside the worktree by design so it
stays out of the server image's build context) and is removed by `cleanup` on
the `trap … EXIT` at :34, on the new `exit 1` path included.

Two residuals in `vm.sh` and one in the log tail, all low; plus one inherited
low that this commit makes durable by committing the prior report.

## Findings

- **[low / confidence: high]** `deploy/gcp/vm.sh:126-136` — the guard now
  bounds the CHARACTERS of the remote's answer, but the answer is still
  interpolated into a command that runs as root on the VM
  (`vm_ssh "sudo ${ctl} status"` → `gcloud compute ssh … --command="$*"`,
  re-parsed by the remote login shell). The accepted home path is
  `$HOME/styrman-crew/deploy/styrman-ctl` — a file the ssh user itself can
  replace. Exploitable in principle only by someone who already has write
  access to the operator's home on the VM (an account that already holds
  passwordless sudo there), so this is a defence-in-depth gap, not an
  escalation. Remediation, no dependency and no extra round-trip: stop
  interpolating a remote-supplied string — re-derive the path remotely in the
  same command, e.g.
  `vm_ssh 'for p in /opt/styrman/deploy/styrman-ctl "$HOME/styrman-crew/deploy/styrman-ctl" /usr/local/bin/styrman-ctl; do [ -x "$p" ] && exec sudo "$p" status; done; exit 127'`,
  keeping the existing probe for the "not installed" message. The allowlist,
  and the whole class of question the two reviews have now spent, disappears
  with it.

- **[low / confidence: high]** `deploy/gcp/vm.sh:132` — the refusal is right
  in every case I probed, but its MESSAGE is not. A legitimate username
  containing a dot (`/home/john.doe/…` — an OS Login or macOS short name), an
  uppercase letter, or more than 32 characters is refused with
  `<instance> answered with an unexpected styrman-ctl path: <path>`, which
  reads as "the VM answered something strange" when the real condition is
  "your username has a character this allowlist does not accept". That is the
  shape `.agents/rules/remote-check-names-transport-first.md` exists to
  prevent: the check reports a condition it did not measure. Fail-closed is
  the correct default and the path is printed, so an attentive operator can
  see it. Remediation: one clause in the `die` string naming the class
  (`… — the home form must match /home/[a-z_][a-z0-9_-]{0,31}/styrman-crew/deploy/styrman-ctl`),
  or adopt finding 1's remediation, which removes the refusal entirely.

- **[low / confidence: low]** `deploy/verify-commit.sh:147-148` — the 20-line
  tail printed on a web-build failure is unscrubbed npm output. The harness
  token is provably absent (see Verdict), and the repo carries no `.npmrc`,
  so this is about an OPERATOR-level `~/.npmrc`: a registry URL with embedded
  `user:pass@`, or a `_authToken` echoed in a 401/404 error line, would be
  printed to stderr. It matters because the recorded practice for this gate
  is to capture its output to `.agents/scratch/…` and quote the failing lines
  into a trail file that gets committed
  (`.agents/docs/testing/2026-09-22-verify-v1.38.0-release.md` does exactly
  that for the passing run). Remediation, stdlib-only, no dependency: pipe the
  tail through a redactor —
  `tail -20 "${LOGDIR}/web-build.log" | sed -E 's#(_authToken=|_auth=|://[^/@[:space:]]+:)[^[:space:]@]+#\1REDACTED#g' >&2`.
  Confidence is low because I did not observe npm emitting such a line; the
  exposure is conditional on the operator's own npm configuration.

- **[low / confidence: high]** *(inherited, now durable)*
  `.agents/docs/reviews/2026-09-22-security-v1.37.0-HEAD.md:80` — this commit
  is what puts the prior report into git, so `83.249.78.58`, the operator's
  own residential address during the BUG-069 outage, gains a third copy in
  history (handoff, BUG-069 record, now this review). `gh repo view` reports
  `{"isPrivate":true,"visibility":"PRIVATE"}`, so there is no live exposure;
  it becomes one the moment visibility changes or an outside collaborator is
  added. Remediation unchanged from the prior report: redact to a description
  if the repo is ever opened. The other address in the delta, `34.51.142.50`,
  is the released GCP static IP already covered by `gcp.md`'s teardown
  section — no action.
