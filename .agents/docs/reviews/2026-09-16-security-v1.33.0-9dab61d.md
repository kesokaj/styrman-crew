# Security review — v1.33.0-9dab61d   (2026-09-16)

Range reviewed: v1.33.0..9dab61d

(v1.33.0 = `21d8fd7c0a9cc2780657f2a20e7809cc3283c848`; head = `9dab61d9140e85e4ec3dbdf586791565dba5457f`.
Diff basis `git diff v1.33.0...9dab61d`: 57 paths, 2454 insertions / 173 deletions, no binary file
(`--numstat` shows no `-`/`-` pair, BUG-007 check). 40 paths are the vendored harness mirror,
17 are `.agents/docs/` trail, 2 are project source/requirements.)

## Verdict: FINDINGS

Nothing high. No secret, no injection, no authz change, no hand-rolled crypto, no new dependency.
The worst item is carried, not introduced: `bash deploy/vulncheck.sh` exits **3** on this tree —
two CALLED `github.com/docker/docker@v28.5.2+incompatible` vulnerabilities (GO-2026-4887,
GO-2026-4883, both "Fixed in: N/A") in the root module and in `deploy/caddy/ingress`. This range
touches neither module's dependencies, so the exposure is unchanged, but a release gate must
re-state the acceptance rather than inherit a `3` silently. The one new executable surface in the
range is `sh-agent`'s `attributionSet` — a hand-written textual JSON editor that adds one key to
`~/.claude/settings.json` inside the guest's own home. It is defensively built (Lstat refuses a
symlink, `O_EXCL` on create, `json.Valid` before the rename, 1 MiB-bounded reads, no file content
ever echoed), it runs unprivileged as the project user, and it is well covered by new tests; the
three low findings below are hardening, not exploitable escalation. The range's substantive
security *delta* is favourable: `checkManagedTree`/`readRegular` (BUG-036) and `Adopt`'s
containment check (BUG-037) close an arbitrary-file-read into every consumer home and a
delete-your-own-repo-root, and `/preflight` gains a real control — refusing to run when a project
agent shadows `reviewer`/`security`/`verifier`/`explorer` (BUG-033).

## Findings

- **[medium / confidence: high]** `deploy/vulncheck.sh` — tree-wide, NOT introduced by this range.
  The project's own release scan exits **3**: `GO-2026-4887` (Moby access-control bypass in the
  privileged-container check) and `GO-2026-4883` (Moby off-by-one in plugin privilege validation),
  both reported as CALLED, in `github.com/docker/docker@v28.5.2+incompatible`. Root module: 2
  called (39 example traces each, reached through the orchestrator's Docker client) plus 3
  uncalled. `deploy/caddy/ingress`: the same 2 called (traces through
  `ingress.Watcher.listenEvents`, `discoverApps`, `containerToApp`, `fetchIP`) plus 7 uncalled.
  `image/harness`: **No vulnerabilities found**. Upstream publishes no fixed version. Exploitable
  in principle only by a party who can already reach the Docker API these clients speak to — on
  this host the styrman server and the ingress, both root-adjacent. Remediation: no upgrade
  exists, so record the acceptance explicitly in the release entry with today's output and the
  reason (daemon-side, no fix available, client-side call sites only), and re-check at the next
  `docker/docker` bump so a `3` never becomes the expected exit status. Do not replace the
  dependency: the stdlib has no Docker API client, and shelling out to the `docker` CLI is
  strictly worse for both injection surface and error handling.

- **[low / confidence: high]** `image/harness/cmd/sh-agent/main.go:487-611` (`attributionSet`) —
  the key is added by TEXTUAL splice (`bytes.TrimRight` → `bytes.LastIndexByte(trimmed, '}')` →
  string concatenation → `json.Valid`), deliberately avoiding `encoding/json`'s round-trip so the
  operator's key order and formatting survive. This is **not** the banned hand-rolled-crypto class
  — no primitive, token, session or auth flow is implemented or composed — but it is structure
  editing of a config file without a parse/serialize boundary. `json.Valid(result)` proves the
  result parses; it does not prove it means what the original meant. A document with duplicate
  top-level keys, or one whose effective value depends on ordering, can in principle come out
  valid and semantically different. Every refusal path already fails safe (print a `settings:`
  line, change nothing), which is the right shape. Remediation (upstream, `styrman-harness`): after
  the splice, `json.Unmarshal` the result into `map[string]json.RawMessage` and assert the key set
  equals the original's plus `attribution` and that each original key's `RawMessage` is unchanged —
  a few lines using the `encoding/json` already imported, no new dependency. Confidence high that
  the construction is hand-rolled; the severity is low because the blast radius is one advisory
  file in the writer's own home.

- **[low / confidence: high]** `image/harness/cmd/sh-agent/main.go:603-607` — a
  `~/.claude/settings.json` the operator deliberately made read-only (mode `0444`) is still
  REPLACED: `os.Rename` over a read-only destination succeeds whenever the containing directory is
  writable, and `os.Chmod(tmpName, info.Mode().Perm())` faithfully copies `0444` onto the
  replacement, so the file looks untouched afterwards. The `Lstat` guard covers a symlink, the size
  guard covers a large file, and nothing covers "the owner said do not write this". The prior
  report (`.agents/docs/reviews/2026-09-16-security-harness-refresh-4aa19be.md`, finding 3) filed
  this upstream and its `## Outcome` records it as unfixed in this range — I re-derived it from the
  shipped code and it still holds. Impact is an integrity/intent violation, not an escalation: the
  writer is the file's own owner and the write only adds one key. Remediation: before the rename,
  refuse when `info.Mode().Perm()&0o200 == 0` and print the existing "add the key by hand" line.

- **[low / confidence: medium]** `image/harness/cmd/sh-agent/main.go:503-509` — in the
  not-exist branch, `os.MkdirAll(filepath.Dir(path), 0o755)` on `$HOME/.claude` succeeds *through*
  a symlink-to-directory (`os.MkdirAll` stats the path, which follows the link, finds a directory
  and returns nil), after which the `O_EXCL` create writes the settings file inside the link's
  target. The `Lstat` guard protects `settings.json` itself but not its parent — the exact shape
  the project's own `.agents/rules/guest-writable-paths.md` names ("`os.MkdirAll` succeeds through
  a symlink-to-dir"). I verified this adds no NEW surface: `harness.Install` →
  `internal/harness/apply.go:32,45` already computes `dest := filepath.Join(home, f.Rel)` and calls
  `writeAtomic` with no symlink check on the home side, so every managed file already lands the
  same way; and `image/entrypoint.sh:167` drops to the unprivileged project user via `runuser -u
  "${USERNAME}"` before any of it runs, so the writer and the only possible planter are the same
  uid. `TestAttributionSet` plants a symlinked `settings.json` but no test plants a symlinked
  `.claude` DIRECTORY. Remediation (upstream): open the home once with `os.OpenRoot(home)` and
  reach `.claude/settings.json` through it — the same pattern `internal/files.Trust` uses on the
  styrman side — which would cover the whole installer, not just this one write. Severity and
  confidence are low because no privilege boundary is crossed in any deployment this mirror ships
  to.

## Checked

- **Secrets** — every added line of the full range (`git diff v1.33.0...9dab61d | grep '^+'`)
  scanned for `PRIVATE KEY`, `-----BEGIN`, `AKIA`, `AIza`, `ya29.`, `token=`, `password=`,
  `ghp_`, `sk-ant`, `xoxb-`, and again for `api_key|secret|password|credential|bearer` shapes over
  the non-docs subset. Three pattern hits exist and all three are PROSE describing the scan
  patterns themselves (`image/harness/skills/preflight/SKILL.md`'s gitleaks fallback list, and two
  prior review records quoting it). No `.env*`, `*.pem`, `*.key`, `*.tfvars`, `*.tfstate` or
  credential JSON is in the range. Nothing new is echoed to a log that could carry a secret:
  `readSettings` and `attributionOff` return fixed `problem` strings by design and never a byte of
  file content, and the entrypoint forwards only `^settings:` lines. `deploy/vulncheck.sh` still
  shadows `deploy/.env` with `/dev/null` when it exists.
- **Injection** — the range's only new shell is `image/entrypoint.sh:162-170`. All expansions are
  quoted; `HI_OUT="$( … )"` is bounded by the existing `timeout 20` and by an installer that
  prints a line per managed file; the forwarding pipeline
  (`printf '%s\n' "${HI_OUT}" | grep '^settings:' | tr -cd '[:print:]\n' | cut -c1-200 | while
  IFS= read -r line; do log "  ${line}"; done`) strips every control byte (so no ANSI/terminal
  escape survives), bounds the line at 200 columns, and `log()` is `echo "[styrman] $*"` — bash's
  builtin `echo` with no `-e`, and the two-space prefix keeps a line from ever parsing as an
  option. The subshell the `while` runs in is discarded and nothing downstream reads its status
  (`set -uo pipefail`, no `-e`). I traced where this lands: `internal/orchestrator.Logs` →
  `internal/httpapi/stats.go:125 projectLogs` → `GET /api/projects/{project}/logs`, which is
  owner-scoped through `getProjectFor` and returns the text `encoding/json`-encoded as
  `{"logs": …}`; the only `dangerouslySetInnerHTML` in `web/src` is in `FileEditor.tsx`, not the
  logs view. Crucially this is no NEW exposure: `image/entrypoint.sh:55` grants the project user
  `NOPASSWD: ALL` inside its own microVM, so the guest can already write arbitrary bytes to PID 1's
  stdout and hence to the whole container log; the new pipeline is strictly MORE sanitized than the
  stream it joins. No SQL, no template rendering, no `exec` of a guest-controlled string is added.
  On the Go side `validName`/`identLike` remain the parse boundary for any frontmatter `name:`
  joined into a path, and `Adopt` now runs it too where it previously did not.
- **Path / symlink handling (the substantive delta, favourable)** —
  `internal/harness/inventory.go` adds `checkManagedTree` (refuses a symlinked `context/`,
  `agents/`, `commands/`, `rules/`, `workflows/` or `skills/`, and any symlinked direct entry of
  the flat ones) and `readRegular` (refuses a symlinked or non-regular `skills/<name>/SKILL.md`),
  and `LoadSkills` now RETURNS that refusal instead of silently `continue`-ing — closing BUG-036,
  an arbitrary-file read that would deploy a link target's bytes into every consumer home and into
  the `AGENTS.md` both CLIs send to the model. `render.go:24` calls `checkManagedTree` too, so
  `RenderContext` cannot be reached around `LoadInventory`. I verified the guard's coverage matches
  the read surface rather than trusting the comment: `LoadAgents` and `LoadDocs` use
  `filepath.Glob(filepath.Join(repo, dir, "*.md"))` — direct entries only, so a direct-entry check
  is exactly right; `skills/` is deliberately exempt at directory level and its tree is walked in
  `plan.go`, whose `WalkDir` already returns an error on any `fs.ModeSymlink`. `adopt.go` adds
  `filepath.Abs` + `validName` + a bidirectional `within()` containment check ahead of the
  `os.RemoveAll(dest)` — closing BUG-037, where a relative `src` of `.`, `..` or `skills/<name>`
  made `Adopt` delete its own repo root or its source; `within` is correct (`rel == "."`, else not
  `..`-prefixed) and applied in both directions. The `init-project` skill's Step 5 likewise stops
  force-replacing `.claude/<n>` (`ln -sfn` → a loop that keeps and reports an existing link or
  file).
- **Authz / authn** — no change. Nothing in the range touches `internal/httpapi` (the auth guard
