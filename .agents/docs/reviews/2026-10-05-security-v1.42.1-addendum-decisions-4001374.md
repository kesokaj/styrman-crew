## Findings

- **[low / confidence: high] `.agents/docs/architecture/DECISIONS.md:2880`: the coverage claim for the High's fix is overstated.**
  - What the tests cover (read at 4001374):
    - `internal/gitrepo/oom_test.go:17-37` calls `setOOMScoreAdj` directly on a `sleep` child.
    - `oom_test.go:40-48` only checks that `EnsureRepo`/`IsRepo` succeed.
    - No test drives `git()` and reads the child's score, so `gitrepo.go:65` (`_ = setOOMScoreAdj(cmd.Process.Pid, 0)`) has no covering test.
  - Corroboration: the code review deleted that line in a scratch copy and every test stayed green (`review-2ba3f79-aa2f3b4.md:17-27`). The prior security review has the same item at `:74-77`.
  - Security consequence if a refactor drops the line:
    - git runs at -999 again.
    - The 4g cap still makes git the victim of an in-cgroup OOM kill.
    - In a host-wide OOM, however, the kernel kills the largest -999 process. That may be a project VM, possibly another tenant's, rather than the git that the tenant's oversized `.git/config` inflated.
  - Remediation:
    - Add the behavioural test the code review describes: a fake `git` on PATH that prints `/proc/self/oom_score_adj` after the test raises its own score.
    - Make the ADR line name what is covered.
  - One fix closes this, code-review finding 1, and the prior security low. Count it once at the gate.

- **[low / confidence: high] `.agents/docs/architecture/DECISIONS.md:2855`: ADR-084's header still says "— Accepted" with no forward pointer.**
  - The project's practice is to mark supersession in the header: ADR-062 (`:2351`) and ADR-073 (`:2723`) carry "— superseded by ADR-074 (2026-09-21)", and ADR-077 (`:2761`) carries a partial-supersession note.
  - ADR-084's Decision (`:2859`) sets `oom_score_adj: -1000`, the value behind the v1.42.1 High (an unkillable host-side git leading to a host hang).
  - Its Consequences line (`:2866`) cites a guard that ADR-085 (`:2874`) says does not exist: "its own health check and restart policy remain the guard".
  - Only ADR-085's body (`:2870`) records the supersession. A reader who reaches ADR-084 first, for example through `sh-agent search` or a grep for `oom_score_adj` or `-1000`, finds an Accepted decision that reintroduces the High.
  - Remediation: append "— superseded by ADR-085 (2026-10-05)" to the ADR-084 header before the v1.42.1 tag.
  - ADR-065 and ADR-066 (`:2403`, `:2429`) lack the marker too, but they predate this range.

- **[low / confidence: medium] `internal/gitrepo/gitrepo.go:59-65`: a failed reset of the git child's score is discarded with no log.**
  - Scope: this is code at aa2f3b4, outside this addendum's range. I reached it while checking ADR-085's claim at `:2880` that git "sets its own child back to 0".
  - Why it matters: if the write ever fails in the production container, git silently keeps -999 and nothing tells the operator the control is off.
  - That container path has never been measured:
    - The gitrepo tests ran on the host.
    - The verifier's `docker run --oom-score-adj -999 … cat /proc/self/oom_score_adj` (`verify-v1.42.1-commit-gate-r2.md:22`) reads the container's own score, not a reset child's.
  - The likely failure modes are rare: the child has already exited, or an LSM policy denies the write.
  - Remediation:
    - Keep running. Failing open is proportionate behind the 4g cap.
    - Log the failure at warn with the pid and the error, never git's output.
    - Cover the failing case in the behavioural test above.
  - Limits of this finding:
    - I did not read `setOOMScoreAdj`'s body. If it logs internally, this finding falls.
    - A keyword grep (`ignored|failed write|setOOMScoreAdj`) of the prior security review found no finding on this, but I did not read that review in full.

- **[low / confidence: high] `.agents/docs/architecture/DECISIONS.md:2883-2887`: the Rejected list omits the input-side bound the answered security review proposed.**
  - What was proposed (`security-v1.42.1-v1.42.0-2ba3f79.md:56-64`): stat `.git/config` through the tenant root, refuse anything over a small bound before host-side git runs, and add a test that plants an oversized config.
  - ADR-085 records `kernel.panic` as rejected, but not this bound.
  - Today a guest-written config still reaches the host-side parser unbounded. The shipped answer is containment only: the child at score 0 plus the server's 4g cgroup cap. The follow-up security review accepted that (`security-v1.42.1-2ba3f79-aa2f3b4.md:200`).
  - The decision record does not show the bound was ever considered. The next change to `internal/gitrepo` therefore inherits an unbounded parsing boundary without knowing it.
  - Remediation: record the bound as rejected or deferred, with its reason.
  - A note for whoever writes that line (medium confidence, not tested here): a size check on `.git/config` alone would not bound git's input, because git follows `[include] path=` from repository config into other guest-writable files.

- **[low / confidence: high] Not a security weakness, reported because it was read. `web/e2e/run.mjs:993`, with its comment at `:986-990`: the fixture proves only the email.**
  - `echo idok-$(git config --global user.email | cut -c1-3)` prints `idok-e2e` whenever `user.email` is set. That includes the case where keystrokes inside `git config --global user.name e2e` were lost, because the `;`-separated line runs on past a failed command.
  - The comment says the fixture "proves the identity is set". A recurrence that loses only the name would still surface as the late 409, with no DIAG line. (git refuses an empty ident name when the guest user has no GECOS entry; this was not verified for this image.)
  - Remediation: make the sentinel depend on both values, for example `echo idok-$(git config --global user.name)-$(git config --global user.email | cut -c1-3)`, and wait for `idok-e2e-e2e`.
