# Security review — v1.37.0-HEAD   (2026-09-22)

Range reviewed: commits v1.37.0..HEAD (git log v1.37.0..HEAD); the diff is git diff v1.37.0...HEAD

## Status: COMPLETE

## Verdict: FINDINGS

Nothing in this range blocks the v1.38.0 gate. Five findings, all **low**: the
worst is a shell-pattern allowlist in `deploy/gcp/vm.sh` whose `/home/*/…` arm
matches `/` and shell metacharacters before the answer is interpolated into a
remote `sudo` command line — a hardening gap, not a live path, because the
answer can only be one of three literals plus `$HOME`, which needs root on the
VM to influence. The other four are an override that stays silently on once
set, an operator residential IP recorded in trail (repo is private), and two
pre-existing dependency advisories the range does not touch.

**The `ip_forward` trade is the right one.** `config.IPForwardProc` is read
once at boot and only when `cfg.SelfContainer != ""`, i.e. from the server
container's own `/proc/sys/net/ipv4/ip_forward`. To make that file unreadable
an attacker needs host root, write access to the compose spec, or code
execution inside the server container — each a strictly larger compromise than
a refused boot. Tenants sit in separate Kata microVMs with no path to the
server's procfs, so no tenant-reachable denial of service is created. Against
that, R12 is non-negotiable and the old `fs.ErrNotExist` branch made the one
guard behind it report "fine" in precisely the case where it had measured
nothing. Fail-closed is correct, the escape hatch is documented, and
`IPForwardMustRefuse` is table-tested over all eight combinations including
"error alongside off=true". `go build ./...` on HEAD is clean (rc=0), so the
`errors`/`io/fs` imports left behind by the removed `errors.Is` are still in
legitimate use elsewhere in `main.go`.

Parts of the range already carry independent security reports. I read their
`## Outcome` sections and cite them rather than repeating:
- 16bc84e (`internal/files`, `internal/httpapi/explorer.go`, `web/src`) —
  `.agents/docs/reviews/2026-09-22-security-phase0b.md`; findings fixed.

No binary files entered the range (`git diff --numstat` shows no `-`/`-` pair

## Findings

- **[low / confidence: medium]** `deploy/gcp/vm.sh:110-126` (`cmd_status`) —
  the remote is asked which `styrman-ctl` it has and its answer is validated
  against a `case` allowlist before `vm_ssh "sudo ${ctl} status"`. The arm
  `/home/*/styrman-crew/deploy/styrman-ctl` uses `*`, which in a shell pattern
  matches `/`, spaces and shell metacharacters — so `/home/a$(id)/styrman-crew/deploy/styrman-ctl`
  passes the guard and is then re-parsed by the remote shell as part of a
  `sudo` command line. Exploitable in principle only from an already-rooted VM:
  the remote command's candidate list is three literals and the single variable
  component is `$HOME`, which a non-root user cannot change. The guard is right
  in intent (its test refuses `/tmp/evil; rm -rf /`); the pattern is not a
  component matcher. Remediation, no dependency: build the candidates locally —
  `/opt/styrman/deploy/styrman-ctl`, `/home/${USER_NAME}/styrman-crew/deploy/styrman-ctl`,
  `/root/styrman-crew/deploy/styrman-ctl`, `/usr/local/bin/styrman-ctl` — and
  compare with `[ "${ctl}" = "${p}" ]` instead of a glob.

- **[low / confidence: medium]** `cmd/styrman/main.go:47-64` +
  `internal/config/ipforward.go:44-53` — the fail-closed change is correct (see
  Verdict), but its documented way through, `STYRMAN_ALLOW_IP_FORWARD=1`, is
  sticky and after boot invisible. Set once in `deploy/.env` to get past a
  transient unreadable sysctl, it disables the only R12 boot assertion on every
  later restart, and the sole signal is one `logger.Warn` line that scrolls
  past. Remediation: surface the override's state where an operator sees it
  repeatedly — the settings/health response the server already returns — or
  re-emit the warning on a timer. Related residual, pre-existing and not a
  finding against this range: the assertion is boot-time only; `ip_forward`
  flipped inside the server's netns after boot is never re-measured.

- **[low / confidence: high]** `.agents/docs/handoffs/2026-09-22-v1.37.0-and-the-gcp-target-live.md`
  (added in this range; also pre-existing in `bugs/BUG-069-gcp-ssh-outage-misdiagnosed.md`) —
  records `83.249.78.58`, the address the operator's own network presented
  during the BUG-069 outage. That identifies a home connection, not a project
  resource. No live exposure: `gh repo view` reports `isPrivate: true`. It
  becomes one the moment the repo's visibility changes or a collaborator is
  added. Remediation: redact to a description (`the operator's ISP address`) if
  visibility ever changes. The other address in the range, `34.51.142.50`, is
  the GCP static address already released back to Google's pool, and 5ecc24d's
  `gcp.md` teardown section already names the dangling-DNS exposure that
  creates — no action.

- **[low / confidence: high]** Accepted dependency advisory, unchanged by this
  range: `govulncheck ./...` exits 3 in both modules on GO-2026-4887 and
  GO-2026-4883 in `github.com/docker/docker@v28.5.2+incompatible`, both
  `Fixed in: N/A`. `deploy/vulncheck.sh`'s own header designates these as
  daemon-side findings with no fix available, "which the reviewer records as
  accepted per release" — this line is that record for v1.38.0. No version in
  the range moved (see Checked → dependencies), so the exposure is identical to
  v1.37.0's.

- **[low / confidence: high]** `web/package-lock.json` (unchanged in this
  range) — `npm audit` reports one high advisory, GHSA-2883-xcg3-v3hh, against
  `js-yaml@4.3.1`. It is reached only through
  `@tanstack/react-start → @tanstack/start-plugin-core → xmlbuilder2`, a
  BUILD-time path: grepping `web/dist/client/assets/` finds no `js-yaml`
  content, so nothing ships it to a browser. The advisory is CPU exhaustion on
  crafted YAML, and the only YAML the build parses is its own. Not a gate
  blocker; fold `npm audit fix` into the next frontend dependency bump rather
  than into a release commit.

  `tr -cd 'a-z0-9.-'` and is guarded by `[ -n "${_eff}" ]`, so an ssh failure

  gap is `vm.sh`'s `case` glob, finding 1. `deploy/verify-commit.sh` adds only
