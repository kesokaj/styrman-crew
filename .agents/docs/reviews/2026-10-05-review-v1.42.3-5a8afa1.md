# Review — v1.42.3-5a8afa1   (2026-10-05)

Range reviewed: v1.42.3..5a8afa1 (`git diff v1.42.3..5a8afa1`, web/dist/ build output excluded)

## Status: COMPLETE

## Verdict: REQUEST CHANGES

No high-severity defect. The memory budget, the per-tenant slot pools, the admin cap
and the per-deployment cookie names hold up when traced end to end. The worst problem
is that the plan's D22 guarantee ("a setting the environment set out of the API's range
never blocks a change to another one") holds only in `config.UpdateOperator`. The
real path goes through the Settings page and `updateRuntime`, which always re-sends and
re-validates the disk and idle values. On a host with `STYRMAN_IDLE_TIMEOUT` below 10m,
an admin cannot set the new caps at all. The test sits at the config layer and cannot
fail for the path that breaks. Two other new behaviours have no test that fails when
they are reverted: the budget skips preview/link/shared tunnels, and uploads get no
body read deadline. Reverting either one leaves every test green. Under the project's
Definition of Done, untested changed code counts as a FAIL. That rule, plus the D22
defect, is why the verdict is REQUEST CHANGES and not APPROVE WITH NITS.

## Findings

- **[medium / confidence: high]** `internal/httpapi/explorer.go:646-657` together with `web/src/routes/settings.tsx:998-1003` — D22 does not hold on the path the feature ships. `RuntimeEditor` always sends `dockerDiskGB: Number(disk)` and `idleTimeout: idle.trim()` alongside the caps. `updateRuntime` then rejects an idle below 10m with a 400 ("idle timeout must be 0 (never) or at least 10m") before `UpdateOperator` runs. Scenario: `STYRMAN_IDLE_TIMEOUT=5m` (legal from the environment, `config.go:180`; the same value `TestACapChangeIgnoresAnOutOfRangeIdleFromTheEnvironment` uses). The admin types a cap in Settings → Runtime and saves. Result: 400, and the cap can never be set from the UI. The disk field does the same through the client's `diskValid` gate when the environment sets a disk outside 5-500. Fix: have the client send only the fields that changed (the API already treats an absent field as "keep"), or have the handler skip validating a field equal to the current value. Add a handler-level test, `PATCH /api/settings/runtime` carrying the out-of-range current idle plus a cap, that fails today.
- **[low / confidence: high]** `internal/httpapi/explorer.go:627-643` and `settings.tsx:1001-1002` — the same shape for the stored caps. The client re-sends the persisted `userMaxCpus`/`userMaxMemoryGiB` on every save, and the handler checks them against the live host. Scenario: a cap of 8 is stored, then the host is moved or resized to 4 CPUs (a GCP VM resize). From then on every Runtime save (idle, disk) returns 400 until the admin lowers the cap. Every save also needs `docker info` (a 503 when it fails), even one that changes only the idle timeout. The same fix as above covers both.
- **[low / confidence: high]** `internal/httpapi/budget.go:197-200` — missing test for changed behaviour: the budget does not charge `uncharged()` tunnels (`/proxy/`, `/p/…/port/`, `/link/`, `/shared/`). Delete the `uncharged` branch and every test still passes. In production that would charge each long-lived proxied connection (a dev server's HMR WebSocket or SSE through the preview) 2 MiB for its whole life. That is the starvation the weight-0 comment warns about. Add a test that fills a tenant's share and asserts a preview path is still served.
- **[low / confidence: high]** `internal/httpapi/budget.go:225-227` — missing test for changed behaviour: `/upload` gets no body read deadline. `TestAStalledBodyGets408` uses `PUT /file`, where `fileSlot` → `acquireSlot` also arms the deadline (`budget.go:270`). That means (a) removing the `bodyDeadline` call in `budgetGuard` leaves the test green, so the deadline on slot-less routes (git/commit, credentials import, …) is untested, and (b) removing the `/upload` exemption leaves every test green, while in production every upload slower than `slotReadTimeout` (30 s) would fail. A 512 MiB cap on a home uplink is well over 30 s. Add a real-server test: a body route with no slot gets 408, and an upload that trickles past the shortened timeout still succeeds.
- **[low / confidence: high]** `internal/httpapi/format.go:80-83`, `internal/httpapi/check.go:357-360` — the new 408 branches have no test. Only `writeFile`'s branch is exercised.
- **[low / confidence: medium]** `.agents/docs/deploy/remote.md` and `.agents/docs/specs/styrman/deploy.md` (token snippet, `if sudo test -s /etc/styrman/gh-token`) — `test -s` counts a newline-only file as "already installed; left as is". That is exactly the file the updater's new `token_file_ok` now refuses ("is empty"). Following the snippet on such a host leaves the updater failing every tick. Use `[ -n "$(sudo tr -d '[:space:]' < /etc/styrman/gh-token)" ]`, the check `token_file_ok` itself uses.
- **[low / confidence: high]** `deploy/update/styrman-update:590-593` — the real tick's `token_file_ok "${GH_TOKEN_FILE}"` call is covered only through the `__check-token-file` hook. Reverting the main-flow call site to the old inline check leaves `TestEmptyTokenFilesAreRefused` green. A coverage gap; the function itself is tested.

## Criteria

1. Dead code — pass. The old `acquireSlot(w, sem, msg)` and the inline csrf limit switch were removed, not left behind. `SetOperator` remains as a wrapper (D25) and is used by existing callers.
2. Flow tracing — pass with the D22 finding. Every `EnsureRunning(` caller in `internal/httpapi` (create `server.go:1014`, start `:1209`, wsBoot via `ensureFor` `:353`, network toggle `network.go:230`, resize `resources.go:333`) goes through `s.runOptsFor(…, user, …)`. The orchestrator evaluates `Resources()` under the project lock, and a size mismatch rebuilds only a stopped container (`orchestrator.go:386`), so a running project is never rebuilt by a cap change. Host-size failure fails the start, which is tested. `membudget`: no lost wake-up. A waiter is enqueued only when something is held or an earlier same-tenant waiter is queued, and both release and cancel call `dispatch`. Granted-while-cancelled is handled under `mu`. The body-deadline clearing at EOF holds for Content-Length bodies decoded by `json.Decoder`. For chunked bodies the deadline can outlive the handler, but net/http starts no background read before EOF, so it cannot cancel the context mid-handler; it only costs keep-alive. Checked against caddy-security v1.1.64 (the version `deploy/caddy/Dockerfile:13` builds): `set cookie name prefix` (`caddyfile_authn_misc.go:65`) and `set access_token cookie name` (`caddyfile_authz_misc.go:80`) exist and produce `<PREFIX>_ACCESS_TOKEN`, matching `AuthCookieName`.
3. Standards conformance — pass. Errors are wrapped, ctx goes into `Acquire`, and `go vet` exits 0. `go test` passed for membudget, config, files, userstore, httpapi and the ingress module at 5a8afa1 (the Go files are clean in the working tree). The REQUIREMENTS check passed: R8 is unaffected (the cookie strip widened, not narrowed), and the BUG-074 fix matches its prevention rule (a unique NAME per deployment).
4. Directory layout — pass. `internal/membudget/` is a new stdlib-only package. Tests sit beside the code. `web/src/lib/historySearch.ts` + `.test.ts` are next to their consumer's lib.
5. Simplicity (DIY-except-security) — pass. No new dependency. `sha256` in `CookiePrefix` only derives an identifier, which is stdlib use, not hand-rolled crypto. Session handling stays with caddy-security.
6. Decoupling — pass. The budget is a small package with a narrow API (`New`, `Acquire`). `budgetGuard` keys on mux patterns, guarded by `TestEveryWeightedPatternIsARoute` (it catches a stale row, not a missing one, which ADR-086 states).
