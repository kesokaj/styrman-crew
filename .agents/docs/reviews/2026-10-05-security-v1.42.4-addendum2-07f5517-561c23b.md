## Status: COMPLETE

## Verdict: FINDINGS (low only — the fix holds)

The fix for the previous addendum's finding 1 holds. `isTunnelRoute` (budget.go:135) takes the pattern from `mux.Handler(r)`, the same lookup `ServeMux.ServeHTTP` runs. Both csrfGuard and budgetGuard use it, and both get the same mux (server.go:455, the only production caller). Every tunnel registration still qualifies, so real tunnels keep no Origin check, no body cap, no charge and no deadline. No API pattern qualifies.

The worst remaining problem is a defense-in-depth gap, not a bypass. authGuard still grants the link exemption from the decoded, cleaned path (auth.go:43). So `…/{wildcard}/..%2F..%2Flink%2Fx` still reaches an API handler with no identity, past only the ingress-token check. I traced every wildcard API handler, and each one fails closed today. It does so by convention, not by a mechanism. The Outcome that records this claims more than the test shows.

## Findings
- **[low / confidence: high]** `internal/httpapi/auth.go:43`: authGuard's link exemption still reads `isLinkPath(path.Clean(r.URL.Path))`.
  - **Weakness.** A request whose wildcard segment carries `..%2F…%2Flink%2Fx` routes to an API handler. authGuard passes it with a zero identity, having checked only `X-Styrman-Ingress`; in header mode no `X-Caddy-Email` is needed.
  - **Why it fails closed today.** I traced all wildcard API handlers in `newMux` (server.go:462-594). Each one refuses before any state change or disclosure, through one of these:
    - `getProjectFor`/`who`/`scopeFor`/`gitContext` → `space("")`, which `userSlugRe` `^[a-z][a-z0-9_-]{0,31}$` (server.go:396) rejects;
    - `requireAdmin` (removeUser);
    - `u.Authorized` (credentialContent, credentials.go:23-27);
    - `storeFor("")` (WS bridge, terminal/bridge.go:168-174).

    Routes without a wildcard cannot carry the encoded segment.
  - **Residual risk.** The three guards now disagree about what a tunnel is: authGuard decides by path, csrfGuard and budgetGuard by route. Some future handler may not need an identity, or may act before resolving it. Such a handler is reachable without a login, and no test would notice.
  - **Remediation.** Pick one:
    - give authGuard the mux and grant the link exemption only when the matched pattern starts with `/link/`;
    - or refuse (400) a request whose cleaned decoded path reads as a tunnel while its route does not.

    Test: `PATCH /api/projects/<id>/terminals/..%2F..%2F..%2F..%2Flink%2Fx` through `n.h` with no identity is refused by authGuard (401/400), not by the handler's 404.
  - **Non-authorized branch (auth.go:76).** It tests the UNcleaned decoded path. That is safe: an API route's decoded path always begins with its literal first segment (`/api/`, `/ws/`), so it can never read as `/shared/`, `/proxy/` or `/p/…/port/`. The same route-based change would remove the need for that reasoning.
- **[low / confidence: high]** `.agents/docs/reviews/2026-10-05-security-v1.42.4-addendum-5a8afa1-07f5517.md:184`: the Outcome overstates its test.
  - **Claim.** "every API handler fails closed (404 before the body is read — asserted in the same test)".
  - **What the test shows.** `TestATunnelLookingAPIRequestGetsEveryGuard` asserts one handler, `updateTerminal`.
  - **What the other handlers do.**
    - `setProjectNetwork` (network.go:93-100) and `setProjectResources` (resources.go:195-215) decode the body before `getProjectFor`.
    - `createLink` (links_api.go:51-69) answers 503 or 400 before resolving identity. The 503 text tells an anonymous caller whether `STYRMAN_PUBLIC_DOMAIN` is configured, which is trivial information.
    - `readFile`, `writeFile`, `formatFile` and `checkFile` take a `fileSlot` for tenant `-` before resolving identity, and release it at once.
    - The bridge answers 500 "invalid user slug".
  - **Impact.** None of these is a bypass. With this fix, every such body read is bounded by the route's cap and the body deadline.
  - **Remediation.** Reword the claim to "fails closed: no handler acts or discloses without an identity (traced; one handler asserted)" and name what is not covered.
- **[low / confidence: high]** `internal/httpapi/budget_test.go:202` (at 561c23b): the `/shared/` case of `TestTunnelsAreNotCharged` cannot fail.
  - The case is `{"", "/shared/nosuchtoken/"}`. It is anonymous, so authGuard answers 401 before budgetGuard runs, and the case passes whether or not `/shared/` is charged.
  - Yet `.agents/docs/reviews/2026-10-05-review-5a8afa1-07f5517.md:86` claims `/shared/` coverage, backed by a mutation run.
  - This is already corrected after the range: 6f72a82 sends the case as `n.admin`, and its comment says why. I read only 6f72a82's diff.
  - Remediation: amend that Outcome item to say the `/shared/` case became real in 6f72a82.

- **Fix: `mux.Handler` edge cases (go1.25.0).**
  - Routing matches on the escaped path, so `%2F` stays inside one segment.
  - A non-canonical path gets a redirect handler, whose pattern is the post-redirect route (or, for the trailing-slash redirect, the redirect path). A guard skip there serves only a 301 and reads no body. The 6f72a82 `TestRouting` case covers the reverse (`/link/../api/projects` → 403).
  - Nothing between the guards and the mux changes the URL or Host.
- **Preview-host rewrite.** `previewHostRewrite` (server.go:649-690) validates the token, then sets `Path` to `/link/<tok>` + the path. The stale `RawPath` makes `EscapedPath` re-escape the decoded path. The mux therefore either routes `/link/{token}/` (a tunnel; behaviour unchanged) or 301s a `..` escape to a non-tunnel pattern.
