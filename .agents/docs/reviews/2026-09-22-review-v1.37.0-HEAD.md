## Findings

- **[medium / confidence: high]** `.agents/docs/specs/styrman/api.md:266` —
  the `STYRMAN_ALLOW_IP_FORWARD` row still reads "A MISSING sysctl file warns
  and continues; any other read error refuses like forwarding-on." Commit
  9e50118 reversed exactly that: `config.IPForwardMustRefuse` refuses on EVERY
  error, `fs.ErrNotExist` included. This is the env table an operator and a
  reviewer check the knob against, and `api.md` WAS edited in this range
  (the `files`/`DELETE`/`rename` rows), so the grep that should have found
  this row ran over the file and stopped at the section being changed.
  Fix: replace that sentence with "Every read error refuses, a missing sysctl
  file included (2026-09-22) — a guard that could not measure must not report
  'fine'; `=1` is the way through." Global AGENTS.md describing-text rule.

- **[medium / confidence: high]** `.agents/docs/testing/styrman/README.md:8`
  — the Tier 1 description of `internal/config/ipforward_test.go` still says
  "a missing sysctl file warns and continues, any other read error refuses
  unless the knob", and does not name the test the commit added,
  `TestIPForwardMustRefuse`. This is precisely the shape
  `.agents/rules/tests-describe-behaviour.md` (BUG-061) exists to stop: a
  boot-time behaviour changed and the text describing its test suite did
  not. Fix: correct the clause and add `TestIPForwardMustRefuse` to the
  named tests in the same edit.

- **[medium / confidence: high]** `web/e2e/run.mjs:294-296` — the new
  "a directory past the listing cap says so" check types
  `… && echo BIGDONE` into the terminal and then waits for
  `document.body.innerText.includes("BIGDONE")`. The shell echoes the typed
  line into `.xterm-rows` before Enter is even processed, so the wait is
  satisfied by the ECHOED COMMAND, not by the 5200 `touch`es completing —
  the 120 s timeout never applies. This file already establishes the
  opposite convention twice, with a comment saying why:
  `run.mjs:190` types `echo styrman-e2e-$((21*2))` and waits for
  `styrman-e2e-42`, and `run.mjs:202-206` carries "Assert the OUTPUT
  sentinel, not the echoed command — otherwise this passes even if neither
  agent exists (F10)". Today the check still passes because the following
  `waitForSelector("… Some are not shown", {timeout: 30000})` absorbs the
  file creation; on a slower or loaded host (the GCP VM) it will fail there
  instead, reporting "the cap notice is broken" for a condition that is
  really "the files were not written yet" — a check naming the wrong
  condition, the `.agents/rules/remote-check-names-transport-first.md`
  family. This matters more than usual because the same commit's README
  entry names this check as the truncation notice's only coverage. Fix:
  make the sentinel unforgeable in the echo, e.g.
  `… && echo BIG$((20+2))DONE` waited on as `BIG22DONE`, or wait on
  `ls big | wc -l` output.

- **[low / confidence: medium]** `deploy/verify-commit.sh:143` (pre-existing,
  not introduced here, but the section was rewritten in 49eb863) — the
  rebuild runs as
  `( cd "${WT}/web" && npm ci … >/dev/null 2>&1 && npm run build >/dev/null 2>&1 )`
  under `set -euo pipefail`. A failing `npm ci` or `npm run build` (including
  `normalize-shell.mjs`'s own `exit 1` when the prerender payload changes
  shape) aborts the whole gate right after the `==> web/dist freshness`
  banner with no message at all. The direction is safe (a FAIL, never a
  PASS), but it is undiagnosable. Fix: send those two to `"${LOGDIR}/web.log"`
  instead of `/dev/null` and print the tail on failure, as the other build
  steps in this script already do.

### Judgement on the two items the dispatch flagged

**9e50118 — can the new refusal strand a host? No; the escape is sufficient
and documented.** The guard runs only when `cfg.SelfContainer != ""`, and
the only NEWLY refusing case is `fs.ErrNotExist` on
`/proc/sys/net/ipv4/ip_forward`. Inside any Linux container with its own
netns that file exists; on the compose path `deploy/docker-compose.yml:83`
sets `net.ipv4.ip_forward=0` as a container sysctl, which Docker applies at
create — a container whose sysctl was accepted necessarily has the file.
The GCP host runs the identical compose path (`deploy/gcp/install.sh` →
`styrman-ctl install`), so it is not a second shape. The escape
`STYRMAN_ALLOW_IP_FORWARD=1` is plumbed end to end:
`deploy/docker-compose.yml:110` passes it through from `deploy/.env`, and it
is documented in `specs/styrman/deploy.md:101`, `api.md:266`, `README.md:163`
and `AGENTS.md:114`. And if it did trip, `api.md`/`deploy.md` both record
that a tripped guard fails the updater's health check and rolls the deploy
back to the previous version, so the failure mode is a rollback, not a dead
host. The residual defect is documentation only — the first finding above.
The refactor itself is sound: with `IPForwardMustRefuse` returning false, the
surviving `switch`'s `ferr != nil` and `!off` arms are reachable only when
`override` is true, which is exactly what their Warn text claims;
`TestIPForwardMustRefuse` covers all eight combinations including
"error alongside off=true".

**49eb863 — can the sha256 comparison produce a false PASS or a false FAIL?
It closes a real false PASS and I found no false-FAIL source.** `dist/client`
holds 52 files; exactly two carry no content hash in their name —
`_shell.html` and `favicon.svg` — and those two were the hole, so the fix is
aimed correctly. On determinism: `_shell.html`'s only known per-build
variance is TanStack's 13-digit prerender timestamp, and
`web/scripts/normalize-shell.mjs` rewrites it to `u:0` as the last step of
`npm run build`, which runs on BOTH sides of the comparison; `favicon.svg`
is a static copy of `public/`; `npm ci` resolves from the committed lockfile.
`find … -exec sha256sum {} + | sort -k2` sorts on the path field, so the two
sides are comparable, and the new FAIL text correctly distinguishes
"same path, different hash" from "path on one side only". The one behaviour
change worth knowing is that a toolchain difference between the machine that
committed `dist/` and the machine running the gate now FAILS where it
previously passed — correct, and the gate runs on the same host anyway.
Two residual false-PASS holes remain, both pre-existing and both outside this
change: the whole section is skipped when `SKIP_WEB_FRESHNESS` is set (which
`AGENTS.md` advertises) or when `npm` is absent, and `shellcheck` is skipped
with a PASS when the binary is missing. Worth knowing for the release run;
not findings against this diff.

**b6e8f0d — the `REQUIREMENTS.md` edit matches ADR-076.** The ADR's decision
names four direct requirements with a non-stdlib reason each and removes
`creack/pty`; the file's Constraints line now says exactly that, and adds
"naming the stdlib alternative it rejects" to the justification rule (a
tightening, not a loosening). `go.mod`'s direct `require` block is those four
and only those four, so list and build now agree — the one thing the ADR says
the list is for. The immutability route was followed as `AGENTS.md` requires:
exact edit proposed → operator approval quoted in the ADR → ADR and file in
one commit. No finding.

   `IPForwardMustRefuse` has one production caller and its post-call `switch`
   is consistent with it (traced above). `go vet ./...` clean;
   `bash -n` clean on all nine scripts the gate now checks; `shellcheck
   -S warning` clean on the six newly covered paths, so the gate's new lines
   will not fail this release. `go.mod`'s promotion of
   `opencontainers/image-spec` traces to two real direct importers
   (`internal/orchestrator/docker.go:12`,
   `internal/orchestrator/fakedocker_test.go:19`).
3. **Standards conformance — fail.** Two stale restatements of the reversed
   boot rule (`api.md:266`, `testing/styrman/README.md:8`) and one e2e check
   departing from the file's own documented sentinel convention.
4. **Directory layout — pass.** `internal/config/ipforward.go` beside its
   test; e2e check beside its neighbours in `web/e2e/run.mjs`; the retirement
   notes sit on the blocks they retire.
5. **Simplicity (DIY-except-security) — pass.** No new dependency: the
   `go.mod` line is `go mod tidy` promoting an existing indirect requirement,
   no version moved. No hand-rolled crypto, auth or session code anywhere in
   the range; `image/Dockerfile`'s new note makes an existing `curl | bash`
   exception state honestly what it does NOT cover (TLS-only trust in
   Google's installer), which is the correct treatment for a float nobody can
   currently pin.
6. **Decoupling — pass.** Moving the rule into a pure `config` function with
   no I/O is what made it testable at all; it introduces no new coupling and
   `main()` keeps the logging.
