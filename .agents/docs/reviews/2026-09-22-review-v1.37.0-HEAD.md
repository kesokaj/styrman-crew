5. **`deploy/gcp/vm.sh:117-136` — fixed; regex checked against both
   directions.** No second round-trip remains: `cmd_status` makes exactly the
   two `vm_ssh` calls it always made (the `for p in …` probe at `:114` and
   `sudo ${ctl} status` at `:135`); nothing resolves `$HOME` locally.
   *Cannot be bypassed:* the two fixed paths are matched literally by `case`;
   the other two go through `[[ =~ ]]` with `^…$` anchors. Bash's `[[ =~ ]]`
   compiles POSIX ERE without `REG_NEWLINE`, so `$` matches only at end of
   string — an embedded newline cannot smuggle a second line past the anchor
   (and `head -n1` has already cut one). The only variable span is
   `[a-z_][a-z0-9_-]{0,31}`, which admits no shell metacharacter, no `/`, no
   space and no quote, and its first-character class forbids a leading `-`
   that could be read as an option by the remote `sudo`. `{0,31}` is an ERE
   interval in bash, so the bound is 1–32 characters, matching Linux's own
   username limit.
   *Cannot reject a legitimate path:* the remote probe only ever offers
   `/opt/styrman/deploy/styrman-ctl`, `"$HOME/styrman-crew/deploy/styrman-ctl"`
   and `/usr/local/bin/styrman-ctl`; `$HOME` on this target is `/root` (root
   ssh) or `/home/<oslogin-user>`, and GCP OS Login usernames are lowercase
   alphanumerics plus `_`/`-`, capped at 32 — inside the class. A username
   containing an uppercase letter or a dot would be refused, but no path on
   this target produces one and the refusal names the offending path, so it is
   diagnosable rather than silent; not a finding.
   The test is real: `TestGCPVMStatusRefusesAMetacharacterCtlPath` drives the
   actual script through the fake-`gcloud` seam with six hostile paths and one
   legitimate home path, asserts both the exit code and the message, and the
   `gcpRun` sentinel guard still applies. Both it and the previously broken
   `TestGCPVMStatusExitCodes` pass here (`go test ./internal/config/ -run
   TestGCPVMStatus -v`: 2 PASS, ok 0.220s).

## Findings

- **[low / confidence: medium]** `deploy/gcp/vm.sh:114` — the styrman-ctl
  probe is `ctl="$(vm_ssh '…' 2>/dev/null | tr -d '\r' | head -n1)"` under
  `set -euo pipefail` + `shopt -s inherit_errexit`. If that ssh fails after
  `ssh_reachable` has already passed (a transient drop, a session limit, or
  `head -n1` SIGPIPE-ing `tr` on a multi-line answer), the pipeline's status
  is non-zero, the assignment fails, errexit terminates the script — and
  `2>/dev/null` has discarded the only explanation. I confirmed the mechanism
  in a scratch script with the same options: the function's body after the
  assignment never runs and the script exits with the inner command's code
  (rc=7 in the probe), printing nothing. The operator then sees `vm.sh status`
  exit with an undocumented code (255 for ssh) and no output, while the
  header comment documents 0/1/2/3 only. This is the condition
  `.agents/rules/remote-check-names-transport-first.md` names — a transport
  failure must be reported as exactly that, with the tool's own
  troubleshooting command — and here it is reported as nothing at all.
  Introduced in 07741b2 (the BUG-073 fix), inside this range; not touched by
  d2c1620. Concrete fix: capture the probe without discarding stderr and
  branch on its status, e.g.
  `if ! ctl="$(vm_ssh '…' 2>"${errf}")"; then echo "ssh to ${GCP_INSTANCE} failed while probing styrman-ctl — $(ssh_hint)"; return 1; fi`
  then `ctl="$(printf '%s' "${ctl}" | tr -d '\r' | head -n1)"`, matching the
  `ssh_reachable`/`ssh_hint` model the rule points at. Not a release blocker:
  the direction is safe (a non-zero exit, never a false healthy), and the
  common path is already guarded by `ssh_reachable`.

No other finding. Nothing in d2c1620 is wrong, incomplete, or introduces a
new defect.
