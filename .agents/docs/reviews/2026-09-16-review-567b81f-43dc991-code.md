# Review — harness channel Phases 1–3, code   (2026-09-16)

Range reviewed: 567b81f..43dc991 (`git diff 567b81f...43dc991`; commits 518c5c0, 28212ac, 43dc991)

## Verdict: APPROVE WITH NITS

Nothing in this range is broken in a way that misdelivers or weakens the signature gate: the walk-down-and-verify selection, the `REQUIRE_SIGNED=1` force on the harness path, the token/clone/content-dir trust assertions, the server's trust check on the mounted export, and the entrypoint's version+commit stamp all do what ADR-073 D1–D5 say, and the tests genuinely exercise them (a foreign key, a lightweight tag, a symlinked tree, the downgrade rule, `--force`, the untrusted-shape subtests, and a Tier 2 swap-while-stopped). The worst finding is a hole in the ONE alarm ADR-073 names as the mitigation for its own residual: a harness release that verifies but fails the smoke is latched and skipped, and `styrman-ctl status` then reports **OK**, not DEGRADED, as soon as a lower tag installs under it — so the "silently not delivered until the alarm is read" residual has no read. Three smaller items follow: an unreachable `.tmp-*` cleanup branch that leaks interrupted exports, a world-writable smoke home that lets any local user fail a good tag, and a drop-trigger that does not fire when the channel is disabled by emptying the env var.

## Findings

- **[medium / confidence: high]** `deploy/styrman-ctl:322-350` — a LATCHED failed harness tag never degrades the status verdict, though the block's own comment at line 319-321 says "a refusal newer than the installed version, **a latched tag**, or a failed service degrades the verdict". `hfail` is read at line 326 and printed at line 379, but the rc block (lines 349-350) checks only `u_hs_s != */failed` and `hdegraded`. `hdegraded` is `harness-refused -nt harness-version` — and in the exact scenario ADR-073's Consequences calls the residual ("a verified-but-broken tag is skipped for a lower verified one above the installed version"), `harness_swap` writes `harness-version` AFTER `harness_alarm` wrote `harness-refused`, so `-nt` is false and the host reads OK while the channel is stuck one release behind with `harness-failed-version` set. Fix: add `[ -z "${hfail}" ] || rc=1` beside the two existing checks (the latch is cleared by `harness_swap` only when the installed tag is at or above the failed one, so the flag clears itself), and either correct the comment or cover it in `internal/config/styrman_ctl_*_test.go`. Note `.agents/docs/specs/styrman/deploy.md:360-362` describes the CURRENT behaviour correctly, so the spec must change with the fix.

- **[medium / confidence: medium]** `internal/orchestrator/orchestrator.go:352-362` — the "drop the binds" trigger is `has && errors.Is(herr, fs.ErrNotExist)`, but when the channel is DISABLED (`cfg.HarnessDir == ""`) `harnessBinds` returns `nil, nil`, so `herr` is nil and a stopped container that already carries the two binds is never rebuilt. The failure this leaves is the one the comment at 337-341 exists to prevent: on a rollback to a compose file without `STYRMAN_HARNESS_DIR` plus removal of `/var/lib/styrman/harness`, the next start has Docker recreate the missing bind sources — `current/repo` as a root-owned directory and `current/bin/sh-agent` as a directory over a file, which fails the start and permanently jams the channel (`styrman-update harness` then refuses with "current is a real directory, not a symlink"). Fix: treat the disabled case as absent for the drop trigger, e.g. `case has && (o.cfg.HarnessDir == "" || errors.Is(herr, fs.ErrNotExist)):`, and add the case to `TestEnsureRunningRecreatesAStoppedContainerToDropTheHarnessBindsWhenTheChannelIsAbsent`'s family.

- **[low / confidence: high]** `deploy/update/styrman-update:303-311` — the `.tmp-*) rm -rf "${d}" ;;` arm of `harness_swap`'s cleanup loop is unreachable: the loop is `for d in "${HARNESS_DIR}"/*`, the script sets no `dotglob` (`set -euo pipefail` only), and `harness_export` names its staging dir `${HARNESS_DIR}/.tmp-${c}` — a dot entry `*` never matches. Consequence: an export interrupted (SIGKILL, TimeoutStartSec, a reboot mid-build) leaves `.tmp-<commit>` under the content dir forever, one per interrupted commit; only a retry of the SAME commit clears it (`rm -rf "${tmp}"` at the top of `harness_export`). Fix: delete the dead arm and sweep explicitly before the loop — `rm -rf "${HARNESS_DIR}"/.tmp-* 2>/dev/null || true` (the glob is harmless when it matches nothing under `set -u`, or guard with `shopt -s nullglob` in a subshell).

- **[low / confidence: medium]** `deploy/update/styrman-update:266-268` — `harness_smoke` creates the scratch home with `mktemp -d` and then `chmod 777`, on the host's shared `/tmp` (the unit sets `RuntimeDirectory=` but not `PrivateTmp=`), for the duration of a docker run that may take minutes. The smoke's exit code is what decides whether a verified tag is installed or latched as failed, so any local unprivileged account can plant into `/home/u` and make `sh-agent install --dry-run` exit non-zero — a durable denial of the update channel for that tag (the latch survives until a newer tag). Fix: keep the dir 0700 and hand it to the smoke's uid instead of the world — `chown 1000:1000 "${home}"` (this path is root in production) — or stage it under the unit's own root-0700 `RuntimeDirectory` (`%t/styrman-harness-update`).

- **[low / confidence: high]** `.agents/docs/testing/styrman/integration.sh:163` — the check name "sh-agent status labels **the image mirror** a plain copy" no longer describes what it asserts: as of this commit `/styrman/harness` in that VM is the scratch CHANNEL export (the mount asserted twelve lines above), not the image's mirror. The assertion itself is right; the label is a stale description of behaviour the same commit changed (project rule `.agents/rules/tests-describe-behaviour.md`). Fix: rename to "sh-agent status labels the mounted harness a plain copy".

## Criteria

1. **Dead code** — one finding: the unreachable `.tmp-*` arm in `harness_swap` (above). No orphaned files, no commented-out blocks, no unreferenced exports; `harnessBinds`/`hasHarnessBind`/`harnessChannelState`/`logHarnessChannel` all have production callers, and `harnessChannelState` is used by `logHarnessChannel` (not test-only).
2. **Flow tracing** — pass with the one gap above. `create` has exactly two call sites (`ensureRunningLocked`, `EnsureSetup`); only the project one passes `harnessBinds`, matching D4's "the setup VM never mounts it", and the mode-toggle and `recreateMissingNetwork` paths both funnel back through `ensureRunningLocked`, so they inherit the binds. Installer tracing is right per `.agents/rules/mechanism-reaches-every-caller.md`: `host-setup.sh` installs both unit files, `host_converge` runs `systemctl enable --now styrman-harness-update.timer` UNCONDITIONALLY (outside the `changed` guard — the BUG-035 recurrence), guarded only on the unit file and the clone existing, and `self_install` treats the new unit pair as OPTIONAL so a rollback to a pre-ADR-073 tag still self-installs the crew files. Errors propagate (`EXPORT_ERR`/`SMOKE_ERR` into `harness_alarm` plus the latch; Go paths wrap with `%w` and `fs.ErrNotExist` is the discriminator the caller keys on). `go vet ./internal/orchestrator ./internal/config` is clean. The new Go tests can all fail — they assert call counts and bind contents against a fake Docker seam, and the shell test drives real signing, a real export and a real container smoke.
3. **Standards conformance** — pass. Go is idiomatic (`slog`, `os.Lstat` not `DirEntry.Info()`, `filepath.EvalSymlinks` with a containment check, no `DirEntry.Info()` under a confined root — `.agents/rules/guest-writable-paths.md` respected, and the content dir is server-only/root-written beside `users/` and `projects/`, never under a mounted home). Describing-text: two mismatches found (findings 1 and 5); the in-range docs (`specs/styrman/deploy.md`, `runtime-image.md`, `versioning.md`, `testing/styrman/README.md`, `deploy/README.md`, `AGENTS.md`) were updated with the code and the Tier 2 count line moved in the same commit as the checks it counts.
4. **Directory layout** — pass. Units beside the updater in `deploy/update/`, the channel's Go code in its own `internal/orchestrator/harness.go` with `harness_test.go` beside it, the script-driving tests in `internal/config/` next to the existing `styrman_ctl_*_test.go` family, the Tier 2 helper in `.agents/docs/testing/styrman/`.
5. **Simplicity (DIY-except-security)** — pass, and the security exemption is honoured the right way round: no primitive, signature format or auth flow is implemented here. Tag verification is delegated to git/ssh-keygen through the pre-existing `verify_tag`, `REQUIRE_SIGNED` is forced to 1 on this path before any candidate is touched (the `update.env` opt-out is unreachable because the harness dispatch sits above where `update.env` is read), the GitHub token travels through a git credential helper reading a root-600 file, and no new dependency is added. `sort -V` + `git archive` + `tar` + `sha256sum` is the stdlib-equivalent choice for a shell path that already lives here.
6. **Decoupling** — pass. The server's seam is three small functions plus one `createSpec` field; the host script's seam to the server is a directory shape (`current/repo`, `current/bin/sh-agent`) that both sides assert independently, which is what lets the two halves be worked on separately. `styrman-ctl` touches only its own status/setup blocks.
