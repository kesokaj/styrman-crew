# Review — v1.21.0 release gate, un-nest project homes (ADR-064)   (2026-09-04)

Range reviewed: v1.20.0..3e2f125

Source scope as dispatched: `internal/config/config.go`, `internal/config/config_test.go`,
`cmd/styrman/main.go`, `cmd/styrman/migrate_test.go`, `internal/orchestrator/orchestrator.go`,
`internal/orchestrator/realbelow_test.go`, `internal/httpapi/server.go`. Callers outside that
set were traced read-only for consistency with the changed `UserHome` semantics.

## Verdict: APPROVE WITH NITS

**No finding blocks the release.** The layout change is correct and the security rounds
landed real hardening: the `os.Root` migration is sound (relative `rt.Rename` both sides,
no `DirEntry.Info()` anywhere near a root — the BUG-004 trap is avoided), the `filters`
label query matches the existing `ReapSetupVMs` idiom exactly, `setupHomeStale` is total
and fails safe (no bind → stale), `EnsureSetup` now proves `base/` is a real directory
before it becomes a Docker bind source (the BUG-003 rule applied to the one path that
previously lacked it), and every `UserHome` caller left outside the diff
(`setup.go:34/127/214`, `credentials.go:263`, `git.go:73`, `explorer.go:443`,
`config.go:372`, `main.go:251`) means "the setup/base home" and is correct under the new
meaning — `migrateBaseHomes` moves exactly the state those callers read. The compose
deploy binds `/var/lib/styrman` at the same path inside and outside the server container,
so `insp.Mounts[].Source` is directly comparable to `cfg.UserHome(user)`; there is no
host/container path skew that would make every setup VM read as stale. The worst thing
here is the shape of the new startup step, not its logic: a synchronous, Docker-blocking
60 s sweep now sits ahead of the listener, in the exact place the adjacent comment warns
once made `/api/health` hang and the ingress return 502.

## Findings

- **[medium / confidence: high]** `cmd/styrman/main.go:68-76` — the stale-setup-VM sweep is
  synchronous, ahead of the HTTP listener, with a 60 s budget (`ContainerList` + one
  `ContainerInspect` per setup container). The comment eight lines below documents the
  incident this shape caused: "after a host reboot a slow dockerd (10 Kata VMs restarting)
  made /api/health hang for minutes, which the ingress reads as 502", which is why `Adopt`
  and the self-attach loop were moved into goroutines. Failure path: on a reboot with a
  slow-starting dockerd the listener does not bind for up to 60 s and the ingress serves
  502 for that window — on every boot forever, not just the upgrade boot, since the
  `ContainerList` call is unconditional. Docker being *absent* is fine (connect refused
  returns immediately, `Warn`, startup continues). Note also that on timeout the code
  proceeds to `migrateBaseHomes` anyway, so the "no guest holds the old mount" ordering
  guarantee is already best-effort — a shorter budget gives up nothing. Fix: drop the
  timeout to ~10 s (one-line change); `EnsureSetup`'s per-user `setupHomeStale` check at
  `internal/orchestrator/orchestrator.go:594` is the durable guarantee and already covers
  anything the sweep misses.

- **[medium / confidence: high]** `cmd/styrman/migrate_test.go` — this diff deletes
  `TestMigrateWorkspaces` and `TestEnsureReposRefusesUnmigrated` while `migrateWorkspaces`
  and `ensureRepos` remain live in `main.go` *and* had their input path silently
  re-pointed by this very change (`cfg.UserHome(user)` at `main.go:251` now resolves to
  `homes/<u>/base`, so the legacy workspace root moved from `homes/<u>/projects/<dir>` to
  `homes/<u>/base/projects/<dir>`). `cmd/styrman` now has no test for either function
  (only the four new migration tests plus `prune_test.go`), and nothing anywhere pins the
  ordering dependency this change created: `migrateBaseHomes` (line 76) MUST run before
  `migrateWorkspaces` (line 81), or a pre-ADR-027 workspace is looked for under `base/`
  before it has been moved there and is silently skipped. The R13 guard the deleted test
  covered — "ensureRepos must not create the new workspace while the unmigrated one still
  exists", i.e. do not shadow a real tree with an empty repo — is not covered by
  `integration.sh` either (its two `.git` checks only exercise the creation path). AGENTS.md
  Definition of Done step 1 calls changed code without a covering test a FAIL. Fix: restore
  both tests against the new layout (they only needed `orchestrator.New`, which works
  without a daemon), and add one assertion that a legacy `~/projects/<dir>` planted in the
  tenant dir survives the full `migrateBaseHomes` → `migrateWorkspaces` → `ensureRepos`
  sequence.

- **[low / confidence: high]** `cmd/styrman/main.go:517-519` — `rt.Rename` failures are
  counted (`failed++`) and the error is discarded; the operator sees `"failed": 3` with no
  cause, for a step that moves a user's credentials and shell state. The entries that
  failed stay at the tenant top level, which no guest mounts and which `files.Trust`'s
  `openRoot` never reaches (it resolves only `base/` and `p/`), so they are invisible from
  the UI and the VM — recoverable only by hand on the host. Same for `left++` at line 514.
  The "counts only, never entry names" rule does not require dropping the *reason*. Fix:
  log the error class without the path, e.g. `logger.Warn("base home migration: entry not
  moved", "user", …, "errno", errors.Unwrap(err))` or a `errors.Is(err, fs.ErrExist)` /
  `ENOTEMPTY` discriminator, so a partial migration is diagnosable from the journal.

- **[low / confidence: medium]** `cmd/styrman/main.go:504-520` — TOCTOU inside the confined
  root: `rt.Lstat("base")` proves `base` is not a symlink, then the rename loop uses it.
  `os.Root` refuses symlinks that escape the root but *does* follow symlinks that stay
  inside it (verified against Go 1.25: `Rename("dot", "base/dot")` through an in-root
  `base -> p/uuid` symlink succeeds and lands in `p/uuid`; through an out-of-root symlink it
  fails with "path escapes from parent"). So a guest that still holds the old tenant-dir
  mount — only possible when the sweep failed or timed out, and note `RemoveStaleSetupVMs`
  swallows per-container `ContainerInspect`/remove errors at
  `internal/orchestrator/orchestrator.go:1349-1360` and still returns a nil error — could
  swap `base` for a symlink to `p/<uuid>` in the window and have the tenant's dotfiles land
  inside one of its own project homes. No host escape, no cross-tenant reach: the blast
  radius is one tenant, and post-ADR-064 no guest mounts the tenant dir at all, so the
  window exists only on the upgrade boot. Accept, or close it by holding a `*os.File`
  handle on `base` and renaming with `renameat` against that fd.

- **[low / confidence: low]** `cmd/styrman/main.go:504` — `base` and `p` become reserved
  names inside a pre-ADR-064 home with no detection. A v1.20 user who had created `~/base`
  in the setup VM gets that directory silently adopted as the new home root (its contents
  surface at `~/…`), and any name collision under it is left orphaned in the server-only
  tenant dir with only a `leftInPlace` count to say so. No data loss; unlikely, but the
  migration cannot distinguish a user's `base` from one it created. Fix (optional): log at
  `Warn` when `base` existed before the migration ran and `left > 0`.

## Criteria

1. **Dead code** — pass. No orphaned symbols: `TenantDir`, `setupHomeStale`,
   `RemoveStaleSetupVMs`, and `migrateTenantIntoBase` all have live callers; no
   commented-out blocks; no leftover `UserHome`-as-tenant-dir call sites (grep confirms all
   30 `UserHome`/`TenantDir` uses are intentional under the new meaning).
2. **Flow tracing** — pass with the medium finding above. Traced
   `migrateLegacy` → sweep → `migrateBaseHomes` → `migrateWorkspaces` → `ensureRepos` and
   `EnsureSetup`/`EnsureRunning`/`createProject`; the ordering is correct as written but
   unpinned by any test. Errors are wrapped with `%w` on the orchestrator paths; the two
   swallowed errors are called out as findings. `sweepCtx` is cancelled on every path.
3. **Standards conformance** — pass. Matches the project's own symlink-defense idiom
   (`os.Root`, `realBelow`, `mkdirAllConfined`), `log/slog` structured logging, stdlib-only;
   `gofmt -l` clean, `go vet ./...` clean, targeted tests green. Two cosmetic drifts, not
   findings: `github.com/docker/docker/api/types/filters` (orchestrator.go:12) and
   `.../types/container` (realbelow_test.go:4) were moved into the stdlib import group, and
   `deploy/host-setup.sh:279` still describes the pre-ADR-064 layout.
4. **Directory layout** — pass. No new files; tests sit beside the code they cover.
5. **Simplicity (DIY-except-security)** — pass. Pure stdlib (`os.Root`, `fs.ReadDir`,
   `os.Rename`); no new dependency; no auth/crypto/session surface touched — the ingress
   token and OAuth paths are untouched by this range.
6. **Decoupling** — pass. `TenantDir`/`UserHome`/`ProjectHome` remain three small
   accessors; `setupHomeStale` is a pure helper with its own unit test;
   `migrateTenantIntoBase` is separable from `migrateBaseHomes` and testable per tenant.

## Requirements

- **R1** (one project = one Kata microVM) — unaffected; the setup VM keeps `cfg.Runtime`
  and its own `SetupNetwork`; nothing in the range introduces a runc path or a shared
  `docker.sock` for project workloads.
- **R3** (per-project home, credentials shared via the broker) — advanced, not violated.
  `p/<uuid>` is never touched by the migration, and the credential revoke sweep
  (`credentials.go:263`) follows the setup home to `base/`, so materialized copies moved by
  the migration are still reachable for revocation.
- **R12** (project network isolation) — unaffected; no network, bridge, or firewall code in
  the range. Removing a stale setup container leaves its `SetupNetwork` behind exactly as
  the pre-existing `ReapSetupVMs` does, and `create` reuses it.
- **REQUIREMENTS.md / AGENTS.md** — one process violation, not a product one: the deleted
  regression tests above against DoD step 1.
