## Findings
- **[medium / confidence: high]** `.agents/docs/deploy/gcp.md:79-83` vs `.agents/docs/specs/styrman/versioning.md:288-289` — gcp.md says "The VM's list holds the NUC's release signer (`SHA256:2bCWnLoM…` since v1.42.4) and the Mac key". versioning.md says the VM "is to list both"; ADR-089 consequences say the VM's list "needs the line added, an operator step"; BUG-094 (INDEX row, `bugs/INDEX.md:95`) records the VM list as NOT checked. Nothing in the range shows the VM was checked or the line added, so gcp.md states an unverified (and per ADR-089 probably false) fact, and a VM still carrying only `5HpY…`+Mac key would refuse every v1.42.4+ tag. Fix: reword gcp.md to "is to list" and name the add of `2bCW…` as an operator step beside the `5HpY…` removal (the way versioning.md and ADR-089 amendment 1 already word it).
- **[medium / confidence: medium]** `README.md:13-16` (also `AGENTS.md:85-89`, `.agents/docs/specs/styrman/deploy.md` "a user pulls a newer release") vs `.agents/docs/architecture/DECISIONS.md` ADR-090 Consequences — the living docs say a user can `sh-agent update` any time with no crew release. ADR-090 says a home whose `sh-agent` is v2.3.2 cannot update now that the newest harness release is unsigned; it works only after the crew release carrying this image reseeds v2.4.1 at next boot. No living doc (remote.md has a "Hosts crossing v1.42.4" section but none for the next release; README:16 already says the image "currently carries" v2.4.1 though v1.42.4, the latest tag, carries v2.3.2) names the caveat. Fix: a one-line caveat in remote.md's upgrade notes (and the release notes) for the release that ships this; README:16 is accurate only once that tag exists.
- **[low / confidence: high]** narrowed: `.agents/docs/specs/styrman/deploy.md:384-390` → `.agents/docs/specs/styrman/versioning.md:101-106`, `.agents/docs/specs/styrman/runtime-image.md:288`, `.agents/docs/testing/styrman/README.md:482` ("Manual, on every `HARNESS_VERSION` bump") — deploy.md and image/README.md now say a bump edits BOTH `HARNESS_VERSION` and `HARNESS_SHA256` and is confirmed by rebuilding the tag. The three other restatements of the bump still speak of `HARNESS_VERSION` alone (runtime-image.md:288 "bumping ... `HARNESS_VERSION` and rebuilding" would now fail the build at the harness RUN step; versioning.md's release step 1 has no hash or rebuild-from-tag step). Fix: add the pin to each, or point each at deploy.md.
- **[low / confidence: medium]** unverified: `.agents/docs/testing/styrman/integration.sh:285` and `image/entrypoint.sh:151` ("v2 harness is 1,788 files") and `runtime-image.md:268` ("v2.3.2's install wrote 1,788 files") — v2.4.1 adds a rules file, and the verifier log (`testing/2026-10-06-verify-harness-v2.4.1.md`) did not re-measure the file count or the 120 s-cap timings.
