# Review — v1.37.0 release gate, round 2   (2026-09-22)

Range reviewed: 2b84e94..worktree (`git diff 2b84e94` over the working tree, plus the four untracked files `git status --porcelain --untracked-files=all` lists)

## Status: COMPLETE

## Verdict: APPROVE WITH NITS

Every round-1 fix does what its `## Outcome` claims, and nothing that worked
before is broken: `cmd_install`'s real path is byte-for-byte the old sequence
moved into `run_host_setup`, the `ssh` verb's interactive path is untouched,
and `internal/config` is green in BOTH terminal states (`timeout 200 go test
./internal/config/ -count=1 -timeout 150s` → `ok … 6.236s`, rc 0; `timeout 260
script -qec "go test ./internal/config/ -count=1 -timeout 180s" /dev/null` →
`ok … 6.176s`, rc 0 — no hang, which is the round-1 defect's must-fail state).
The worst remaining problem is new and is in the very check the security review
asked for: `assert_no_public_ssh` fails OPEN and SILENT when `python3` is
missing or the firewall JSON is unparseable, so the operator is told nothing
and the "no public port 22" posture is asserted by nothing again. That is one
line to fix and should land before the tag; it does not block the release
artifact itself, which is why this is APPROVE WITH NITS and not REQUEST
CHANGES.

## Findings

- **[medium / confidence: high]** `deploy/gcp/lib.sh:94,124` — `assert_no_public_ssh`
  fails open and silent. The filter pipeline ends `2>/dev/null || true`, so
  `python3: command not found`, a `json.load` traceback, or any other python
  failure yields `exposed=""` and the function returns 0 having printed
  nothing. Nothing in `vm.sh`/`lib.sh` requires `python3` — `need_gcloud`
  (`lib.sh:50`) checks only gcloud; `install.sh:112` requires python3 but that
  is a different script that runs later. Contrast the `[ -z "${json}" ]` branch
  at `lib.sh:87`, which correctly warns "leaving the 'no public port 22' claim
  UNVERIFIED". This is BUG-034's family — silence from your own instrumentation
  read as a pass. **Fix:** run the filter as its own statement and read its
  status (`exposed="$(… python3 …)"; rc=$?`), have the python print a sentinel
  (e.g. `CHECKED <names>`), and `die`/`warn UNVERIFIED` when the sentinel is
  absent or `rc != 0`. A must-fail state for the test already exists: run the
  suite with a `PATH` whose `python3` is a stub exiting 127 and assert the
  UNVERIFIED warning.

- **[low / confidence: medium]** `deploy/gcp/lib.sh:99-101` — false negative on a
  numeric `IPProtocol`. `covers_22` matches only `"tcp"` and `"all"`, but the
  Compute firewall API documents `IPProtocol` as "tcp, udp, icmp, esp, ah,
  sctp, ipip **or the IP protocol number**". I ran the exact filter against
  `{"IPProtocol":"6","ports":["22"]}` from `0.0.0.0/0`: `NOT FLAGGED`. A rule
  created through Terraform or the raw API with `"6"` is tcp and is missed. No
  test covers it. Fix: treat `"6"` as tcp and `"0"`/`"all"` as all.

- **[low / confidence: high]** `deploy/gcp/lib.sh:110-118` — two false positives,
  both verified by running the filter as written. (a) The filter never reads
  `r["network"]`: a rule in an unrelated VPC in the same project is `FLAGGED`
  and refuses the create, naming a rule that cannot reach this instance
  (`GCP_SUBNET=europe-north2` puts the VM in one specific network;
  `firewall-rules list` returns every network's rules). (b) A rule scoped by
  `targetServiceAccounts` (no `targetTags`) is `FLAGGED`, although the VM runs
  `--no-service-account` (`vm.sh:76`) and such a rule can never apply to it.
  Direction of failure is safe (refuse, with `GCP_ALLOW_PUBLIC_SSH=1`), but the
  die message asserts something false. Fix: compare `r["network"]`'s basename
  against the instance's network, and skip a rule carrying
  `targetServiceAccounts` when it carries no matching `targetTags`.

- **[low / confidence: medium]** `deploy/gcp/lib.sh:107` — two gaps worth naming
  in the comment rather than fixing. (a) `::/0` is not matched: verified `NOT
  FLAGGED`. Harmless *today* only because `vm.sh create` makes an IPv4-only
  instance (no `--stack-type`/`--ipv6-*`, an IPv4 `--address`), i.e. the check
  silently depends on a property of the sibling function. (b) In a shared-VPC
  service project `firewall-rules list` returns `[]` — a non-empty string, so
  the `[ -z "${json}" ]` warn does not fire — and the check passes silently
  while the rules that govern the instance live in the host project. The
  function's header comment claims the property is "a property of the PROJECT";
  it is a property of *this* project's layout.

- **[low / confidence: medium]** `deploy/styrman-ctl:932` (`__run-host-setup`) —
  the guard in `cmd_internal` is weaker for an exec hook than for the write
  hooks it was written for. The loop over `"${@:2}"` constrains only arguments
  matching `/*`; a **relative** path (`../../home/x/evil.sh`) is not checked at
  all and is handed straight to `run bash "${script}"`, which under `sudo
  styrman-ctl` is root. The realistic exposure is small — `STYRMAN_CTL_TEST=1`
  is required and sudo's `env_reset` strips it, and `$TMPDIR` defaults to the
  world-writable `/tmp` in any case — so this is hardening, not a live hole.
  Fix: in the `__run-host-setup` arm, require the script argument to be
  absolute (`case "$4" in /*) ;; *) die …` ) so the existing TMPDIR
  confinement actually applies to it.

- **[low / confidence: high]** `.agents/docs/specs/styrman/versioning.md:91-97`
  vs `.agents/docs/testing/2026-09-22-verify-v1.37.0-release.md:113` — the new
  step 0 requires "the words `fresh-host path unexercised` in the gate report".
  The gate report does not contain that phrase (grep: no match); it states the
  fact correctly in its `## Not examined` section in different words. The
  release that introduces the rule therefore fails it as literally written.
  Relatedly, `2026-09-22-review-v1.36.0-HEAD.md`'s Outcome item 3 claims "the
  gate report's verification row and its 'What was not checked' section say
  'fresh-host path unexercised' in as many words" — neither that section name
  nor that phrase exists in the report. The substance is on record; the two
  claims about it are not. Fix (one edit, either side): reword step 0 to "says
  the fresh-host path was not exercised", or add the phrase to the gate report
  and correct the Outcome sentence.

- **[low / confidence: high — nit]** `deploy/gcp/vm.sh:146` — the `--dry-run ssh`
  line is faithful in argv but not in quoting. `--command=\"${ARGS[*]}\"`
  prints literal double quotes around the flattened command, so a command
  containing `"` or `$` prints a line that is wrong if copy-pasted. The concrete
  case is the one this same diff introduces: `install.sh:120`'s new WARN tells
  the operator to run `deploy/gcp/vm.sh ssh -- 'rm -rf "$HOME/.styrman-install"'`,
  and under `--dry-run` that prints `--command="rm -rf "$HOME/.styrman-install""`,
  where `$HOME` would expand on the operator's own machine. The real
  (non-dry) path is correct — `vm_ssh` passes `--command="$*"` as one argv
  element. This matches `run()`'s existing `echo "+ $*"` flattening, so it is
  not a regression; `printf '%q'` would make the plan copy-pasteable.

### Answers to the dispatch's specific questions

1a. **`Setsid: true` does remove the controlling terminal** — `setsid(2)` makes
the child a session leader, and a new session has no controlling tty until the
process opens one with `O_NOCTTY` clear. Confirmed empirically: the pty run
that hung the package in round 1 now completes in 6.2s. **No test in either
file depends on a tty being present**; every tty-related assertion is a
no-tty one (`TestGCPVMCreateNeedsYesWithoutTerminal`, `vm.sh:59`'s `has_tty ||
die`, `styrman_ctl_test.go:821` "no level, no tty"), so the change makes them
deterministic rather than breaking them. `--confirm`-based tests bypass the
prompt entirely.

1b. **The hook's exposure** — see the `__run-host-setup` finding: gated
correctly behind `STYRMAN_CTL_TEST=1`, but the TMPDIR restriction does not
apply to relative paths and `/tmp` is world-writable, which is a weaker guard
for "exec this file" than for "write this file". **`cmd_install` behaves
exactly as before for a real run**: `run_host_setup "${gh_token_file}"
"${OPERATOR}"` reproduces the old block verbatim — same `private_file`, same
`tr -d '\n'`, same `export`, same `log`, same `run bash
"${REPO}/deploy/host-setup.sh" --user "${OPERATOR}"` (default third argument).
The only behavioural delta is `[ "${DRY}" = 1 ] ||` on the read, which is the
security review's item 5 and is correct: `private_file`'s permission checks
still run under `--dry-run`, only the secret is not read.

1c. **The firewall filter** — of the shapes named in the dispatch: `sourceRanges`
absent is correctly *not* flagged (no `sourceRanges` means the source is tags or
service accounts, not the internet); `::/0` is missed (finding 4a);
`sourceTags`/`sourceServiceAccounts` as *sources* are correctly ignored;
another network is wrongly flagged (finding 3a); `IPProtocol: "6"` is missed
(finding 2); a shared VPC passes silently (finding 4b). Plus one the dispatch
did not name: `targetServiceAccounts` is wrongly flagged (finding 3b).
**Test coverage** (`TestGCPVMCreateRefusesPublicSSH`): covered are bare
`tcp:22`, a `20-30` range, a portless `tcp`, `all` on one of our tags, and the
six must-pass shapes plus the override — a genuinely good must-fail/must-pass
pair. **Not covered:** numeric protocol, `::/0`, another network,
`targetServiceAccounts`, shared VPC, a higher-priority DENY rule, and the
python-failure path of finding 1.

1d. **`reset --hard` + `clean -qfdx`** — correct and an improvement. The
existing-checkout path now guarantees the tree `verify-tag` vouches for is the
tag's tree; `clone --branch v${VERSION}` leaves a detached HEAD, so the reset
moves HEAD and rewrites no branch. Nothing the install needs lives untracked in
`~/styrman-crew` (the staged secrets are in `~/.styrman-install`, the deployed
copy is `/opt/styrman`), so `-x` is safe. The pinned `-c gpg.format=ssh -c
gpg.ssh.program=ssh-keygen` are highest-precedence in git's config order and
close the repo-local-config redirection the security review named. Worth
knowing rather than fixing: neither `reset --hard` nor `clean` touches
`.git/config`, so a hostile config planted by the VM user persists — the three
keys that matter are pinned, and the threat actor here already owns the install
account, so this is not a finding.

1e. **`--dry-run ssh`** — argv-faithful, quoting-lossy; see the nit.
`${ARGS[0]:+…}` is safe on an empty array under `set -u` (verified on bash
5.2.37: `A:[]`, rc 0), so the interactive `--dry-run ssh` with no CMD prints
the right line and does not abort.

2. **Nothing that worked is broken.** `cmd_install`'s real path, the `ssh`
verb's interactive no-CMD path, and every existing test's assumptions hold;
both terminal states are green.

3. **Nothing new is worse than what it replaced**, with one structural note
under Decoupling below.

## Criteria

1. **Dead code** — pass. No orphans: `run_host_setup` has two real callers
   (`cmd_install` and the hook), `vm_ssh` is still the non-dry path of the
   `ssh` verb, `assert_no_public_ssh` is called from `cmd_create`. No
   commented-out blocks, no leftover debug output, no unused imports (`syscall`
   is used in both test files).
2. **Flow tracing** — pass, with findings 1-3. Every hop checked:
   `cmd_create` → `assert_no_public_ssh` (placed before the address reservation
   and the instance create, so a refusal plans nothing — the test asserts
   exactly that); `cmd_install` → `run_host_setup` → `private_file` →
   `run bash`; `install.sh` fetch → reset → clean → verify-tag → install.
   `GCP_ALLOW_PUBLIC_SSH` is a read-only env opt-in with no other reader. Every
   new test can fail: `TestGCPVMCreateRefusesPublicSSH` drives four must-fail
   states through the real script, and the token test now reads the child's
   ENVIRONMENT through a fake `host-setup.sh` instead of asserting on plan text
   — the exact weakness round 1 named.
3. **Standards conformance** — pass. The describing text was moved with the
   behaviour (`vm.sh:84`'s wait line, `lib.sh:63-67`'s `vm_ssh` header,
   `install.sh:143-145,157-159`'s comments, `gcp.md`'s reversed credential-reuse
   guidance, the 2026-09-21 review's addendum). The one restatement that did not
   land is finding 6 (`versioning.md` step 0's literal phrase vs the gate
   report). `.agents/rules/verify-bare.md`'s family is what finding 1 violates.
4. **Directory layout** — pass. No new files in the range; the shell tests stay
   in `internal/config/*_test.go` beside the rest of the deploy-script suite,
   which is the existing convention.
5. **Simplicity (DIY-except-security)** — pass. No dependency added (`python3`
   was already the JSON tool; `jq` correctly avoided). Nothing hand-rolled:
   the range's trust decisions are `git verify-tag` → `ssh-keygen -Y verify`,
   now *more* tightly pinned to the vetted program. `run_host_setup` is a
   straight extraction, not an abstraction.
6. **Decoupling** — pass, one note. `vm.sh:146` now rebuilds `vm_ssh`'s argv by
   hand for the dry-run line, so the two must stay in sync: a future change to
   `SSH_ARGS` or the flag order in `vm_ssh` would silently make the plan lie.
   `TestGCPVMSSHDryRunRunsNothing` asserts `--tunnel-through-iap` and the
   command text, which guards part of it. Having `vm_ssh` itself print under
   `DRY=1` would remove the duplication.
