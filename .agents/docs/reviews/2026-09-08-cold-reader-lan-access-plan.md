# Review — cold-reader check: per-project LAN access plan   (2026-09-08)

Range reviewed: `.agents/docs/plans/2026-09-08-per-project-lan-access.md` (plan document, not a diff), plus the code surfaces it cites: `deploy/host-setup.sh`, `internal/config/config.go`, `internal/httpapi/server.go`, `internal/project/store.go`, `web/src/lib/{api.ts,projects.ts}`, `web/src/components/SidePanelPorts.tsx`, `deploy/docker-compose.yml`, `deploy/update/styrman-update`, `REQUIREMENTS.md`, `.agents/docs/architecture/DECISIONS.md`, `.agents/docs/specs/styrman/deploy.md`, `.agents/docs/deploy/local.md`, `.agents/docs/specs/styrman/guide.md`, `.agents/docs/testing/styrman/README.md`. Live host facts (`iptables -S STYRMAN-FWD/INPUT/DOCKER-USER/FORWARD`, `ip -4 route`, `systemctl cat`, `systemctl --version`) were checked read-only; nothing on the host or in the repo was changed.

## Verdict on the two questions

**(1) Gaps — two concrete ones, both correctness/behavior questions, not D1–D7 territory:**

- **Sync-vs-PUT race, unaddressed.** `netpolicy.Dir.Sync(want)` is invoked from `cmd/styrman/main.go` at boot and again every 2 minutes (a *new* ticker there, per "Surfaces touched" — it is not, and cannot cleanly be, the orchestrator's own `RunIdleReaper` ticker in `internal/orchestrator/orchestrator.go:1141`, which knows nothing about `project.Store`/`netpolicy`; the plan's phrasing "the idle-reaper tick... re-runs Sync" only reads unambiguously once you cross-reference "Surfaces touched," so the mechanism itself should be stated plainly, not implied). The interface section documents `netMu` serializing overlapping HTTP PUTs, but never states how a `Sync` cycle (which snapshots `want` from disk via `forEachProject` *before* calling `Sync`, then deletes any on-disk marker "not in want") avoids deleting a marker that a concurrent PUT creates moments after the snapshot was taken. Both `SetMarker` and `Sync`'s own additions are stated idempotent (`O_CREATE|O_EXCL`, `os.Remove`) so double-writes are harmless, but the *deletion* side ("removes uuid files not in want") has no freshness guard and no shared lock with `s.netMu`. This is a real lost-update: a project enabled via PUT can have its brand-new marker deleted by the next Sync tick, silently reverting the toggle the UI just showed as "on."
- **Destroy marker-removal placement is a range, not a point.** "Interfaces / Destroy" says `SetMarker(id, false)` + `Kick("delete")` go "after `orch.Destroy` and the credential sweep, before `projects.Remove`" (`internal/httpapi/server.go:882`). That range spans the optional wipe block, which can early-return on `wipeFailed` and *keep the project record* for a retry (lines ~936–966). If marker removal is placed right after `sweepProjectCredentials` (the start of that range) rather than right before `sp.projects.Remove` (the end), a failed wipe silently revokes LAN access on a project that is still visible, still running, and awaiting retry — a behavior nobody decided on and the failure-modes table doesn't cover. The plan needs to pin this to one specific point, not a range.

Everything else checked against the plan's own citations held up: the `deploy/host-setup.sh:167-232` heredoc range, the `BridgeNameFor`/`NetworkName` sha1 derivation and its golden vector (`sdb-3e6a772c-… → sdb-e660d58459e`, reproduced independently), the live host's 4-DROP vs. repo's 6-DROP drift and the script's 2026-08-30 mtime, `LAN_DEV=enp114s0`/`LAN_CIDRS=192.168.86.0/24`, `DOCKER-USER`/`FORWARD` jump order, the server's own netns (`network_mode: host` in compose belongs to `caddy`, not `styrman`), the 1 MiB body cap, the 5 s shared `useProjects` poll, `ConfirmDialog`/`tryUI` existing, `sharedPorts` genuinely missing from `api.ts`'s `Project` type, no `role="switch"` in the frontend yet, `deleteProject`'s exact step order, `settings()` living in `explorer.go`, R12's line 78 "RFC1918 + metadata" text, and all three stale-count doc citations (`deploy/local.md:40`, `guide.md:520` "60 checks" vs. README's "68"). This is a plan whose citations were done with real diligence — the two gaps above are the exceptions, not a pattern.

**(2) Readiness — not implementation-ready.** A first-pass implementer would have to stop and ask both questions above (how Sync and a concurrent PUT are kept consistent; exactly where in `deleteProject` the marker removal goes relative to the wipe-failure early return) before `internal/netpolicy` and the `deleteProject` integration could be written correctly. Two open questions, not zero.

## Findings

- **[medium / confidence: medium]** Plan §"Boot / runtime reconciliation" + §"Interfaces / Server side" (`netpolicy.Dir.Sync`) — periodic/boot `Sync` deletes on-disk markers not in a `want` snapshot taken before `Sync` runs, with no described coordination with `s.netMu` or any freshness guard; a PUT that enables LAN access can race a `Sync` tick and have its marker deleted within the same cycle, reverting the setting without the user's action. Needs either sharing `netMu` for the duration of `Sync`, or a grace-period exemption (e.g., skip markers younger than the tick interval) in the "remove stale" step.
- **[low / confidence: medium]** Plan §"Destroy" vs. `internal/httpapi/server.go:882-983` (`deleteProject`) — marker removal is specified as somewhere in the range spanning the wipe block's `wipeFailed` early return; placed too early it revokes LAN access on a project that a failed wipe kept alive for retry. Pin it to immediately before `sp.projects.Remove`.

## Criteria

1. Dead code — n/a (plan document, no code diff to review for this).
2. Flow tracing — mostly holds end-to-end (PUT → store → marker → spool → root script → status → UI derivation all connect); the one break is the Sync-vs-PUT race above.
3. Standards conformance — plan follows the project's ADR-052 (no in-script defaults), ADR-064-shape ADR/amendment format, and R12 amendment discipline (ADR-055 precedent) correctly; ADR-029/036 citations check out.
4. Directory layout — new `deploy/firewall/` package and `internal/netpolicy` both land where an unfamiliar engineer would look; consistent with existing `deploy/update/` and `internal/<feature>` conventions.
5. Simplicity (DIY-except-security) — stdlib-only Go package, shell reconciler following the existing script's idioms; no new dependency introduced; root/server split is the minimum privilege separation the constraint (server has no NET_ADMIN) forces.
6. Decoupling — server and root halves communicate only through named files (markers/spool/status), a clean seam; the one blur is the undecided relationship between `main.go`'s periodic `Sync` and `httpapi`'s `netMu`-guarded PUT path (finding above).

### Both round-1 gaps: resolved

**Gap 1 (Sync-vs-PUT race).** The revised `Dir.Sync` interface doc now states explicitly: Sync "takes d.mu for the WHOLE cycle: calls `want()` (the disk snapshot) INSIDE the lock, then adds missing markers and removes uuid files not in want"; `SetMarker` also takes `d.mu`. Traced the resulting interleavings by hand: the PUT handler writes the store record (`SetLanAccess`, unlocked) strictly before it calls `SetMarker` (locked), so by the time a PUT contends for `d.mu`, the on-disk record it wrote is already visible to any `want()` snapshot a concurrently-running `Sync` takes. The one remaining interleaving — `Sync`'s `want()` snapshot lands before the PUT's store write — is the one the plan calls out: `Sync` then correctly does nothing (the marker isn't there yet either), and the PUT creates the marker after `Sync` releases the lock; the next cycle converges. No interleaving loses a toggle. Phase 2's checklist pins a concrete test for exactly this ("a `SetMarker` issued while `Sync` holds the lock is never deleted by that cycle"). This is a sound, mutex-only fix requiring no shared lock with `netMu` — resolved.

**Gap 2 (destroy marker-removal placement).** The revised "Destroy" section now pins removal to ONE statement — "immediately BEFORE `sp.projects.Remove(p.ID)`, i.e. AFTER the optional wipe block and its `wipeFailed` early return" — and states the consequence plainly: a failed wipe keeps record, container state AND marker together. Verified against the actual code: `deleteProject` (`internal/httpapi/server.go:882`) reaches `sp.projects.Remove(p.ID)` at line 975, after the `wipeFailed` early-return block; the plan's insertion point is that exact statement, not a range. The failure-modes table and Phase 2 checklist both restate the same single point and the same wipeFailed consequence, so no residual ambiguity. Resolved.

### Full re-run: no new blocking gaps found

- Traced the marker's fate across the whole destroy sequence: `orch.Destroy` (which tears down the project's bridge) runs as the FIRST step of `deleteProject`'s goroutine, well before marker removal. So even in the residual scenario where a concurrent `Sync` tick reads the store before the record is removed (the window between marker removal and `sp.projects.Remove`) and re-creates the just-deleted marker, the underlying bridge interface is already gone — the root script's own desired-state computation would classify the project as `pending:no-bridge` and install no rule. The next `Sync` cycle (after the record disappears) deletes the resurrected marker. Benign, self-correcting, and consistent with the plan's own stated GC reasoning for a failed `SetMarker` call. Not a gap.
- Minor editorial leftover, not a design gap: "Surfaces touched" still lists `cmd/styrman/main.go (... idle-tick re-sync)`, which is the pre-fix phrasing round 1 flagged as ambiguous. The authoritative sections ("Boot / runtime reconciliation" and the Phase 2 checklist) both now say plainly "a DEDICATED `time.NewTicker(2 * time.Minute)` goroutine ... NOT the orchestrator's `RunIdleReaper`" — unambiguous and repeated twice. An implementer reading only the summary line could momentarily misread it, but the two authoritative sections resolve it without needing to ask the author. Noting it, not counting it as a question.
- Re-verified the file:line citations touched by this round's fixes and a sample of round 1's: `deleteProject` at `server.go:882`, `sp.projects.Remove(p.ID)` at `server.go:975`, `RunIdleReaper` at `orchestrator.go:1140`, `forEachProject` at `main.go:298`, `NetworkName`/`BridgeNameFor` in `config.go`, `SharedPorts` present in `store.go` but still absent from `api.ts`'s `Project` type, R12 text and its `ip_forward=0` claim, `network_mode: host` at `docker-compose.yml:20`, ADR-055 present in `DECISIONS.md`. All hold.
