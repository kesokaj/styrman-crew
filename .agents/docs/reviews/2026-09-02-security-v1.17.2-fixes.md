# Security review — v1.17.2 fix set (updater DOCKER_CONFIG + editor save path)   (2026-09-02)

Scope: uncommitted working tree at HEAD `36210ff` (v1.17.1) — `deploy/update/styrman-update`,
`deploy/update/styrman-update.service`, `web/src/lib/editorPane.ts`,
`web/src/components/{EditorPane,FileEditor,FileExplorer}.tsx`,
`web/src/routes/p.$project.$term.tsx`, `web/e2e/run.mjs`, rebuilt `web/dist/`.
Blast radius followed outward to `internal/files/files.go`, `internal/httpapi/{explorer,server}.go`
(the endpoints the changed client code drives), the installed unit/script on the host (read-only),
and the docker-CLI inputs a root `docker build` still reads.

## Verdict: FINDINGS (nothing blocking)

The worst thing here is an asymmetry, not a hole: `styrman-update` asserts root ownership and
non-group/world-writability for *every* root-executed input it consumes — the state dir, the deploy
clone, `deploy/.env` — except the one this change introduced. `DOCKER_CONFIG` is accepted verbatim
whenever it is already set (`[ -z "${DOCKER_CONFIG:-}" ]`, line 94) and it is a genuine
root-code-execution input: `config.json`'s `credsStore`/`credHelpers` cause the CLI to exec
`docker-credential-<name>` off `$PATH`, and `cliPluginsExtraDirs` causes `docker compose`/`docker
buildx` to load binaries from an arbitrary directory. In production that value comes from the unit
and is a systemd-managed per-run tmpfs, which I verified on the host, so there is nothing exploitable
today; the residual is hand-runs, drop-ins and any future ExecStart wrapper. The editor changes hold
up: I could not construct a cross-scope mis-save after the `docKey`/`key={docIdentity}` fix, the
failed-load revert genuinely re-syncs the store with what is on screen, `sanitizeRecents` is a proper
constructing parser whose output cannot escape `os.Root` or reach a managed subtree, chips are
React-escaped text with no HTML sink, and the `useBlocker` prompt has no trap state. Everything below
is low severity; none of it should hold the release.

## Findings

- **[low / confidence: high]** `deploy/update/styrman-update:94-98` — an inherited `DOCKER_CONFIG` is
  honoured without the ownership/mode assertion every other root-executed input in this script gets
  (compare the `STATE_DIR` guard at 118-122 and the `$DEPLOY_DIR/.git` guard). `config.json` under
  that directory drives root code execution at the `docker build` (line 361) and `docker compose
  build/up` (373-374) calls via `credsStore`/`credHelpers` (exec of `docker-credential-*`) and
  `cliPluginsExtraDirs` (arbitrary plugin binaries). Not exploitable in production — the unit pins a
  0700 tmpfs, verified above — but the guard is `-z`, not a trust assertion, so a group/world-writable
  value arriving from a drop-in, an operator shell, or a future wrapper would silently become a
  root-exec path with no complaint. Remediation: after resolving `DOCKER_CONFIG`, assert
  `stat -c %u` = 0 and `find -maxdepth 0 -perm /022` empty, exactly as `STATE_DIR` does; or ignore
  any inherited value that is not under `/run` and always mint a fresh per-run dir.
- **[low / confidence: high]** `deploy/update/styrman-update:95-97` — the fallback dir is created by
  `mktemp -d`, which honours an inherited `$TMPDIR`, and the cleanup is `trap ... EXIT` only. SIGTERM
  and SIGINT do run it (measured); SIGKILL and a hard power loss do not, leaving an empty 0700
  root-owned directory in `$TMPDIR`. Content leakage is nil (the dir is empty by construction), so
  this is litter plus a theoretical placement issue if root's env were ever tainted. Remediation
  (optional): create the dir under `/run` rather than `$TMPDIR`, so a reboot clears any leak.
- **[low / confidence: medium]** `web/src/components/FileExplorer.tsx:245,296` — the new
  `closeIfOpen(inDir(f.name))` sweep runs only *after* `await api.uploadFiles(...)` resolves, and it
  reconstructs the target path itself instead of using the server's answer. Two divergences follow.
  (a) The server writes `path.Join(dir, filepath.Base(part.FileName()))`
  (`internal/httpapi/explorer.go:260-264`) while the client computes `dir + "/" + f.name`; any
  `File.name` carrying a separator (a directory upload, a programmatic `File`) makes the two disagree
  and the pane holding the overwritten file is not closed. (b) `uploadFile` aborts the whole request
  on the first failing part *after* earlier parts are already on disk, so a partial upload throws,
  `tryUI` catches, and no pane is closed at all — a stale buffer then reverts a landed upload on the
  next Save, which with ADR-055 (no backups) is unrecoverable outside git. Remediation: the handler
  already returns `{"saved": [...]}` and the client discards it — close on that list, in a `finally`.
- **[low / confidence: high]** `web/src/components/FileExplorer.tsx:138-144` — `createError` is a
  client-side check against the last-loaded `entries`, so it is both bypassable and TOCTOU-racy: the
  `PUT .../file` endpoint is `O_CREATE|O_TRUNC` with no create-only variant
  (`internal/files/files.go:236-252`), so a raw API caller, or the UI itself when an agent or another
  terminal created the file since the last `load()`, still truncates silently. **Residual is
  data-loss only, not privilege**: the route resolves through `getProjectFor` (owner-scoped project
  lookup), writes go through `os.Root` confinement plus `cleanRel`, and `managedHomeTarget` blocks the
  managed subtrees — so the only file a caller can truncate this way is one they may already write.
  With no backup layer the loss is unrecoverable outside git, which is why it is worth naming rather
  than closing. Remediation: an `O_EXCL` create-only path (`?create=1` or a dedicated endpoint).
- **[low / confidence: high]** `web/src/components/FileEditor.tsx:97,124` — `docIdentity` and `docKey`
  are `${scope.kind}:${file.path}`; they omit `scope.project`, and `Scope` carries a project on both
  variants. Same-path-different-project is prevented only by `key={`${project}/${term}`}` on
  `<EditorPane>` in `p.$project.$term.tsx:190` — an invariant enforced in a different file from the
  one that depends on it, and exactly the shape of the bug finding 1 just fixed. No live mis-save:
  the key does remount, so the buffer cannot survive a project switch. Remediation (defence in
  depth): make the key `${scope.kind}:${scope.project}:${file.path}` so it is correct without help.
- **[low / confidence: medium]** `web/src/lib/editorPane.ts:118-124,183` — `canonicalPath` bounds
  length, rejects absolute/`.`/`..`/empty segments and dedups, but accepts NUL and other control
  characters and backslashes; and `openFileInPane` stores the **raw** path in the pane state while
  `noteRecent` stores the canonicalised one. Consequences are contained: a control-char path reaches
  `PUT/GET .../file` and dies at `os.Root` with EINVAL → a 400 toast (no traversal, `cleanRel` +
  `os.Root` + `managedHomeTarget` all hold), and no current caller passes a non-canonical path, so
  pane-vs-recents spellings cannot diverge today. But if one ever did, `matches()` would compare a
  canonical chip against a raw pane path and `closeFileInPane` would miss the pane — the same class of
  miss finding 3 closed. Remediation: reject control characters in `canonicalPath`, and run the
  pane's path through it in `openFileInPane` so one parser governs both sides.

## Non-findings I explicitly checked and cleared

- **Cross-scope save integrity (finding 1).** Traced `openFileInPane` → store `{scope, path}` →
  `EditorPane`'s load effect (its `same` check compares `path`, `scope.kind` **and** `scope.project`)
  → `useFileEditorState(loaded.req.scope, loaded.file)` → `save()` calling
  `api.saveFile(scope, file.path, text)`. Scope and content now come from the same `loaded` object, the
  render-phase reset is keyed on `scope.kind + file.path`, and `key={st.docIdentity}` forces CodeMirror
  to take a fresh initial document. `savedContent` is reset in the same render as `text`, so the dirty
  baseline cannot be inherited from the other scope. I found no path where a Ctrl+S lands on the wrong
  scope.
- **Failed-load revert (finding 5).** On `readFile` rejection the store is set back to `loaded.req`
  (or `null`), which is precisely what the render reads, so `closeFileInPane`'s `matches()` sees the
  on-screen file. `setFile(null)` with `loaded === null` also leaves `st` on `EMPTY`, whose
  `st.dirty` is false, and the publish effect writes that back — no stale `dirty:true`.
- **`sanitizeRecents` as a parsing boundary.** Output is a fresh `{scopeKind, path}` with foreign
  properties dropped, capped at 8 with the loop breaking on the cap; worst-case work is one linear
  pass over a blob bounded by the ~5 MB localStorage quota, once per project per page load (the
  `recents` Map caches it). Only same-origin JS can write that key.
- **XSS in the Recent strip.** `chipLabel()` output is a React *text child*; `title` and `aria-label`
  are attributes — all escaped. No `dangerouslySetInnerHTML` in `FileExplorer.tsx`. The one
  `dangerouslySetInnerHTML` in the diff's blast radius is the markdown preview
  (`FileEditor.tsx:389`); re-verified with the pinned `micromark@^4.0.2`:
  `[x](javascript:…)` compiles to `href=""` and raw `<img onerror=…>` is escaped, and the
  `replaceAll("<a href=", …)` rewrite cannot match escaped text.
- **`useBlocker` trap.** The `ConfirmDialog` is rendered unconditionally in the route body whenever
  `blocker.status === "blocked"`, with `proceed` on confirm and `reset` on both cancel and close, so
  there is no blocked-with-no-dialog state. The one stale-flag window — `pane.dirty` lives in the
  module store and outlives the route unmount — self-corrects on the next mount's publish effect, and
  even during that window the dialog is present and "Discard and leave" works.
- **Build artefacts.** The rebuilt `web/dist/` genuinely contains the source changes
  (`editor-path`, `editor-toggle-desc`, "already exists here" all present in
  `p._project._term-2BEKDnzH.js`), so the committed bundle is not stale relative to `src/`.

# Round 2 — security delta (2026-09-02)

Narrow scope as briefed: the `/run/*` acceptance in `deploy/update/styrman-update`, the
upload close-by-saved-name change (`web/src/lib/api.ts`, `web/src/components/FileExplorer.tsx`,
server side `internal/httpapi/explorer.go:236-277`), and the status of the six round-1 residuals.

## Verdict: FINDINGS (nothing blocking, nothing new above low)

The `/run/*` case statement is an improvement over `-z` but it is still a **path-shape check, not a
trust assertion** — and unlike `STATE_DIR` twenty lines below it, the accepted directory gets no
ownership or mode check. Measured on this host, `/run` contains directories that satisfy `/run/*`
and are writable by a non-root user: `/run/lock` is `drwxrwxrwt` (1777, sticky, world-writable) and
`/run/user/1000` is `drwx------ kesokaj:kesokaj`. Nothing is exploitable here — `sudo -l` for the
operator is `(ALL : ALL) NOPASSWD: ALL`, so there is no privilege boundary left to cross, and
`env_reset` is on so `DOCKER_CONFIG` is dropped unless `-E` is passed — but the guard's own stated
purpose ("close the `sudo -E` surface") is only met by host accident, not by the check. The upload
change is sound on the security axis: a hostile `saved[]` cannot traverse or cross scope; the two
residues there are a client crash on a `null` slice and the still-unclosed partial-upload path.

## Round-2 findings

- **[low / confidence: high]** `deploy/update/styrman-update:94-102` — the accepted branch trusts a
  **prefix**, not the directory. Compare `STATE_DIR` at lines 128-131, which asserts
  `stat -c %u` = 0 **and** `find -maxdepth 0 -perm /022` empty before trusting a far less dangerous
  input. `DOCKER_CONFIG` is a root-code-execution input (`config.json`'s `credsStore`/`credHelpers`
  → exec of `docker-credential-<name>` off `$PATH`; `cliPluginsExtraDirs` → arbitrary plugin
  binaries loaded by `docker compose`/`docker buildx`) consumed at the root `docker build` (line
  361) and `docker compose build/up` (373-374). Any non-root-writable `/run` subdir defeats the
  check: measured `/run/lock` (1777) and `/run/user/<uid>` (0700, uid-owned) both match `/run/*`.
  Exploitable in principle wherever the env var can be set by someone who is not already root —
  a narrowed sudoers (`NOPASSWD: /usr/local/bin/styrman-update` + `SETENV`), a systemd drop-in, or
  a future ExecStart wrapper. Not exploitable on **this** host (operator sudo is `ALL`).
  Remediation: keep the `/run/*` case, and inside it add the two `STATE_DIR` assertions to the

- **[low / confidence: high]** `web/src/lib/api.ts:459-465` + `web/src/components/FileExplorer.tsx:244,297`
  — the handler declares `var saved []string` and `writeJSON`s it, so a request in which **every**
  part is skipped by the base-name filter (`name == "" || "." || "/"`,
  `internal/httpapi/explorer.go:259-262`) returns `{"saved": null}`. `for (const name of r.saved)`

  and/or initialise `saved := []string{}` server-side; call `load()` in a `finally`.
- **[low / confidence: high]** `web/src/components/FileExplorer.tsx:241-249,294-300` — round-1

- **[low / confidence: medium]** `web/src/lib/editorPane.ts:222-241` — `closeFileInPane` drops the

  hazard it exists to fix, but it is unannounced data loss. Remediation (UX-side, optional): surface

## Assessed and cleared in round 2

- **Hostile `saved[]` → traversal or wrong-scope close: not reachable.** The server emits
  `filepath.Base(part.FileName())`, so an element can never contain `/` or be empty. The client
  wraps it as `inDir(name)` (current directory prefix, itself from the explorer's own state) and
  `closeIfOpen` pins `scope.kind` from the component's scope; `matches()` requires
  `entry.scopeKind === target.scopeKind` **and** exact path or `startsWith(target + "/")`. So a
  hostile element cannot address another scope, cannot climb out of the current directory, and
  cannot be a bare prefix of unrelated paths. The one filter gap — the handler skips `""`, `"."`,
  `"/"` but **not** `".."` — is contained on both sides: server-side `path.Clean("/"+path.Join(dir,
  ".."))` is anchored at `/` so the write target can only collapse to `""`/an in-root path (and
  `files.SaveStream` then fails), and client-side `inDir("..")` yields a path no pane holds, so the
  worst case is a **missed** close, never an over-close. An over-close would require a saved name
  equal to an existing sibling **directory** name, which `SaveStream` rejects before the name is
  appended to `saved`.
- **`mktemp` fallback + trap, re-verified in the new `case` form.** Single EXIT trap, single-quoted
  body evaluated at trap time, variable never reassigned after the trap is set, `set -u` aborts
  rather than expanding an unset value into `rm -rf /`. Runs on normal exit, on the `flock` skip
  path, and on SIGTERM/SIGINT (measured in round 1); still not on SIGKILL — see round-1 F2, which is
  unchanged and still only litters an empty 0700 root-owned dir under an inherited `$TMPDIR`.

# Round 3 — security delta (2026-09-02)

Narrow scope as briefed: `internal/httpapi/explorer.go` `uploadFile` (`saved := []string{}` + the
`uploadErr` closure), the `/run/*` ownership/mode assertion in `deploy/update/styrman-update`, a
read-only host re-check, and the residual list for the changelog. Blast radius followed to
`internal/files/files.go` (`SaveStream` → `openRoot` → `os.Root`), `web/src/lib/api.ts`
`uploadFiles`, `FileExplorer.upload`, `evictFromPanes`, and — because Go is in the diff for the
first time this cycle — the module graph via `govulncheck`.

## Verdict: FINDINGS (nothing blocking; both round-2 highlights are closed)

The worst thing in round 3 is that the handler's own comment overstates what it delivers: it says
`saved` is "reported on EVERY exit", but the `mr.NextPart()` failure branch
(`internal/httpapi/explorer.go:268`) still calls `writeErr` and **discards** the list — and that is
the branch a truncated body, a malformed boundary, or the 512 MiB `MaxBytesReader` cap actually
lands on. So F3b is narrowed to the rarer failures, not closed. On the questions asked: I found
**no information disclosure** in the new error body (every element of `saved` is
`filepath.Base(part.FileName())` — bytes the caller itself sent, echoed back to the same
owner-scoped principal; both new messages are compile-time constants), **no change to the
authz/confinement path** (`scopeFor`, `managedHomeTarget`, `scopeRel`, `files.cleanRel` and the
`os.Root` confinement are untouched — the diff is two hunks, neither of them a guard), and
**reporting partial progress is not a problem for any threat model here** — it is data the client
originated, and withholding it is the *more* dangerous option, because a pane holding a pre-upload
buffer then overwrites a landed upload on Save with no backup layer (ADR-055). On the updater: the
**hard fail is the right call and I withdraw my fail-closed-to-mktemp proposal** (reasoning below),
and the round-2 counter-examples are measurably dead — `/run/lock/*` and `/run/user/1000/*` are now
rejected. `realpath -m` is still warranted, for a reason that is not the one round 3 assumed.

## (1) `uploadFile` — information disclosure, confinement, partial progress

- **Disclosure: none.** `saved` is built only at `explorer.go:286` from
  `filepath.Base(part.FileName())`, i.e. the caller's own `Content-Disposition` filenames,
  base-named. No server path, no `errno`, no filesystem state, no other tenant's data can enter it.
  The two messages routed through `uploadErr` are constants (`"path is managed by styrman"`,
  `"cannot save upload"`) — the 500 in particular does **not** wrap the `SaveStream` error, so
  ENOSPC/EISDIR/EACCES are not distinguishable from the body. Recipient is the same authenticated,
  owner-scoped principal who sent the parts.
- **Reflection is not a sink.** `writeJSON` sets `Content-Type: application/json` and Go's encoder
  escapes; the client renders the message and the names as React text. The endpoint is POST-only
  behind `csrfGuard`, so a hostile filename cannot be reflected into a top-level navigation.
  (Pre-existing, unchanged, out of scope: no `X-Content-Type-Options: nosniff` anywhere in
  `internal/httpapi`.)
- **Confinement path unchanged.** Verified by reading, not assuming: `scopeFor` (`explorer.go:34`)
  still resolves `who(r)` → `sp.projects.Get(id)` → `ProjectHome`/`ProjectWorkspace`;
  `managedHomeTarget` (`explorer.go:102`) is byte-identical and still runs **per part, before**
  `SaveStream`; the target is still `strings.TrimPrefix(path.Clean("/"+path.Join(dir, name)), "/")`;
  `files.SaveStream` still goes through `openRoot`/`os.OpenRoot`. `internal/files/files.go` is not
  in the diff at all. The `uploadErr` closure captures the `saved` **variable** (not a copy), so
  `append` reassignment is visible to it — the new test proves this end-to-end (400 body carries
  `saved:["a.txt"]` and `a.txt` is really on disk).
- **Partial progress: correct, and the safer default.** The alternative (report nothing) is what
  round-1 F3b flagged as unrecoverable data loss. There is no confused-deputy angle: `saved` grants
  no authority, it only names panes to evict, and `matches()` still pins `scopeKind` plus an exact
  path or a `path + "/"` prefix, so a hostile element cannot address another scope or climb out of
  the current directory (re-verified from round 2; the element can never contain `/` because it is
  `filepath.Base`d).
- **Client side now consumes it correctly**, which is what makes the server change worth anything:
  `api.uploadFiles` no longer throws (`web/src/lib/api.ts:458-472`), parses defensively
  (`res.json().catch(() => ({}))`, `body.saved ?? []`), and `FileExplorer.upload:164-170` evicts on
  every reported name, calls `load()`, and only then rethrows. **Round-2 findings 2 and 3 are
  closed.**

## (2) `styrman-update` — verdict on hard fail, and on `realpath -m`

**Hard fail vs fail-closed-to-mktemp: reviewer r3 is right, and I withdraw my proposal.** Three
reasons, the third decisive:

1. The condition being detected is not "no docker config available" — it is "root's environment is
   making a claim about a directory that does not hold up". Silently recovering converts a
   tamper signal into a no-op, and the same tainted environment plausibly taints `$PATH`,
   `$TMPDIR` and everything else this root script reads.
2. Under the timer the value comes from the unit. If `RuntimeDirectory` ever stopped being root
   0700, a silent mktemp fallback would mask a host misconfiguration the operator must fix; a
   failed oneshot is visible in `systemctl --failed` and the journal.
3. **The fallback is itself env-influenced.** `mktemp -d` honours an inherited `$TMPDIR` (my own
   round-1 F2). Falling closed *to* mktemp would fall from one attacker-influenceable variable to
   another — not a fail-closed at all. The `*)` branch is fine where it is, because there the
   environment is making no claim.

Placement checked: the block is at lines 97-116, i.e. **before** the `flock` and before any state
mutation, so a hard fail leaves no partial state and cannot wedge the lock. `fail()` (line 69)
writes to stderr and `exit 1`; it prints the path, never a token or a config value.

**`realpath -m` before the `case`: yes, warranted — but not for the reason implied.** Measured
(read-only extraction of the guard block, run against real host paths — no side effects, the
snippet only calls `dirname`/`stat`/`find`):

| `DOCKER_CONFIG` | round-3 result |
|---|---|
| `/run/styrman-update/docker` | ACCEPT (asserted on `/run`) |
| `/run/lock/evil` | **REJECT** — group/world-writable (`/run/lock` is 1777) |
| `/run/user/1000/evil` | **REJECT** — not root-owned |
| `/run/../etc/x` | ACCEPT (asserted on `/run/../etc`) |
| `/run/..` | ACCEPT (asserted on `/run/..`, i.e. `/`) |
| `/run/../home/kesokaj/evil` | **REJECT** — not root-owned |
| `/tmp/evil`, unset | FALLBACK to mktemp |

So the ownership+mode assertion does all the real work and the traversal cannot reach
attacker-controlled content: every accepted target is root-owned and not group/world-writable, so
only root can place a `config.json` there. What the traversal **does** break is the change's other
invariant — *ephemerality*. A value outside `/run` is not systemd-managed, is never wiped, and the
accept branch registers **no cleanup trap**, so root's docker config would persist at e.g. `/etc/x`
(or be read from `/config.json` for `/run/..`) and accrete root-executed docker state across runs —
exactly what this change exists to eliminate. Two caveats if `realpath -m` is added: assert **and
export** the resolved value (otherwise the check and the use diverge), and re-apply the `/run`
prefix test *after* resolution. Note it also changes symlink semantics in a small way: today a
symlinked `DOCKER_CONFIG` fails closed for free, because `find -P` reports the link itself and every
symlink is `lrwxrwxrwx`, so `-perm /022` matches; after resolution the target is judged instead.
That is acceptable (the target must still be root-owned), but it should be a deliberate choice.

## Round-3 findings

- **[low / confidence: high]** `internal/httpapi/explorer.go:263-269` — the `mr.NextPart()` failure
  branch still calls `writeErr(w, 400, err)` and drops the accumulated `saved`, contradicting the
  comment at 250-253 ("reported on EVERY exit"). This is the branch reached by a truncated or
  malformed multipart body and by the 512 MiB `MaxBytesReader` cap (`server.go:486-487`) — the most
  likely mid-stream failures — so the F3b hazard (stale pane buffer overwrites a landed upload,
  unrecoverable under ADR-055) survives for exactly those cases. It is also the only place in this
  handler where a raw `err.Error()` reaches the client; multipart/textproto error text can embed
  request-supplied bytes (cf. GO-2026-5039, fixed in the pinned 1.25.13 builder), and while it is
  JSON-escaped and rendered as React text so there is no sink, a constant message would match the
  other two exits. Remediation: route that branch through `uploadErr` with a constant message.
- **[low / confidence: high]** `web/src/lib/api.ts:451` — even with the handler perfect, a `fetch`
  rejection (connection dropped mid-upload) produces no response at all, so parts that landed are
  never reported and nothing is evicted. Same residual class as above; unavoidable in-band.
  Remediation (cheap): on a thrown `fetch`, have `FileExplorer.upload` evict the *attempted* names
  as a conservative fallback, or simply `load()` in a `finally` so the listing is at least honest.
- **[low / confidence: medium]** `deploy/update/styrman-update:97-98` — the `case` remains lexical:
  measured, `/run/../etc/x` and `/run/..` are ACCEPTED. Not an attacker-content path (the ownership
  assertion holds), but it defeats the ephemerality invariant — an accepted non-`/run` directory is
  never wiped and the accept branch registers no cleanup trap, so root-executed docker config and
  cli-plugin state would persist there across runs. Remediation: `realpath -m` before the `case`,
  assert and export the resolved value, re-test the `/run` prefix after resolution (caveats above).
- **[low / confidence: low]** `deploy/update/styrman-update:103-108` — the assertion covers only the
  **nearest existing** directory, not every component of the path. On a layout where a root-owned
  0700 leaf sits inside a non-root-owned parent, the parent's owner can rename the leaf away and
  swap in their own between the check and docker's use (classic TOCTOU); the walk at line 104 never
  looks above the first existing directory. Not reachable on this host and it requires an odd
  pre-existing layout. Remediation if cheap: assert every component from `/` down, or require the
  value to equal the unit's `${RUNTIME_DIRECTORY}/docker`.
- **[low / confidence: medium]** dependencies — `github.com/docker/docker@v28.5.2+incompatible`
  carries **GO-2026-4887** (AuthZ plugin bypass on oversized request bodies) and **GO-2026-4883**
  (off-by-one in plugin privilege validation), both **`Fixed in: N/A`** — no upgrade exists. Both
  are moby **daemon** bugs; govulncheck reaches them only through package `init` traces (the
  `+incompatible` module ships daemon code alongside the client), and this binary is a docker
  *client* that runs no AuthZ plugin. Judged not exploitable from our code, but it is an accepted,
  unfixable-today residual that must be re-checked every release rather than filtered out.
- **[low / confidence: high]** tooling — `govulncheck ./...` on this host reports **31 called
  vulnerabilities**, because the host toolchain is **go1.25.0** while `deploy/Dockerfile.server:9`
  pins **`golang:1.25.13-trixie`**. The **shipped artifact is not affected**: every stdlib fix
  listed is ≤ go1.25.13, and `git tag --contains cbd8b05` shows the pin is present in v1.16.1,
  v1.17.0 and v1.17.1 — the deployed version. Two of the 31 are worth naming because they land
  precisely on this diff's blast radius: **GO-2026-4970** (root escape via symlink plus trailing
  slash in `os`, fixed 1.25.12) and **GO-2026-4602** (`FileInfo` can escape from a `Root`, fixed
  1.25.8) — `os.Root` *is* the confinement every "cannot escape" clearance in rounds 1-3 rests on
  (`internal/files/files.go:53`), and a guest with a shell can trivially plant symlinks in its own
  workspace. The finding is therefore about the **gate, not the artifact**: local `go test` and any
  local verification run on a vulnerable stdlib, and a 31-line noise floor is where a future real
  advisory will hide. Remediation: run `govulncheck` inside the builder image (or bump the host
  toolchain to the pinned patch) so the security gate measures what actually ships.
