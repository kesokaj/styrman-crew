# Security review — sh-agent release binary replaces the harness channel   (2026-09-21)

Range reviewed: working tree vs HEAD (`589f424`) — `git diff HEAD` plus the staged
deletions from `git status --short`: the whole `image/harness/` mirror (155 files),
`deploy/update/styrman-harness-update.{service,timer}`, four Go test files
(`internal/config/harnessdir_test.go`, `styrman_ctl_harness_test.go`,
`styrman_harness_test.go`, `internal/orchestrator/harness_test.go`) and
`.agents/docs/testing/styrman/make-scratch-harness.sh`.

## Status: COMPLETE

## Verdict: FINDINGS (worst: medium)

No secret leaks, no injection, no guest escalation. The token handling is careful
everywhere — `--secret` at every build site, never `--build-arg`, never on argv —
and the signature chain in the Dockerfile is not bypassable without the signing
key. The worst problem is a **supply-chain pin regression**: what runs inside every
project VM is now a prebuilt binary named only by a MUTABLE tag
(`ARG HARNESS_VERSION=v1.6.0`), with no expected content hash anywhere in the
repository, replacing a vendored source tree pinned by commit plus a 155-line
`SHA256SUMS`. Two builds of the same crew commit can install two different
binaries with no diff in styrman-crew to show it. That breaks the repo's own
standard, which digest-pins every base image (`debian:trixie@sha256:…`). Second
is that the harness *content* — the instructions every agent in every project VM
follows, the platform's highest-leverage prompt-injection surface — has left the
review boundary entirely.

## Findings

- **[medium / confidence: high]** `image/Dockerfile:146-159` — **the harness is pinned by a mutable tag, not by content.** `ARG HARNESS_VERSION=v1.6.0` drives `gh release download "${HARNESS_VERSION}" --repo kesokaj/styrman-harness`, and the only content assertion is the *release's own* signed `SHA256SUMS`. GitHub release assets can be deleted and re-uploaded and tags can be moved; the signature proves only that the signing key signed *some* sums file naming that version. So the same crew commit, built twice, can install two different `sh-agent` binaries into every project VM — and neither `git diff`, `verify-commit.sh` (which compares only the reported version string, `deploy/verify-commit.sh:105-109`) nor the Tier 2 checks would show it. The old design pinned `harness/COMMIT` plus a full `SHA256SUMS` of the vendored tree, and the same Dockerfile digest-pins both its FROM lines. Remediation, no new dependency: add `ARG HARNESS_SHA256=<sha of sh-agent-linux-amd64>` beside `HARNESS_VERSION` and assert it directly — `printf '%s  sh-agent-linux-amd64\n' "${HARNESS_SHA256}" | sha256sum -c -` — *in addition to* the signature, and have `image/bump-pins.sh` refresh it the way it refreshes the base digests. The repository then pins content, and a re-uploaded asset fails the build instead of shipping silently.

- **[medium / confidence: medium]** `image/harness/` (deleted, 155 files) — **the harness content has left the review boundary.** Every skill, agent definition and context file that *instructs* the agents running in every project VM used to be in the diff and reviewable; it is now inside an opaque binary, and what a reviewer of a styrman-crew change can see about it is a version string. `deploy/verify-commit.sh:113` prints only the skill and subagent *counts*, and the new Tier 2 check (`integration.sh`, "skills and agy agents seeded equal the binary's inventory") compares counts as well — no check in this repository reads what those files say. This is ADR-074's deliberate trade, so it belongs on the record as an accepted risk rather than a defect; but it should be accepted explicitly, with the mitigation named: the content pin from the finding above, plus a documented rule that a `HARNESS_VERSION` bump is reviewed against the styrman-harness release diff before it lands here. Without that, a compromise or a mistake upstream reaches every tenant's agent with no signal in crew.

- **[low / confidence: high]** `image/entrypoint.sh:144-145, 193-196, 220-224` — **an unreadable `sh-agent` silently disables the harness and still logs the boot pass signal.** When `/styrman/bin/sh-agent version` fails, `HARNESS_REL=unknown`; `sort -V` ranks any `vX.Y.Z` above `unknown` (verified: `printf 'unknown\nv1.6.0\n' | sort -V | tail -1` → `v1.6.0`), so the never-downgrade guard fires for *any* home that records an embedded release, the install is skipped, `HI_OK` stays `1`, the stamp `${HARNESS_VER}+unknown` is written, and the block logs `agent harness deployed (version …, sh-agent unknown; …)`. The stamp then suppresses every later retry. That contradicts the design stated three lines above it ("the stamp is written only when EVERY step succeeds, so a failure is retried next boot"). Concrete path to it: a container created under v1.35.0 still carries ADR-073's read-only bind of `/var/lib/styrman/harness/current/bin/sh-agent`, and the code that dropped those binds is deleted in this diff; if the image-upgrade recreate at `internal/orchestrator/orchestrator.go:298-311` does not fire (its `ImageInspect(cfg.Image)` fails, or the tag resolves to the same image), Docker re-resolves the now-absent source and creates it as a root-owned *directory* — `[ -x /styrman/bin/sh-agent ]` is true for a 0755 directory, `version` fails, and the project keeps its old harness forever while the log says "deployed". Remediation: add `[ "${HARNESS_REL}" != unknown ]` to the guard's condition so an unreadable binary always takes the install path, and set `HI_OK=0` when the release cannot be read so the WARN fires and the stamp is withheld.

- **[low / confidence: high]** `deploy/update/styrman-update:182` — **`TRUST_UID` is read from the ambient environment on the production path.** The test hook itself is sound: `__retire-harness-units` is refused without `STYRMAN_UPDATE_TEST=1` (line 220), and `internal/config/styrman_update_test.go` asserts that refusal *and* that the refused hook removed nothing. But `TRUST_UID` is never initialised outside the hook, so `${TRUST_UID:-0}` in the unit-dir guard picks up an exported `TRUST_UID` from the updater's environment and lowers the ownership bar for a root `rm`. Reaching it requires control of root's environment (`sudo -E`, an edited unit), so it is not an escalation path on its own — it is a guard whose value can be set by something other than the code meant to set it, exactly the seam this script closes explicitly elsewhere (the `DOCKER_CONFIG` inheritance block, lines ~275-300, refuses an inherited value for this reason). Remediation: `TRUST_UID=0` next to `trusted_dir()`, above the test-hook block; the hook's own assignment already overrides it.

- **[low / confidence: medium]** `deploy/host-setup.sh` (`[ -f /etc/styrman/gh-token ]` branch), `deploy/styrman-ctl:475`, `deploy/verify-commit.sh:15-16` — **the new token-file readers skip the bar the updater sets for itself.** All three hand `/etc/styrman/gh-token` to `docker build --secret …,src=…` after nothing more than an existence test. The updater asserts root ownership and no group/world access on the same file at `deploy/update/styrman-update:376-379`, with the message "refusing to authenticate with a token another user controls". The impact of the gap is token *substitution* in a root-run build, not code execution (the signature check still gates the binary), but a root process authenticating with a credential it did not vet is the thing that assertion exists to prevent, and the file now has a second consumer. Remediation: lift the updater's two-line check (`stat -c %u` = 0, `find -perm /077` empty) into each site — or into a shared helper — before the `src=` form is used.

- **[low / confidence: medium]** `.agents/docs/testing/styrman/ensure-test-image.sh:48-54`, `deploy/verify-commit.sh:13-21` — **`export GH_TOKEN` from `gh auth token` widens a broad developer credential across the whole run.** `gh auth token` on a developer box returns the `gh auth login` OAuth token, typically scoped `repo`/`read:org`/`workflow`/`gist` — far beyond "read kesokaj/styrman-harness" — and `export` puts it in the environment of every child of the script, including the docker CLI subtree and, through `integration.sh`, the steps that boot project VMs. I checked `deploy/docker-compose.yml` for bare-name environment passthrough and found none, so nothing in this diff carries it into a guest: this is exposure surface, not a leak. Remediation: drop the `export` and set the variable only on the one command that needs it (`GH_TOKEN="$t" docker build --secret id=gh_token,env=GH_TOKEN …` — BuildKit reads it from the child's environment), or write it to a 0600 file under `.agents/scratch/` and use `src=`; and recommend a fine-grained token scoped to the one repo over `gh auth token` in the FATAL message's advice.

- **[low / confidence: high]** `deploy/update/styrman-update:194-198` + `internal/config/styrman_update_test.go` — **the `--check` mode of the root delete step is untested, and so is the unit-dir refusal.** By reading, `--check` is correct: `[ "${CHECK_ONLY}" = true ] && return 0` sits above the four `rm -f`s on `${STATE_DIR}`, and the unit loop logs "would remove". But the test hook hardcodes `CHECK_ONLY=false` (line 222), so the hook cannot express the read-only run and nothing asserts that `--check` removes nothing; likewise the "missing, not root-owned, or group/world-writable" refusal is never exercised in its must-fail state (the hook sets `TRUST_UID="$(id -u)"`, which always satisfies it). The project's own rule is that a check is validated once in the must-pass and once in the must-fail state. Remediation: give the hook an optional fourth argument that sets `CHECK_ONLY=true`, and add two cases — `--check` leaves both units and all four state files in place; a 0777 unit dir produces the WARN and removes nothing.

- **[low / confidence: medium]** `image/entrypoint.sh:193` — **the guest-writable manifest is read without the timeout its neighbours carry.** `sed -n … "${HOME_DIR}/.config/sh-agent/state.json"` reads a path the project's own root can replace, and the block's comment two dozen lines above states the rule it breaks: "this block sits ahead of `/run/styrman/ready` and the home is user-controlled, so a stall here must never brick a boot" — which is why `harness-migrate.sh`, the install and the two MCP registrations are each wrapped in `timeout 20`. A FIFO at that path blocks the entrypoint indefinitely before the ready marker. It is self-inflicted (only that project's guest and the server can write there) and `ContainerStart` does not wait on the entrypoint, so the blast radius is the project's own VM never becoming ready — but it is a new uncapped read of a user-controlled path on a path the design says must never stall. Remediation: `timeout 5 sed -n …`, matching the neighbours.

### Trust model: what is weaker, equal, stronger

**Weaker.** (1) A prebuilt binary is trusted where source was previously built locally in a pinned builder from a vendored, reviewable tree — findings 1 and 2. (2) The pin is a mutable tag rather than a commit plus content hashes. (3) The host's `/etc/styrman/gh-token`, until now documented as "this repo only, Contents: Read-only" (`styrman-update:395`), must now also read a *second, private* repo, and is mounted into a build container that runs `gh` — a real scope widening of a root-held credential. (4) The entrypoint advertises an in-guest `sh-agent update` using "gh via the broker's token": a self-update path inside a VM whose user is root, authenticated with a credential that must read the operator's private repository. No code for it is in this diff, and the guest could always run arbitrary code in its own VM, so this is not an escalation — but it makes "a credential that reads `kesokaj/styrman-harness` is present in every project VM" a design expectation, which deserves an explicit decision about *which* token that is.

**Equal.** Verification happens once, at export/build time, in both designs; neither re-verifies at boot. The signing key and the `ssh-keygen -Y verify` primitive are the same. The image's binary is root-owned and not guest-writable, as the mounted export was.

**Stronger.** Far less root machinery on the host: a root timer that fetched, walked tags, built Go offline, smoke-tested and swapped a directory under `/var/lib/styrman` is gone, along with its bind mounts into guests and their recreate logic — about 900 lines of root-path and orchestrator code deleted, and with them the symlinked-content-dir, foreign-owner, half-export and stale-bind failure classes the old reviews kept finding. The signer is now visible in `docker history` as an ARG, so a substituted key is auditable. The retire step is idempotent, runs on every tick outside the firewall guards (the BUG-035/BUG-064 lesson applied correctly), and its removals are two fixed filenames inside a directory asserted root-owned and not group/world-writable, so no symlink or path injection is reachable there; `rm -f` on the four state files removes a symlink, never its target.

### Verified clean (not findings)

- **No token on argv, no token in a layer.** Every build site uses `--secret` (`env=` or `src=`); no `--build-arg` carries a token anywhere in the diff. `docker history` records only `HARNESS_VERSION` and `HARNESS_SIGNER` (an ed25519 *public* key — committing it is correct, and its presence in image metadata is a plus). The download, `allowed_signers`, the sums and the signature all live in one `mktemp -d` created and `rm -r`'d inside the single RUN, so nothing lands in a layer; the token is only ever read from `/run/secrets/gh_token`. `required=true` fails the build when the secret is absent.
- **No ARG injection.** `RUN` in shell form is *not* subject to Dockerfile variable substitution — ARG values arrive as environment variables of `/bin/sh` — and every use is double-quoted: `printf '%s\n' "${HARNESS_SIGNER}"`, `-I "${HARNESS_SIGNER%% *}"`, `grep -qxF "# styrman-harness ${HARNESS_VERSION}"`, `test "$(…)" = "sh-agent ${HARNESS_VERSION}"`. There is no `sh -c` re-interpolation of either value.
- **No wrong-host risk.** `--repo kesokaj/styrman-harness` is a literal; the Dockerfile declares no `ARG GH_HOST`/`GH_ENTERPRISE_TOKEN`, and `--build-arg` for an undeclared ARG does not reach the RUN environment, so the documented build commands cannot redirect the token to another host.
- **The signature chain does not have a bypass I can construct without the key.** `ssh-keygen -Y verify` runs with a pinned namespace (`-n sh-agent-release`); `-I` is derived from the same ARG line, so the identity check is tautological and the real anchor is the public key in the ARG default. `grep -qxF "# styrman-harness ${HARNESS_VERSION}"` closes the genuinely-signed-but-older-release replay. `sha256sum -c - --ignore-missing` fails closed when nothing was verified (GNU coreutils exits non-zero with "no file was verified"), which is exactly the case a signed sums file omitting the linux asset would produce — so `--ignore-missing` opens nothing. The binary is checksum-verified before it is executed for the version check. `verify-commit.sh:105` enforces the canonical `vX.Y.Z` shape of `HARNESS_VERSION` at release-verification time (the Dockerfile itself does not).
- **The guest cannot turn `state.json` into anything but a skip.** `sed -n 's/^ *"repo": *"embedded:\(v[0-9][0-9.]*\)".*/\1/p' … | head -1` captures `v` plus digits and dots only; the value is used in two `[` comparisons, a `printf | sort -V` pipeline and a `log` line, all double-quoted — no command execution, no path construction. The worst outcome is a guest pinning its own project's harness, and the guest is already root in that VM with write access to `~/.claude`, so the guard grants no new capability. Homes are per project per user (`/var/lib/styrman/homes/<u>/p/<uuid>` bound to `/home/${USERNAME}`), so one project cannot pin or downgrade another project's or another user's harness. The `HARNESS_REL=unknown` case is the one place the guard misbehaves — finding 3, and that one is not guest-triggered.
- **Orchestrator after the mount removal.** `HarnessDir` is gone from `config.Config`, `harnessBinds` is gone from `createSpec`, and `create` appends nothing beyond the home and workspace binds. No host path is bound into guests by the new code. Stopped containers from v1.35.0 lose their stale ADR-073 binds through the image-upgrade recreate (`orchestrator.go:298-311`) since this release ships a new image version; a *running* container keeps them until its next stop/start, which is how every image upgrade has always behaved. The residual is finding 3's scenario.
- **Never-downgrade is covered by Tier 2**, including the planted `embedded:v99.0.0` manifest, the "left alone" log line, the untouched home binary (sha compared) and the rewritten stamp (`integration.sh`, new checks).

## Checked

- **Secrets** — no credential, key or token literal added anywhere in the diff (`grep` for `ghp_`/`github_pat_`/PEM headers over added lines: 0 hits). The only committed key material is the ed25519 *public* key in `HARNESS_SIGNER`. Token never on argv, never in a layer, never echoed: `styrman-ctl`'s `run` prints `--secret id=gh_token,env=GH_TOKEN`, not a value; the token file is installed `install -m 600 -o root -g root` and written under `umask 077`. Findings 5 and 6 are about *reading* the token, not about leaking it.
- **Injection** — Dockerfile RUN shell-expansion of both ARGs, the entrypoint's `sed`-derived `HOME_REL`, and the updater's `${u}`/`${f}` loops all reviewed; every interpolation is double-quoted and every guest-derived value has a digits-and-dots grammar. No `eval`, no `sh -c` with an interpolated value, no SQL, no template surface in scope.
- **Authz/authn** — no HTTP route, middleware or identity code in the diff. The privilege boundaries touched are: root in the updater (findings 4, 7) and guest-root in the VM (finding 3 and the `state.json` analysis). Per-user/per-project home isolation re-confirmed for the new guard.
- **Crypto** — nothing hand-rolled. `ssh-keygen -Y verify` (OpenSSH) with a pinned namespace and a pinned public key, and `sha256sum` from coreutils; both used as designed. No new primitive, protocol, token or session format. The change *removes* a hand-maintained verification pipeline rather than adding one.
- **Dependencies** — none added: `go.mod`, `go.sum`, `deploy/caddy/ingress/go.{mod,sum}`, `web/package.json` and `web/package-lock.json` are all unchanged (confirmed, not assumed). One new *runtime* dependency of the build: GitHub Releases reachability plus `gh` (already installed in the image at `image/Dockerfile:39`). `govulncheck ./...` ran locally (go1.27.1, module declares go 1.25.0) and exited 0 with **2 vulnerabilities reaching called code, both in `github.com/docker/docker@v28.5.2+incompatible`: GO-2026-4887 and GO-2026-4883, both "Fixed in: N/A"** — pre-existing, unrelated to this diff, no upstream fix to take; worth an eye on the docker module's next release. - **GCP surface** — none. Self-hosted platform; `.agents/docs/deploy/gcp.md` records GCP as not applicable, and nothing in the diff touches IAM, Cloud Run or Secret Manager.

Written by the author, 2026-09-21.

1. Mutable-tag pin (medium) — REBUTTED, accepted risk recorded in ADR-074's consequences: the content pin is the operator's signature on the release's `SHA256SUMS`, whose header names the version the Dockerfile asked for; a re-uploaded asset under the same tag needs that signing key, and the harness's own release rule forbids moving a pushed tag (a bad release gets the next PATCH). A `HARNESS_SHA256` ARG with a `bump-pins.sh` refresh was offered to the operator on 2026-09-21 and struck ("This sounds excessive … don't complicate things"); `verify-commit.sh` compares the version the signed sums bind.
2. Harness content outside the review boundary (medium) — ACCEPTED explicitly in ADR-074's consequences: the harness is reviewed in its own repository's gate (ADR-073 already accepted this trade); a `HARNESS_VERSION` bump names the harness release in its changelog entry and is read against that release's notes before it lands (`specs/styrman/versioning.md` step 1).
3. `HARNESS_REL=unknown` wins the guard (low) — FIXED: the comparison is now `harness_home_newer <home> <image>`, true only when BOTH are canonical `vX.Y.Z` and the home's is strictly newer; an `unknown` image release takes a WARN path (`HI_OK=0`, no install, no stamp, retried next boot). Test on the finding's trigger: `TestEntrypointHarnessHomeNewer` (internal/config/entrypoint_guard_test.go) extracts the function from the entrypoint and asserts `(v9.9.9, unknown)` is false; must-fail proven: with the image-side canonical check deleted, that case returned true.
4. `TRUST_UID` from the ambient environment (low) — FIXED: `TRUST_UID=0` is set on the production path right after the test-hook block; only the hook assigns it otherwise.
5. Token-file readers skip the updater's bar (low) — FIXED: `host-setup.sh` and `verify-commit.sh` assert root ownership and no group/world access before using `/etc/styrman/gh-token` (the `verify-commit.sh` site was missed in the first pass and caught by the round-2 code review); `styrman-ctl install` runs `private_file` on it; `styrman-update deploy()` reads `GH_TOKEN_FILE`, already checked in its preamble.
6. `export GH_TOKEN` widens the token (low) — FIXED: `verify-commit.sh` and `ensure-test-image.sh` keep the token in a local variable, `unset GH_TOKEN`, and set it only on the docker build command (a temporary environment for that one call); the FATAL messages recommend a fine-grained token that reads only `kesokaj/styrman-harness`.
7. `--check` and the unit-dir refusal untested (low) — FIXED: the test hook takes an optional `--check`; `TestStyrmanUpdateRetiresHarnessUnits` gained two cases — `--check` leaves both units and all four state files and calls no `systemctl`; a 0777 unit dir logs `harness-retire skipped` and removes nothing. Must-fail proven: with the `--check` early return deleted, the state file was removed under `--check`.
8. Uncapped `sed` on the guest-writable manifest (low) — FIXED: the manifest is read only when it is a regular file and not a symlink, under `timeout 5`.
