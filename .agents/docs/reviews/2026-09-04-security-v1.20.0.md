# Security review — v1.20.0 release gate (whole range)   (2026-09-04)

Range reviewed: v1.19.1..d24fe40

Scope: the whole tag range as one change, not the pieces again. Prior reports read and
each open item re-checked against HEAD: `reviews/2026-09-03-security-fail-to-fetch.md`,
`…-harness-phase1.md`, `…-phase2.md`, `…-phase3.md` (3 rounds, not converged),
`reviews/2026-09-04-security-session-lifetime.md`, and `bugs/BUG-001..003`.
Blast radius followed outward from the diff: `internal/orchestrator` (every Docker bind
source), `internal/files` (`Trust`/`openRoot` and all `files.*` callers),
`cmd/styrman/main.go` (the root janitor and the two migrations), `internal/httpapi`
(`setup.go` roster, `explorer.go`, `credentials.go`, `server.go` create/delete),
`internal/history`, `internal/project` (Dir/UUID validation), `image/entrypoint.sh` +
`image/configs/harness-migrate.sh` (the boot path of every project VM), `image/harness`
(third Go module), `deploy/caddy/ingress` (session lifetime), `web/src/lib/api.ts`
(session expiry), and the release gates `deploy/verify-commit.sh` / `deploy/vulncheck.sh`.

## Verdict: FINDINGS (nothing release-blocking)

**Blocking: no.**

The post-round-3 orchestrator fix is correct and it closes the round-3 high: `realBelow`
is no longer create-only. What is left at HEAD is a genuine but narrower residual — the
check at `orchestrator.go:226` is a sequence of `Lstat`s, and Docker resolves the bind
source again at `ContainerStart`/`ContainerCreate`, so a tenant who keeps a setup VM
running and swaps `~/p/<uuid>` in a loop while repeatedly stopping and starting a project
can still win the race and get an arbitrary host path mounted as `$HOME` in a microVM
where they are root. That is materially *less* exposure than v1.19.1 shipped (where the
start path had no check at all and no race was needed), it is exactly what BUG-003 now
records as its residual, and the durable fix (un-nesting project homes) is already an
open ADR proposal for the operator in `TODO.md`. Everything else I found is low: two
host-side `MkdirAll`s that were not swept by BUG-003's own prevention rule, four
previously accepted lows that exist in review files but in no actionable list, and one
runbook omission. No secrets, no injection, no authz regression, no hand-rolled crypto,
no new dependency anywhere in the range.

## Findings

- **[medium / confidence: high]** `internal/orchestrator/orchestrator.go:226` (guard) vs
  `:234`, `:239` (start) and `:829` (create) — **the check is not atomic with Docker's own
  resolution, and the walk itself is not atomic either.** `projectHomeIsReal` →
  `realBelow` (`:1241-1257`) walks `p`, then `p/<uuid>`, `Lstat`ing each; the create path
  re-checks after `MkdirAll` (`:274`). Both are correct predicates (`filepath.Rel`
  normalises, so a sibling-prefix base is refused; `rel == "."`/`".."` refused; a missing
  component is tolerated only by `projectHomeIsReal`, and I confirmed ENOTDIR is *not*
  `fs.ErrNotExist` on this toolchain, so a non-directory component fails closed). The
  residual, stated precisely: (a) between the last `Lstat` and dockerd's mount setup, and
  (b) between the `Lstat` of `p` and the `Lstat` of `p/<uuid>`, a guest can replace either
  component. The guest reaches those components only from the setup VM, which mounts
  `<homes>/<u>` with NOPASSWD sudo (`orchestrator.go:591` → `:803`,
  `image/entrypoint.sh:55`); the setup VM takes a different project lock
  (`:550` vs `:173`), so it can run concurrently with a project start, and the user can
  re-trigger it from Settings at will. Winning the race mounts the symlink target as
  `$HOME` in a root-guest microVM: another tenant's `.claude/.credentials.json`,
  `.ssh/id_ed25519`, `.config/gcloud/*`, or a host path under `/var/lib/styrman`.
  Requires an attacker-controlled loop plus repeated stop/start attempts, which is why
  this is medium and not high. **Remediation:** the durable one is the recorded ADR
  proposal (project homes out of the setup VM's mounted tree). Short of that, resolve the
  home through an `openat2(RESOLVE_NO_SYMLINKS)`/`Root.OpenRoot` handle and hand Docker
  the verified path, and hold the project lock across the check and the start (it already
  is held — the gap is dockerd's own re-resolution, so only a resolved path closes it).
- **[low / confidence: medium]** `internal/orchestrator/orchestrator.go:283` and
  `internal/httpapi/server.go:723` — **two host-side `MkdirAll`s still walk a
  guest-plantable path, and BUG-003's own prevention rule ("on EVERY path that reaches
  that sink") was not applied to them.** `os.MkdirAll(filepath.Join(phome, "projects",
  opts.Dir), 0o755)` runs *after* the `realBelow` re-check, but `realBelow` only proves
  the components *down to* `phome`; `<phome>/projects` is inside the project home, where
  the guest is root, and a symlink planted there is followed by the host. Likewise
  `os.MkdirAll(s.cfg.ProjectHome(u.Username, p.ID), 0o700)` on project create runs with no
  check on `p` at all. Reachable effect is bounded: directory creation as the server user
  at an attacker-chosen path the server can write (`/var/lib/styrman/**`), with a final
  component that is a kebab-case project slug (`internal/project/store.go:36-43`, `:150`),
  so no dotfile name can be manufactured — a cross-tenant nuisance/availability primitive,
  not a read or a write of content. The second one additionally self-DoSes the attacker
  (a symlinked `p` then fails `projectHomeIsReal` on every boot). **Remediation:** call
  `realBelow(phome, <phome>/projects/<dir>)` before the mountpoint `MkdirAll`, and
  `projectHomeIsReal` before the create-time `MkdirAll` in `server.go`.
- **[low / confidence: high]** `TODO.md` — **four lows accepted across phases 1–3 exist
  only inside review files, in no actionable list.** The phase reviews flagged this exact
  pattern ("deferred-with-no-record is how a finding evaporates") and it then happened to
  four of their own items: (1) `internal/history/history.go:39,125,207` still call raw
  `os.OpenRoot(ProjectHome(...))`, outside `files.Trust`'s reach — the third consumer of
  the unsafe root, weak today only because the target must already carry
  `.styrman/logs/<the requester's own UUID>`; (2) `files.Trust` is established from
  `httpapi.New` (`internal/httpapi/server.go:126`) while `cmd/styrman/main.go:44,66` run
  the two migrations first, so `files.ContainedPath` at `main.go:228` executes with an
  empty base list (harmless today, latent trap for any future `files.*` call added before
  `New`); (3) `image/configs/harness-migrate.sh` never refuses a symlinked `~/.claude`,
  `~/.gemini`, `~/.agents` or `~/.styrman` parent (self-harm only); (4) `sh-agent`'s
  `update` verb ships in the tenant binary and is a pull-and-execute path with an implicit
  `FindRepo`. Grepped `TODO.md` and `ROADMAP.md`: no entry for any of them (the upstream
  bullet covers `filepath.IsLocal`, the version stamp, the `git rev-parse` ascent and the
  partial install — not these). **Remediation:** one TODO line each, at the severity the
  reviews gave them.
- **[low / confidence: high]** `.agents/docs/specs/styrman/deploy.md:89` — **the incident
  lever is not in the runbook.** The new session-lifetime bullet says what the lifetime is
  and that authorization is re-checked per request, but not that rotating
  `STYRMAN_JWT_KEY` and restarting the ingress is now the *only* way to force every
  session out (pinned key + no deny list + 8 h `exp`). That sentence exists only in
  ADR-063's Consequences (`DECISIONS.md:2383`). The session-lifetime review asked for it
  in `deploy.md` specifically, because that is what an operator reads under pressure.
  The append-only change record (`changes/2026-09-04-session-lifetime.md:13,15`) also
  still calls the value "operator-tunable"/"configurable via `SessionLifetimeSeconds`"
  when it is a compile-time `const` needing a caddy image rebuild — that file cannot be
  rewritten, so the runbook is the place to be correct.
- **[low / confidence: medium]** `internal/orchestrator/orchestrator.go:230-240` — an
  adopted container's recorded bind source is never compared with the expected
  `phome` before `ContainerStart`. Round 3 recommended this alongside the hoist; only the
  hoist landed. Not tenant-reachable (a container with a foreign source needs host-level
  Docker access, and tenants have only their own in-VM dockerd), which is why it is low —
  but it is the cheap half of "prove the source, don't just prove the path".

## Answers to the questions asked

1. **Is the post-round-3 fix correct and complete?** Correct, and complete for the
   enumerated sinks; the residual is timing, not a missed path. I enumerated every
   `ProjectHome(`/`UserHome(` use in `internal/` and `cmd/` and classified each:
   - **Docker bind sources** — project create (`:292` → `:803`) and project start
     (`:234`, `:239`): both now gated by `:226`, create additionally by `:274`. Setup VM
     create (`:591`) and start (`:576`) use `UserHome`, whose parent `HomesDir` is mounted
     into no guest (compose mounts `/var/lib/styrman` only into the server,
     `deploy/docker-compose.yml:120`) — server-controlled, correctly unguarded.
     `workspacePath` = `StateDir/projects/<u>/<uuid>` — the guest sees its contents, never
     the parent that holds the name — server-controlled.
   - **Opened as an `os.Root`** — `explorer.go:48`, `setup.go:196` (`rosterHome`),
     `credentials.go:246,272`, `main.go:228` all go through `files.openRoot`
     (`internal/files/files.go:88-121`), which anchors at `<base>/<tenant>` and confines
     every component below it. The janitor (`main.go:379-414`) opens the tenant root and
     reaches `p/<uuid>` via `Root.OpenRoot`, stats via `fs.Stat(home.FS(), …)`, and
     `Root.Remove` never follows a link — confined, and its scope is `.styrman/logs` only.
     `internal/history` is the one unconverted consumer (finding 3, item 1).
   - **Host-side `MkdirAll`** — two unswept (finding 2).
   `go vet ./...` clean; `go test ./internal/orchestrator/ ./internal/files/
   ./internal/httpapi/ ./cmd/styrman/` all `ok`, including
   `TestProjectHomeIsRealAllowsMissingRefusesLinks`. BUG-003's record is now accurate
   (status fixed, residual stated as the race) — the round-3 complaint about a mis-stated
   fix is resolved.
2. **Interactions between the pieces.** Checked, and all but one are clean:
   - *Migration helper vs a symlinked `p/<uuid>`* — cannot arise outside finding 1's race:
     `projectHomeIsReal` refuses the boot before any container starts, and the setup VM
     (the only guest that can see `p/`) runs with `STYRMAN_MINIMAL=1`
     (`orchestrator.go:594`), which the entrypoint's harness block skips
     (`image/entrypoint.sh:130`), so `harness-migrate.sh` never runs with `HOME` =
     `<homes>/<u>`. If the race were won the mount is already total compromise; the helper
     adds no capability.
   - *Janitor vs "move, never delete"* — clean, and this is the one I most expected to
     break. `harness-migrate.sh` parks the previous harness in
     `~/.styrman/harness-backup-<ts>/`; the janitor walks `.styrman/logs` only
     (`main.go:392`), so the backups are not silently reaped after `TranscriptTTL`.
   - *Janitor vs orchestrator vs a live guest* — no cross-tenant reach: the janitor holds
     a tenant-anchored root for the whole walk, and the worst a lost stat→`Remove` race
     costs stays inside the tenant's own `.styrman/logs`.
   - *Roster vs janitor* — disjoint subtrees (`.claude/*`, `.gemini/config/*` vs
     `.styrman/logs`); no shared state.
   - *Eight-hour token vs BUG-001's reload cap* — the cap survives. It counts reloads, and
     `api.ts:319-345` now clears it only after 10 s of health *and* only if no re-auth
     fired, so the partial-failure reset the fail-to-fetch review found is closed; a
     longer token makes genuine expiry rarer, not the cap weaker. The real interaction is
     the recorded WebSocket low: BUG-001's reload used to re-handshake (and re-check
     `IsAuthorized`) roughly every 15 minutes by accident, and ADR-063 stretches that
     incidental revocation to ~8 h. Secondary and negligible: a settings tab now polls the
     roster continuously for 8 h instead of being reset every quarter hour — bounded by
     `maxListNames` = 1000 and the per-user project count.
3. **The three lows from the lifetime review** — all three are in `TODO.md` (verified:
   WebSocket handshake-only auth, no `caddy validate`/`adapt` gate, substring-only
   assertion). **Accept as recorded, with one qualification:** the WebSocket item is no
   longer "pre-existing in kind, unchanged in practice" — it is now the widest revocation
   gap in the product (a removed user keeps a root-capable shell for up to eight hours),
   so it deserves scheduling rather than indefinite recording. Do not escalate for this
   release; do not let it sit unscheduled through the next.
4. **Tooling.** `bash deploy/vulncheck.sh` → **exit 3**, as documented (report, not gate):
   root module and `deploy/caddy/ingress` each report the two accepted, no-fix,
   daemon-side findings **GO-2026-4887** and **GO-2026-4883** in `github.com/docker/docker`
   (v28.5.2 and v27.5.1, both "Fixed in: N/A"); `image/harness` → **"No vulnerabilities
   found."** `npm audit` in `web/` → **found 0 vulnerabilities**, exit 0. Nothing new
   versus the piecewise reviews.
5. **Anything that must block the release** — no. Finding 1 is a strict improvement over
   what v1.19.1 shipped and is recorded with an owner-level decision already queued;
   findings 2–5 are low.

## Checked

- **Secrets** — clean. The full range diff (13.7k lines, `web/dist` excluded) scanned for
  PEM headers, `AKIA`, `ghp_`/`gho_`/`github_pat_`, `sk-ant`, `AIza`, `xox*`: the only
  hits are two prior review files quoting their own grep patterns. No `.env`, key, or
  token added; `image/.dockerignore` (new) now keeps `.git`, `*.env`, `*.pem`, `*.key` out
  of the runtime image context, which the repo-root `.dockerignore` did not cover. The new
  ingress line emits `{env.STYRMAN_JWT_KEY}` as a placeholder, never a value. Nothing new
  is logged: `harness-migrate.sh`'s `plain()` strips control characters from every file
  name that reaches the container log, and `realBelow`'s error text names only the
  caller's own tree.
- **Injection** — clean. No SQL, no template, no shell string built from request data.
  Parsing boundaries in the range: directory entry names (used as `os.Root`-relative path
  components, filtered by the anchored RE2 `oldHarnessBackup`, `setup.go:170`), markdown
  frontmatter and a JSON manifest inside `image/harness` (same-principal, in-guest, and
  the unvalidated `name`→path flow is recorded upstream), `filepath.Rel` over two
  server-derived absolute paths, and one `%d` of an untyped int constant into the
  Caddyfile. `harness-migrate.sh` quotes every expansion, uses `mv -T`, and its one
  deliberate unquoted glob feeds a quoted function argument.
- **Authz/authn** — no regression. `GET /api/settings/tools` sits behind `authGuard` with
  no exemption; no route in the range skips middleware; no identifier is newly trusted
  from the client (project UUIDs are re-validated on load and quarantined on failure,
  `project/store.go`). The one authn change is configuration: `crypto default token
  lifetime 28800` (`generator.go:271`), whose trade is now stated correctly in ADR-063
  after the session-lifetime review's medium was fixed in the text before commit — I
  re-read `DECISIONS.md:2383` and it no longer claims a redeploy flushes sessions.
- **Crypto** — nothing hand-rolled, nothing added. The lifetime change is an integer
  handed to the vetted caddy-security/go-authcrunch primitives; signing stays HMAC over
  the pinned env key. No new hashing, token, or session code in Go or TypeScript.
- **Dependencies** — no change: `git diff --stat v1.19.1..d24fe40 -- go.mod go.sum
  web/package.json web/package-lock.json deploy/caddy/ingress/go.{mod,sum}` is empty. The
  third module `image/harness` declares zero `require`s and no `go.sum`, and its build
  stage pins `GOTOOLCHAIN=local GOPROXY=off` (`image/Dockerfile:13`) so a future
  requirement fails the build rather than fetching. Stdlib-first satisfied; the only new
  imports across the range are stdlib. `deploy/vulncheck.sh` and `deploy/verify-commit.sh`
  both now know about the module; I ran the gate's integrity section by hand at HEAD:
  `sha256sum -c --quiet SHA256SUMS` passes, the unlisted-file diff is empty, and
  `find . -type l` in the mirror is empty — so the "blind to additions and symlinks" low
  from phase 1 round 2 is closed in the shipped gate.
- **GCP surface** — not applicable and untouched. styrman is self-hosted
  (`.agents/docs/deploy/gcp.md`); no IAM binding, service account,
  `--allow-unauthenticated`, Secret Manager usage, or service-account key file appears in
  the range or its reach.
