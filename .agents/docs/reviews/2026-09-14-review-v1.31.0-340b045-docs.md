# Review — v1.31.0..340b045 docs (`/review --docs`)

Range reviewed: v1.31.0..340b045

The behaviour change (d285015: `wsBoot` in `internal/httpapi/server.go` now
calls `EnsureSelfAttached` synchronously before the WS upgrade) was accompanied
by doc edits in the SAME commit to `guide.md`, `deploy.md`,
`.agents/docs/testing/styrman/README.md`, and `AGENTS.md`, and those four are
accurate and consistent with the code (verified against `wsBoot`'s doc comment
and `ensureRunningLocked`'s NOTE in `orchestrator.go`, both also updated in
d285015). One architecture document that states the general rule this change
carves an exception into was NOT touched, and now contradicts the shipped
code.

## Verdict: REQUEST CHANGES

## Findings

- **[high / confidence: high]** `.agents/docs/architecture/DECISIONS.md:419-439` (ADR-021, "Async project creation; the server never reconfigures its own network on a request path") — decision (b) states "Self-attach happens only in the background (post-create, post-start, at boot for adopted projects)" and the ADR's own title asserts the server never reconfigures its network on a request path. `wsBoot` (d285015) now does exactly that: it calls `EnsureSelfAttached` synchronously, inside the WS-upgrade request handler, before the upgrade — a fourth, non-background self-attach path the ADR's enumeration and title both contradict. Grepped both wsboot review artifacts (`.agents/docs/reviews/2026-09-14-review-wsboot-attach.md`, `-security-wsboot-attach.md`) and the bug record (`BUG-060-terminal-ws-boot-never-joined-the-project-bridge.md`) for "ADR-021" / "request path" / "never reconfigures" — no hits, so the contradiction was never reconciled or reasoned about in this range, only worked around in `wsBoot`'s own doc comment ("this path has no response to protect"), which is a different rationale than ADR-021 gives (protecting an in-flight HTTP response) and doesn't amend the ADR. Fix: append a note to ADR-021 (ADRs are append-only per `AGENTS.md`) recording the exception and why it's safe (no committed response to lose), or file a new ADR that supersedes decision (b)'s enumeration.

- **[low / confidence: low]** `.agents/docs/specs/styrman/terminal-protocol.md:20` — "Connecting boots the project's microVM if it is stopped (this is the one slow path — up to a few seconds; the HTTP upgrade completes only after readiness)." This is the doc most naturally responsible for describing terminal-WS connect timing, and it still doesn't mention that "readiness" as of BUG-060 also includes a synchronous bridge (re)attach that can itself disturb the connection (per `wsBoot`'s doc comment, "a client whose handshake a fresh attach disturbed simply reconnects"). Not contradicted, just silent — a reader relying on this file alone would not learn that the first connect to a stopped project can now also race a netns reconfigure, the same class of caveat `api.md` documents for the sibling browser-relay endpoint (503 + Retry-After for exactly this reason). Consider a one-line addition; not blocking on its own.

- No over-claiming found: the new doc/verification artifacts in this range (`.agents/docs/testing/2026-09-14-wsboot-attach-verify.md`, `BUG-060-*.md`, both 2026-09-14 handoffs) consistently and correctly scope the fix as "unit-verified only" / "Live proof pending next deploy," matching the actual verifier run (unit tests + fakes, no live Kata/broker).
