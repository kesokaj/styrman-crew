# Security review — v1.42.2-v1.42.1-ef22f5c   (2026-10-05)

Range reviewed: v1.42.1..ef22f5c (a6e6eb6 handoff, ef22f5c v1.42.2 work; 16 files, +305/-27, no binaries per `git diff --numstat`). HEAD has since moved to c350683 ("v1.42.2 review fixes …"). That commit is OUTSIDE this range and was not reviewed.

## Status: COMPLETE

## Verdict: FINDINGS

**Worst problem: the new token step persists an over-scoped credential.** The step is `gh auth token | sudo install -D -m 600 /dev/stdin /etc/styrman/gh-token`. It does keep the value out of argv, the environment, shell history and the journal. But it writes the operator's `gh` LOGIN token, an OAuth token with the gh CLI's default scopes, into the root file that the image build and the auto-updater both keep using. Those scopes include `repo`: read/write on every repository the account reaches. The project's own design for that file is a fine-grained, read-only token: `host-setup.sh` step 8c, and remote.md "Agent harness token (ADR-074)". The "Post-upgrade steps" block that runs on existing hosts also silently overwrites that narrow token (medium).

**Second: the history-search fix does not reach its goal.** The semaphore bounds `Search` as designed. But row 1's goal was that a tenant cannot crash-loop the server under its 4g cap, and the sibling `readHistory` path still allows it. That path holds about 30+ MiB per request, with no concurrency bound and no write deadline, so it reproduces the crash-loop more cheaply than search did (medium, medium confidence).

**The semaphore's cross-tenant cost is real but smaller.** The global 4-slot semaphore lets one tenant deny every other tenant's search with a 429. That is strictly less severe than the crash-loop it replaces (low).

Rows 2, 4, 6, 8 and 9 are confirmed. No high finding.

## Findings

- **[medium / confidence: high]** `deploy/host-setup.sh:307`, `.agents/docs/deploy/remote.md:88`, `.agents/docs/specs/styrman/deploy.md:262` and `:341-342`
  - **The weakness:** the new token step writes the operator's `gh` login token into `/etc/styrman/gh-token`.
    - `gh auth token` prints the gh CLI's stored github.com OAuth token. Its scopes are those granted at `gh auth login`: by default `repo`, `read:org` and `gist`, where `repo` means full read/write on every repository the operator reaches.
    - That file is the build secret `host-setup.sh` passes to `docker build`. It is also the auto-updater's standing credential (`deploy/styrman-ctl:542`, `STYRMAN_GH_TOKEN_FILE=${ETC_DIR}/gh-token`).
  - **It contradicts the project's own design:** the same tree specifies a FINE-GRAINED token for that file, "Contents: Read-only" (`host-setup.sh` step 8c's printed instructions). remote.md's "Agent harness token (ADR-074)" section says the crew token there "must also read `kesokaj/styrman-harness` (grant it in that fine-grained GitHub token's settings)".
  - **It overwrites the narrow token:** the step sits in remote.md's "Post-upgrade steps for the next tag" block, which runs on EXISTING hosts. On every auto-updating host (dave, the GCP VM), `install` overwrites the narrow token without a prompt. The updater then runs as root with the broad one.
  - **Scenario:**
    - Any read of that root file (host root, which on dave is one sshd password guess from a LAN project per remote.md's own advice section; a backup or image of `/etc`; a mistaken `chmod`) yields write access to all of the operator's repositories.
    - The copy survives `gh auth logout` on the host.
    - On dave the same broad token already sits in the operator's gh config, so the marginal exposure there is the persistence and the updater's use of it, not a first copy.
  - **Remediation:**
    - Document the fine-grained token (read-only, on `styrman-crew` and `styrman-harness`), written through stdin from the operator's own file (`sudo install -D -m 600 /dev/stdin /etc/styrman/gh-token < <file>`), or `styrman-ctl install --gh-token-file`.
    - Never `gh auth token` into a file that outlives the run.
    - Refuse to overwrite an existing `/etc/styrman/gh-token` without an explicit flag.
  - c350683's subject says this changed ("installs a fine-grained token file (never the gh login token, never empty)"). That is not verified here.

- **[medium / confidence: medium (mechanism read in code; per-request memory computed from `encoding/json`'s behaviour, not measured — production host, no load experiments)]** `internal/httpapi/explorer.go:481-502` (`readHistory`), `internal/history/history.go:216-265` (`Read`), `internal/httpapi/server.go:1388-1392` (`writeJSON`), `cmd/styrman/main.go:157,171,179`
  - **Where row 1's fix stops:** row 1 is fixed for `Search` only. The original remediation said "on `Search` and on any handler that holds multi-MiB buffers".
  - **Mechanism, step by step:**
    - `GET /api/projects/{p}/history/{id}?bytes=4194304` reads up to 4 MiB of a guest-writable transcript.
    - It copies that tail into a string and through `ansiRe` and two `ReplaceAll` calls.
    - `writeJSON` (`json.NewEncoder(w).Encode`) then marshals `{"text": …}` into an in-memory buffer before `Write`.
    - The encoder escapes `<`, `>`, `&`, control bytes and invalid UTF-8 as 6-byte `\uXXXX`. A planted tail of `<` or `0xFF` becomes about 24 MiB of JSON, in a buffer that grows to about 32 MiB.
    - That buffer is live until `Write` returns. The servers set only `ReadHeaderTimeout`, so there is no write deadline. No `response_buffers`/`flush_interval` is configured in `deploy/caddy` (grep), so Caddy streams and a client that never reads keeps the handler blocked.
    - The handler is outside `searchSlots` and has no per-user or server-wide bound.
  - **Scenario:**
    - A tenant writes one 4 MiB transcript of `<` under `~/.styrman/logs/<pid>/` from inside its VM.
    - It opens about 120-150 concurrent reads with `bytes=4194304` and reads none of them, at about 36 MiB live each.
    - The server passes its 4g cap and is OOM-killed. `unless-stopped` restarts it, every tenant's sessions drop, and the tenant repeats. This is row 1's crash-loop, with no CPU-bound search needed.
    - `GOMEMLIMIT` cannot help: the memory is live, not garbage. The ingress `DEFAULT_RPS` limiter (not traced) slows the build-up but does not stop stalled requests accumulating.
  - **Same class, from constants only, not traced:**
    - `/file` save, `/format` and `/check` take 8 MiB bodies (`server.go:701-711`).
    - The editor's file read (2 MiB, x6 when escaped).
    - `browser.go:270`'s 16 MiB guest-controlled relay frames.
  - **Remediation:**
    - Put every multi-MiB handler behind one server-wide, memory-weighted limiter that answers 429. Stdlib is enough: a buffered channel of tokens per MiB, or a mutex and a counter; `golang.org/x/sync/semaphore` is not needed.
    - Give those handlers a write deadline with `http.ResponseController.SetWriteDeadline` (stdlib, per handler, so WebSocket and terminal paths are untouched).
    - Stream the transcript (`text/plain` or chunked) instead of materialising a 6x-escaped copy.
    - Test: stalled concurrent reads past the limit get 429, with a must-fail run without the limiter.

- **[low / confidence: high]** `internal/httpapi/explorer.go:440,457-463`, `internal/httpapi/server.go:185`: cross-tenant starvation.
  - **The weakness:** the 4 slots are server-wide, there is no per-user share, and a full semaphore answers 429 at once. One tenant holds all 4 with 4 concurrent searches over planted transcripts: 50 x 4 MiB, mixed case and CRLF, at about 144 ms of `ToLower` per 4 MiB measured in an earlier review, so each search runs for seconds. Every other tenant's history search then gets 429 for as long as it likes, at under one request per second.
  - **Requirement:** `REQUIREMENTS.md:11` says "each user fully isolated".
  - **Is it worse than the crash-loop?** No. It denies one non-critical feature: no crash, no data exposure, other endpoints unaffected, and at most 5 allowlisted users. The crash-loop took the whole platform down. The trade is a net improvement.
  - **The stated reason is wrong:** the comment's reason for 429 instead of a queue (`explorer.go:444-445`, "a queue would hold the requests, and their memory, anyway") is inaccurate. A waiting request holds a goroutine and its headers (KiB). The multi-MiB buffers exist only inside `history.Search`.
  - **Remediation:**
    - Cap each user at 1 slot inside the global 4 (stdlib map and mutex).
    - Optionally wait a few seconds, bound to `r.Context()`, before the 429.
    - Test: user A holding its share does not 429 user B.
  - c350683's subject claims "one history search per user". Not verified here.

- **[low / confidence: high]** `deploy/styrman-ctl:514`, `deploy/README.md:36`: restatements of the leaky form remain.
  - **Leftover text:**
    - `styrman-ctl`'s die text still says "… or run with GH_TOKEN set". `styrman-ctl` runs as root under sudo, so the ways to do that are `sudo GH_TOKEN=…` and `sudo --preserve-env=GH_TOKEN`, which the range now documents as logging `ENV=GH_TOKEN=<value>`.
    - `deploy/README.md:36` contrasts `--gh-token-file` with "the bare `GH_TOKEN=$(gh auth token) bash host-setup.sh` form" and gives no sudo caveat.
    - The ticked plan line `.agents/docs/plans/2026-10-05-project-resources.md:406` (historical) still reads `sudo GH_TOKEN=… …/host-setup.sh`.
  - **Measured on dave, which raises the stakes:** `journalctl _COMM=sudo` run as `kesokaj` returned 2430 entries. `kesokaj` is in neither `adm` nor `systemd-journal`, so sudo's log lines, `ENV=` values included, are readable without root by every process of the operator's uid.
  - **Remediation:** make both texts name only `--gh-token-file` or the stdin file form.

- **[low / confidence: high]** `deploy/host-setup.sh:307` and the guide lines in finding 1: the pipe masks a `gh` failure.
  - **Mechanism:** the pipe has no `pipefail`, so its status is `install`'s. A logged-out or failing `gh` still produces an EMPTY file, root-owned and mode 600. That passes `host-setup.sh`'s owner/mode check in step 7 (304-305), and the failure resurfaces later as a GitHub auth error in the image build or the updater. On an existing host, it has also just replaced a working token.
  - **Remediation:** have `host-setup.sh` refuse an empty or whitespace-only token file, and check the input before replacing.
  - c350683 claims "never empty". Not verified here.

- **[low / confidence: high]** `deploy/docker-compose.yml:93-94`, `internal/config/compose_oom_test.go:63`: the `GOMEMLIMIT` text overclaims.
  - **The comment:** it says the GC "runs hard near it instead of letting the kernel OOM-kill the server". `GOMEMLIMIT` only reclaims garbage. A live set past the cap is still OOM-killed (finding 2's path). Near 3 GiB live, the GC spends up to its 50% CPU limiter, slowing every tenant first.
  - **The test pin:** it uses `strings.Contains` over the whole file rather than the per-service block the same test builds, so the line would pass under `caddy:`. c350683 says "GOMEMLIMIT check scoped".
  - **Remediation:** reword the comment to "collects garbage before the cap; does not bound live memory".

## Outcome
(main agent, 2026-10-05)
1. **Fixed (c350683, ef04b30).** The token step installs a fine-grained, read-only token from a 600 file, only when the host has none (no overwrite), refuses an empty file, and shreds the plaintext. It never uses the `gh` login token.
2. **Fixed.** `readHistory` takes a server-wide slot (`readConcurrency` = 8, else 429), and search and read get a 30 s write deadline through `http.ResponseController`, so a client that never reads releases its slot. `TestHistoryReadIsLimitedServerWide` was red first.
3. **Accepted (low).** One tenant holding all search slots gets a retryable 429, not a crash. A per-user share was tried in c350683 and reverted in ef04b30: the history panel does not abort its previous search, so it broke a quick second search. Follow-up: client abort with server-side cancel.
- The journal's `ENV=GH_TOKEN=` entry: `journalctl | grep -c 'ENV=GH_TOKEN='` reads 0 on dave now. The main agent's sudo probe used `PROBE_TOK` with a dummy value.
- The six files named under Not examined go to an addendum review.
