# Security review — 5571b57-57179a4   (2026-10-02)

Range reviewed: 5571b57..57179a4 (`git diff 5571b57...57179a4`, one commit: 57179a4 "Review fixes", answering `reviews/2026-10-02-security-v1.40.0-5571b57.md`)

## Status: COMPLETE

## Verdict: FINDINGS

Nothing high or medium; two lows. The worst is that the status-path fix in `deploy/update/styrman-update` closes only the static half of the earlier finding 2. It now refuses a relative path, a `..`, a `//` and a symlink that is already on the path (all checked). But `realpath -m` checks only once. It never looks at who owns, or who can write, the directories above the status directory. So the race the earlier finding named is still open: an ancestor that a lower-privileged uid can write can be swapped between the check and `mktemp`/`mv`. A probe through the gated test hook shows a world-writable ancestor is accepted. Also, unlike the state dir, the status path is not refused under `/var/lib/styrman`, so "like the state dir's" in the comment, two specs and the Outcome overstates it. Production is not affected, because the path is pinned under root-only `/etc/styrman`. The second low is about key custody, not code. The new ADR-082 paragraph is accurate (both fingerprints and the public key were checked against the tag signatures). It shows that the original release signer is the production NUC's own default SSH identity, and how that key is protected is not recorded anywhere. The key material in the ADR is NOT sensitive (see Checked). `GuestGoingAway`'s wait as committed in 57179a4 gives no finding: it is bounded by the request, never blocks in `Lock()`, and no caller holds the lock while it waits (see Checked).

Separately, while this review ran, another actor changed the working tree. These edits are uncommitted and outside the range. Between 21:14 and 21:15 they touched `internal/orchestrator/ports.go`, `internal/httpapi/browser.go`, `internal/httpapi/guestexec_test.go`, `internal/orchestrator/ports_lifecycle_test.go` and `internal/config/styrman_update_status_test.go`. The `ports.go` edit makes `GuestGoingAway` call `o.Status` on every 100 ms tick while it waits. Those edits need their own security pass (see Not examined). My Go test runs (21:16) ran on that tree and are not evidence for 57179a4.

## Findings
- **[low / confidence: high]** `deploy/update/styrman-update:114-135` (`write_status`), restated in `.agents/docs/specs/styrman/deploy.md` (status bullet, "like the state dir's"), `.agents/docs/specs/styrman/versioning.md` (auto-updater section) and the `## Outcome` of `reviews/2026-10-02-security-v1.40.0-5571b57.md` ("fixed … matching the state dir's rule").
  - **What is wrong:** the new rule (absolute, and `realpath -m` must equal the path) is checked once. The owner and mode checks still cover only `dir`, plus its parent when `dir` is created. Nothing is checked for the directories above it.
  - **Shown, not inferred:** through the gated `__write-status` hook (`STYRMAN_UPDATE_TEST=1`, my uid, scratch only), a status dir at 0755 below a 0777 (non-sticky) ancestor was written with no WARN (`rc=0`, `updater.json` present). The control: a symlinked ancestor was refused ("is not canonical") and nothing was written. `deploy/` is unchanged in the working tree, so this probe ran against 57179a4's script.
  - **Why it matters in principle:** a uid that can write an ancestor can rename the status directory and plant a symlink in its place after the check and before `mktemp`/`mv -f`. Root then creates a fixed-name, fixed-content, 0644 `updater.json` in a directory of that uid's choosing. That is the BUG-009 shape, with small impact.
  - **Differs from the state dir:** `STATE_DIR` is also refused under `/var/lib/styrman` (`:396-399`) and at `/` or a top-level system directory (`:409-412`). The status path is refused in neither case, although the comment at `:76` says "Never under /var/lib/styrman".
  - **Not reachable in production:** the unit pins `/etc/styrman/status/updater.json`, `/etc/styrman` is root 0700, and only root-controlled unit and compose config set `STYRMAN_UPDATE_STATUS_FILE`.
  - **Remediation:**
    - Walk every ancestor of `dir` from `/` with `trusted_dir`'s bar: owned by `TRUST_UID`, not a symlink, not group- or world-writable. This is what `realBelow` does in Go, and it closes the race because no lower-privileged party can then change any component.
    - Refuse `/var/lib/styrman` and `/var/lib/styrman/*` as `STATE_DIR` does.
    - Add a hook test that needs no root: plant a 0777 ancestor (as in the probe) and assert `WARN: status not written`.
    - Or, if the static-only check is kept, reword the comment, both specs and the Outcome to "a symlink or non-canonical spelling present at check time".
- **[low / confidence: medium]** `.agents/docs/architecture/DECISIONS.md:2821-2824` (ADR-082, "Keys, custody and revocation").
  - **What the record shows:** the paragraph is correct (verified, see Checked). It shows that the original release signer is the NUC's default SSH identity (`~/.ssh/id_ed25519`, set as git's `user.signingkey` with `gpg.format=ssh`). The NUC is the production host: it runs the multi-tenant microVMs, and its server holds the Docker socket. Every host whose `allowed_signers` lists this key (the GCP VM) builds and runs as root any tag the key signs.
  - **Why it matters in principle:** whoever gets root on the NUC, or can use the operator's key there, gets root on the GCP VM at that VM's next update tick.
  - **What is missing:** how this key is protected (passphrase, agent-only, hardware) is not recorded. The Outcome hands the operator only the Mac key's protection.
  - **Scope:** the policy predates this range; this range only makes it visible.
  - **Remediation:**
    - Add the NUC key's protection to the handoff's operator Next Steps, beside the Mac key's.
    - State in the ADR that a compromise of the NUC extends to every host that lists the key.
    - Prefer a dedicated release-signing key, not the host's general SSH identity. It should be passphrase-protected or hardware-backed (`sk-ssh-ed25519`), and ideally not kept on a host that runs tenant workloads.

## Checked
- **The dispatch's three questions:**
  - **`write_status` path rule:** these forms are refused, each verified with the script's own comparison: `//` at the start or in the middle, `/./`, a trailing `/`, and a trailing newline (the `basename` check alone passes that one; the canonical check refuses it). A relative path is refused by the new `case`. A symlinked ancestor is refused (probe control and the new test). If `realpath` itself fails, the output is empty and the path is refused, so it fails safe. What the rule does not cover is finding 1.
  - **ADR-082 key material is not sensitive.**
    - An ed25519 public key and SHA-256 fingerprints are public information. They give no help in forging a signature, and publishing them is what lets an operator check a host's `allowed_signers`.
    - The paragraph holds no private key material and no key comment. The NUC's `.pub` comment is an e-mail address, and the ADR does not reproduce it. `~/.ssh/id_ed25519` is the default path and tells an attacker nothing new.
    - Minor and not a credential exposure: a published SSH public key lets a third party ask an SSH server whether it accepts that key for an account, and match the key with other services.
    - Consistency checked in scratch:
      - `ssh-keygen -lf` on the ADR's blob gives `SHA256:XeeDl8Y8nxiYguhziu4FKdG4qMuNs5uF8I+FDqACFNE`, the v1.39.0 tag's signer (`ssh-keygen -Y check-novalidate -n git`).
      - The v1.40.0 signer is `SHA256:5HpYQJjpG+yE1xXBTOIZPsTkbkgkVnV8z0eG8hBawyU`, which equals `~/.ssh/id_ed25519.pub` on this NUC, the file `user.signingkey` names.
  - **`GuestGoingAway`'s wait as committed in 57179a4 (`internal/orchestrator/ports.go:135-157`):** no finding. I read it from the commit's diff and from the file before the uncommitted edit landed.
    - **Callers:** `proxy.go:26` (`ListeningPorts`) and `browser.go:171/200/221` (REST status, start and stop) all pass `r.Context()`. So does the relay at `browser.go:374`, which calls it before `websocket.Accept`, so its context still ends when the client disconnects.
    - **Can a request be held longer than before?** Yes. It now lasts as long as a lifecycle change on the caller's OWN project holds the lock. That is bounded by the change itself (`waitReady` 90 s, the stop timeout, the mode toggle's 3-minute context at `network.go:37/118`, `Destroy`) and by the client's connection. `http.Server` sets only `ReadHeaderTimeout`, so no server-side deadline caps the wait.
    - **Can the server be made to wait on the lock indefinitely?** No. It calls `TryLock` every 100 ms and exits on `ctx.Done()`, so it never blocks in `Lock()`. Each tick costs only a `TryLock`. It holds the lock only between `TryLock` and `Unlock`, with no work in between.
    - **Wait-for-self:** none. The lock holders (`EnsureRunning`, `WithProject`, `Stop`, `stopIfIdle`, `Destroy` in `orchestrator.go`) and the only `WithProject` callback (`network.go:141`) never reach `ListeningPorts` or `browserExec`.
    - **Cross-tenant:** none. The key is the authenticated user's project (`getProjectFor`, otherwise 404), so this gives no cross-tenant stall and no timing oracle.
    - **Relay slots:** a waiting relay holds one of its slots (8 per user, 32 server-wide, `browser.go:263-300`), as a live relay already does, so the per-user cap still bounds one user.
    - **Comparison:** `EnsureRunning`'s own waiters block in a `Lock()` that no context can end, which is worse and predates this range.
    - **Optional hardening:** cap the loop with `context.WithTimeout` at the longest lifecycle bound.
    - **Not security:** `TryLock` can be starved by a stream of `Lock()` waiters (the mutex's starvation mode). The context bounds that too.

## Outcome
