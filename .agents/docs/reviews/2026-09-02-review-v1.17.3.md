# Review — v1.17.3 updater self-install + pinned-toolchain vulncheck   (2026-09-02)

## Verdict: REQUEST CHANGES

The worst problem is not in the self-install path — that part is sound, and I verified its two
load-bearing claims empirically. It is in the new security gate: `deploy/vulncheck.sh` does **not**
exit with govulncheck's status, contrary to what its own header comment, the changelog entry and
`.agents/docs/testing/styrman/README.md` all assert. `go run` collapses every nonzero child status
to `1`, so the script cannot distinguish "vulnerabilities found" (govulncheck's `3`) from "the scan
failed to run" (`1`). Measured on this tree today: real govulncheck exit `3`, script exit `1`.
For a gate whose whole job is to be believed, a broken scan and a real finding are currently
indistinguishable. Second, `self_install()` writes a root-owned `0755` executable and two systemd
units to paths taken from the environment with **no trust assertion at all** — the only root-write
target in a 500-line script whose entire hardening history (ADR-052, STATE_DIR, DOCKER_CONFIG,
GH_TOKEN_FILE, `deploy/.env`) is about asserting exactly this class of input. Both fixes are one to
three lines. Neither endangers the self-install mechanism itself.

## What I verified by execution (not by reading)

- **Atomic replace under a running bash — HOLDS.** Sandbox test (`scratchpad/inode/`): a running
  script whose file was replaced by `install` to a sibling temp + `mv -f` printed its remaining
  lines from the old inode and the *next* invocation ran the new content. The temp name
  `"${UPDATER_BIN}.new.$$"` is by construction in the same directory as the target, so `mv` is a
  same-filesystem `rename(2)`; `/tmp` never enters the picture. The "takes effect next run" claim
  is correct **because** it is a rename and not an in-place write.
- **Concurrent-run collision on `$$` — impossible.** `exec 9>"${LOCK}"` + `flock -n 9`
  (`styrman-update:142-143`) runs before any deploy work and exits 0 on contention; only one run per
  host can ever be inside `self_install`.
- **`cmp -s` against a missing target** returns 2 and prints nothing (GNU cmp) — a first install on
  a host with no file installs cleanly and silently. Confirmed.
- **Sandbox harness of the exact function body** (`scratchpad/si/`): fresh install →
  `0755` bin + `0644` units + reload; identical second run → complete no-op, no log line; a source
  file missing from the checkout → one WARN, `return 0`, nothing installed. All three behave as
  documented.
- **State-before-self-install ordering — confirmed on both paths.** Success path writes `${STATE}`,
  conditionally `${STATE_SHA}`, `rm -f ${FAILED}`, *then* `self_install`, then `exit 0`
  (`:497-508`). Rollback path writes `${STATE}` *then* `self_install` then `fail` → `exit 1`
  (`:529-534`). A self-install failure or hang can never lose the recorded deploy state.
- **`govulncheck@v1.7.0` is a real release.** `proxy.golang.org/golang.org/x/vuln/@v/list` ends
  `… v1.5.0 v1.6.0 v1.7.0` — v1.7.0 is the newest published version.
- **The pinned-toolchain premise holds today.** `docker run --rm golang:1.25.13-trixie sh -c
  'go run …govulncheck@v1.7.0 -version'` reports `Go: go1.25.13` — no toolchain switch inside the
  image. (On *this host* the same command prints `switching to go1.26.8`; see finding 4.)
- **Full script run:** both modules report exactly `GO-2026-4887` + `GO-2026-4883`, zero stdlib
  findings — the operator's baseline reproduces. The `:ro` mount held: `git status` shows no
  `go.mod`/`go.sum`/cache droppings in the repo afterwards.
- **shellcheck 0.10.0:** `deploy/vulncheck.sh` clean (rc 0); `deploy/update/styrman-update` only two
  SC2015 *info* notes, both on the new lines, and there `A && B || C` is the intended semantics
  (any failure ⇒ clean up the temp, WARN, return 0).

Side effects of this review on the host: two ephemeral `--rm` containers from the public
`golang:1.25.13-trixie` image, and the two named cache volumes the script itself creates
(`styrman-vulncheck-cache`, `styrman-vulncheck-gocache`). No production container was started,
stopped, restarted or removed; no file in the repo or under `/var/lib/styrman`, `/etc/styrman`,
`/usr/local/bin` or `/etc/systemd/system` was touched.

## Findings

- **[medium / confidence: high]** `deploy/vulncheck.sh:30` — the exit status is *not* govulncheck's.
  `go run pkg@version` prints `exit status 3` on stderr and itself exits `1`, so `rc` can only ever
  be `0` or `1`. Measured: `go run` form → script rc `1`; `go install …@v1.7.0 && govulncheck ./...`
  in the same image → rc `3`. That collapses govulncheck's meaningful codes (`3` = called
  vulnerability, `1` = the scan itself failed) into one value, so a gate — or an operator — cannot
  tell a real finding from a broken run, in either direction. The claim is repeated verbatim in
  three places that are now wrong: `deploy/vulncheck.sh:9-12`,
  `.agents/docs/testing/styrman/README.md` ("Exit status is govulncheck's own"), and
  `.agents/docs/changes/2026-09-02-…-vulncheck.md`. **Fix:** replace
  `sh -c "go run ${GOVULN} ./..."` with `sh -c "go install ${GOVULN} && govulncheck ./..."`
  (verified: preserves `3`; `/go/bin` is ephemeral per run but the build cache volume makes the
  reinstall near-free), then leave the three documents' claim as written — it becomes true.

- **[medium / confidence: medium]** `deploy/update/styrman-update:362-363, 375-385` —
  `STYRMAN_UPDATER_BIN` / `STYRMAN_UPDATER_UNIT_DIR` are consumed with **zero validation**, unlike
  every other externally supplied root input in this file: `STATE_DIR` is canonicalized with
  `realpath -m` and refused under `/var/lib/styrman` (`:80-88`), `DOCKER_CONFIG` is owner- and
  mode-asserted (`:104-116`), `GH_TOKEN_FILE` likewise (`:187-191`), `${DEPLOY_DIR}/.git` and
  `deploy/.env` likewise (`:152-163`). Here the script installs a root-owned `0755` executable and
  two systemd units at whatever paths the environment names — no canonicalization, no assertion
  that the destination directory is root-owned and not group/world-writable, no log of the resolved
  targets. The empty-default guard defends against *omission* only, which is half of the ADR-052
  lesson; the other half — a privileged run that names a production path **on purpose but by
  mistake** (a copy-pasted `Environment=` line in a test) — is exactly the incident this project
  already lived through, and it is now armed against `/usr/local/bin` and `/etc/systemd/system`
  instead of the state dir. **Fix:** before installing, `realpath -m` both targets and apply the
  same two assertions used for `STATE_DIR` to `dirname "${UPDATER_BIN}"` and `${UPDATER_UNIT_DIR}`
  (`stat -c %u` = 0, `find -maxdepth 0 -perm /022` empty), and log the resolved destinations so the
  journal records where root just wrote an executable.

- **[low / confidence: high]** `deploy/vulncheck.sh:29` — `-e GOFLAGS=-mod=mod` contradicts the
  read-only source mount and buys nothing. Measured: identical output and status with the variable
  removed. `-mod=mod` explicitly authorizes writes to `go.mod`/`go.sum` that a `:ro` mount can never
  satisfy, so the day a `go.sum` entry is missing the operator gets a confusing write failure
  instead of the clean `missing go.sum entry` diagnostic that `-mod=readonly` (the default) gives.
  **Fix:** delete the `-e GOFLAGS=-mod=mod` line.

- **[low / confidence: medium]** `deploy/vulncheck.sh:25-30` — no `GOTOOLCHAIN` pin. The script's
  stated purpose is "measure the toolchain that ships"; with `GOTOOLCHAIN` at its default (`auto`),
  the day `golang.org/x/vuln` or one of its dependencies raises its `go` directive above the pinned
  builder, the go command silently downloads a newer toolchain and scans a *different* stdlib —
  re-creating the exact mismatch this script was written to eliminate, announced by one easily
  missed line. This is not hypothetical: on this host the identical command prints
  `golang.org/x/vuln@v1.7.0 requires go >= 1.25.0; switching to go1.26.8`. Inside
  `golang:1.25.13-trixie` no switch happens today (verified, `Go: go1.25.13`). **Fix:** add
  `-e GOTOOLCHAIN=local` so a future mismatch fails loudly instead of silently measuring the wrong
  artifact.

- **[low / confidence: medium]** `deploy/update/styrman-update:375-385` — orphan temp files. A
  `SIGKILL`, an OOM kill or a power loss between `install` and `mv -f` leaves a root-owned `0755`
  `${UPDATER_BIN}.new.<pid>` in `/usr/local/bin` (and `0644` unit litter in `/etc/systemd/system`)
  that nothing ever removes; the existing `trap` covers only the `mktemp` `DOCKER_CONFIG` case, and
  one file accumulates per kill. **Fix:** `rm -f "${UPDATER_BIN}".new.* "${UPDATER_UNIT_DIR}"/*.new.*`
  at the top of `self_install` — safe precisely because the `flock` guarantees no concurrent run
  owns one.

- **[low / confidence: medium]** `deploy/update/styrman-update:380-395` — `self_install` never
  `systemctl enable`s, and `daemon-reload` alone does not restart the timer. Today that is fine
  because `host-setup.sh:370` enabled `styrman-update.timer` once. But a future release that adds a
  `[Install]` section, a new unit, or changes `OnUnitActiveSec` will ship the *file* and not the
  *activation* — the same "deployed everything except the updater" class of gap this change exists
  to close, one level up. `.agents/docs/specs/styrman/deploy.md` currently says only "nothing
  already running is restarted"; it should say plainly that unit **enablement** and timer restarts
  remain manual/`host-setup.sh` territory.

- **[low / confidence: low]** `deploy/update/styrman-update:380-388` — partial install skips the
  reload. If `styrman-update.service` installs successfully and `styrman-update.timer` then fails,
  the `return 0` in the failure branch is taken while `changed=1`, leaving a changed unit file on
  disk that was never `daemon-reload`ed. Narrow (it needs a per-file failure inside a writable
  directory — an unwritable directory fails both files and changes nothing), but the fix is free:
  set a warn flag instead of returning, and always fall through to the `changed=1` reload.

- **[low / confidence: high]** `deploy/update/styrman-update:393` — `systemctl daemon-reload
  2>/dev/null` discards the only explanation of the failure and the WARN carries none. On a root
  timer, an unexplained reload failure is precisely what you want preserved in the journal. Drop the
  redirect, or capture stderr into the log line.

- **[low / confidence: low]** `deploy/vulncheck.sh:18` — the `sed` extraction is correctly anchored
  (`^FROM golang:… AS builder$`) and fails closed with `exit 2` when nothing matches (verified
  against the current `FROM golang:1.25.13-trixie AS builder`). Two edges: a second matching builder
  stage yields a two-line `IMAGE` that passes the `-n` check and reaches `docker run` as one
  newline-containing argument (an obscure docker error rather than a clear one), and the pattern
  misses legal Dockerfile spellings — `FROM --platform=… golang:…`, multiple spaces, lowercase `as`.
  Cheap hardening: match `[[:space:]]\+[Aa][Ss][[:space:]]\+builder`, and assert exactly one match.

- **[low / confidence: medium]** `TODO.md:109-116` — the item "Add `deploy/caddy/ingress` to
  `/preflight`'s verification — no gate scans it today" is marked `[x]`, but `vulncheck.sh` adds
  *vulnerability scanning* only. `AGENTS.md`'s `go test ./...` and `go vet ./...` run from the repo
  root and do not cross the module boundary, so the ingress module still has no vet or test gate
  (its compilation is covered, but only incidentally, by `docker compose build`). Either narrow the
  closure text to what actually shipped or add the second module to the vet/test commands.

## Criteria

1. **Dead code — pass.** Nothing orphaned or commented out. `self_install` has two live call sites;
   both new environment variables are consumed; both new `Environment=` lines in the unit are read
   by the script. The three closed TODO items were marked done in place rather than left to rot.
2. **Flow tracing — pass** (with the findings above). `self_install` is defined after the `--check`
   early exit (`:344-348`) and before both call sites, so `--check` can never install. `deploy()`
   leaves the clone checked out at the ref it deployed and never restores it, so the files installed
   always match what is actually running — including the rollback path, where installing the *older*
   updater is the correct outcome. The function returns `0` on every path, so it can never trip
   `set -e` or convert a healthy deploy into a failure. State is written before the call on both
   paths (verified above).
3. **Standards conformance — pass.** Against the `bash` skill: `set -euo pipefail` in both files,
   every expansion quoted, `local` for function variables, `$()` throughout, no `eval`,
   `#!/usr/bin/env bash` on the new script. shellcheck is clean on `vulncheck.sh` and raises only
   two informational SC2015 notes on the new updater lines, where the flagged construct is the
   intended semantics. `vulncheck.sh` is 32 lines — well inside the "shell is the right tool" band.
4. **Directory layout — pass.** `deploy/vulncheck.sh` sits beside `host-setup.sh` where the other
   deploy-time shell lives; the updater files stay in `deploy/update/`. The install modes and paths
   in `self_install` match `host-setup.sh:347-349` exactly (`-m 755` → `/usr/local/bin`, `-m 644` →
   `/etc/systemd/system`), so the two installers cannot silently drift.
5. **Simplicity (DIY-except-security) — pass.** No new Go or JS dependency; `govulncheck` is pinned
   to a real published `@v1.7.0` and invoked as a tool, not vendored. The builder image is parsed
   from `Dockerfile.server` instead of being pinned a second time — one source of truth, which is
   the *less* complex option here, not the more. No hand-rolled auth, crypto, hashing, session or
   JWT/OIDC code anywhere in this diff; the release's trust anchor remains the existing signed-tag
   verification.
6. **Decoupling — pass.** `self_install` touches nothing `deploy()` owns and communicates with the
   rest of the script only through two globals and `DEPLOY_DIR`; `vulncheck.sh` reads
   `Dockerfile.server` and otherwise stands alone. Both files are independently editable — a second
   engineer working the deploy path would not collide.

vulncheck gate now returns govulncheck's own status — measured `EXIT=3` on this tree with the

## Fresh-eyes findings (round 2)

- **[low / confidence: high]** `deploy/update/styrman-update:375` — `atomic_install`'s
  `mv -f "${dst}.new.$$" "${dst}"` **succeeds** when `${dst}` is an existing directory, moving the
  temp file *into* it. Reproduced in the sandbox with `styrman-update.service` present as a
  directory: `install` succeeded, `mv` succeeded, `changed=1`, `failed=0`, and the function logged
  `updater self-installed from … (takes effect next run)` while the unit was never replaced and a
  `styrman-update.service/styrman-update.service.new.<pid>` orphan was created — one more per
  deploy, forever. The basename pin and `trusted_dir()` do not catch it (the pin only checks the
  name; `trusted_dir` checks the *parent*). The realistic shape is
  `STYRMAN_UPDATER_BIN=/usr/local/bin/styrman-update` where that path is a directory. **Fix:** use
  GNU `mv -fT` (`--no-target-directory`), which fails cleanly and routes into the existing
  `failed=1` + WARN path; or assert `[ ! -d "${dst}" ]` at the top of `atomic_install`.

- **[low / confidence: high]** `deploy/update/styrman-update:373` — the orphan sweep lives *inside*
  `atomic_install`, so it only ever runs for the file currently being replaced. Round 1 asked for it
  at the top of `self_install` for a reason: a `SIGKILL` mid-install leaves
  `/etc/systemd/system/styrman-update.service.new.<pid>` behind, and that orphan then survives every
  subsequent deploy until the `.service` file *itself* changes again — potentially months.
  Reproduced: with orphans planted for both the binary and the service and only the script drifting,
  `styrman-update.new.999` was removed and `styrman-update.service.new.999` survived. The glob
  itself is correct and safely scoped — `rm -f "${dst}.new."*` left an unrelated `unrelated.new.1`
  and a space-containing `keep me` untouched, unmatched globs pass through to `rm -f` as a literal
  and exit 0, and the fixed absolute prefix makes a leading-`-` argument impossible. **Fix:** one
  sweep at the top of `self_install` over `"${bin}".new.*` and `"${unitdir}"/styrman-update.*.new.*`
  (safe: the `flock` at `:142-143` guarantees no concurrent run owns one).

- **[low / confidence: medium]** `deploy/vulncheck.sh:40` — `|| rc=$?` is **last-wins, not
  worst-wins**. Module `.` reliably exits `3` today (the two accepted docker/docker findings), so
  any later failure of the ingress scan overwrites that `3` with a `1` and the run reports "the scan
  broke" while a real called-vulnerability finding is discarded; the reverse ordering hides a broken
  scan behind a `3`. That is a smaller version of the exact ambiguity round-1 finding 1 removed, and
  it makes the "Exit status is govulncheck's own" claim in `vulncheck.sh:9-12`,
  `testing/styrman/README.md:43-44` and the changelog true per *module* rather than per *run*.
  **Fix:** make `1` sticky, e.g. `s=$?; [ "${rc}" = 1 ] || rc="${s}"`, and say so in the header.

- **[low / confidence: high]** `deploy/update/styrman-update:366-368` — `trusted_dir()` is the
  **fourth** copy of "root-owned and not group/world-writable" in this file (`DOCKER_CONFIG`
  `:104-116`, `/etc/styrman/update.env` `:232-237`, `ALLOWED_SIGNERS` `:294-297`) and, being defined
  at `:366`, is too late in the file for any of them to use it. The predicate is now the script's
  central trust rule and deserves one definition near the top plus a file-shaped sibling; four
  hand-copies is how one of them eventually drifts.

- **[low / confidence: high]** `deploy/update/styrman-update:424` — the success line
  `updater self-installed from ${src} (takes effect next run)` is emitted whenever `changed=1`,
  including runs where `failed=1`. Observed sandwiched between `WARN: could not self-install …` and
  `WARN: self-install incomplete …`, which does disambiguate it, but the line itself asserts
  something untrue. Reword to "re-read units after self-install" or gate it on `failed=0`.

- **[low / confidence: high]** `deploy/vulncheck.sh:10` — the header comment lost its wrap during
  the edit: one ~110-column line in a file that otherwise wraps at ~78. Cosmetic only.
