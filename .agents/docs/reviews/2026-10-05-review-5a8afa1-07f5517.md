## Verdict: APPROVE WITH NITS

Nothing in the range is broken. I traced the code against the handler chain
(`previewHostRewrite(authGuard(csrfGuard(budgetGuard(mux))))`, server.go:456),
the route table and `config.UpdateOperator`, and it is correct. The worst
problem is a coverage gap in the security fix. 07f5517 moves two decisions
from the decoded path onto the matched pattern: the body cap and the upload
exemption from the body read deadline. Only the cap has a test that fails
when the change is reverted. Put `strings.HasSuffix(r.URL.Path, "/upload")`
back at budget.go:232 and every test stays green. The security report's
Outcome still marks its finding 1 "fixed", although it names both triggers.
Under the project's Definition of Done ("a finding is fixed only when every
trigger it names has a test that fails without the fix"), that Outcome line
overstates the evidence. The second gap is smaller: the "positive control"
in `TestTunnelsAreNotCharged` cannot fail. These are gaps in tests and
records, not defects in the code, so the verdict is not REQUEST CHANGES.

## Findings

- **[medium / confidence: high]** `internal/httpapi/budget.go:232` (`if !strings.HasSuffix(pattern, "/upload") { bodyDeadline(w, r) }`). Nothing tests the deadline half of the security fix.
  - `TestAnEncodedSlashDoesNotBuyTheUploadCap` (budget_test.go:268) sends its requests through `httptest.ResponseRecorder`. There, `http.NewResponseController(w).SetReadDeadline` returns "not supported", and `bodyDeadline` discards that error (budget.go:178). So the test cannot observe a deadline.
  - `TestBodyDeadlineCoversBudgetedRoutesButNotUploads` uses a real `/upload` path. Its path and its pattern both end in `/upload`, so it cannot tell the two keys apart.
  - Failure scenario: someone keys the exemption on `r.URL.Path` again. That is the pre-fix shape, still the natural one to write, and `uncharged()` beside it still keys on the path. Then `PATCH /api/projects/<id>/terminals/x%2Fupload` with a trickled body holds its budget reservation with no read deadline. That is the slow-body hold the deadline exists to stop, and the whole suite stays green.
  - The security report's Outcome item 1 (`.agents/docs/reviews/2026-10-05-security-v1.42.4-v1.42.3-5a8afa1.md:100`) cites a mutation for the cap key only, yet marks the whole finding fixed.
  - Fix: add the encoded-slash case to the real-socket test. Use `slowRequest` against `httptest.NewServer` with `PATCH …/terminals/x%2Fupload` and a small stalled JSON body, and expect 400 at the deadline. Then amend the Outcome so it names this test, or names the gap.
- **[low / confidence: high]** `internal/httpapi/budget_test.go:197-200` (`TestTunnelsAreNotCharged`). The "positive control" cannot fail.
  - The comment says "an API request of the same tenant is charged". The request it makes is for a different tenant (`n.admin`, not `-`) on `GET /api/version`, which has weight `fixed(0)` (budget.go:77) and is never charged. The assertion is also negated: it checks "not 503".
  - Effect: the test never shows that the held budget actually refuses a charged `-` request. The `/link/` assertion is sound today: `Acquire` clamps to the share, the share of 1 is fully held, and authGuard passes `/link/` through, so a charged link request would 503. But if a later harness change stops the hold from blocking, the link assertion would pass for the wrong reason, with no control to catch it.
  - Coverage: the test covers `/link/` only. Drop `isPreviewPath` or `isSharedPath` from `uncharged()` and it stays green. The earlier review's Outcome item 3 says "fixed" without naming that gap.
  - Fix: make the control a charged route for tenant `-` (or for the admin, with the hold on the admin's tenant) and assert 503. Name preview/shared/proxy as not covered, or add one case each.

The changed behaviour I checked was otherwise test-guarded:
- Revert the cap to path keying and `TestAnEncodedSlashDoesNotBuyTheUploadCap` goes red.
- Remove the keep-normalization in `updateRuntime` and `TestARuntimeSaveIgnoresUnchangedOutOfRangeValues` goes red. With the old code, the idle `5m0s` and the cap of 16 against an 8-CPU host both 400.
- Remove `bodyDeadline` from `budgetGuard`, or remove the upload exemption, and `TestBodyDeadlineCoversBudgetedRoutesButNotUploads` goes red. The network handler answers 400 only on a decode failure (network.go:97).

I ran the seven changed or added tests bare in `./internal/httpapi/` (`-count=1`): rc=0, all PASS. I ran no mutations myself: the brief forbids changing the tree.
