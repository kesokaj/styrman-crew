## Verdict: FINDINGS

The code in the range is clean. No finding is about the code. The worst problem
is what the range's root actions left on the production host (dave).
`/etc/styrman/gh-token` now holds the operator's personal `gh` OAuth login
token. Its scopes are `repo` (write to every repository), `admin:public_key`,
`gist` and `read:org`. The token sits where a read-only, two-repository token
used to be, and a root updater uses it for git and as a build secret. Second:
the trail now records that the release-signing key is a plain file with no
passphrase, on the same host where the coding agents run with passwordless
sudo. That key authorizes root deploys on the GCP VM as well. Both are recorded
as the operator's choices, and both are medium.

No credential material leaked into the trail. The range diff holds only SSH
public-key fingerprints and one ed25519 public key (a context line that was
already there). No token bytes, no private key and no passphrase appear. The
`write_status` locale fix holds under C, en_US.UTF-8 and C.UTF-8 (probe results
below). The shared lifecycle wait bounds what one tenant causes and cannot carry
one tenant's answer to another.

## Findings
- **[medium / confidence: high]** `.agents/docs/bugs/BUG-084-host-auto-updater-failing-unnoticed-v1.39.0-not-taken.md:26-27`, `.agents/docs/changes/2026-10-03-0344-dave-updater-token-and-key-protection.md:18-24`: an over-scoped credential was installed for a root daemon.
  - **What changed.** The updater needs Contents:Read on `kesokaj/styrman-crew` and `kesokaj/styrman-harness`. `/etc/styrman/gh-token` now holds the operator's `gh` login token instead, with write access to all of the operator's repositories plus `admin:public_key`. Root uses it in two places:
    - root's `git fetch`, through the inline credential helper (`deploy/update/styrman-update:578`);
    - every runtime-image build, as a BuildKit secret (`deploy/update/styrman-update:879` into `image/Dockerfile:192-194`). There the image's own `gh` binary, from an earlier layer, consumes it.
  - **Impact of a leak** (a root-readable file, a build step, a crash or debug dump): write access to every repository the operator owns. `admin:public_key` also lets the holder add an SSH key to the account, which is persistent push access. Two things make this worse than a dedicated token:
    - It is the operator's interactive session token. It has no expiry of its own.
    - After an incident it cannot be revoked without also logging out the operator's CLI.
  - **Signed tags still hold.** A leaked token alone cannot get code run as root, because hosts deploy only tags signed by an allowed key.
  - **Remediation.** Mint a fine-grained token: Contents: Read-only, those two repositories only, with an expiry. Install it the same way (`umask 077`, root:root 0600, through a pipe). Then rotate the `gh` login (`gh auth logout` followed by `gh auth login`, or revoke the OAuth grant) so the copy that was in `/etc` is dead.
- **[medium / confidence: high]** `.agents/docs/architecture/DECISIONS.md:2826-2830` (ADR-082 addendum): the release-signing key has no passphrase and sits on the production host.
  - **The key.** The original signer (`~/.ssh/id_ed25519` on dave, mode 600) has no passphrase and is held by no agent.
  - **What it authorizes.** It decides what runs as root on dave and on the GCP VM. The VM's updater deploys every tag signed by an allowed key, and per `DECISIONS.md:2823` its `allowed_signers` lists this key.
  - **Who can use it.** The account that holds the key runs the coding agents. `/preflight` signs tags with it, and the account has passwordless `sudo -n`. On dave the key therefore adds nothing beyond root. It does turn any compromise of that account into root on the GCP VM: sign a tag, then push it with the account's `gh` token. That includes a prompt-injected agent session.
  - **Status.** Accepted by the operator (`DECISIONS.md:2829`). It is recorded here so that the risk stays visible and is not taken for a fix.
  - **Remediation.** Make every signature need a human. Options:
    - a passphrase, with the key held in `ssh-agent` under `ssh-add -c` (confirm each use);
    - a hardware-backed `ed25519-sk` key;
    - signing on a machine where agents do not run.
- **[low / confidence: high]** `.agents/docs/changes/2026-10-03-0328-v1.41.0-deployed-on-dave-break-glass.md:12-14`, `.agents/docs/changes/2026-10-03-0344-dave-updater-token-and-key-protection.md:29`: root steps on the production host went through without the global context's gate.
  - **The rule.** A root step needs the operator's word AND a standing-permission record in `deploy/local.md` § Operator steps. The entry itself says "records no standing permission, and none was added". The break-glass deploy, the token install and the key inspection all went ahead on chat consent alone. `.agents/docs/deploy/local.md` has no Operator steps section (grep found none).
  - **Two of those steps crossed the signature gate's boundary:**
    - root git fetched from the operator's working checkout, which agents can write. The tag's signature was verified afterwards, so the content is safe;
    - `sudo deploy/styrman-ctl update` ran the working tree's unsigned copy of `styrman-ctl` as root.
  - **Why it is low.** The operator account already has passwordless sudo, so neither step is an escalation on dave. It is a step outside the "only signed code runs as root" principle, and outside the rule that keeps root actions from being reachable through conversation alone.
  - **Remediation.** The operator records a scoped standing permission in `deploy/local.md` § Operator steps, or agents keep handing root steps back with the exact command. Root tooling runs from the verified clone at the deployed tag, not from the working tree. Confidence on the "verified clone" part is medium: I did not check whether `styrman-ctl` is meant to run from `/opt/styrman`.
- **[low / confidence: low]** `.agents/docs/changes/2026-10-03-0344-dave-updater-token-and-key-protection.md:14-17`, `.agents/docs/handoffs/2026-10-03-0345-dave-updater-fixed.md:34`: the rejected token is kept at `/etc/styrman/gh-token.rejected-2026-10-03`.
  - **Why it may still be live.** BUG-084:21 says GitHub rejected it as "expired or revoked; which one was not established". If it was refused for any other reason, it is a live fine-grained credential kept for no purpose.
  - **Remediation.** Confirm in GitHub's fine-grained token settings that it is expired, or delete it there, then remove the file. Keep the record in the trail, not on disk.

- **Authz / tenant isolation of the shared wait (`internal/orchestrator/ports.go:138-209`):** no finding.
  - **What one tenant can cause.** At most one poller per (user, project, container). It asks Docker at most every 100 ms (`ContainerInspect` through `Status`) and stops within 20 s however many requests are parked. v1.41.0 polled once per parked request, N × 10/s; that path is gone.
  - **How a tenant keeps it running.** Both triggers are the tenant's: a guest-controlled non-zero exec code, and a lock hold from its own start or stop. So a tenant can keep one poller per own project (two during a container replacement) running continuously. That is bounded by its project count.
  - **New behaviour.** The poller runs on `context.Background()`, so it outlives a client that disconnects (up to 20 s). It is still one per key, so this is no amplification.
  - **Parked requests.** They are not capped per user, but each ends when its shared wait ends (at most 20 s) or when its own ctx does, the same exposure as any slow handler.
  - **Cross-tenant answers.** The key is `DeriveUsername` slug + `/` + project ID + NUL + Docker container ID.
    - The slug is `[a-z0-9_-]` only (`internal/identity/identity.go:14-34`), with no `/` and no NUL.
    - The project ID comes from `getProjectFor` (`internal/httpapi/proxy.go:21-26`; `browser.go:171,200,221` pass `u.Username`, `p.ID`).
    - So two tenants cannot share a key. The answer reads only the project's own container, and the lock is the same per-project lock as before.
  - **Data races.** `gone` is written before `close(done)` and read after `<-done`. `Delete` runs once per goroutine, and a new store can only follow it, so an earlier goroutine never deletes a later wait. The race-detector run above passes.
