## Verdict: FINDINGS

**Worst: finding 2 of the earlier review is answered for transcript reads only, not for its whole scope (medium).** f3a5f53 bounds `readHistory` correctly. It allows 8 reads server-wide (more get a 429), the slot is taken after authz, it is released on every path, and the 30 s write deadline does take effect in production. But that finding's goal was "no tenant can crash-loop the server under its 4g cap", and its "same class" list named the editor's file read. That path is still unbounded. One `GET …/file` holds up to 2 MiB of content plus about 12 MiB of escaped JSON, in a buffer that grows to 16 MiB. It has no slot and no write deadline. About 200-250 stalled requests from one tenant reach the cap. The earlier review's Outcome marks finding 2 "Fixed" without fixing, accepting or deferring these paths.

The token step from c350683/ef04b30 is confirmed. It no longer uses the `gh` login token, nothing passes through sudo's argv or environment, it does not overwrite an existing file, and it refuses an empty file. Four lows remain around it, listed below. The rest are lows.

## Findings

- **[medium / confidence: medium — computed from code, not measured: production host, no load experiments]** `internal/httpapi/explorer.go:77-91` (`readFile`), `internal/files/files.go:34` (`MaxReadBytes` 2 MiB) and `:314-315` (text whenever valid UTF-8 with no NUL), `internal/httpapi/server.go:1392-1396` (`writeJSON` builds the whole body before `Write`), `cmd/styrman/main.go:169-172` (only `ReadHeaderTimeout`: no `WriteTimeout`, no `ReadTimeout`).
  - **Weakness:** the memory-amplifying response path that f3a5f53 bounded for transcripts is unbounded for workspace and home files. The `<`, `>` and `&` characters are valid UTF-8 and escape to 6 bytes each, so a 2 MiB file becomes about 12 MiB of JSON. The encoder's buffer grows to 16 MiB, plus the transient copy made while it grows.
  - **Scenario:** a tenant writes a 2 MiB file of `<` in its own workspace. It opens about 200-250 concurrent `GET /api/projects/{p}/file?path=<it>` requests and reads none of the responses. Each one holds about 18-20 MiB live: no slot, no deadline. Some of that may sit in socket buffers, which are also charged to the container's cgroup. The server passes `mem_limit: 4g` and is OOM-killed, `unless-stopped` restarts it, and every tenant's sessions drop. The tenant can repeat this. `GOMEMLIMIT` cannot help, because the memory is live.
  - **Same class, still open:** the 8 MiB request bodies on `PUT …/file`, `/format` and `/check` (`server.go:702-716`). With no read deadline, a slowly trickled body keeps its decoder buffer alive. The earlier review also listed the browser relay's 16 MiB frames; I did not trace them.
  - **Why it is a finding here:** `reviews/2026-10-05-security-v1.42.2-v1.42.1-ef22f5c.md` finding 2 named these paths ("Same class … the editor's file read (2 MiB, x6 when escaped)"), and its remediation covered "every multi-MiB handler". Its Outcome item 2 says "Fixed" and mentions only `readHistory`.
  - **Remediation (stdlib, no new dependency):**
    - Put `readFile` behind `acquireSlot`, or better, one shared limiter weighted by MiB, together with the write deadline.
    - Set `http.NewResponseController(w).SetReadDeadline` on the large-body handlers.
    - Or stream the file content instead of marshalling it into a 6x buffer.
    - Test: stalled concurrent file reads past the limit get 429, with a must-fail run without the limiter.
    - If you accept the risk instead, record it in that review's Outcome; do not record it as fixed.

- **[low / confidence: high]** `internal/httpapi/explorer.go:445,518-521`, `internal/httpapi/server.go:186-188,267` — new cross-tenant starvation on transcript reads.
  - **Weakness:** the 8 read slots are server-wide, with no per-user share. A slot is held until the response is written or the 30 s write deadline fires.
  - **Scenario:** one allowlisted tenant plants a large transcript (4 MiB of `<`). It keeps 8 reads with `bytes=4194304` in flight and never reads the responses: 8 requests per about 30 s, at no CPU cost. Every other tenant's transcript view then gets 429 for as long as it keeps this up.
  - This is the same class as the search low that was accepted, but cheaper to sustain: the hold time is the deadline, not search CPU. Neither f3a5f53's change entry nor the Outcome mentions it for reads.
  - **Remediation:** a per-user share inside the global 8 (for example at most 4). Check the history panel's read pattern first: the per-user search cap was reverted for blocking a quick second request. Streaming the transcript (`text/plain` from the file) would remove the 6x buffer, and with it most of the reason for the bound.

- **[low / confidence: high]** `internal/httpapi/explorer.go:457-459` — the write deadline's error is discarded, and its comment claims a fallback that does not exist.
  - The comment says that without deadline support "the bound then falls back to the server's own timeouts". The server has none: `main.go:169-172` sets only `ReadHeaderTimeout`.
  - Today the deadline works. `internal/httpapi` has no ResponseWriter wrapper (`authGuard` and `csrfGuard` pass `w` through), and Go 1.25 resets the write deadline after each request (local GOROOT `net/http/server.go:2117`), so it does not leak into a keep-alive successor.
  - The risk is a future middleware wrapper without `Unwrap()` (logging, metrics, gzip). It would silently remove the only thing that frees a slot held by a client that never reads. No test would notice: both limit tests use `httptest.ResponseRecorder`, which does not support deadlines. The deadline is untested.
  - **Remediation:**
    - Correct the comment.
    - Log a warning when `SetWriteDeadline` returns an error.
    - Add a test over `httptest.NewServer` with a non-reading client and a short injectable deadline, asserting that the slot frees. Include a must-fail run.

- **[low / confidence: high]** `.agents/docs/deploy/remote.md:92-94`, `.agents/docs/specs/styrman/deploy.md:265-267` — three problems in the token snippet:
  - **(a) The error message can be wrong.** In `test -s F && sudo install … && shred -u F || echo "no token installed: … missing or empty"`, the `||` also catches a failed `install` or `shred`. Take a token file saved read-only (0400): `shred` cannot open it for writing without `-f`. The token is installed, the plaintext is not removed, and the operator is told no token was installed.
  - **(b) The plaintext file is not created safely.** The step says "Save it to a 600 file you own" but gives no command, and `test -s` checks neither mode nor owner. A file written by an editor, or by `echo <token> > ~/fine-grained-token` under umask 022, is world-readable until it is shredded. `echo` also puts the value in shell history, which is the exposure the step exists to prevent.
  - **(c) `shred` is not a guarantee.** It cannot promise an overwrite on SSD/NVMe, journaled or copy-on-write storage (GNU shred's own caveat; the GCP target uses Hyperdisk). "Removed" is accurate; the shred adds no real control.
  - **Remediation:** drop the plaintext file. The repo already has the right shape at `deploy/host-setup.sh:367` (`umask 077; read -rs t; printf …`), for example:

    ```
    sudo test -e /etc/styrman/gh-token || { read -rs t && [ -n "$t" ] && printf '%s\n' "$t" | sudo install -D -m 600 -o root -g root /dev/stdin /etc/styrman/gh-token; unset t; }
    ```

    That is the stdin form, which the earlier review measured as not logged on dave. Note the caveat for a host where sudo uses `log_input`. If you keep the file: create it with `(umask 077; cat > F)`, use `shred -fu`, and give the `echo` its own branch.

- **[low / confidence: high]** `deploy/host-setup.sh:301-306`, `deploy/update/styrman-update:567-572`, `deploy/styrman-ctl:510-512` — "never empty" is enforced only by the doc snippet.
  - All three consumers check owner and mode only. An empty or whitespace-only `/etc/styrman/gh-token`, or `--gh-token-file`, passes, and fails later as a GitHub auth error at build or fetch time.
  - c350683's subject says "never empty". The earlier review's finding 5 remediation (refuse an empty file in `host-setup.sh`) was not taken.
  - Impact is availability and diagnosability only; nothing is exposed.
  - **Remediation:** add `[ -s ]` and a non-whitespace check at the three consumers.

- **[low / confidence: medium]** `deploy/host-setup.sh:356-362` against `remote.md:36-39` and `remote.md:83-84` / `deploy.md:256-257` — two descriptions of the scope of the same token.
  - Step 8c's printed instructions say the updater token is "scoped to this ONE repository … Repository access = only this repo". ADR-074's image build reads `kesokaj/styrman-harness` with the same file, and the guides now say "Contents: Read on kesokaj/styrman-crew and kesokaj/styrman-harness".
  - An operator who follows 8c mints a token that fails the harness download at the next build. That kind of failure invites an ad-hoc broader token: the `gh` login token this range just removed from the docs.
  - **Remediation:** make 8c name both repositories.

- **[low / confidence: high — pre-existing, not introduced by the range; found while reading host-setup.sh end to end]** `deploy/host-setup.sh:240-248` — `deploy/.env` briefly readable by other local users.
  - The file holds the freshly generated `STYRMAN_INGRESS_TOKEN` and `STYRMAN_JWT_KEY`. It is created by `sed … > .env` under root's umask (normally 0644), and only chmodded to 600 after it is written and chowned.
  - A local user watching the directory can read it in that window. The ingress token is what stops a caller from spoofing `X-Caddy-Email`, so holding it means impersonating any user (`api.md:259`).
  - **Remediation:** write it in a `(umask 077; …)` subshell, or `install -m 600 /dev/null` first.

## Confirmed / refuted (the dispatch's questions)

- **f3a5f53, transcript reads: confirmed by reading.**
  - The slot is taken after `getProjectFor` (authz) and after the `bytes` clamp (`explorer.go:503-521`), so an unauthorised or other-tenant request cannot take one.
  - The release is deferred, so it runs on normal, error and panic paths.
  - `history.Read` (`history.go:216-267`) is safe on input: it validates the id with `idRe`, opens through `os.Root` (no symlink escape), and is FIFO/device-safe (`Lstat`, `O_NONBLOCK`, `fstat`).
  - Memory at 8 slots: about 8 × (4 MiB read + 3 copies + a 32 MiB encoder buffer), roughly 0.4 GiB or less. Add search's 4 slots (about 0.9 GiB, earlier review) and the total stays under GOMEMLIMIT=3GiB and the 4g cap. Computed, not measured.
  - `TestHistoryReadIsLimitedServerWide` discriminates: without the slot, the second request would be 200. It does not exercise the deadline.
- **f3a5f53, 30 s write deadline: confirmed effective for HTTP/1.x in production.**
  - There is no wrapper, and Go 1.25.0 locally and 1.25.13 in the builder both reset the deadline per request.
  - A client that never reads frees its read slot within 30 s. A search slot frees within its search time (at most about 7 s) plus 30 s.
- **f3a5f53 against finding 2 as a whole: refuted.** See the medium finding: the editor's file read and the large-body handlers are unbounded.
- **c350683/ef04b30, token step: confirmed.**
  - It does not use the `gh` login token.
  - No token value reaches sudo's argv, environment or stdin.
  - `sudo test -e … ||` prevents overwriting an existing file, and `test -s` refuses an empty source.
  - The result is root:root 0600, which passes `host-setup.sh:304-305`.
  - The `host-setup.sh:307` hint now names a fine-grained token and the file form.
  - `host-setup.sh` never writes `GH_TOKEN` into `/etc/styrman/gh-token` (read whole), so the earlier `--preserve-env` guidance cannot have left a broad token in the updater's file through that script.
  - The residual issues are the token lows above.
- **ef04b30, search revert: confirmed.** `explorer.go:482-485` has the server-wide 4 only. The fairness low was already accepted in the earlier Outcome.
- **c350683 `compose_oom_test.go` `serviceText`: scoped, and cannot pass vacuously.** It returns "" when the service is missing. Agrees with `reviews/2026-10-05-review-ef22f5c-c350683.md`.
