## Verdict: FINDINGS

The worst problem is new, measured evidence on the prior review's decided item 1 (whole host by default). It does not argue the decision again; it shows that the risk the operator accepted was described with the wrong victim. The prior finding said host OOM would usually kill "the largest cloud-hypervisor process". On dave, every Kata VMM runs at `oom_score_adj -999`, inherited from containerd. Its host cgroup has `memory.max = max`, and `vm.overcommit_memory = 1`. The production server `styrman-server` (pid 631457) and the Caddy ingress run at adj 0. So when whole-host-sized VMs drive the host out of memory, the kernel kills the shared control plane and the ingress first: every tenant loses the UI and terminals. The VMs causing the pressure keep running, and Docker restarts the server into the same pressure. The second finding is a documentation regression. The new post-release step (re-run `host-setup.sh` as root) is written as `sudo GH_TOKEN=… bash …` in four places. That puts the operator's broad `gh` token on sudo's argv and into sudo's log. The GCP line contradicts the project's own 2026-09-21 High, which was fixed so the token "never belongs on a command line". Everything else in the range holds:
- The new endpoint's authz and input parsing are sound.
- f507278's force-remove retry is bounded in every caller.
- The entrypoint grow gate crosses no boundary.
- `web/dist` is proven equal to a rebuild of the commit's own source.
- There are no secrets.
- The one new dependency bump is integrity-checked.

## Findings

- **[medium / confidence: high (measured adj and cgroup values), medium (exact victim order under real pressure; not provoked)]** `internal/orchestrator/resources.go:105-129` (unlimited means the whole host), `internal/httpapi/resources.go:150-161` (any owner may choose 0 = unlimited), with host facts measured read-only on dave — **the OOM victim is inverted: the shared control plane dies, not the VM.** This is new evidence on decided item 1 of `.agents/docs/reviews/2026-10-05-security-project-resources.md`; the decision itself is not re-argued.
  - **Measured:**
    - cloud-hypervisor pids 1167842 and 1361679 run at `oom_score_adj -999` (oom_score 22-23 at about 2.1 GB RSS).
    - Their host cgroup (`system.slice:docker:<id>`) has `memory.max = max`; one sandbox's `memory.current` was 17.6 GB.
    - containerd runs at -999 and dockerd at -500.
    - `styrman-server` (pid 631457 = `docker inspect styrman-server` State.Pid) runs at adj 0 (oom_score 666), and so does Caddy.
    - `vm.overcommit_memory = 1` and `vm.panic_on_oom = 0`.
  - **Scenario:** two tenants' default (whole-host, about 60 GiB each) projects run memory-heavy builds at once. One VM is enough when the host is otherwise loaded, and an agent-driven test suite can do it by accident.
    - Overcommit 1 never refuses the allocations, and the VM cgroups have no limit, so the global OOM killer runs.
    - With every VMM at -999, the highest-scoring tasks are the adj-0 ones: the styrman server, the ingress and other host services.
    - The control plane is killed, restarted by Docker, and killed again while the pressure lasts.
    - The admin's tool to stop the offending project is the thing being killed, so recovery needs a host shell.
  - **Remediation (the cap or no-cap choice stays the operator's):**
    - Invert the priorities: give the server and the ingress a strongly negative `oom_score_adj` in the compose file (for example -900).
    - Make the VMMs the preferred victims: a positive adj applied to the VMM processes by a host-setup step or a containerd/shim drop-in. Measure that it sticks per sandbox.
    - Add the corrected victim statement to ADR-083's Consequences.
    - Re-confirm the whole-host default with the operator before tagging. The premise they accepted ("another tenant's VM may be killed") is not what this host does.

- **[medium / confidence: high (argv placement and the project's own classification), medium (where the value persists on each host)]** `.agents/docs/deploy/gcp.md:196`, `.agents/docs/deploy/remote.md:30`, `.agents/docs/specs/styrman/deploy.md:159`, `.agents/docs/plans/2026-10-05-project-resources.md:399` — **the new post-release step puts the GitHub token on a sudo command line.**
  - **The documented commands:**
    - `sudo GH_TOKEN=$(gh auth token) bash /opt/styrman/deploy/host-setup.sh …`
    - on GCP: `deploy/gcp/vm.sh ssh -- 'sudo GH_TOKEN=… bash …'`
  - **Where the value goes:** it becomes sudo's argv. Any local account can read it in `/proc/<pid>/cmdline` for the whole run, and sudo records command-line environment assignments in its log. The project's own words for this form are "a sudo-logged command line" (`.agents/docs/reviews/2026-09-21-review-e5bd830-docs.md:52-55`).
  - **GCP line:** the single quotes stop local expansion, so the operator substitutes the value by hand. Whatever they substitute reaches sudo's argv and log on the VM, and a pasted literal also lands in the Mac's shell history.
  - **Precedent:** the 2026-09-21 GCP review rated this exact shape **High** on the VM and fixed it. The token now goes "by path only (`--gh-token-file`) … environment only, never argv" (`.agents/docs/reviews/2026-09-21-security-gcp-compute-engine-target.md:198`; `.agents/docs/changes/2026-09-21-gcp-compute-engine-target.md:36`).
  - **remote.md:30 contradicts itself:** it says the GCP run goes "with a token file — see gcp.md", but gcp.md:196 shows `GH_TOKEN=…`.
  - **Which token:** per the 2026-10-03 handoffs (Key Decisions), this is the operator's broad `gh` login token, not a fine-grained one.
  - **Remediation:** document the token-file paths that already exist:
    - `deploy/host-setup.sh:286-293` reads root-owned, mode-600 `/etc/styrman/gh-token` and refuses a loose one.
    - `deploy/host-setup.sh:353` prints a stdin-only recipe to install that file.
    - `styrman-ctl install --gh-token-file <600 file>` exports the token inside its own process.
    - On GCP, reuse `install.sh`'s token-file transfer.
    - Where `/etc/styrman/gh-token` already exists, drop `GH_TOKEN=` from the line entirely.
    - This is docs-only and cheap; fix it before the operator runs the step.
