## Findings (Gaps)

- **[low / confidence: medium]** Interfaces → `deploy/gcp/vm.sh status`'s exit-code scheme (plan lines 168–171: "Exit 0 running+healthy, 1 running+degraded/not installed, 2 no instance") has no distinct case for an instance that **exists but is `stop`ped** — a state `vm.sh stop`/`start` (kept in scope per D9, the plan's own cost-saving mechanism) deliberately creates. If a stopped-but-existing instance also reports exit 2, `install.sh` step 1 ("`vm.sh status` must report RUNNING (exit 0 or 1); else stop with 'run `deploy/gcp/vm.sh create` first'") gives the wrong remedy: `create`'s own documented behavior for an already-existing instance is a no-op that "print[s] its state and IP, exit 0" — it does not start a stopped instance. An operator who ran `vm.sh stop` to save the ~USD 230/month difference (the plan's own Cost risk) and later re-runs `install.sh` (e.g. to redeploy a new version) would be told to run `create`, which would silently do nothing useful, rather than `start`. Non-blocking: a first-pass implementer following the letter of the spec produces working code either way (the precondition still correctly refuses to proceed against a non-running VM); the only defect is the message text pointing at the wrong follow-up command. Worth a one-line fix (`vm.sh status`'s exit-2 message, or `install.sh`'s own precondition message, should say "create or start" when the instance exists but isn't running) but does not fork the implementation.

- **[low / confidence: low]** Interfaces → `deploy/gcp/install.sh` step 7's verify curl, `https://<STYRMAN_HOSTNAME:-styrman>.<BASE_DOMAIN>/`, implies `install.sh` reads an optional `STYRMAN_HOSTNAME` key from `--env-file` (defaulting to `styrman` if absent) to build the URL it checks — but the Interfaces section's `--env-file` documentation only names the six must-fill keys it validates ("each must be non-empty… `--gh-token-file`: …"); `STYRMAN_HOSTNAME` is never listed as a key `install.sh` reads. Since Phase 2's own env-file-derivation task explicitly writes `STYRMAN_HOSTNAME=crew` into the generated file, this resolves correctly in the one bring-up the plan performs, but a from-scratch implementer reading only the Interfaces section would have to infer that `install.sh` parses this extra, optional key rather than hardcoding the default. Non-blocking: any reasonable implementation (read it if present, default to `styrman` if not) satisfies both the Interfaces prose and the Phase 2 bring-up.

- **[low / confidence: low, operational not design]** `deploy/gcp/install.sh` step 2 ("Remote: `sudo apt-get install -y -q git curl python3`") does not run `apt-get update` first. A freshly-created Debian 13 GCE instance's package index may be stale enough (or, per Google's image-build convention, usually is populated but not guaranteed current) that the install could fail with "unable to locate package." This is a smoke-test-time risk, not a design ambiguity — the fix, if it surfaces during Phase 2, is a one-line addition an implementer makes without needing a design decision.
