# Review: v1.42.0-2ba3f79   (2026-10-05)

Range reviewed: v1.42.0..2ba3f79 (0debdd7 handoff, 2ba3f79 OOM + review follow-ups)

## Status: COMPLETE

## Verdict: REQUEST CHANGES

No code defect ships in this range. The compose setting is valid, the reaper and recreate changes are correct, and the extended fake leaves every older test meaning what it meant. Two gaps need fixing first. (1) ADR-084 names a guard against a leaking server that does not exist. Docker without Swarm never restarts a container for being unhealthy, and the server's HEALTHCHECK is read only by the updater's release check. At -1000, with no memory limit, a leaking server is never killed: the kernel kills the VMs and the host's services around it instead. The ADR also says -1000 is "the only value that ranks below the VMs". That is imprecise, and it rejected -999 without considering it. (2) The behaviour this range changes in `ReapSetupVMs`, one deadline per pass instead of one per VM, has no test. Putting back the per-VM `WithTimeout(ctx, time.Minute)` leaves every test green, and the Definition of Done counts changed code without a covering test as a FAIL.

## Findings

- **[medium / confidence: medium]** `.agents/docs/architecture/DECISIONS.md:2866` (ADR-084 Consequences), `:2859` (Decision), `:2861-2864` (Rejected).
  - **False guard.** The Consequences line says "A server that leaks memory is never killed by the kernel; its own health check and restart policy remain the guard."
    - Neither one acts on a leak. `restart: unless-stopped` fires only when the process exits, and an `oom_score_adj -1000` process never exits through the OOM killer.
    - Docker without Swarm does not restart an `unhealthy` container. The `HEALTHCHECK` in `deploy/Dockerfile.server:25` is consumed only by `deploy/update/styrman-update:912-931` (`reports_version`, release verification).
    - `deploy/docker-compose.yml` sets no `mem_limit` on the server.
    - Scenario: the server leaks. Before this change it was the kernel's first pick and Docker restarted it. Now the kernel kills ordinary host processes, dockerd (-500), and then every project VM (-999) by size, while the leaking server survives. The host ends up worse off than before.
  - **Inaccurate ranking claim.** "The only value that ranks below the VMs" is imprecise. The kernel's `oom_badness` computes `rss + adj*totalpages/1000`, so at an equal -999 the larger RSS dies first. A server at -999 ranks below every VM bigger than itself and stays killable once its own leak makes it the biggest. The Rejected list covers "-900 or similar" but not -999.
  - **Fix.** Correct the Consequences line so it says no mechanism restarts a leaking server, then let the operator choose:
    - keep -1000 and accept that a server leak is unguarded, or
    - use -999 for `styrman` (Caddy can stay at -1000), so the RSS tie-break keeps the server killable as the last resort. This is my recommendation.

    Either way, add the -999 alternative to Rejected or Decision. My confidence in the kernel's tie-break is high. The confidence is medium because the victim order was never provoked on a real host; the preflight report says the same.

- **[medium / confidence: high]** `internal/orchestrator/orchestrator.go:1680` with `internal/orchestrator/destroy_zombie_test.go:106-148`: nothing tests the per-pass deadline. No test sets `reapPassBound` (grep: only the declaration at `orchestrator.go:1475` and its use).
  - `TestReapSetupVMsWaitsOutAnExitingVM` has one VM that clears after three removes. It passes under both the old per-VM bound and the new per-pass bound.
  - Fix: plant two setup VMs whose remove always answers `zombieErr`, set `reapPassBound = 50*time.Millisecond` and `zombieRetryEvery = time.Millisecond`, and assert that `ReapSetupVMs` returns in under about 2× the bound. Under a per-VM bound it takes at least 2× the bound (or 2 minutes with the old hardcoded minute), so the test fails.

- **[low / confidence: medium]** `internal/orchestrator/orchestrator.go:1681-1684`: when one VM uses up the pass's deadline, every later VM's `ContainerInspect(rctx)` fails at once and is skipped by `continue`, with no log line.
  - Scenario: a setup VM never finishes exiting. Each 2-minute tick spends its minute on it, and any abandoned setup VM listed after it is never reaped. Nothing in the log says VMs were deferred.
  - The impact is small: Docker lists newest first, so only VMs created before the stuck one are starved.
  - Fix: check `rctx.Err()` at the top of the loop, log how many VMs were deferred, and `break`. Inspect with `ctx` so an expired deadline cannot read as "not running".

- **[low / confidence: high]** `.agents/docs/changes/2026-10-05-1433-oom-protection-and-review-follow-ups.md` (Tests bullet) says of all three new tests: "Each was mutation-checked: putting back the one-shot remove fails it."
  - `TestReapSetupVMsLeavesAYoungVM` (`destroy_zombie_test.go:138`) never reaches a remove, so that mutation cannot fail it. Only a broken age check fails it.
  - Its pass also depends on the label filter matching: an empty `ContainerList` would pass it vacuously. The sibling test guards that today.
  - The coverage claim is wrong for one of the three tests. The entry is append-only, so correct it in the handoff or the next entry.

## Answers to the dispatch's questions

- **`oom_score_adj -1000`: Docker and Compose acceptance.** Valid.
  - The compose spec key is `oom_score_adj`, and the Engine accepts `HostConfig.OomScoreAdj` in [-1000, 1000]. runc sets the value as root before exec, so it works even if a service runs as a non-root `user:`.
  - The change entry says `docker compose config` renders both services. I did not re-run it.
  - Children the server forks inherit -1000. They are short-lived host-side tools, so this is not a concern.
- **A leaking server.** See finding 1: nothing guards it.
- **The updater's compose invocation.** Both invocations use `-f .../deploy/docker-compose.yml` (`deploy/styrman-ctl:516` and `:776`), so the setting reaches the NUC and GCP.
  - The changed service config makes compose recreate both `caddy` and `styrman` at the release. That means a short ingress restart, as at any release.
  - A rollback to v1.42.0's compose returns both to 0.
  - `deploy/host-setup.sh:435` runs `docker compose up` without `-f`, from the clone's `deploy/` directory. It would also auto-load a local `docker-compose.override.yml`, but the repo has none.
- **Does the compose test parse robustly or pass vacuously?** It is robust enough and cannot pass vacuously.
  - A missing service is a `Fatalf`. A missing line or a different value (for example -999) is an `Errorf`. A commented line does not match exactly.
  - A 2-space key ending in `:` under `networks:` or `volumes:` starts its own block, so it does not mix into `caddy` or `styrman`.
  - The change entry says the test was red before the compose edit; I did not re-verify that.
  - It does not see an override file or an env-interpolated value. Neither exists today.
- **The reaper's single deadline.** It is correct, and it is acceptable for one stuck VM to use the whole bound: the bound (1 min) is half the tick (2 min), and the idle-project pass that follows is no longer held for N minutes. The two gaps are the missing test (finding 2) and the silent deferral (finding 3).
- **Does the extended fake change any existing test's meaning?** No.
  - `ContainerList` returns nothing unless a test sets `list`, so the default path is byte-for-byte the old one.
  - `StartedAt` is `""` for every container no test sets, exactly as before.
  - `labels` is stored at create time and read only by the opt-in list.
  - The fake ignores `ListOptions.All` and key-only label filters. No current caller depends on either.
- **Can each new test fail?**
  - Reaper-waits: yes. A one-shot remove leaves the container in place, and a broken label filter means nothing is listed.
  - Recreate-waits: yes. A one-shot remove returns "recreate for workspace bind" from `EnsureRunning`.
  - Young-VM: yes, but only through the age check (finding 4).
  - Compose: yes.
  - I ran all five: they pass (`go test -run 'Compose'` in `internal/config`, and `-run 'Reap|PreADR027|Zombie|Exiting'` in `internal/orchestrator`, both exit 0). I did not mutate any source, since the reviewer may not.
- **The pre-ADR-027 recreate's `forceRemove(ctx)`.** It cannot loop forever: every `EnsureRunning` caller passes a bounded context (`server.go:965,1066,1197`, `resources.go:142`, `network.go:120`, each 2 to 5 minutes, or the WebSocket request context). It holds the project lock for at most that bound, which is the same exposure `Destroy` already has.
- **The `integration.sh` truncate.** The guard order is right: the VM is stopped, the path is a regular file, it is not a link, its realpath equals the path, and `truncate -c` never creates a file.
  - It fails closed (a red check, not an unsafe truncate) if `STATE` has a symlinked ancestor.
  - The check count is unchanged because the check was replaced in place.
