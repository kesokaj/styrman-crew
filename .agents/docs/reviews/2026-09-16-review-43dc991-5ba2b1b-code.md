# Review — 43dc991..5ba2b1b (fix rounds after the whole-feature reviews)   (2026-09-16)

## Verdict: REQUEST CHANGES

Nothing in the range is functionally broken — every fix I could trace does what its commit message claims, `go vet ./...` is clean and `go test ./internal/orchestrator ./internal/config` is green. The problems are all of one kind, and it is the kind this project has a rule for: **three descriptions of behaviour the fixes changed were left standing**. The sharpest is `deploy/styrman-ctl`'s new refusal of `STYRMAN_HARNESS_REPO_DIR` / `STYRMAN_HARNESS_ORIGIN`, which `specs/styrman/deploy.md` still advertises as operator overrides — an operator following the living doc now gets a hard `exit 1`. The second is `harnessBinds`'s own doc-comment, which still tells the next reader that "a refused channel never rebuilds a container", the exact rule commit cafd632 inverted. Secondarily, the new Tier 2 remount check hides the `mount` command's status, so it can pass without ever having remounted anything.

## Findings

- **[medium / confidence: high]** `.agents/docs/specs/styrman/deploy.md:359-361` — the harness-setup paragraph still documents "clones `https://github.com/kesokaj/styrman-harness.git` (override `STYRMAN_HARNESS_ORIGIN`) to `/opt/styrman-harness` (override `STYRMAN_HARNESS_REPO_DIR`, default beside the crew clone)". Commit cafd632 added both names to `deploy/styrman-ctl:49`'s test-seam list, so outside `STYRMAN_CTL_TEST=1` either variable now aborts the run with "is a test seam, not a production knob (unset it)". The living doc describes a capability the code refuses. Fix: say the two variables are test seams and that the origin and clone path are fixed (the origin defaults to the styrman-harness repo, the clone to `/opt/styrman-harness`), in the same change.
- **[medium / confidence: high]** `internal/orchestrator/harness.go:37-38` — `harnessBinds`'s doc-comment still ends "…untrusted, which the caller treats differently from absent (a refused channel never rebuilds a container)". The caller no longer does: `orchestrator.go:365` is now `case has && len(hbinds) == 0` and cafd632's whole point (and its new test at `harness_test.go:329`) is that a refused channel DOES drop the binds. A stale contract line beside the function is read as a guarantee by whoever next changes the recreate rule. Fix: replace the parenthesis with the one-comparison rule the caller now implements. Same sentence survives in `internal/orchestrator/harness_test.go:21-22` ("An untrusted channel changes nothing.") and in `.agents/docs/plans/2026-09-16-harness-channel.md:30` ("A trust failure on a present channel is NOT a recreate trigger: it logs a WARN and the container starts as it is") — the plan's design paragraph is what a cold reader reads before the code.
- **[medium / confidence: medium]** `.agents/docs/testing/styrman/integration.sh:142-143` — the new check runs `mount -o remount,rw /styrman/harness 2>/dev/null; ! touch …`. The remount's exit status is discarded, so if `mount` is absent from the runtime image, refuses the remount, or names the mountpoint differently, the check degenerates into the plain read-only check two lines above and still reports PASS under the name "guest cannot write the channel even after remounting it rw (host-side ro, R12)". That is the BUG-034/BUG-040 shape the project's own rules name: a green signal that measured something else, and here it is the *security* property (host-side `:ro` enforcement) that would silently stop being tested. Fix: assert the remount actually took effect before asserting the write fails — e.g. require the remount to exit 0 and `grep -E ' /styrman/harness .*\brw\b' /proc/mounts` (or `/proc/self/mountinfo`) to match — so a guest that cannot even attempt the remount fails the check rather than passing it.
- **[low / confidence: medium]** `deploy/styrman-ctl:27,49` — the new refusal of `STYRMAN_HARNESS_REPO_DIR` is bypassable through a variable the same block keeps allowing: `HARNESS_REPO_DIR` defaults to `$(dirname "${DEPLOY_DIR}")/styrman-harness`, and `STYRMAN_DEPLOY_DIR` is documented two lines above as a knob. Under the `sudo -E` scenario the comment names, an attacker who can set `STYRMAN_DEPLOY_DIR` still chooses the tree root clones into and (via `uninstall`) the neighbourhood root deletes from. The pre-existing `STYRMAN_DEPLOY_DIR` power is out of range, but the fix's claim that the harness path is "refused outside the harness" is not true as written. Fix: derive `HARNESS_REPO_DIR` from a literal (`/opt/styrman-harness`) rather than from `DEPLOY_DIR`, or add `STYRMAN_DEPLOY_DIR`'s derived paths to the same assertion.
- **[low / confidence: high]** `deploy/update/styrman-update:859` — the new harness-unit block sweeps `${unitdir}/${hf}.new.*` only inside the `differs` branch, where the equivalent self_install block sweeps orphans for ALL targets up front precisely because that was an earlier review finding (`styrman-update:765-767`, "an earlier SIGKILLed attempt"). A `.new.<pid>` left in `/etc/systemd/system` by a killed run is never removed once the unit matches again. Inert to systemd (not a unit suffix), so litter rather than a defect — but it re-opens a finding the neighbouring code already closed.
