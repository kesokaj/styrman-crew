## Findings (Gaps)

- **[medium / confidence: high]** Scope → "In" (plan lines 46–49) names `deploy/README.md`, `README.md` (host list), `AGENTS.md` Deploy section, `.agents/docs/testing/styrman/README.md` Tier 1 count, and ADR-075 as deliverables; D1 (line 357) repeats "the ADR-075 to write." None of the Phase 1 or Phase 2 checklist items (lines 315–329) carries a `docs:` clause pointing at any of these five — only `.agents/docs/deploy/gcp.md` (Phase 1's `vm.sh`/`install.sh` tasks) and `.agents/docs/specs/styrman/versioning.md` (the `verify-commit.sh` task) are wired in. Neither Phase's Checkpoint "expect" line (319, 329) checks for their existence either. An implementer who treats the Phase checkpoints as the plan's completion gate — the pattern the rest of the document trains, e.g. Phase 1's checkpoint literally lists `go test`/`go vet`/shellcheck as its only "expect" — can satisfy both checkpoints without writing ADR-075 or touching the other four files. This is exactly the "a task changing a command, flag, endpoint, config key or deploy step with no docs clause" case the project's own Definition of Done calls out (step 3, "a new command, flag, endpoint, or deploy step is not done until the file that describes it says so"); `internal/config/gcp_scripts_test.go`, `deploy/gcp/vm.sh`, `deploy/gcp/install.sh` are new commands/deploy steps with no such clause covering four of the five files Scope already promised for them. Add explicit tasks (or `docs:` clauses on the existing ones) for each of the five, or state in Decisions that they are left to the standing `documentation` dispatch outside this plan.

- **[medium / confidence: medium]** Interfaces → `deploy/gcp/vm.sh` (plan line 124) declares `[--yes] create` in the usage grammar, but the flag's effect is never stated. `create`'s described flow (lines 138–153) is fully automatic — describe the address, describe the instance, create either if absent, wait for ssh, print the IP — with no interactive step for `--yes` to skip; `delete`'s confirmation is a separate, typed `--confirm <NAME>` mechanism (line 160), not gated by `--yes` in the text. Given the Risks section itself flags `create` as provisioning a resource costing "roughly USD 250–300/month while running" (line 351), a reasonable implementer might add a cost-confirmation prompt to `create` gated by `--yes` (mirroring `styrman-ctl`'s own `ask()`/`--yes` convention cited at line 69–70); another, reading the fully-automatic flow as written, would treat `--yes` as accepted-but-unused. `TestGCPVMCreatePlan`'s spec (lines 240–246) doesn't mention `--yes` at all, so the test suite doesn't settle it either. Say explicitly what `--yes` does for each of `create`/`status`/`ssh`/`stop`/`start`, or drop it from the grammar if it does nothing.

- **[low / confidence: medium]** Interfaces → `deploy/gcp/vm.sh create`'s tail — "then waits until `ssh -- true` succeeds (≤ 5 min) and prints the external IP" (line 153) — doesn't state its `--dry-run` behavior. Under `--dry-run` the real `instances create`/`addresses create` calls never run (line 135–137: "prints `+ gcloud …` and runs nothing"), so there is no real instance to ssh into or IP to print; `TestGCPVMCreatePlan`'s spec (240–246) asserts only the two `create` lines appear in the dry-run plan, which by omission implies the wait/print tail is skipped entirely under `--dry-run`, but the Interfaces prose never says so. An implementer who takes the "every side effect goes through `run()`" rule literally could instead have the wait loop attempt a real `ssh -- true` under `--dry-run` (since `ssh` there isn't obviously a "write"), which would hang for up to 5 minutes against a VM that (under dry-run) doesn't exist and turn `TestGCPVMCreatePlan` into a slow, likely-failing test. One sentence closes this ("the wait+print tail is itself wrapped in `run()`/skipped entirely under `--dry-run`") would remove the ambiguity; as written it's inferable but not stated.

- **[low / confidence: low]** Interfaces → `deploy/gcp/vm.sh`'s validation guarantee — "Instance name, zone, project and tags are validated against [regexes] before reaching any command line" (163–165) — doesn't cover `install.sh`'s `--user <U>` (default: local `$USER`, but overridable), which is interpolated into the remote `styrman-ctl install --yes --user <U> …` command string assembled locally (step 5, line 219). This is the same risk class `TestGCPVMRejectsBadNames` (249–250) exists to close for `vm.sh`'s own inputs, but no equivalent test or regex is named for `--user`. Low severity/confidence because it matches the codebase's existing risk tolerance — `styrman-ctl`'s own `--user`/`$SUDO_USER` isn't regex-validated either (`deploy/styrman-ctl:446`, `host-setup.sh:29`, just a non-empty + `id` check) — so this isn't a regression, just an unaddressed edge the plan could have closed while it was already adding the analogous guard for the other four values.
