## Verdict: FINDINGS

The eight fixes the previous round applied are correct and, with one exception, complete:
the every-tick unit install adds **no** new path for an unverified tree (it inherits the
firewall converge's full gate — `REQUIRE_SIGNED`, unit-pinned targets, root-owned
`bindir`/`unitdir`, `deployed-sha` equal to the deploy clone's `HEAD`, the clone and its
`.git` asserted root-owned and not group/world-writable at `styrman-update:561-569` before
`host_converge` runs at `:1013`, and content read from the git OBJECT via `git show
${SELF_HEAD}:…`, never the worktree); the smoke home under the content dir cannot reach
anything the server trusts (`harnessTrusted` reads the content dir and `current` only, and
only root can write `current`); dropping the binds on a refused channel costs one
remove+create per stopped project on the transition and then stops, which is the right
trade against re-resolving a bind source the server has just refused. The exception is the
new origin check: `setup_harness_channel` validates `STYRMAN_HARNESS_ORIGIN` with
`printf … | grep -qE '^https://…$'`, which is **line-wise**, while the crew clone's
`https_origin()` — the check it says it mirrors — uses bash's whole-string `[[ =~ ]]`. A
multi-line value whose SECOND line is a valid https URL passes the new check (measured:
`grep` rc=0) and the whole value, first line included, is what reaches the root
`git clone --`. The seam guard at `:49` refuses the variable outside `STYRMAN_CTL_TEST=1`,
but `STYRMAN_CTL_TEST` is itself an ungated ambient variable, so both are settable in the
one scenario — a poisoned environment under `sudo -E` — that the guard's own comment names.

## Findings

- **[medium / confidence: medium]** `deploy/styrman-ctl:653-654` — still live at 2f86816.
  The new plain-https gate is
  `printf '%s' "${HARNESS_ORIGIN}" | grep -qE '^https://[a-z0-9.-]+/[A-Za-z0-9._/-]+$' || die …`.
  `grep` anchors per LINE, so a value with an embedded newline passes whenever ANY line
  matches — confirmed here against the exact regex, rc=0 for
  `"ext::not-a-url\nhttps://github.com/a/b"` (no git involved; the property is grep's).
  The value then reaches `run env GIT_TERMINAL_PROMPT=0 git … clone -- "${HARNESS_ORIGIN}"`
  (`:671`) whole, and git selects a transport from the string's PREFIX — the first line.
  `--` blocks option-shaped values, not a non-https transport (`ext::` executes its
  argument). By contrast `https_origin()` (`:448`), for the crew clone, uses
  `[[ "${o}" =~ ^https://[a-z0-9.-]+/[A-Za-z0-9._/-]+$ ]]`, which bash evaluates against the
  WHOLE string, so an embedded newline is refused there. The new check is therefore
  strictly weaker than the one its comment cites as its model. Reachability: the seam guard
  (`:49`) refuses `STYRMAN_HARNESS_ORIGIN` unless `STYRMAN_CTL_TEST=1`, and that variable
  has no gate of its own (`:48`, `:964`), so an environment that can set one can set both —
  the `sudo -E` threat model the guard was written for. I did not test whether git takes the
  first line's transport from a multi-line argv (that is exploit work), hence medium
  confidence on impact; the weakness in the check is certain. **Remediation, one line:** use
  the form `https_origin()` already uses —
  `[[ "${HARNESS_ORIGIN}" =~ ^https://[a-z0-9.-]+/[A-Za-z0-9._/-]+$ ]] || die …`.
- **[low / confidence: high]** `deploy/styrman-ctl:583,657` — still live at 2f86816. The fix
  single-quoted `${ETC_DIR}` inside both credential-helper snippets, which stops a SPACE or
  a `$(…)` in the path from being evaluated by git's shell as root. A single QUOTE in
  `ETC_DIR` still closes the quoting and hands the remainder to that shell. `ETC_DIR` is
  refused as a production override outside the test seam, so this is hardening, not an open
  door — but the updater already solved the same problem properly on the same feature:
  `styrman-update:375-376` exports `HARNESS_GH_TOKEN_FILE` and writes the helper in a
  bash single-quoted string so the path is never interpolated at all, and git's shell reads
  it from its own environment (`"$(cat "${HARNESS_GH_TOKEN_FILE}")"`). **Remediation:** copy
  that shape into `styrman-ctl` for both helpers — export the path, interpolate nothing.
- **[low / confidence: high]** `internal/orchestrator/orchestrator.go:355-370` — still
  live at 2f86816 (`orchestrator.go` is untouched there; 2f86816 fixed only the two
  COMMENTS that described this rule, not the code). The comment and the plan's D26 state the rule as "one comparison: the binds a
  STOPPED container carries must equal what `harnessBinds` answers now", and both new tests
  are named for it. The code compares PRESENCE, not equality: `hasHarnessBind`
  (`harness.go:131-138`) returns true for any bind whose destination is `/styrman/harness`,
  whatever its source, and the switch fires only on `len(hbinds) > 0 && !has` or

  `harnessBinds` would mount — the operator moves `STYRMAN_HARNESS_DIR`, or a release

## Answers to the dispatch's explicit questions

- **Does the every-tick unit install open a path for an unverified tree to place a unit?**
  No. `host_converge` (`styrman-update:807-870`) reaches the new block only after: both
  `STYRMAN_FW_INSTALL_BIN` and `STYRMAN_UPDATER_UNIT_DIR` are set (unit-pinned, ADR-052, no
  in-script default); `REQUIRE_SIGNED=1` (read — not sourced — from a root-owned,
  non-group/world-writable `/etc/styrman/update.env`, anchored grep); the firewall binary's
  basename pinned; `trusted_dir` on both `bindir` and `unitdir` (exists, root-owned, no
  `/022`); `deployed-sha` present, 40-hex, and EQUAL to `git rev-parse HEAD` in the deploy
  clone; and the firewall trio present in the tree. Above all of it, before `host_converge`
  is ever called, the top level asserts `trusted_dir "${DEPLOY_DIR}"`, `.git` root-owned and
  `.git` not group/world-writable (`:561-569`) — which is what makes the `-c safe.directory`
  waiver in the `git()` wrapper safe, and what keeps a non-root local user from planting a
  `refs/replace/` ref that would change what `git show ${SELF_HEAD}:…` resolves to. Content
  comes from the git OBJECT, never the worktree; `atomic_install` writes a temp file,
  `chmod 644`, `chown root:root`, then `mv -fT`. `--check` counts drift and installs nothing.
  Two non-findings worth naming: (a) the harness block sits AFTER the firewall loop's
  "pre-ADR-065 tree → `return 0`", so a verified tree carrying the harness pair but not the
  firewall trio would skip the harness install — impossible in practice (ADR-065 predates
  ADR-073), and it fails closed; (b) a failed harness install sets the shared `failed=1`,
  whose closing WARN names only the firewall script — cosmetic.
- **Can the smoke home under the content dir affect what the server trusts or mounts?** No.
  `harnessTrusted` (`harness.go:64-104`) inspects the content dir itself, `current`,
  `current`'s resolved target, and that target's `repo`/`bin` and two files; it never
  enumerates the dir's other entries, and nothing in the server reads `.smoke-*`.
  `harness_swap`'s cleanup enumerates, but only removes `.tmp-*`, `.smoke-*` and 40-hex
  names. `current` can be created only by root (`HARNESS_DIR` is root 0755), so a uid-1000
  foothold inside a 0700 `.smoke-*` cannot become a bind source. The residual is the
  same-uid-as-the-server point in the fourth finding above.
- **Does dropping the binds on a refused channel create a new failure mode?** One, bounded
  and accepted: the transition costs a `ContainerRemove` + `ContainerCreate` for each
  STOPPED project, so anything living only in the container filesystem is lost — the same
  cost the ADR-067 mode toggle already documents; home and workspace are bind mounts and
  survive, and ADR-028's apt manifest replays installed packages. It does not churn: after
  the rebuild `has` is false and `hbinds` is empty, so the trigger cannot re-fire until the
  channel's state changes again. A refusal from a genuinely transient cause (an `EACCES`
  stat) therefore costs one rebuild rather than mounting a source the server just refused,
  which is the correct direction. Running containers are untouched. The remaining gap is the
  presence-vs-equality one above.
- **Is the origin regex sufficient against git transports?** The pattern itself is:
  anchored `^https://` refuses `ext::`, `file://`, `ssh://`, `git://` and a bare path; the
  host class `[a-z0-9.-]` refuses userinfo (`user:pass@host`, since neither `@` nor a second
  `:` is allowed) and percent-encoding; `--` before the URL refuses option-shaped values;
  `to_https` is deliberately not applied first, so an `scp`-form origin fails closed. What is
  insufficient is the way it is APPLIED — `grep`'s line semantics, the first finding.
- **Anything the quoted helper snippet still evaluates?** The snippet git's shell receives
  is `!f() { echo username=x-access-token; printf 'password=%s\n' "$(cat '<ETC_DIR>/gh-token-harness')"; }; f`.
  With the path single-quoted, a space, a `;`, a `` ` `` or a `$(…)` in `ETC_DIR` is now
  inert. A single QUOTE in `ETC_DIR` is not: it closes the quoting and the remainder is
  shell to that root process. `ETC_DIR` is seam-refused, so no open door — second finding,
  with the updater's exported-path pattern as the remediation. The token itself never
  appears: the snippet carries the PATH, the secret is read at git's call time, and the ctl
  test asserts no token text reaches the plan.

## Outcome

Written by the main agent, 2026-09-16, in the round-3 commit of the v1.35.0 gate (the config and orchestrator packages and the whole module green after the edits). Four of the nine findings were already remediated by 2f86816 while the review ran, as the findings themselves note; the rest:

- `styrman-ctl:653-654` per-line `grep` on the origin — fixed: `[[ "${HARNESS_ORIGIN}" =~ ^https://…$ ]]`, the whole-string form `https_origin` uses; `TestStyrmanCtlHarnessOriginIsGated` refuses `ext::sh -c id`, a two-line value whose second line is valid, and `file:///…` before any clone (the must-fail states), and shows the seam guard refusing `STYRMAN_HARNESS_ORIGIN` and `STYRMAN_HARNESS_REPO_DIR` outside `STYRMAN_CTL_TEST`.
- `orchestrator.go:355-370` presence, not equality — fixed: `harnessBindsOf` picks the container's two harness binds (sources included) and the rule is `slices.Equal(got, hbinds)`; a moved channel dir re-binds (`TestEnsureRunningRecreatesAStoppedContainerWhenTheChannelMoved`), equal binds start without churn (`TestEnsureRunningLeavesAStoppedContainerWhoseHarnessBindsMatch`); the describing text now states what the code does.
- `styrman-ctl:583,657` a single quote in `ETC_DIR` — fixed the way `styrman-update` does it: the token path travels as `STYRMAN_GH_TOKEN_FILE` / `STYRMAN_HARNESS_GH_TOKEN_FILE` on the one git call's `env` line and the snippet reads the variable; nothing from the path is interpolated into the text the helper's shell parses.
- Smoke home chowned to uid 1000, the server container's own uid — rebutted: uid 1000 is the operator's uid by design (`STYRMAN_UID` in `deploy/.env`, the server runs as it and owns the platform's state); the home is 0700 under a root 0755 dir for the seconds a smoke takes, and the only thing a write into it could do is fail that smoke, which latches the tag and is recoverable with `--force`; the smoke runs as the uid a project user has so the dry-run install sees what a project sees.
- No must-fail test for the origin regex and the seam guard — fixed: `TestStyrmanCtlHarnessOriginIsGated` above.
- Remediated in 2f86816 (the clone-path literal, the doc-comment, the test header, the plan clause) — confirmed by the round-2 reviewer (`reviews/2026-09-16-review-5ba2b1b-2f86816-code.md`).
