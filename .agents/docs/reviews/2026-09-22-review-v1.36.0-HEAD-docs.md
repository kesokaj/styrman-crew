## Findings

- **[medium / confidence: medium]** `.agents/docs/specs/styrman/versioning.md`
  "Release procedure" (lines 74–171) — this section describes what a release
  does and what it must verify, but says nothing about the GCP Compute
  Engine target added this range. Two concrete gaps: (1) `gcp.md`'s "Update /
  rollback" section states the GCP VM runs the same `deploy/update/`
  auto-updater as the NUC and follows every signed tag on its own — but
  `versioning.md` step 4 ("Within one `styrman-update.timer` tick… brings the
  stack up at `/opt/styrman`") and step 5's verify list only speak of the one
  host; a reader following only `versioning.md` for "what does a release do"
  has no pointer to a second host now converging on the same tag. (2) The new
  rule `.agents/rules/shared-path-learnings.md` requires: "A step guarded by
  'already installed' is verified only by a host that has not installed it. A
  change to such a step, or a release carrying one, states how the
  fresh-host path was exercised… or 'fresh-host path unexercised' in the gate
  report — never a green re-run on the NUC." `versioning.md`'s release
  procedure (steps 1–5) has no line asking for this statement, so the
  obligation currently lives only in the rule file, not in the document a
  release is actually checked against. Fix: add a sentence to step 1 or 5
  pointing at `gcp.md` for the second target, and a line (e.g. after step 2 or
  in "Verify") asking the release to record the fresh-host-exercise status
  per `shared-path-learnings.md`. Owner: `documentation`.
  Confidence is medium because the plan's own Phase-3 checklist explicitly
  scoped `versioning.md`'s *gate script list* out (`[-]`, "versioning.md
  names no script list and no shellcheck at all") — that dropped item is
  about a different sentence than the one this finding names, so it is not
  already covered by that decision, but a reader could argue the release
  procedure's silence on a second target is deliberate until the first real
  GCP release happens.
