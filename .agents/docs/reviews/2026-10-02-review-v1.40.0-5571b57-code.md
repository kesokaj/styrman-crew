Range reviewed: v1.40.0..5571b57 (`git diff v1.40.0...5571b57`; commits b03bc91 handoff, 837b3b9 Phase 1, 5571b57 Phase 2; `web/dist/` excluded; under `.agents/docs/` only the plan, the testing scripts and the testing README read, plus BUG-088's Fix section to check the lock trade-off)

## Status: COMPLETE

## Verdict: REQUEST CHANGES

The worst problem is in `GuestGoingAway` (BUG-088's fix). It uses "the project's lock is held right now" to mean "the guest is going away". The lock is also held by operations that take nothing away: `EnsureRunning` on a project that is already running, which every terminal WebSocket boot and reconnect runs, and `stopIfIdle`'s `projectBusy` probe, which runs execs while holding the lock and then may leave the VM up. A real launcher or port-scan failure that lands in that window is reported as "project stopped" or as "no ports" on a running project, and the launcher's log tail is thrown away — the only diagnostic for a failed browser start. The window is narrow and the effect is a wrong diagnosis rather than lost data. That is still the misread-signal family the project has graduated a rule for, so this needs a fix or a recorded rebuttal.

The rest is sound. `styrman-update` has one EXIT handler, installed for every mode. That handler cannot change the tick's exit status (it returns 0 and never calls `exit`). The status is armed only below the lock and never under `--check`. The writer refuses symlinked, foreign-owned or loose directories and renames over the file rather than writing through it. No non-root party can steer a root write. The hooks stay behind `STYRMAN_UPDATE_TEST=1` and run with the caller's own uid, then exit before the production trap and the `TRUST_UID=0` line. The parser (`updatestatus.Read`) validates every field against a closed set and never defaults to "ok". The frontend timers, listeners and probe waiters are all cleared or resolved. One low finding: a host with no token file is told GitHub "rejected this host's token".

## Findings

- **[medium / confidence: medium]** `internal/orchestrator/ports.go:129-140` (`GuestGoingAway`), callers `ports.go:108` and `internal/httpapi/browser.go:95` — **What is wrong:** `TryLock()` failing is treated as "a lifecycle change is in flight". The lock holders are `EnsureRunning`/`ensureRunningLocked` (`orchestrator.go:196`), `WithProject`, `Stop`, `stopIfIdle` (`orchestrator.go:1274`) and `Destroy`, and two of them routinely hold the lock while the guest stays put:
  - `EnsureRunning` on an already-running project: `wsBoot` calls it on every terminal open and reconnect (`server.go:1142`), and Phase 1 adds reconnects on silence.
  - `stopIfIdle`: it runs `projectBusy` guest execs under the lock and then returns with the VM still up.

  Two concurrent failing calls can also see each other's momentary `TryLock`. **Failure scenario:** a project page opens, so its terminal WS boot takes the lock for `EnsureRunning` on the running VM. At the same time the browser relay runs the launcher's `start`, which exits non-zero (Chromium failed to come up). The `TryLock` at that instant fails. `browserExec` returns `errProjectNotRunning`, the relay closes with `CloseProjectStopped` "project stopped" (`browser.go:374-378`), the REST start returns 409, and the launcher's log tail is dropped. That tail is the "only diagnostic there is" (`browser.go:121-123`). `/ports` in the same window answers `[]` for a real scan failure.

  BUG-088's Fix section counts "boot via `EnsureRunning`" as a lifecycle change, which is only true for a stopped project. The tests cover a lock held around a stop-like failure and no lock at all. They do not cover a lock held by a no-op `EnsureRunning`, which is where the failure is.

  **Fix (either):**
  - An explicit per-project "taking the guest away" marker, set only by `Stop`/`stopLocked`/`Destroy`/the mode toggle around the stop, and asked by `GuestGoingAway` instead of the lock.
  - Or wait for the lock, bounded by `ctx`, and re-ask `Status` once the holder releases it, so "going away" is observed rather than inferred.

  Add a test where the lock is held by `EnsureRunning` on a running container and an exec failure is still reported.

- **[low / confidence: high]** `deploy/update/styrman-update:544-547` with `web/src/lib/updaterNotice.ts:40-42` — **What is wrong:** `*"could not read Username"*` is classified `fetch-auth`. Git prints that message when there is no credential at all: with `GIT_TERMINAL_PROMPT=0` (`:511`) and no token file, no helper is added (`:520`). **Failure scenario:** on a host whose `/etc/styrman/gh-token` was never installed or was removed, Settings says "GitHub rejected this host's token (/etc/styrman/gh-token)" and the operator goes looking for a rejected token that does not exist. The notice also hard-codes the default path, while `STYRMAN_GH_TOKEN_FILE` can move it (`styrman-ctl` passes `${ETC_DIR}/gh-token`). **Fix:** a separate code (`no-token`), set where `[ -f "${GH_TOKEN_FILE}" ]` is false and the fetch fails, with its own sentence. Add it to `failingCodes` in `internal/updatestatus/updatestatus.go` and to the updaterNotice tests in the same change.

No other finding. Checked and clean:
- **EXIT handler:** `on_exit` returns 0 and never calls `exit`, so the tick's status is the one passed to `exit` or `fail`.
- **Arming:** the status is armed only after `flock`, and not under `--check`. A skipped tick ("another run is in progress") and every refusal above the lock leave the status unwritten; the server shows "stale" after 60 minutes.
- **Status writer:** refuses a symlinked, foreign-owned or group/world-writable directory, and creates a missing directory only under a parent that meets the same bar. `mktemp` plus `mv -f` replaces a planted symlink at the file name instead of following it. `since` is read only from a non-symlink regular file and only through a strict timestamp regex. Tags are filtered through `is_release_tag`.
- **Hooks:** gated, and they exit before the production `TRUST_UID=0` and the trap.
- **Rollout:** the first tick after this ships runs the old updater. `self_install` then installs the new script and unit with `daemon-reload`, so the next tick records the status. The compose mount arrives with the deploy. This is the `mechanism-reaches-every-caller` order, and the steps are idempotent.
- **`updatestatus.Read`:** reads at most 4 KiB, rejects unknown fields, rejects trailing data, and maps anything that fails a check to `unknown`. A missing file means no key. Only admins get the key (`updaterFor`).
- **`cdp.alive`:** every path ends in `done()`, which clears the timer and both waiter sets. `send` never throws synchronously. `close()` runs `handleClose`, so a probe in flight resolves false.
- **BrowserPane probe:** the `probing`, `disposed` and `clientRef.current === client` guards stop a stale probe from reconnecting a newer socket. Cleanup clears the interval and both listeners.
- **TerminalPane outbox:** every former `outbox.length`/`splice` use is replaced, and the outbox has its own unit tests.
- **e2e (rule check):** the Settings check reloads in a `finally`, its restoring calls are wrapped in `.catch`, and it removes the planted file. The browser dead-socket check uses a throwaway page (terminal 2, like `third`/`fourth`) and closes it in a `finally`.
- **Integration:** `integration.sh` removes its plant unconditionally.
- **Counts:** the README count lines change in the same commits as the checks.

## Criteria
1. Dead code — **Pass.** The old inline re-checks in `ListeningPorts` and `browserExec` were replaced, not left beside the new call. The hand-run trap was removed, and a text pin guards against its return. No orphaned exports: `GuestGoingAway` has two callers plus the `guestRuntime` interface.
2. Flow tracing — **Fail (finding 1).** `GuestGoingAway`'s lock heuristic reaches both callers, but it is not true for every lock holder. The updater's flow is otherwise traced end to end: the unit's environment, `styrman-ctl`'s `UPDATER_ENV`, the compose environment and mount, `config.Load`, `updaterFor`, the settings JSON, `api.ts` and the notice. The code paths that set each status code match `failingCodes` and the notice's switch. The tests in `TestStyrmanUpdateStatusWiring` are text pins and say so in their own comment; their behaviour is covered through the gated hooks plus `TestStyrmanUpdateStatusEarlyRefusalWritesNothing`. Not covered by any test: a real root tick writing its status, and the BrowserPane probe's `online` and 25-second interval triggers (the e2e test drives only the visibility trigger).
3. Standards conformance — **Pass, with finding 2 (a wrong diagnosis in the notice text).** Go errors are handled, the parser is closed-set, and nothing is said "ok" by default (the BUG-014 shape). Bash follows the ADR-052 shape (no in-script default), with root-input trust checks like the rest of the script. TypeScript has no floating promises (`void client.alive().then`). The removed comment ("the script's ONLY trap") has no live restatement left; hits remain only in dated trail records.
4. Directory layout — **Pass.** `internal/updatestatus/` is a new package beside its consumer, tests sit beside their code, and `web/src/lib/termOutbox.ts`, `updaterNotice.ts` and the cdp changes stay inside `web/`.
5. Simplicity (DIY-except-security) — **Pass.** Stdlib only, no new dependencies, and no hand-rolled security primitive. The status file is plain JSON written by `printf` from closed-set values.
6. Decoupling — **Pass.** `GuestGoingAway` is added to the consumer-side `guestRuntime` interface in `httpapi`, and the fake mirrors it. The writer and reader of the status file are joined only by the documented format and a cross-check test (`TestStyrmanUpdateStatusPathMatchesTheComposeMount`).
