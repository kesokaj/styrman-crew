# Security review — ADR-067 network mode by bridge prefix   (2026-09-09)

Range reviewed: 44e81e0..5481ea2 (`ADR-067 Phase 0` .. `Phase 5`)

Blast radius followed: `internal/config` (bridge-name derivation), `internal/orchestrator`
(network create/rebuild, `ports.go`, `ResolveProjectByIP`), `internal/httpapi/network.go`
+ `server.go` + `explorer.go`, `internal/credbroker`, `internal/credstore`,
`internal/project/store.go`, `deploy/firewall/*`, `deploy/docker-compose.yml`,
`deploy/host-setup.sh`, `deploy/update/styrman-update`, `deploy/verify-commit.sh`,
`REQUIREMENTS.md` R12, and the live-run write-up
`.agents/docs/testing/2026-09-09-lan-mode-live.md`.

## Verdict: FINDINGS

No cross-user credential path was found, and the mechanism the dispatch worried about holds
for a structural reason rather than a lucky one: the broker's caller identity is not just
"some IP in a project subnet" — `ResolveProjectByIP` requires the source address to be an
address the resolved project's container *actually holds* (`containerHoldsIP`,
`internal/orchestrator/orchestrator.go:492`), and it re-verifies that on every cache hit. A
LAN project sending its own source address to any broker address it can reach resolves to
*itself* and is served *its own* user's credentials. Getting another user's secrets requires
forging a source address held by that user's container, and the broker is TCP/HTTP, so a
forged source gets its SYN-ACK routed out the victim's `sdb-` bridge where the attacker
cannot see it. That is a blind-ISN problem, not a design gap. **But it is untested**: the
broker was absent from the live run, and this host's `rp_filter` is `0` on `all` / `2`
(loose) on `default`, which means the kernel will *not* drop a packet arriving on `lan-…`
whose source belongs on `sdb-…`. The remaining defence is the TCP handshake alone. The
concrete test that would settle it is specified below.

The worst *actual* finding is a different one: **a failed LAN→sandbox toggle leaves the
project running with LAN reach while the record, the API and the UI all say sandbox, and
nothing ever reconciles it** — ADR-067 deleted the derived state and the periodic reconcile
that used to catch exactly this, and `bridgeModeMismatch` is consulted only for *stopped*
containers. Second worst: the enforced precondition that a host granting LAN reach must not
accept sshd password authentication is gone (downgraded to prose advice), on a host that
publishes `0.0.0.0:22` and sets no explicit `PasswordAuthentication`.

## Findings

- **[medium / confidence: high]** `internal/httpapi/network.go:100-124`,
  `internal/orchestrator/orchestrator.go:232-240` — **revocation can silently fail open.**
  `setProjectNetwork` persists `LanAccess=false` *first*, then stops and rebuilds. If `Stop`
  or `EnsureRunning` fails, the handler returns 500 but the record is already `false`, and
  every read path (`projectView.LanAccess`, `GET .../network`) reports the record, never the
  actual bridge. `bridgeModeMismatch` is only reached inside
  `if err == nil && (insp.State == nil || !insp.State.Running)` — a *running* container is
  never checked — and ADR-067 deleted both the 2-minute reconcile ticker
  (`cmd/styrman/main.go`) and the derived `lanState`/`lanMessage` fields
  (`internal/httpapi/server.go`). So a project can keep `lan-<hash>` (full host + LAN reach)
  indefinitely while the admin who revoked it sees "sandbox". Remediation: read the live
  bridge name in the project read paths (one `NetworkInspect`, cached like `selfAttached`)
  and surface `mode != record` as an explicit mismatch; or restore a periodic reconciler
  that stops+rebuilds a running container whose bridge prefix disagrees with its record.
  Cheapest correct variant: when *tightening* (`on == false`), persist the record only after
  the rebuild succeeds.

- **[medium / confidence: high]** `deploy/firewall/install.sh:44-46`, `REQUIREMENTS.md` R12 —
  **the sshd password-auth precondition was deleted, not migrated.** ADR-065/066's
  `require_sshd_hardened` refused to install the LAN allowance on a host whose sshd accepted
  passwords; at HEAD `--i-accept-sshd-passwords` is "obsolete … ignoring" and R12 says only
  "SHOULD NOT accept password authentication … advice in `docs/deploy/remote.md`, not an
  enforced precondition". Meanwhile LAN mode is now *unconditional* host reach — no
  `LAN_ALLOW_HOST` opt-in survives, so the operator no longer makes a second, deliberate
  decision. On this host: `0.0.0.0:22` is listening, and neither `/etc/ssh/sshd_config` nor
  `/etc/ssh/sshd_config.d/*.conf` sets `PasswordAuthentication` — Debian's compiled default
  is `yes`. A LAN project runs untrusted agent-driven code with `cap_net_admin` and can now
  reach and spray the host's sshd. Mitigating: no `~kesokaj/.ssh/authorized_keys` exists
  (checked), so the broker-served SSH key is not itself a key into this host. Remediation:
  either re-add the check to `install.sh` (advisory-with-override is fine, but it must
  *run*), or make it a blocking step in `/preflight` and `docs/deploy/remote.md`; and set
  `PasswordAuthentication no` explicitly rather than relying on a distro default.

- **[medium / confidence: medium]** `internal/credbroker/broker.go` (whole file),
  `deploy/docker-compose.yml:102-106` — **the broker's "bridge-only binding" no longer means
  what it meant.** The binding itself is unchanged (`:8091` inside the server container,
  never published; the server is on `styrman-ingress` plus each project bridge). What
  changed is the *reachability model around it*. Before ADR-067, `INPUT -i sdb-+ -j DROP`
  plus the `DOCKER-USER -i sdb-+ … -j DROP` set meant a project's packets could not leave
  its own bridge toward any private address at all, so "the broker is only reachable at the
  caller's own bridge" rested on two independent layers (styrman's drops *and* Docker's
  per-bridge isolation). For a `lan-` project only Docker's layer remains:
  `-A DOCKER ! -i <br> -o <br> -j DROP`. The live run measured that layer holding for a
  container address (A → `172.21.0.2` blocked) and it is interface-keyed, so the server's
  endpoint on that same bridge is covered by the identical rule — but **the broker endpoint
  itself was never exercised** (the broker only starts when `cfg.SelfContainer != ""`,
  `cmd/styrman/main.go:121`, and the live run used a host-process server). Treat cross-bridge
  broker reachability as *argued, not measured*. Remediation: measure it (test below) and
  record the result beside the live-run file; and state the narrowing in ADR-067, because a
  guarantee that weakened without its code changing is precisely what a diff-only review
  misses.

- **[low / confidence: medium]** `internal/orchestrator/orchestrator.go:438-498` — **source-IP
  forgery is now the only thing between a LAN project and another user's credentials, and
  the kernel is not helping.** `ResolveProjectByIP` is sound: subnet match *plus*
  `containerHoldsIP` *plus* a re-verified cache, so forging a victim container's address is
  necessary. The guest holds `cap_net_admin` (confirmed in the live run) and
  `net.ipv4.conf.all.rp_filter=0` / `default=2` (loose) on this host means the kernel does
  **not** reverse-path-drop a packet arriving on `lan-…` with an `sdb-…` source — the forged
  SYN reaches the broker's socket; only the unseen SYN-ACK (routed to the victim's bridge,
  where it also draws a RST) stops the flow. That is adequate for TCP and I did not attempt
  it. It stops being adequate the moment any connectionless or single-packet request-reply
  surface is added on a bridge. Remediation (cheap, defence-in-depth): set
  `net.ipv4.conf.all.rp_filter=1` (or per-bridge) in `deploy/host-setup.sh` so the forgery
  fails in the kernel rather than relying on ISN randomisation; never add a UDP listener to
  the broker.

- **[low / confidence: medium]** `deploy/firewall/styrman-firewall.sh:59-62, 92-111` — **LAN
  mode inherits host-loopback and IPv6 posture from unasserted kernel defaults.** With no
  `INPUT -i lan-+` rule, the only thing keeping a LAN project off the host's loopback-bound
  services is `route_localnet=0`, which nothing in this repo sets or checks (measured `0` on
  `all`, `default` and every existing bridge — it holds *today*). Docker sets
  `route_localnet=1` per-interface when a container publishes to a loopback address, so one
  unrelated `-p 127.0.0.1:…` elsewhere on this host would open it. What sits behind it right
  now: `127.0.0.1:2019`, the Caddy admin API — unauthenticated by design, on a container the
  compose file itself describes as "full Docker API access … treat any RCE in it as host
  root" — and, during testing, a `127.0.0.1:18080` styrman listener with auth off (the
  compose comment's assurance that "project VMs cannot reach" a host loopback server is a
  SANDBOX-mode statement and no longer covers LAN mode). Separately the `disable_ipv6` loop
  and the `ip6tables` drops are `sdb-*`-only by design, so a LAN bridge has no IPv6 policy at
  all. Remediation: assert `net.ipv4.conf.all.route_localnet=0` in `deploy/host-setup.sh` and
  read-and-warn on it in the firewall script; bind or disable the Caddy admin API; state the
  IPv6 position in R12 instead of leaving it implied.

- **[low / confidence: medium]** `deploy/update/styrman-update:499-535` — **the updater no
  longer converges `styrman-firewall.path` away, only `install.sh` does.** A host that
  upgrades across this release via the auto-updater keeps an enabled `.path` unit
  (`DirectoryNotEmpty=/run/styrman-firewall/spool`, `Unit=styrman-firewall.service`) and the
  spool tmpfs, until someone hand-runs `host-setup.sh`. The in-code comment calls the
  leftover "inert"; it is not quite — anything with the operator uid can still write the
  spool and trigger the service, and the *new* `styrman-firewall.service` was written on the
  assumption that "nothing but the timer starts this unit" (`StartLimitBurst=20`). Twenty
  triggers in 60 s would put the unit in `failed`, after which the 60 s self-heal timer stops
  running too — the existing drops persist in iptables, but they would no longer be
  reinstated after a `docker` restart flushes the jumps. Requires the trusted operator uid,
  hence low. Remediation: have `host_converge` disable-and-remove the `.path` unit and the
  spool mount unit, exactly as `install.sh:73-82` does, or state in
  `docs/deploy/remote.md` that this release requires a hand-run of `host-setup.sh`.

- **[low / confidence: high]** `internal/httpapi/server.go:221-222` — leftover empty
  `if err == nil { }` block where `kickLAN` was removed, and a dangling doc comment at
  `internal/httpapi/server.go:200-202` ("NetPolicy exposes the marker dir so main can run the
  boot-time and periodic Sync…") whose function was deleted. The empty block is already
  fixed in the uncommitted working tree (not in the reviewed range); the dangling comment is
  not. Not exploitable; recorded
  because a comment describing a removed mechanism is exactly what misleads the next
  implementer — the same pattern the 2026-09-08 audit caught in `LanChecker`. Remediation:
  delete both.

- **[low / confidence: low]** `internal/config/config.go:479-489` — `BridgeNameFor` truncates
  SHA-1 to 11 hex (44 bits). The derivation is safe: the prefix comes from the bool alone and
  cannot be influenced by any input, the suffix hashes the network name only, so there is no
  wrong-prefix path and no injection. The residual is availability, not confinement — a
  44-bit collision between two project network names would make the second
  `docker network create` fail on a duplicate interface name and `bridgeModeMismatch` would
  read a `cur` that never converges. Birthday bound ~2^22 networks, so theoretical on a
  single NUC. No change recommended; recorded so a future multi-host variant does not widen
  it silently.

## Accepted-risk note (question 2: the cost of deleting the SSH-key latch)

The operator decided to delete `LanEverEnabled` and `credstore.IsHostReaching`; this is not a
relitigation, only the bill. Bought back: a LAN project is credentialed like any other, and
`Project` loses a permanently-latched field that could never be cleared. Cost, precisely:

1. **The transitive path ADR-065 follow-up (g) named is open again.** A LAN project holds the
   user's `~/.ssh` key *and* can now reach every host on the local network. Any LAN host that
   trusts that key is reachable from agent-driven code inside the microVM. Nothing in the
   platform bounds which hosts those are.
2. **It is not mitigated by this host having no `authorized_keys`.** That check (still true —
   `~kesokaj/.ssh/authorized_keys` does not exist) only says the key does not loop straight
   back into *this* box. It says nothing about the rest of `192.168.5.0/24`.
3. **The latch was the one control that could not be wrong; its replacement is nothing.**
   Combined with finding 1 (a revoked project that never actually left LAN mode), the system
   now holds no state at all recording "this project has been exposed".
4. **What is genuinely not lost:** the latch never protected *other users'* credentials, and
   the broker's per-user scoping (`GetGit(user, …)`, `AllEnv(user)`, `AllFiles(user)`) is
   untouched by this diff. The deletion is a blast-radius regression for the owning user's
   own key, not a tenancy regression.

Proportionate replacement, if one is wanted and cheaper than the latch: do not enrol a
`~/.ssh` file credential at all on a deployment that uses LAN mode, or broker a scoped deploy
key instead. Both are configuration, not code.

## Answers to the three dispatched questions

1. **Can one user's LAN project obtain another USER's credentials from the broker?**
   Not by any path I could establish, and the reason is `containerHoldsIP` — reaching a broker
   address is not enough; the source address must be one the *resolved* project's container
   holds, re-verified on cache hits. Reaching another project's bridge address is additionally
   blocked by Docker's own `! -i <br> -o <br> -j DROP` (measured for a container address in
   the live run; argued, not measured, for the server's endpoint on that bridge). Source-IP
   forgery is available to the guest (`cap_net_admin`, loose/absent `rp_filter`) but must
   complete a TCP handshake whose SYN-ACK goes to the victim's bridge — blind ISN.
   **What I could not establish:** anything *measured* about the broker. It was absent from
   the live run and I did not run the compose deployment. Read this as "no cross-user path
   found by reading, one measurement outstanding", not "verified safe".
2. **Is deleting the SSH-key latch safe given (1)?** Yes with respect to (1) — the latch was
   never what kept users apart. It is a real regression for the owning user's key against the
   local network; itemised above.
3. **Does the broker's bridge-only binding still mean what it meant?** No. The binding is
   byte-identical, but it used to rest on two independent layers and for `lan-` projects it
   now rests on Docker's alone.

## The one test that settles it

Against the **compose deployment** (the broker only starts when `STYRMAN_SELF_CONTAINER` is
set): two projects owned by **two different users** — not one user's two projects, the
interesting answer is the cross-tenant one — A in LAN mode, B sandboxed, both running so the
server has attached to both bridges. Read B's broker address from
`docker network inspect sdb-<B-uuid>` (the server's endpoint, subnet-broadcast-minus-1).
From A's guest, four `curl -sv --max-time 5` probes:

| probe | expected |
|---|---|
| `http://<A-broker-ip>:8091/env` | 200 with A's own user's map — baseline, proves the broker is up |
| `http://<B-broker-ip>:8091/healthz` | **timeout** (Docker's per-bridge DROP) |
| `http://172.<B>.0.1:8091/healthz` | **connection refused** — the host address IS reachable in LAN mode, but nothing should listen there; a 200 means the broker reached the host and is stop-the-line |
| `http://<host-uplink-ip>:8091/healthz` | **connection refused**, and the same probe from a non-styrman machine on 192.168.5.0/24 must also refuse |

Record the result next to `.agents/docs/testing/2026-09-09-lan-mode-live.md`. Anything other
than the right-hand column is a finding; a 200 in rows 2-4 is high severity. No forgery step
belongs in this test — the handshake argument is sound and `rp_filter=1` is cheaper than
proving the negative.

## Checked

- **Secrets** — no credential, token or key added by the diff; `git diff --name-status`
  scanned for `.env`/`.pem`/`.key`/`tfvars`/`tfstate`/credential paths: none. `.gitattributes`
  is new and only marks `web/dist/client/_shell.html` as `diff` (BUG-007 follow-up); it
  commits no content and changes no bytes. Broker logging (`broker.go:94,124,155`) records
  user/project/host and **counts**, never values — correct and unchanged.
  `setProjectNetwork` logs the actor's email on an isolation change (`network.go:108`), which
  is the right audit line and the only durable trace left of a mode flip.
- **Injection** — the one new parsing boundary on the root side is
  `deploy/firewall/styrman-firewall.sh:128-153`, re-parsing `iptables -S` to delete stale
  ADR-065/066 rules. Well defended: strict whole-line regex; the args character class
  excludes `"` so no second quoted comment can hide inside it; reconstruction is argv, never
  a shell string; deletion is a full content match with the tag comment *required*, so it
  cannot delete a base DROP; a tagged `-j DROP` is refused outright; non-matching tagged
  lines are left with a warning; matching is by content, never by rule number (BUG-013). Its
  only input is root-writable. `BridgeNameFor` takes no attacker-influenced input. The
  handler body is a single `*bool` with an explicit nil check. No new path, template, SQL or
  command construction anywhere in the diff.
- **Authz/authn** — enabling LAN is admin-only (`network.go:79` → `requireAdmin`,
  `auth.go:100`); disabling is deliberately open to the owner, correct (tightening is never
  refused). `getProjectFor` runs *before* any authz signal and 404s on another user's
  project, so the endpoint leaks no existence. An admin can only toggle projects in their own
  space — there is no cross-user project handle on this route. `CanEnable` is a server-side
  field, not UI-inferred (BUG-019). The deletion race is held under `netMu`. No endpoint lost
  a middleware; the ingress-token guard is untouched.
- **Crypto** — nothing hand-rolled; no auth, session, JWT/OIDC or password code touched.
  SHA-1 in `BridgeNameFor` is a non-security name derivation (uniqueness only, no
  collision-resistance claim, no attacker input), documented as such — not a finding.
- **Dependencies** — **no dependency changed in this range**: `go.mod`, `go.sum`,
  `deploy/caddy/ingress/go.{mod,sum}`, `web/package.json` and `web/package-lock.json` are all
  untouched. Tool runs (see caveat): `go vet ./...` clean.
  `govulncheck ./...` (root) — 31 callable, `govulncheck ./...` (`deploy/caddy/ingress`) — 29
  callable. **Caveat, stated rather than glossed:** I ran the LOCAL toolchain, `go1.25.0`,
  not the pinned `golang:1.25.13-trixie` builder that `deploy/vulncheck.sh` uses and that
  actually builds the release, so the great majority of both counts are stdlib advisories
  (`crypto/tls` GO-2025-…, `crypto/x509` GO-2025-4007, etc.) already fixed in 1.25.13 and not
  present in the shipped binary. Run `bash deploy/vulncheck.sh` for the number that matters.
  What survives the toolchain difference is module-level and pre-existing:
  `github.com/docker/docker@v28.5.2+incompatible` — GO-2026-4887 (AuthZ plugin bypass on
  oversized request bodies) and GO-2026-4883 (off-by-one in plugin privilege validation),
  both **Fixed in: N/A**; they are daemon-side paths reached through the client library and
