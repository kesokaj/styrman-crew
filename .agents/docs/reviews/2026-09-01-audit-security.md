# Security review — audit-security (whole tree, HEAD 86e4b9e / v1.16.0)   (2026-09-01)

Scope: whole project at `86e4b9e` plus the three uncommitted doc corrections.
EXCLUDED: `image/harness/**` (verbatim vendored mirror, ADR-046).
Deliberately NOT re-litigated: the auto-updater and `internal/httpapi/check.go`
(three passes today — `2026-09-01-security-*`). Nothing new was found in them.

Threat model applied throughout: a project user ALREADY has arbitrary code
execution as root inside their own Kata microVM. A finding counts only when it
crosses a boundary — to the **HOST**, to **ANOTHER project**, or to **ANOTHER
user**.

## Verdict: FINDINGS

The worst problem is not in styrman's own request path — that surface held up
well — it is in front of it. The Caddy ingress runs `network_mode: host` with the
Docker socket mounted, and its own comment says "treat any RCE in it as host
root." That same container exposes Caddy's **admin API on the host's
`127.0.0.1:2019`, unauthenticated by design**, and `internal`'s watcher uses it
by POSTing the whole generated Caddyfile to `/load`. Nothing in the repo
restricts its origins, nothing validates that `CADDY_ADMIN` binds loopback (in
pointed contrast to `config.go`, which refuses to start if `STYRMAN_DEV_ADDR`
is non-loopback), and the module's declared Caddy floor — `v2.9.1` — predates
**both** admin-API fixes govulncheck flags: GO-2026-4537 (cross-origin config
application via `/load`, fixed 2.11.1) and GO-2026-5743 (admin authorization
bypass via `/config`, fixed 2.11.3). Anything that can send one HTTP request to
that port replaces the entire ingress config, and the ingress is the sole thing
that decides which `X-Caddy-Email` reaches the server — so config replacement is
full impersonation of every styrman user including admin, plus host root via the
socket. The cross-origin variant is specifically designed to be reachable from a
browser page rather than a shell.

Second: a guest-planted symlink turns credential deletion into cross-tenant file
deletion. `sweepMaterializedFile` carries the comment "Never let a crafted stored
path escape the home root" over a purely **lexical** `filepath.Rel` check, then
calls `os.Remove`, which follows symlinks. The sibling code in `setup.go` fixed
exactly this class by moving to `files.Save` (os.Root); this call site did not.

Everything else is medium or below. The parts I expected to break did not: the
`authGuard` chain fails closed on unknown modes, `config.Load` refuses to start
in header mode without an ingress token, the ingress strips every client-supplied
identity header before the authorizer injects the authentic ones, `internal/files`
is genuinely `os.Root`-confined at every entry point, link tokens are 128-bit
`crypto/rand`, no auth/crypto/session/JWT is hand-rolled, the username-slug
collision that would collapse two tenants into one is refused at both load and
`Add` (H3), and `ResolveProjectByIP` re-verifies `containerHoldsIP` on every
cache hit. No secrets are committed.

## Checked

- **Secrets** — Clean. No credentials, tokens, or keys in code, config, or tests; no committed `.env` (`.gitignore` covers `.env`/`*.env` with an `!.env.example` exception, and `deploy/.env.example` holds only empty placeholders). `host-setup.sh:290-300` generates `STYRMAN_INGRESS_TOKEN` and `STYRMAN_JWT_KEY` with `openssl rand -hex 32` (urandom fallback) and writes `deploy/.env` `chmod 600`, owner-only. Credential files are `0600` under `StateDir/credentials/<user>/` via `credstore.atomicWrite`. Log hygiene is good: `redactURL` (`server.go:606`) strips userinfo before clone URLs are logged, `revokeLink` logs `token[:8]+"…"`, and the broker logs counts, never values. `credentialContent` returns plaintext secrets but is `u.Authorized`-gated, `u.Username`-scoped, and audit-logged. Grep for high-entropy assignments across Go/TS/YAML/shell/JSON returned nothing.
- **Injection** — No SQL. Command execution is argv-based everywhere it matters (`orchestrator.Exec`, `gitExec`); the four `bash -lc`/`sh -c` sites with interpolation are all bounded (`setupTool` allowlist at `bridge.go:193-203`, `hostnameRe` at `explorer.go:472`, `shellQuote` at `credharvest.go:184`, `nameRe` at `server.go:771` — the last flagged as finding 6). Path handling is the strong point: `internal/files` is `os.Root`-confined at every entry, refuses non-regular files with `O_NONBLOCK` (FIFO/device DoS), and `scopeFor` keys the workspace/home split on the **registered** `r.Pattern`, not on client input. Every destructive explorer verb goes through `managedHomeTarget`. Template injection into the generated Caddyfile is finding 5. Body sizes are capped per route by `csrfGuard`; `Exec` output is capped at 2 MiB (`maxExecOutput`).
- **Authz/authn** — Middleware order is `previewHostRewrite → authGuard → csrfGuard → mux`, with no route registered outside the chain. `authGuard` fails closed on an unknown mode (M16) and `config.Load:198` refuses to start in header mode without an ingress token, so the `IngressToken != ""` conditionals in `auth.go:39,54` cannot be reached un-set in production. The ingress strips `X-Caddy-Email`/`X-Caddy-User`/`X-Caddy-Role`/`X-Caddy-Subject`/`X-Styrman-Ingress` at the site level **and** strips the upstream claim headers before `authorize` runs (`generator.go:133,166-169,376,390-393`), so a spoofed claim can never win the placeholder. `proxy.go:171-181` strips `Cookie`/`Authorization`/`X-Styrman-Ingress` and sweeps `X-Caddy-*` on the way to a guest app. Every project handler resolves through `getProjectFor`/`who` in the caller's own store; the two `/api/settings/backups/...` routes that address raw ids are regexp-validated and user-scoped by path construction. `previewAllowed` correctly requires `u.Authorized` on the owner branch so a guest slug collision cannot claim ownership, and `userstore.New`/`Add` refuse two authorized e-mails that derive the same username slug (H3) — the tenancy key stays unique. Admin rights come only from `STYRMAN_ALLOWED_EMAILS`, never from an ingress role. WebSocket upgrades use `websocket.Accept(w, r, nil)`, i.e. the library's default same-origin enforcement.
- **Crypto** — Nothing hand-rolled. Authentication, sessions, and JWT/OIDC are entirely delegated to Google OAuth + caddy-security at the ingress; the server never mints, parses, or verifies a token. Link tokens are `crypto/rand` 16 bytes hex (`links/store.go:96`), and the ingress-token comparison is `crypto/subtle.ConstantTimeCompare` (`auth.go:40,55`). `STYRMAN_JWT_KEY` is generated by `openssl rand -hex 32` and consumed only by caddy-security. No password hashing exists because no passwords exist. Constitution's ban on hand-rolled auth/crypto/hashing/sessions/JWT is respected — no violations.
- **Dependencies** — `npm audit` in `web/`: **0 vulnerabilities** (`{info:0, low:0, moderate:0, high:0, critical:0}`); the 39 runtime deps are all justified (CodeMirror language packs, xterm addons, TanStack router/start, micromark, React, Tailwind) with no incidental transitive bloat. `govulncheck` needed installing (absent from the image; `@latest` demands a go1.26 toolchain that would not download here — pinned `golang.org/x/vuln@v1.5.0` built under `GOTOOLCHAIN=go1.25.0` works). Main module: **33 CALLED**, of which 2 are the known-unfixable `github.com/docker/docker@v28.5.2` pair (GO-2026-4887, GO-2026-4883) already recorded in `TODO.md:52-53` and **not** re-reported here. The other 31 are Go standard library at `go1.25` — an artefact of *my scanner's* toolchain, not the shipped artefact: `deploy/Dockerfile.server:5` builds `FROM golang:1.25-trixie`, a floating tag that resolves to the current patch. Worth noting anyway because `archive/tar` (GO-2025-4014, GO-2026-4869 — `internal/backup` parses tar) and `net/http/httputil` (GO-2026-4976 — the preview `ReverseProxy`) are directly on hot paths, and the documented "roll back by rebuilding at the desired tag" workflow uses whatever local Go is present, with no toolchain-floor gate. **The second module, `deploy/caddy/ingress`, is not scanned by any existing gate** — running it there surfaced finding 1 plus stale declared floors: `caddyserver/caddy/v2@v2.9.1` (GO-2026-5743, GO-2026-4537), `quic-go@v0.48.2` (GO-2026-5676), `golang.org/x/net@v0.52.0` (GO-2026-5026, GO-2026-4918), `golang.org/x/text@v0.35.0` (GO-2026-5970), and `docker/docker@v27.5.1` — a full major behind the main module. Because `deploy/caddy/Dockerfile` builds via `xcaddy` on `caddy:2-builder`, MVS most likely lifts these to whatever that floating image pins, so the *shipped* versions probably exceed the floors — but nothing in the build records or asserts which versions actually shipped (the only build-time check is a `caddy list-modules | grep`). Recommend adding `govulncheck ./...` for `deploy/caddy/ingress` to `/preflight`, raising the declared floors, and capturing the resolved Caddy version as a build label.
