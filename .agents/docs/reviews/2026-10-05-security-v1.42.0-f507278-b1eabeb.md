## Status: COMPLETE

## Verdict: FINDINGS

Nothing high or medium. Three low findings.

**Worst problem (test suite):** the new Tier 2 retry-branch check runs `truncate -s 22G` from the HOST, as the operator's uid, on `${STATE}/homes/${ME}/p/${ID}/.dockerd/${ID}.img` (`.agents/docs/testing/styrman/integration.sh:534-537`).
- Every component below `p/${ID}` is inside the project home. That home is bind-mounted into the guest and writable from it, which is the layout `.agents/rules/guest-writable-paths.md` covers: "everything the guest writes below any mounted home can still be a link".
- GNU `truncate` follows symlinks and creates a missing file (no `-c`). A guest that planted a link at `.dockerd` or at the `.img` before the stop would make the suite resize, or create, any host file the operator can write.
- The `stat -c %s` that follows does not dereference. It would fail the check, but only after the write.

**The production change:** `ReapSetupVMs` now uses `forceRemove` under a 1-minute bound. It crosses no trust boundary:
- It selects by a label that only the server sets on the host Docker. Tenants run their own dockerd inside their VM.
- It removes by full container ID, so a replacement created during the retry window cannot be hit.

Its remaining weaknesses are availability (the bound is per VM and runs serially inside the idle-reaper tick) and coverage (no test).

## Findings
- **[low / confidence: medium]** `.agents/docs/testing/styrman/integration.sh:534-537`: host-side write through a guest-writable path.
  - **The path:** `IMGF` sits under the project home (`homes/<u>/p/<uuid>`, bind-mounted into the guest, ADR-031/064). The guest creates `.dockerd/` and the image (`image/entrypoint.sh:90`, `:376` `runuser -u ${USERNAME} -- truncate … ${IMG}.tmp`). In auth-none mode the suite runs as the same OS user (`ME="$(id -un)"`, `integration.sh:36`).
  - **Why it is a weakness:** the guest can replace either component with a symlink while it runs. The host's `truncate -s 22G` then resolves the link in the HOST namespace and writes to any operator-writable file. It extends the file with a 22 GiB hole, cuts a larger file down to 22 GiB (data loss), or creates the file.
  - **Exposure:** limited, because the guest is the suite's own project booted from the image under test. A compromised package inside that image (claude, agy, npm globals) is the realistic actor. That is why the severity is low.
  - **Remediation:** before the truncate, assert the VM is down (`docker inspect -f '{{.State.Running}}' ${CN}` reads `false`), so no guest can race. Then assert a real regular file with no link component: `[ -f "$IMGF" ] && [ ! -L "$IMGF" ] && [ "$(realpath -e -- "$IMGF")" = "$IMGF" ]`. Use `truncate -c` so a missing file is never created.
  - The rule's "New paths" bullet asks for a planted-link variant that proves the guard.
- **[low / confidence: medium]** `internal/orchestrator/orchestrator.go:1684-1688` (called from `RunIdleReaper`, `:1581`): the 1-minute bound is per VM and runs serially.
  - `ReapSetupVMs` runs synchronously before `Adopt` and the idle-project pass. Each setup VM caught in Docker's "is zombie" window can now hold the tick for up to 60 s. Before this change it was one attempt.
  - With several setup VMs exiting at once (one per user with a setup VM, each sized to the whole host), the idle-project pass is delayed by up to one minute per VM. That pass is the resource control for running project VMs.
  - A tenant cannot lengthen the window directly (it is the hypervisor's teardown).
  - The comment at `:1683` ("The bound keeps one stuck VM from stalling the tick") overstates: the bound limits the stall, it does not prevent it.
  - **Remediation:** put one deadline around the whole reap pass (a `context.WithTimeout` created before the loop). Alternatively, reap after the idle-project pass, or in its own bounded goroutine. Correct the comment.
- **[low / confidence: high]** `internal/orchestrator/orchestrator.go:1663-1690`: the reaper change has no test.
  - No `*_test.go` names `ReapSetupVMs` (grep at b1eabeb). The review Outcome concedes this (`.agents/docs/reviews/2026-10-05-review-f507278.md:76`).
  - Reverting `:1684-1688` to the old one-shot `_ = ContainerRemove(...)` keeps every suite green. That would silently bring back BUG-090's leaked exited setup container and network, and drop the new failure log.
  - `TestDestroySetupRetriesAVMStillExiting` (`destroy_zombie_test.go:74-99`) covers `DestroySetup` only.
  - **Remediation:** let the fake's `ContainerList`/`ContainerInspect` return one running `LabelSystem=setup` container with an old `StartedAt`. Then add two cases. Case one: plant one zombie refusal and assert two removes. Case two: refuse always with a 1 ms `zombieRetryEvery`, and assert the call returns within the bound and logs the Warn.
