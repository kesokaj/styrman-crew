## Status: COMPLETE

## Verdict: APPROVE WITH NITS

The worst problem is that the new editor-file slot is taken before the request body is read, and nothing bounds how long that read can take. The server sets only `ReadHeaderTimeout` (cmd/styrman/main.go:157-179). Caddyfile.base sets no `request_buffers` and no `read_body` timeout. So one signed-in user who sends 8 PUT/POST bodies very slowly holds every `fileSlots` slot for as long as those connections stay open. Every tenant's editor open, save, format and check then gets 429. The 30 s write deadline only limits the response side. This is the same kind of problem as preflight row 3 (server-wide slots with no per-user share), which was accepted as low. It costs a tenant less here, and this diff introduces it: before this range these endpoints had no slot. I rate it medium and do not block on it. The fix is cheap: also set a read deadline in `acquireSlot`. The rest of the range does what rows 1-4 and 6 asked: slots are released on every path, there is no silent loss of an edit, the history abort is correct, the host-setup temp file and rename are correct under `set -e`, and the e2e network sweep is scoped correctly. One stale restatement remains in deploy.md.

## Findings
- **[medium / confidence: medium]** `internal/httpapi/explorer.go:274-277` (writeFile), `internal/httpapi/format.go:61-64`, `internal/httpapi/check.go:338-341`. Scenario: an allowlisted user opens 8 connections and sends each body (up to 8 MiB) one byte at a time. Each handler holds its `fileSlots` slot inside the JSON decode, with no read deadline: server ReadHeaderTimeout only (main.go:157,171,179), and the ingress streams the body. Every other tenant's `GET/PUT .../file`, `/format` and `/check` answers 429 until those connections close, which can be indefinitely. Before this range the same requests cost memory but blocked no one. Fix: in `acquireSlot`, also call `http.NewResponseController(w).SetReadDeadline(time.Now().Add(historyWriteTimeout))` (or a separate body deadline). Add a real-server test, modelled on write_deadline_test.go, that trickles a body and asserts the slot is freed. A per-user share of the 8 slots would also close the row-3 class.

On such a host the test passes without exercising the deadline. With the Linux default maximums (4 MiB write plus 6 MiB read) it does block, and it passed `-race -count=3` here. ## Answers to the dispatch's questions (rows 1-4, 6)
- **fileSlot release:** all four handlers take the slot first and release it with `defer func() { <-s.fileSlots }()` immediately after a successful take. Every return path releases it, and a refused take returns before the defer, so nothing is double-released. The test (`file_limit_test.go`) fills the slots, gets 429 on all four endpoints, then confirms they are not 429 when idle and that 0 slots are held afterwards.
- **429 in normal single-user use:** this is unlikely. There is no autosave: save is only Ctrl-S or the button (FileEditor.tsx:247, CodeEditor onSave). Check runs on idle and aborts the previous one (FileEditor.tsx:186-189), so one user holds at most about one check slot plus one save, format or read slot per open editor. A 429 becomes possible when several tenants run slow checkers at once (8 slots shared server-wide).
- **Can an edit be lost silently?** No. A 429 on save goes through `tryUI`, which shows an error toast (api.ts:316-321). `setSavedContent` is not reached, so the buffer stays dirty. A 429 on open shows a toast and points the store back at the file on screen (EditorPane.tsx:99-110). A 429 on check shows "syntax check unavailable", never a clean gutter.
- **Write-deadline test:** it is robust under `-race` and load. The positive control polls every 2 ms against a slot held for at least the encode time, and both waits are bounded. It passed with `-race -count=3` (rc=0, .agents/scratch/review-a265b48-go.log). It relies on the response being larger than the socket buffers (finding 3). net/http clears the write deadline after each request (go1.25 server.go:2117), so the deadline does not carry over to the next keep-alive request.
- **History abort:** stale results are blocked by the gen check, and a superseded search raises no toast (`ac.signal.aborted`). A 20 s timeout still shows a toast, because `ac` itself is not aborted. The server search already runs under `r.Context()` (explorer.go:507), so an abort frees the slot. The vitest passes (4/4). The gaps are the empty query and unmount (finding 5).
- **host-setup:** the subshell status propagates under `set -e`. The file is created 600 by umask, chmod and chown are applied to the temp file, and `mv` within the same directory keeps owner and mode. A leftover temp file is possible on failure (finding 6). The `-s` refusal of an empty token is correct; a token that is only whitespace or a newline still passes, which is harmless.
- **e2e harness:** `run.mjs` refuses to run without `--base` and refuses a status file outside `STYRMAN_E2E_STATE`. Screenshots go to a private mkdtemp directory. The `run.sh` sweep: network names are always `sdb-<uuid>` (config.go:482), so `${n#*-}` is the UUID. `create()` logs `"container":"styrman-<uuid>"` right after `createBridgeNetwork`, with no fallible step in between (orchestrator.go:1087-1109), so the run's own networks are in `OWN_IDS`. The one exception is a server killed in that instant by the trap's own `kill`, which is negligible. Production networks are not in the run server's log, and the timestamp guard still applies, so the sweep cannot touch them.
