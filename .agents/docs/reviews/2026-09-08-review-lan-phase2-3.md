## Verdict: APPROVE

This is a thorough, well-tested implementation that matches its own plan closely. `Derive`'s table was traced branch-by-branch against the plan and the doc comment: every combination (absent, stale+applied, stale+not-applied×lan, per-project error, on/off agreement, no-bridge pending, fresh/old mismatch) is reachable, correct, and — where the code's priority order differs from the plan table's row order (errors checked before on/off; staleness overrides everything including a live per-project error) — the code is the *more* conservative, security-correct choice (never claims "on"/"off" when the reconciler's last word can't be trusted), and its own doc comment states the actual priority accurately. The status cache's `now.After(d.cachedAt)` guard correctly defeats an out-of-order/backdated call from poisoning the cache, and TTL expiry always forces a fresh disk read (`TestStatusCacheAndLimits` covers absent→cached-absent→fresh→oversized→garbage). `Sync`'s cold-reader race (a `SetMarker` landing between the snapshot and the delete pass) is fixed by taking `want()` inside `Dir.mu` and is proven by `TestSyncDoesNotEatConcurrentSetMarker`. `Kick`/`KickThrottled` are used correctly at each call site (unthrottled `Kick` on the user-initiated PUT and delete; throttled on the boot-path kicks in `ensureFor`/`createProject`/`startProject`). The handler's rollback path, `deleteProject`'s marker removal placed after the wipe block's early return, `listProjects`' one cached `Status` read reused across the whole list, and `main.go`'s goroutine reordering (necessary so the Adopt goroutine's closure can call `api.NetPolicy()`, which now must be constructed earlier) were all traced and are correct. `go build`, `go vet`, and `go test -race ./...` (whole module) all pass; the coordinator separately confirmed `npm run check && npm run lint && npm test` (80/80 vitest) pass.

## Findings

- **[low / confidence: medium]** `internal/httpapi/network.go:1028-1034` — the rollback after a failed `SetMarker` calls `sp.projects.SetLanAccess(p.ID, prev, now)` using the *current* request's `now`. Since `SetLanAccess` only skips the timestamp when the value is unchanged, and the rollback IS a value change (from the just-applied `on` back to `prev`), `LanChangedAt` moves forward to `now` instead of being restored to its true prior value. Failure scenario: an admin's enable/disable fails at the marker-write step (e.g. transient disk-full on `NetPolicyDir`); the client gets a 500 as designed, but the persisted record now carries a `LanChangedAt` that is later than the actual last successful change, which can shift the `Derive` pending→error grace window (`PendingGrace`, 90 s) on a subsequent read of the same still-unchanged `lanAccess` value. Low impact (a rare failure path, and the boot/2-min `Sync` and a future successful PUT both re-stamp it correctly), but worth a one-line fix (roll back to the original `LanChangedAt` too, or skip the timestamp bump on rollback) if it's cheap.
- **[low / confidence: low]** `internal/netpolicy/dir.go:1735-1744` (`KickThrottled`) — releases `kickMu` before calling `Kick`, so two concurrent `KickThrottled(tag, window)` calls that both land just outside the window can both read "not throttled" and both proceed to `Kick`, each writing a spool entry. This is explicitly documented as best-effort dedupe and is harmless (root drains and re-triggers idempotently), so it is not a correctness or security issue — noting only because it's a real (if inconsequential) TOCTOU gap in a lock-then-release-then-act pattern.

No dead code, no unreachable `Derive`/`Availability` branches, no deadlock risk (the boot/periodic `Sync`'s `want()` callback in `main.go` only reads project stores from disk — it never calls back into `netpolicy.Dir`), and no divergence found between the `netMu`-guarded PUT critical section and the `Dir.mu`-guarded `Sync`/`SetMarker` pair; `TestNetworkConcurrentPutsStayConsistent` (20 concurrent PUTs) and the dedicated lock test both pass under `-race`.
