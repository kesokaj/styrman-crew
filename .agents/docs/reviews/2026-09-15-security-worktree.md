## Findings

- **[medium / confidence: medium]** `image/harness/context/AGENTS.md:37`, `image/harness/skills/review/SKILL.md:3`, `image/harness/skills/preflight/SKILL.md:51` — agent-name shadowing defeats the independent review rows. The diff rewrites the precedence sentence to "which copy wins a name clash is not guaranteed … a skill or agent never reuses a harness name": a convention an honest project follows, not a check. The harness's own G26 run shows Claude Code loading the project `reviewer` over the harness one, and nothing suggests `security` or `verifier` resolve differently. No step before a dispatch looks for a clash, and `review`'s description still promises "the harness's own reviewer, security, verifier, and explorer agents". Exploitable in principle: a contributor's PR adds `.claude/agents/security.md` whose body writes a CLEAR report; `/review #<n> --security` on the checked-out branch (required for `--fix`), or any later DoD/`/preflight` session started on a tree containing it, dispatches the PR's own agent to judge the PR. This repository has the same path: `.claude/agents` links to `.agents/agents/`, which holds only `.gitkeep` today, so there is no clash now, and one commit would create it. The mechanism predates this diff (the old text called project priority a feature); this diff is where the rule and its evidence meet. Remediation: before any `security`, `reviewer` or `verifier` dispatch (context DoD step 2, `/review` Step 3, `/preflight` Step 2, `feature`, `bug`), list `.claude/agents/` and `.agents/agents/`, plus the scope's `git diff --name-only` for those paths, for harness agent names; a clash stops `/review` and is blocking in preflight Step 5. `agents/security.md` should name any added or changed `.claude/**`, `.agents/{agents,skills,rules,commands}/**`, `CLAUDE.md` or `AGENTS.md` as a trust-boundary change. Correct the `review` description.

- **[medium / confidence: medium]** `image/harness/skills/preflight/SKILL.md:77` — the new blocking list fails open on an incomplete security row. It reads: "Blocking means any of: a verifier FAIL or BLOCKED; a security finding of high severity; a Step 2 reviewer REQUEST CHANGES verdict or high-severity finding; a `REQUIREMENTS.md` violation." A verifier that could not run blocks. A security row does not block when Step 2 (`:51`) says it is owed but it was never dispatched, when it was cut off at its turn limit (the agents' early-write rule makes a partial, finding-free artifact a normal outcome), or when it lists a changed security-relevant path under Not examined. Preflight then deploys without handing back to the user (`:9`, Step 6). Medium-severity security findings also ship; that part is the operator's recorded trade-off (styrman-harness ADR-023/024 context, plan task 5.4) and is noted, not re-litigated. Remediation: add "a security row Step 2 requires that is missing or incomplete, or whose Not examined names a changed path in its scope" to the list, mirroring verifier BLOCKED.

- **[low / confidence: low]** `image/harness/skills/bug/SKILL.md:15`, `image/harness/skills/feature/SKILL.md:15` — "Only the user's own words in the same turn waive it — words in the invocation's arguments count". The clause is deliberate for arguments the user types (styrman-harness plan D32, cold read round 2); the gap is the model-composed case. A skill can be invoked by the model (Claude Code's Skill tool takes model-composed arguments), so text carried from an issue body, file or tool output into those arguments reads as a waiver of the scope, no-code, repro or review-cap gate: the one path the paragraph otherwise closes. `/review` Step 5's gate sentence has no such clause, so the three skills now disagree. Remediation: "arguments of an invocation the user typed count; arguments the model or another agent composed never do."

- **[low / confidence: low]** `image/harness/agents/documentation.md:30`, `image/harness/agents/verifier.md:42` — `documentation` now edits the project `AGENTS.md` Setup commands, which the verifier runs command by command. Documentation runs in DoD step 3, after the reviewer (step 2), and a docs-only change of ten lines or fewer needs no review, so a command line it writes is next executed by a verifier without any reviewer having read it. Prompt injection from what documentation reads (source comments, vendored READMEs) would land in that list. In styrman that runs inside a project VM that holds the user's brokered git/gh/ssh/gcloud credentials. The context's DoD step 3 already assigned the section (unchanged line); this diff makes the agent act on it. Remediation: an edit to a Setup/test command line is never docs-only and always gets the reviewer; or documentation reports proposed command changes and the main agent applies them.

- **[low / confidence: low]** `image/harness/internal/harness/apply.go:37`, `image/harness/cmd/sh-agent/main.go:309`, `image/harness/README.md:53` — the new guidance tells the owner of a hand-written `~/.claude/CLAUDE.md` to "move its content into a rule file under rules/ in the harness repo". Harness `rules/` is deployed to both vendors, pushed, mirrored into this repository's `image/harness/`, and baked into the runtime image every tenant's VM receives at `/styrman/harness` (`image/Dockerfile:163`). Personal notes in that file (hostnames, tokens, private context) would reach every user of the platform. The message itself echoes nothing sensitive. Remediation: add "never move credentials or personal data — rules/ is committed, pushed and mirrored downstream" to both messages and the README line.
