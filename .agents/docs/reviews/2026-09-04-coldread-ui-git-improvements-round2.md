# Cold-read (round 2) — UI + git improvements v1.22.0   (2026-09-04)

Range reviewed: `.agents/docs/plans/2026-09-04-ui-git-improvements-v1.22.0.md` (plan document, not a diff) plus the code surfaces it names: `web/src/lib/{hooks,terminal,editorPane}.ts`, `web/src/components/{TerminalPane,CodeEditor,FileEditor,FileExplorer,SidePanelGit,SidePanel}.tsx`, `web/src/routes/{settings,p.$project.$term}.tsx`, `web/src/lib/api.ts`, `internal/httpapi/{git.go,server.go}`, `web/src/index.css`, `image/skel/{bash_exports,bashrc}`, `README.md`, `REQUIREMENTS.md`.

All five round-1 findings (`.agents/docs/reviews/2026-09-04-coldread-ui-git-improvements.md`) were verified against the current code and are correctly resolved in this revision: the `repo`-flag/4xx split matches `git.go:94-119`'s existing `gitStatus` convention exactly; `SidePanel.tsx:100` really is a one-line add mirroring `PortsTab` at `:97`; `CodeEditor.tsx` really has `themeComp`/`wrapComp` compartments (`:163,166`) and a bare static `EditorView.theme` with the font rules at `:244-253` for `fontComp` to absorb; `editorPane.ts`'s `set()` no-op guard (`:69-76`) really omits fields not in its identity comparison, confirming the `diff` gotcha; and the two hardcoded defaults really differ (terminal 13px/Google Sans Code at `terminal.ts:104-106`, editor 12px/bare system stack at `CodeEditor.tsx:246-252`). Round 1's fixes hold up under a fresh read.

## (1) Gaps

1. **The `?commit=<hash>` diff has no specified git invocation, and `gitDiff` today silently swallows exit codes.** `git.go:332-361` — the current `gitDiff` handler never checks `code`/`err` from `gitExec` in any branch (`_, out, _ = s.gitExec(...)`); a failing `git diff` just returns whatever `out` contains as a 200. The plan's table (`## Interfaces → Git API`) adds `?commit=<hash>` and promises `400 invalid hash` for a malformed hash, but never states what git command produces a single commit's diff (`git show <hash>`? `git diff <hash>~1..<hash>`?), and never addresses the root-commit case (no parent to diff against) or a well-formed-but-nonexistent hash (currently would silently return 200 with an empty or garbled `diff` — is that acceptable for this new path too, or does it now need the `code` check it never had?). This is exactly the kind of "existing code doesn't do what the plan assumes" gap round 1 was hunting for and it's still open in the commit-diff path specifically.

2. **`stash list` returns raw `{output}` text, but the panel needs a stash list UI.** `## Interfaces → Git API` table gives every `stash` op (`push`/`pop`/`list`) the same `200 {output}` shape, unlike `branches`/`log` which get typed JSON (`{repo, local[], remote[]}`, `{repo, commits:[...]}`). Phase 6's task list calls for "stash controls" in the panel, which implies rendering a list of stash entries — but there's no defined shape for that list, so the frontend would have to parse `git stash list`'s porcelain text itself. Undecided: does `stash {op:"list"}` get a structured type like `log`, or is client-side text parsing the intended design?

3. **`DiffPane`'s mount lifecycle is unspecified, unlike `EditorPane`'s.** `p.$project.$term.tsx:39-44,173,181-182` — `EditorPane` is deliberately lazy-mounted behind `editorUsed.current` (gated on `pane.view === "editor" || pane.file`) and toggled with a hidden `<div>`, not unmounted, specifically because unmounting would tear down live state (this pattern's rationale is spelled out in the file's own comments, tied to two named past review findings). The plan's Phase 5 tasks ("`DiffPane.tsx` + third header segment") never mention an analogous `diffUsed.current` gate or hidden-div wrapper for the third view. Without one, `DiffPane` either mounts unconditionally on every terminal page (fetching against a null target) or the implementer has to independently rediscover the exact pattern that took two prior review rounds to get right for the editor.

4. **The third header-segment button's behavior with no diff ever opened is undecided.** `p.$project.$term.tsx:105-160` — today's two-item segment control (`terminal`/`editor`) always renders both buttons regardless of state; the editor button's dynamic filename badge is conditional but the button itself is not. For a "Diff" button to join that array, does it always render (and if clicked before any diff was opened, show what — an empty pane, disabled state?), or does it appear only once `pane.diff` is non-null (mirroring `editorUsed.current` gating existence rather than just visibility)? Tied to gap 3; neither the Interfaces section for `DiffPane` (`## Interfaces → Diff pane`) nor the failure-mode table covers "no target ever set."

5. **The `FONT_STACKS["google-sans-code"]` literal in the plan doesn't match today's actual terminal fontFamily string, contradicting the plan's own "nothing changes" guarantee.** Today's `terminal.ts:104-106`: `"'Google Sans Code Variable', 'JetBrains Mono', ui-monospace, SFMono-Regular, Menlo, monospace"` (6-part fallback chain). The plan's `FONT_STACKS` table gives `"'Google Sans Code Variable', ui-monospace, monospace"` (3-part — drops the `'JetBrains Mono'`, `SFMono-Regular`, `Menlo` fallbacks). `web/src/index.css:4-5` confirms `'JetBrains Mono'` (non-variable) was never bundled, so this is low-impact in practice (`ui-monospace` covers most systems), but it is a literal discrepancy in code the plan hands the implementer verbatim, and it directly undercuts the plan's explicit promise ("Nobody's rendering changes until they touch a control") — exactly the class of bug round-1 finding 5 caught for font sizes. Undecided whether `FONT_STACKS` should reproduce the exact current 6-part chain or the shorter one is an intentional, if unstated, change.

6. **Inconsistent `encodeURIComponent` coverage across the git API client after this change.** `api.ts:588-628` — none of today's git methods (`gitStatus`, `gitDiff`, `gitStage`, `gitUnstage`, `gitDiscard`, `gitCommit`, `gitPush`) encode `project` in their template strings. The plan says "every new template encodes its interpolations" and gives `gitLog` as the example, but `gitCommit` and `gitDiff` are *modified* (gain `all`/`commit` params) while reusing their existing, unencoded `project` template. The plan doesn't say whether these two in-place edits should also gain encoding. Left as written, the git client ends this release with some methods encoding `project` and others not, on the same object, with no rule distinguishing them beyond "was the URL template's text literally rewritten." (Practical risk is low — `project` is a server-issued UUID — but the plan's own Follow-ups note treats this pattern as worth getting consistently right going forward.)

## (2) Readiness

A first-pass implementer would hit real ambiguity and have to ask, at minimum:

1. What git command computes a `commit`-scoped diff (`show` vs `diff <hash>~1..<hash>`), and how is a root commit (no parent) handled? (gap 1)
2. Does `?commit=<hash>` on `gitDiff` now check `gitExec`'s exit code where the existing handler never did, or does an existing-but-invalid hash silently 200 like today's bad paths do? (gap 1)
3. Does `stash {op:"list"}` get a structured JSON shape (entries array) like `log`/`branches`, or is raw text output + client-side parsing the intended design? (gap 2)
4. Does `DiffPane` need a lazy-mount gate (`diffUsed.current`) and a hidden-`<div>` toggle mirroring `EditorPane`'s, or is eager/conditional mount acceptable here? (gap 3)
5. Is the third "Diff" header-segment button always rendered (clickable to an empty state before any diff is opened), or does it appear only once a diff target exists? (gap 4)
6. Should `FONT_STACKS["google-sans-code"]` reproduce today's exact 6-part fallback chain from `terminal.ts:104-106`, or is the shorter 3-part version in the plan intentional? (gap 5)
7. Should the modified `gitCommit`/`gitDiff` client templates in `api.ts` also gain `encodeURIComponent(project)`, to stay consistent with the newly-added methods, or are they explicitly excluded per the Follow-ups note's "not fixed wholesale" carve-out? (gap 6)

None of these are design-breaking — each has a small, locally-scoped answer — but each would produce a different diff depending on the answer, and at least gaps 1, 3, and 4 touch patterns (exit-code handling, lazy-mount lifecycle) that this codebase has visibly been bitten by before (the comments at `TerminalPane.tsx:287-292` and `p.$project.$term.tsx:30-44` exist because of prior review findings in the same file). An implementer who doesn't independently re-derive those patterns risks reintroducing the class of bug they were added to prevent.

## Verdict

design needs revision / implementation not ready
