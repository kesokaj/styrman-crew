that is false: `3e2f125` contains none of them.

## Verdict: FINDINGS

**Blocking: no** — nothing in the range is an exploitable weakness, and the layout
change is a real net reduction in attack surface. **But do not tag `3e2f125`.** Cut
the tag from a commit that contains the working-tree restorations; see finding 1.

The un-nesting does what it set out to do. There are exactly two bind sources in the
whole binary and after ADR-064 they are siblings — `homes/<u>/base` for the setup VM
and `homes/<u>/p/<uuid>` for a project VM — with the tenant dir `homes/<u>` mounted
into no guest at all. Every server read and write below `HomesDir` is confined by an
`os.Root` anchored at the (now server-only) tenant dir, with two named exceptions.
BUG-003's check-to-mount residual is closed for `p/<uuid>`: the guest has no writable
handle on any component of the project home's path any more, so there is no longer a
component to swap between `realBelow` and dockerd's re-resolution. Both post-round-2
fixes are present at HEAD and correct. What is left is one pre-existing, non-regressed
raw-path rename (`migrateWorkspaces`) whose source now roots at the still-guest-writable
`base/` and whose only test the range **deleted**, plus a handful of documentation
statements that are now more reassuring than the code.

- **[medium / confidence: high]** `cmd/styrman/migrate_test.go` at `3e2f125` —

  `LegacyWorkspaceExists` fail-safe and is the guard that stops `ensureRepos` from
  silently recreating a workspace over a real tree. A deleted test cannot fail, so

  is recorded as BUG-005 and already fixed in the working tree (both restored verbatim,
  seven tests, `go test ./cmd/styrman/ -race` green here). **Remediation:** commit the

- **[medium / confidence: medium]** `cmd/styrman/main.go:251` + `:285`
  (`migrateWorkspaces`) — **the last unconfined host-side rename whose source has a
  guest-writable component, and the new startup sweep does not protect it after the
  upgrade boot.** `files.ContainedPath(cfg.UserHome(user), "projects/"+p.Dir)` resolves
  with `EvalSymlinks` (not `os.Root`), then `os.Lstat(oldWS)`, then — across an
  `os.Stat(newWS)`, a Docker `Status`/`Stop` round trip and an `os.MkdirAll` — a raw
  `os.Rename(oldWS, newWS)`. `UserHome` is now `base/`, which the setup VM mounts
  read-write with a root guest whose uid is the server's own
  (`docker-compose.yml:75 user: '${STYRMAN_UID}:…'`), and `/var/lib/styrman` is one
  bind (`:120`), so cross-directory renames succeed. A guest that makes
  `base/projects` a real directory at check time and a symlink at rename time redirects
  the rename; naming its own project so that `p.Dir` is `base` makes the redirected
  source `homes/<victim>/base`, which lands at
  `StateDir/projects/<attacker>/<uuid>` — the attacker's own workspace, bind-mounted
  into their microVM and readable through the file explorer. Preconditions are what
  hold this to medium: the project record must exist while `ProjectWorkspace` does not
  (reachable via `server.go:903-921`, where the wipe loop removes `ProjectHome` first,
  keeps going after a failure, removes `ProjectWorkspace`, then sets `wipeFailed` and
  *keeps the record* — plus the "restored metadata without data" case the code names at
  `main.go:342`), the tenant must have a live setup VM at the moment of a server
  restart, and the race must be won. Note the amplifier: a guest that populates
  `base/projects/<own-dir>` makes `LegacyWorkspaceExists` true, which makes both
  `ensureRepos` (`main.go:339`) and `EnsureRunning` (`orchestrator.go:257`) refuse to
  recreate the missing workspace — so the guest can pin the vulnerable state open
  across boots instead of letting it self-heal. **Not a regression:** identical shape in
  v1.20.0 and earlier, where `UserHome` was the tenant dir and `projects/` was equally
  guest-writable; the range only renames the directory it points at. It is recorded
  here because the round-2 rebuttal (`reviews/2026-09-04-security-unnest-phase1.md`,
  "which incidentally hardens `migrateWorkspaces` too, since … now runs at a moment
  when nothing has `base/` mounted") is **true only on the upgrade boot**:
  `RemoveStaleSetupVMs` removes setup VMs whose bind is *stale*, so from the second
  v1.21.x boot onward a current setup VM holding `base/` is correctly left running
  while `migrateWorkspaces` executes. **Remediation:** do the resolve and the rename
  through `os.Root` at the tenant dir — `rt.Rename("base/projects/"+p.Dir, …)` is not
  expressible across roots, so open `os.OpenRoot(TenantDir)`, `rt.OpenRoot("base")`,
  and move via a confined handle (or copy-then-verify); at minimum re-`Lstat` the
  resolved parent immediately before the rename and refuse a changed inode. Restoring
  `TestMigrateWorkspaces` (finding 1) is the precondition for touching it safely.

- **[low / confidence: high]** `internal/httpapi/git.go:73` — **the only server read

- **[low / confidence: high]** `cmd/styrman/main.go:68-75` +

### 2. Does any guest mount contain a path another guest or the server treats as trusted?

**No, for guest-vs-guest — the enumeration is exhaustive and short.** Docker binds are
built in exactly one place, `orchestrator.go:838-844`:

| guest | bind source → destination |
|---|---|
| project VM | `homes/<u>/p/<uuid>` → `/home/<guest>` |
| project VM | `StateDir/projects/<u>/<uuid>` → `/home/<guest>/projects/<dir>` |
| setup VM | `homes/<u>/base` → `/home/<guest>` (no workspace bind) |

`base/` and `p/<uuid>` are now siblings under `homes/<u>`, which is mounted into
nothing. The only remaining nesting is a project's own workspace inside its own home —
same guest, same project. No guest gets the Docker socket (`docker-compose.yml:117`
mounts it into the server only; the ingress gets it `:ro`, which restricts the file
node and not the API, and that is documented at `:22-25`); the per-project dockerd is
a separate daemon inside the microVM, so a guest cannot reach the host daemon's API to
influence any container's labels, env or mounts.

**BUG-003's check-to-mount residual (`reviews/2026-09-04-security-v1.20.0.md` finding
1): closed, plainly.** That finding turned on one sentence — "the guest reaches those
components only from the setup VM, which mounts `<homes>/<u>`". After ADR-064 the setup
VM mounts `homes/<u>/base`, so no guest has a writable handle on `p` or on `p/<uuid>`,
and there is nothing left to swap between `realBelow` (`orchestrator.go:226`, `:282`)
and dockerd's re-resolution at `ContainerCreate`/`ContainerStart`. The race is not
narrowed, it is unreachable: the attacker has no write access to any component of the
path. The `realBelow`/`projectHomeIsReal`/`files.Trust` guards remain as the second
line ADR-064 says they are. The class is *not* fully gone from the codebase, because
`base/` is still a guest-writable directory the server touches by raw path in the two
sites named above — which is why finding 6 asks the rules file to stop saying the
layout was "removed".

### 3. The startup sweep as an availability surface

- **Slow Docker daemon.** `orchestrator.New` (`:125-131`) only constructs a client — it
  does not ping — so a slow daemon does not abort startup. The sweep is one
  `ContainerList` (label-filtered, cheap), one `ContainerInspect` per setup container
  (at most one per user — the name is `styrman-setup-<user>`), and one force
  `ContainerRemove` per stale one. The whole pass is bounded by the 60 s deadline at
  `main.go:68`; once it expires, each remaining SDK call fails fast with a context
  error, `ContainerInspect` failures `continue` and `ContainerRemove` failures `Warn`
  and continue, so the loop drains quickly rather than blocking per item. Worst case:
  up to 60 s of added pre-listener latency, during which `/api/health` does not answer
  and the ingress serves 502 — the exact incident class `main.go:88-91` records
  (finding 5; the working tree's 10 s is the right value).
- **Docker absent.** `ContainerList` errors → `RemoveStaleSetupVMs` returns `(0, err)`
  → `logger.Warn("stale setup VM sweep failed")` → `migrateBaseHomes` runs anyway.
  Correct, because the migration is confined and because with the daemon down there is
  no live guest either. Startup continues to the listener.
- **Many containers.** The filter is `styrman.system=setup` and only setup VMs carry
  `LabelSystem` (`orchestrator.go:634`; project VMs get `LabelManaged`/`LabelProject`/
  `LabelName`/`LabelUser`, no `LabelSystem`), so the candidate set is at most one per
  user regardless of how many project VMs, ingress or server containers exist. No
  unbounded fan-out.
- **Sweep incomplete.** If the deadline cuts the pass short, stale setup VMs survive
  into `migrateBaseHomes`. That is the *stated* precondition of ADR-064's safety claim,
  and it degrades to round 2's accepted same-tenant residual rather than to anything
  cross-tenant, because every migration step is inside `os.Root`. Recorded as finding 4.
- **Can a guest make the sweep remove a container that is not stale?** **No.** Every
  input to the predicate is server-set at create and unreachable from a guest:
  `insp.Config.Labels[LabelUser]` and `insp.Mounts` come from the server's own
  `createSpec`; `containerGuest(insp.Config.Env)` reads `STYRMAN_USER` from the same
  container's stored env, so even though the in-guest terminal username is
  user-configurable, the value read back always matches the `/home/<user>` destination
  that was created from it — a rename of the setting cannot desynchronise them within
  one container, and a *changed* setting is already handled by the separate
  guest-changed branch at `EnsureSetup`. A guest cannot reach the host Docker API at
  all. Two non-guest ways a live container gets removed, both fail-safe and
  self-healing, are in finding 8: a transiently empty `Mounts` from the daemon, and the
  daemon-wide label scope if two styrman instances shared one daemon.

### 4. Rollback: a v1.20.x server on a migrated state dir

What breaks, in decreasing severity:

1. **The old layout comes back.** v1.20.x `UserHome(user)` is `homes/<u>`, so a setup
   VM it *creates* binds the tenant dir again — with `base/` and every `p/<uuid>`
   inside it, writable by a root guest. That reinstates the BUG-002/003 layout and the
   accepted medium of `reviews/2026-09-04-security-v1.20.0.md` finding 1 in full. It is
   not worse than what v1.20.0 shipped, but it is a security consequence and ADR-064
   states it as a UX one.
2. **Non-determinism about which home is in use.** v1.20.x has no `setupHomeStale`
   check (it is new in this range), so a v1.21.0 setup container that survives the
   downgrade is silently *reused* at `base/`, while one that has been reaped is
   *recreated* at the tenant dir. The same user can therefore land in either layout
   depending on container lifetime.
3. **Readiness and identity read the wrong directory.** `setup.go`'s
   `files.Exists(UserHome, ".ssh/id_ed25519" | ".claude/.credentials.json" | …)` and
   the `setup-done` marker, plus `git.go:73`'s `.gitconfig`, all point at
   `homes/<u>` after the downgrade while the files are in `homes/<u>/base` — every tool
   reads not-set, and a user who "signs in again" re-materialises credentials into the
   tenant dir. Nothing is lost: the broker's own store is `StateDir/credentials`,
   untouched by the layout, so a rolled-back host still serves the current credentials
   to projects.
4. **The file explorer's Home scope widens.** v1.20.x roots it at the tenant dir, so
   the user sees (and can delete through `files.Remove`) `base/` and every `p/<uuid>` —
   their own projects only, but the pre-ADR-031 blast radius.
5. **Rolling forward again is safe.** `migrateBaseHomes` is idempotent: it skips `base`
   and `p`, moves whatever the v1.20.x setup VM wrote to the tenant top level into
   `base/`, and leaves collisions in place. Expect duplicate dotfiles stranded at the
   tenant level and one "base home migration incomplete"-class log line.

**Is it stated in ADR-064?** Partly. The ADR does say the migration is one-way and does
name the readiness symptom and the manual remedy — that is more than most ADRs carry —
but it stops at point 3 and words it as UX. Points 1 and 2 are not stated anywhere, and
point 1 is the one an operator weighing a rollback needs. Finding 6.
