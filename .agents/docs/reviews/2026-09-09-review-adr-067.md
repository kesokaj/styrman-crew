# Review — ADR-067 (per-project LAN mode as bridge-prefix)   (2026-09-09)

Range reviewed: `git diff 44e81e0..HEAD` (HEAD = `5481ea2`)

## Verdict: APPROVE WITH NITS

This is a large, disciplined deletion (root-side marker/spool/status machinery,
the ADR-065/066 firewall reconciler, the credential-broker LAN latch) replaced
by a much smaller mechanism: the network mode is now purely the bridge
interface prefix (`sdb-`/`lan-`) chosen at `docker network create`. I traced
every deleted symbol (`netpolicy.*`, `LanChecker`/`LanExposed`,
`pruneHostReachingCreds`, `BridgeNameForNetwork`, `FirewallRunDir`,
`NetPolicyDir`, the `.path` unit) and found no dangling reference; `go build
./...` and `go vet ./...` are clean on HEAD. The removal of the credential
broker's LAN-based withholding is consistent with the amended R12 text, which
now marks that behaviour as historical ("Was, ADR-065/066: ... withholding the
operator's SSH key ...") rather than current. The one real defect is a timeout
mismatch that reintroduces the shape of BUG-022 (client aborts before a
rebuild that is still succeeding server-side) — not as severe as the original
(150s vs 180s, not 20s vs however-long), but the same bug class, in code that
exists specifically because BUG-022 was found once already. Two small dead-code
leftovers from the deletion round it out.

## Findings

- **[medium / confidence: high]** `web/src/lib/api.ts:490` (`setProjectLan`) —
  client-side `AbortSignal.timeout(150000)` (150 s) is *less* than the
  server's own budget for the same request, `internal/httpapi/network.go:36`
  `lanRebuildTimeout = 3 * time.Minute` (180 s), which
  `setProjectNetwork` uses for `context.WithTimeout` around the synchronous
  stop+`EnsureRunning` rebuild. If the rebuild legitimately takes 150–180 s
  (a slow Kata stop or boot), the browser aborts and the UI reports failure
  for a change that then succeeds server-side — the exact symptom BUG-022
  recorded ("a new endpoint performing an operation an existing endpoint
  already does inherits that operation's timeout budget too"). The adjacent
  `startProject`/`stopProject` client calls get this right: their client
  timeout (150 s) is *larger* than their server context (`2*time.Minute` at
  `internal/httpapi/server.go:1043`/`1065`). `setProjectLan` copied the same
  150000 constant without checking it against `lanRebuildTimeout`, which is
  larger, not smaller. Fix: raise the client timeout past 180 s (e.g. 200000)
  or lower `lanRebuildTimeout` to something under 150 s.

- **[low / confidence: high]** `internal/httpapi/server.go:221-223` —
  `ensureFor` was left with an empty conditional:
  ```go
  id, err := s.orch.EnsureRunning(ctx, user, p.ID, orchestrator.RunOpts{...})
  if err == nil {
  }
  return id, guest, p.Dir, err
  ```
  This is the residue of deleting `s.kickLAN(user, p.ID)` from inside the
  `if`. It compiles and `go vet` is silent on it, but it is dead code per
  criterion 1 and should be removed (collapse to just the `EnsureRunning`
  call + `return`).

- **[low / confidence: medium]** `web/src/lib/api.ts:477-479` — the comment
  above `projectNetwork:` is stale: "The PUT answers with the derived state —
  \"pending\" right after a change, never \"on\" from the [request itself;
  root's next reconcile ...]" describes the deleted ADR-065 `lanState`
  derivation. The current `ProjectNetwork`/`lanView` has no derived state at
  all (`lanAccess`, `canEnable`, `rebuilt` only) and the PUT *does* return the
  actual outcome of a synchronous rebuild. Per the dispatch's instruction to
  treat comments as claims to verify rather than evidence: this one is simply
  wrong now and should be deleted or rewritten, not load-bearing for any
  behaviour but misleading to a future reader.

## Criteria

1. **Dead code** — fail (low severity): the empty `if err == nil {}` block
   above; everything else I traced (netpolicy package, LanChecker,
   BridgeNameForNetwork, FirewallRunDir/NetPolicyDir, the `.path` unit and its
   install-time removal logic, `HostFirewall`/`hostFirewall` in the frontend)
   was fully and consistently deleted with no remaining references anywhere
   in `.go`/`.ts`/`.sh`.
2. **Flow tracing** — pass except the timeout finding above.
   `RunOpts.Lan`/`p.LanAccess` is threaded consistently through
   `ensureFor`, `createProject`, `startProject`, and `setProjectNetwork`'s own
   rebuild call. `bridgeModeMismatch`/`createBridgeNetwork` are the single
   choke point for network creation (good — the comment's claim that both
   `create` and `recreateMissingNetwork` route through it checks out in the
   diff). Partial-failure path in `orchestrator.create()` (NetworkRemove
   failing after the old container is already gone) leaves the project
   retryable on its next start rather than corrupted, matching the existing
   `Destroy` pattern it says it reuses — not a new risk introduced here.
   `ports.go`'s swallowed-error condition is narrow: it only treats a scan
   failure as "no ports" after re-confirming via `Status` that the container
   actually changed/vanished, not on every non-zero exit.
3. **Standards conformance** — pass; Go error wrapping, `inherit_errexit` in
   the new/edited root shell scripts, and the `web/e2e/run.sh` EXIT-trap fix
   (verified empirically: `exit "$status"` after `trap cleanup EXIT` still
   propagates `$status` even though `cleanup` ends in `... || true`) are all
   correct.
4. **Directory layout** — pass; no new files land outside their established
   trees (`internal/config`, `internal/orchestrator`, `internal/httpapi`,
   `web/src/lib`, `deploy/firewall`).
5. **Simplicity** — strong pass; this diff is the poster case for the "shorter
   is better" principle — replacing a root-owned marker/spool/status
   reconciler with an immutable bridge-name prefix and deleting ~2500 lines
   of firewall/netpolicy machinery net of what it added.
6. **Decoupling** — pass; `internal/httpapi/network.go` no longer reaches into
   `internal/netpolicy` (deleted) or `internal/credstore` directly; the
   orchestrator owns the one bridge-naming choke point
   (`createBridgeNetwork`/`bridgeModeMismatch`).
