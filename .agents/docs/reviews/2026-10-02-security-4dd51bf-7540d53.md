## Verdict: FINDINGS (two low; no medium or high)

**Worst problem: the fix is correct, but the queue it guards can still be replayed after a suspend.** The fix for the earlier finding 1 (`if (closedForGood) outbox.length = 0;` in `reconnectNow`) is correct, and it covers every way out of a closed-for-good pane. It introduces no defect, and the shipped bundle carries it. It is not complete for the hazard, though. A pane that is still inside its retry window keeps its queue on purpose. The comment and the spec justify that with "those keys are seconds old", which stops being true when the machine sleeps during that window. On resume, the pending reconnect (or the wake handler that cuts it short) flushes keys typed before the sleep into whatever is in front in the shell. This is pre-existing N6 behaviour, not something the fix introduced. It is the same class and the same low severity as the finding the fix closes.

**Second: the release-signing trust root now has two keys, and no decision record.** This range writes into `versioning.md` and `deploy/gcp.md` that the GCP VM trusts two release-signing keys, the second being the operator's Mac `~/.ssh/id_ed25519`. No ADR decides that.

**The ingress change (BUG-087) is sound:**
- the read is bounded;
- only stdlib is added;
- a failed load can no longer be latched as applied;
- the logged error text is escaped by slog's JSON handler.

**Clean:** `web/dist/client` is the build of the source beside it. There are no secrets, no new injection surface, no authz change and no crypto.

**For the gate:**

A tag the NUC does not trust is refused there, and so are BUG-087's fix and ADR-080's hardening. BUG-084 (its rejected gh-token) already blocks the NUC on its own.

## Findings
- **[low / confidence: medium]** `web/src/components/TerminalPane.tsx:352-355`, with `:312-317`, `:375-377`, `:408-424` and `:262`. The restated claim is at `.agents/docs/specs/styrman/terminal-protocol.md:175-177`, with D24 at `.agents/docs/plans/2026-10-02-tool-updates-freeze-harness-v2.md:341`. Keys queued during a retry window have no age bound, so a suspend inside that window replays them on resume.
  - **The path:**
    1. The socket closes transiently, and `:312-317` arms the 2–15 s backoff timer.
    2. The user types. Each chunk goes into `outbox` at `:418-424`, because the pane is not closed for good.
    3. The machine sleeps before the reconnect lands.
    4. On resume, `visibilitychange` or `online` reaches `onWake`. With `closedForGood` false and `reconnectTimer` set, `:377` calls `reconnectNow()`. `:355` keeps the queue, because the pane had not given up, and the `onopen` handler's `flushOutbox()` (`:262`) sends it.
  - **The wake handler is not needed for this.** Without it, the pending timer fires within seconds of resume and does the same flush. That is so whether the browser's timer clock paused during the suspend or counted it: a paused timer has seconds left, and a counted one is overdue.
  - **The claim it breaks.** The comment at `:352-354` ("those keys are seconds old and the user is waiting on them") and the spec at `terminal-protocol.md:175-177` justify keeping the queue. Across a suspend, the keys can be hours old.
  - **Exposure:** the same as the earlier finding, which the fix closes. It is the user's own input, in their own session, so nothing crosses to another user. But it lands out of context, in whatever the tmux session shows on resume. An agent CLI that kept running in the VM may be at a permission prompt by then.
  - **Bounded by the idle reaper.** `STYRMAN_IDLE_TIMEOUT` defaults to 8 h (`internal/config/config.go:181`). After a longer suspend the project is stopped, and the retry is answered with 4002, which never flushes.
  - **Pre-existing.** N6's queue flushed after a suspend before v1.39.0; ADR-079's wake path only makes the flush immediate.
  - **Not covered by tests.** The testing README says "NOT covered by any tier: a real sleep/wake".
  - **Remediation:**
    - Bound the queue by wall-clock age, on every path at once. Stamp each pushed chunk with `Date.now()`, which advances across a suspend, unlike `performance.now()` or timer clocks. In `flushOutbox`, drop what is older than a short bound, such as 30 s. Keep the closed-for-good clear as a second line.
    - Put the policy in a pure module with an injected clock, tested like `web/src/lib/termLiveness.ts`, with a case that fails without the bound. The e2e cannot suspend a machine.
    - Correct the "seconds old" claim in the comment, the spec and D24 in the same change.
  - **Confidence is medium** because it was reasoned from the code, not observed in a browser.
- **[low / confidence: medium]** `.agents/docs/specs/styrman/versioning.md:281-286` and `.agents/docs/deploy/gcp.md:79-83`. The trust root of the root-run auto-updater was widened to a second release-signing key. This range records that as a fact; it is decided nowhere.
  - **The two keys.** The GCP VM's `allowed_signers` lists the original release key (`SHA256:5HpYQJjpG+…`) and the key that signed v1.39.0 (`SHA256:XeeDl8Y8…`). Per `.agents/docs/handoffs/2026-09-22-gcp-deploy-and-v1.39.0.md:48`, the second is `~/.ssh/id_ed25519` on the operator's Mac, a general-purpose SSH key.
  - **No decision record.** `DECISIONS.md` has no entry for it; no hit for the fingerprint, "second signer", "second key" or "Mac key".
  - **Why it matters.** A tag signed by either key, once pushed, runs as root on that host through the updater (ADR-051). Every trusted signer is a key whose compromise is root on the fleet. The code review's medium finding asked for "an ADR"; the commit added the docs only.
  - **Remediation:** an ADR, amending ADR-051, that decides the signer set. It either retires the Mac key from the VM's list and signs future tags with the original key, or keeps it and records where it lives and how it is protected. It names each host's `allowed_signers`.
  - **Confidence is medium** because neither host's `allowed_signers` was read; the content comes from the docs and handoffs.

## Checked
- **The fix to the earlier finding 1: correct; complete for the path it names; no defect introduced.** I re-read every declaration the fix touches and every reference to them:
  - `closedForGood` (declared at `:201`): `:228, 247, 278, 284, 293, 300, 308, 320, 355-356, 368, 400, 418, 489`;
  - `outbox` (declared at `:407`): `:355, 410, 418, 423`.
  - **Every exit from closed-for-good drops the queue.** Those exits are the wake (`onWake` `:369-370`, resumable `wake`) and the reclaim (`:369` when shown, and `reclaimRef` `:400`), and all of them pass through `reconnectNow`, which now drops the queue. The Reconnect and Start buttons bump the epoch and re-run the effect with a fresh `outbox`.
  - **No new socket can flush the old queue.** `connect()` refuses while closed for good (`:228`). `closedForGood` is set only by the current socket's `onclose`, or by cleanup after `dropSocket` has nulled the handlers. So no socket can open, and flush, after the pane gave up without passing through `reconnectNow`.
  - **No temporal-dead-zone hazard.** `outbox` is declared after the first `connect()` (`:361`). `reconnectNow` only runs from handlers and timers, which fire after the effect body has finished. The new statement also reads `outbox` only when `closedForGood` is true, which nothing sets synchronously.
  - **Reclaim behaviour is unchanged in practice.** Its queue is empty anyway: a 4001 arrives on a socket that was open and already flushed.
  - **The shipped bundle carries the fix.** `TerminalPane-DGlXIpWj.js` contains ``le=()=>{clearTimeout(g),g=void 0,oe(),f&&(C.length=0),f=!1,p=`no`,m=0,y()}``, where `f` is closedForGood and `C=[]` is the outbox flushed by `fe`.

- **Ingress, `deploy/caddy/ingress/watcher.go:357-377` and `:436-457`.**

  - **Read errors fail closed.** A read error is a plain error, so it is retried and never latched. A masked failure is returned as a plain error, not `errAdminUnreachable`. `noteReloadFailure` resets `adminDown` and re-arms the 15 s retry, so the retry loop is unbounded but paced, and it never takes the fatal exit.

  - **The error text adds no exposure.** Caddy's error message joins the returned error and is logged through `slog.NewJSONHandler` (`cmd.go:34`), which escapes it, so there is no log injection. Caddy's admin API already logs the same message itself, and the warnings array is discarded.
  - **One accepted edge.** A body cut at 1 MiB decodes as "no error", so a failure would read as success. That would take about a megabyte of adapter warnings before the error object, against the one "not formatted" warning in BUG-087's body. The tenant-controlled share of the Caddyfile was not re-traced here.
