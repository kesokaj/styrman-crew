# Security review — editor syntax-check + tag-gated auto-update   (2026-09-01)

Scope: the whole uncommitted working tree at `HEAD = c57abb2` plus its blast radius —
`internal/httpapi/{check.go,format.go,server.go}`, `internal/orchestrator/exec.go`,
`internal/conversation/store.go`, `deploy/update/**`, `deploy/host-setup.sh` step 8c,
`deploy/Dockerfile.server`, `image/Dockerfile`, and the new/changed `web/src` editor
components. Reached outward through `gitContext` → `getProjectFor` → `authGuard`,
`project.ValidateName`, `deploy/docker-compose.yml`, and `.dockerignore`.
Out of scope by ADR-046: `image/harness/**`.

## Verdict: FINDINGS

The worst problem is not in the shell-injection surface — that one is genuinely fixed.
It is in the new root process: `deploy/update/styrman-update` turns any `vX.Y.Z` tag that
appears on the remote into unattended root-run code on the homeserver within ~5 minutes,
and it verifies **nothing** about where that tag came from. There is no `git verify-tag`,
no allowed-signers file, and the first `git fetch` runs under
`StrictHostKeyChecking=accept-new`, so the very first contact is trust-on-first-use for a
root-privileged fetch. The operator has consciously accepted "a pushed tag becomes root
code"; what is not yet decided is that the accepted set is *anyone who can push a tag* —
a GitHub account compromise, a future collaborator, or a write-capable CI token — rather
than *the operator*. A tag signature check is the one control that narrows it back, and it
is missing.

Everything the review was asked to confirm as *not* broken checks out: `safeSuffix()` is a
complete fix, no other caller-derived value reaches either guest script, `authGuard` is
byte-identical to `HEAD` and still exempts only `/api/health`, the `.env`-token-grep
residue is gone, and the lint gutter is not an XSS sink.

## Findings

- **[medium / confidence: high]** `deploy/update/styrman-update:132` — `git checkout --detach --force "${tag}"` followed by `docker build` + `docker compose up` executes the tag's contents as root, with the docker socket, on a 5-minute timer, with **no integrity check on the tag**. `git fetch --tags --force --prune-tags` additionally accepts a *re-pointed* tag, and `docker-compose.yml` is itself part of the checkout — so a hostile revision can simply add a `/:/host` bind mount. Exploitable in principle by anyone who gains tag-push rights on the private repo (account takeover, a stolen PAT, a collaborator, a future CI job); the read-only deploy key constrains the *host*, not the *pusher*. Remediation: require annotated, signed tags and fail closed —
  `git -c gpg.ssh.allowedSignersFile=/etc/styrman/allowed_signers verify-tag "${LATEST}"` (or GPG equivalent) before `checkout`, with the signer file root-owned `0644` and the key material never on the host. Reject lightweight tags explicitly (`git cat-file -t "${LATEST}"` must be `tag`), since a lightweight tag cannot carry a signature.

- **[medium / confidence: medium]** `deploy/update/styrman-update:78` and `deploy/host-setup.sh:344,373` — `StrictHostKeyChecking=accept-new` on a fetch that runs as **root** and whose result is built and executed as root. On first contact root's `known_hosts` is empty, so an on-path attacker during that single window pins their own host key and thereafter serves an arbitrary repository; `accept-new` never re-prompts afterwards. The existing precedent at `internal/httpapi/server.go:745` is a *guest-side* git clone with far lower stakes, so it does not carry over. Remediation: pre-seed the host key out-of-band and pin it — `-o UserKnownHostsFile=/etc/styrman/known_hosts -o StrictHostKeyChecking=yes`, with `/etc/styrman/known_hosts` populated from GitHub's published SSH key fingerprints (verified against `https://api.github.com/meta`), not from an unverified `ssh-keyscan`.

- **[medium / confidence: medium]** `image/Dockerfile:44-49` — `hadolint` (new this cycle) and `yq` are fetched from `releases/latest/download/...` with no version pin and no checksum; `helm` and OpenTofu are installed by `curl … | bash` on the line above. Two distinct consequences. (a) Cross-user: the runtime image is shared by every user's microVM and those VMs hold seeded gcloud/gh credentials, so a compromised upstream release or registry response lands attacker code next to other users' credentials — this crosses the per-user boundary that makes "runs code in the guest" otherwise uninteresting. (b) New this cycle: the updater's rollback promise is "rebuild the previous tag", but `latest` resolves differently on every rebuild, so rolling back to `vX.Y.Z` does **not** restore the image that tag originally produced. Remediation: pin explicit versions and verify — `HADOLINT_VERSION=…` + `sha256sum -c` against a checksum recorded in the repo; same for `yq`. If the precedent is kept for `helm`/`tofu`, record that as an explicit accepted risk in `DECISIONS.md` rather than by omission — but the deterministic tag→image mapping is worth having regardless, now that rebuilds are automated and unattended.

- **[low / confidence: high]** `deploy/update/styrman-update:70` — the `git()` wrapper injects `-c safe.directory="${DEPLOY_DIR}"` unconditionally, which disables git's protection against root operating on a repository owned by another user. The subsequent `docker build` of that tree is root-equivalent. In the intended deployment `/opt/styrman` is root-owned (host-setup clones as root) so this is not currently reachable, but the override removes the exact safety net that would catch a mis-provisioned or operator-owned clone. Remediation: assert ownership instead of suppressing the check — `[ "$(stat -c %u "${DEPLOY_DIR}")" -eq 0 ] && [ "$(stat -c %u "${DEPLOY_DIR}/.git")" -eq 0 ] || fail "deploy clone must be root-owned"` — and drop `safe.directory` once that holds.

- **[low / confidence: medium]** `deploy/update/styrman-update:132` — `git checkout --force` discards tracked modifications but leaves **untracked** files in place, and `deploy/docker-compose.yml:63` builds the server with `context: ..` (the whole deploy clone). A file planted in `/opt/styrman` therefore survives every checkout and is fed into every subsequent image build. This is a persistence/escalation aid, not an entry point (it presupposes write access to a root-owned tree), and `.dockerignore` does exclude `**/.env` and `.git` from the context. Remediation: build from a clean tree — `git clean -xdff -e deploy/.env` after checkout, or export the tag with `git archive` into a scratch dir and build from that. `--force` itself is correct here and should stay: it does not touch the gitignored `deploy/.env`.

- **[low / confidence: high]** `deploy/update/styrman-update:97,123,205` — `CURRENT`/`PREVIOUS` are read from `${DEPLOY_DIR}/.deployed-version` with no validation and flow into `git log "${CURRENT}..${LATEST}"` and `git checkout --detach --force "${PREVIOUS}"`. Quoting prevents shell injection, but a value beginning with `-` becomes a git *option* rather than a ref (argument injection). The file is root-written and root-owned so this is not attacker-reachable today; it is a missing invariant, not a live hole. Remediation: after reading, require `^v[0-9]+\.[0-9]+\.[0-9]+$` (the same anchored pattern already applied to `LATEST`) and fail otherwise.

- **[low / confidence: high]** `deploy/update/styrman-update.service` — the unit runs as root with the docker socket, which is root-equivalent by construction; `ProtectSystem=strict` / `ReadOnlyPaths` would break `docker build` and buy nothing, because a hostile tag's payload executes inside the *daemon*, not inside this unit's cgroup. Stated plainly so it is on the record: **sandboxing this unit is not the control that matters — finding 1 is.** `NoNewPrivileges=yes` and `ProtectHome=yes` are free and harmless (the docker CLI needs neither setuid nor `/home`), and `PrivateTmp=yes` is safe given the lock lives in `/run`; add them if desired, but do not mistake them for mitigation.

## Checked

**Secrets** — Clean. No credentials, tokens, keys, or committed `.env` anywhere in the diff (scanned the source diff excluding `web/dist` and `package-lock.json`; `web/e2e/**`, `check_test.go`, `deploy/update/**` scanned individually). The earlier `.env` token-grep + `docker run` header is fully **removed**: `styrman-update` now touches `deploy/.env` only in an existence check (`:57`) and never reads its contents, and nothing in the updater's stdout — which lands in root-readable journald — carries a secret value. `.dockerignore` excludes `**/.env`, `*.env`, `deploy/.env` and `.git` from the `context: ..` server build. `host-setup.sh:299-300` creates `deploy/.env` `chown OPERATOR` + `chmod 600`; the step-8c instructions correctly tell the operator to `chmod 600` the deploy clone's copy, and correctly do **not** automate copying a secrets file. `.gitignore` covers `.env`, `*.env`, `/styrman`, `wsprobe`.

**Injection** — The `safeSuffix()` fix is **complete**, verified by exhausting the paths rather than by inspection of the fix alone. In `checkScript`/`formatScript` exactly three values are interpolated: the suffix (`safeSuffix`, `[A-Za-z0-9]{1,16}` with a `"txt"` fallback — non-alphanumerics are dropped, not escaped, so `$(id)` → `id`), a `%d` byte count from `len(body.Content)`, and `c.cmd`/`formatInPlace(ext)` which are **compile-time constant strings** in every branch, including the concatenated shellcheck branch. The Dockerfile basename bypass is closed because the sanitizer is applied to the extension at the call site (`check.go:346`), after `checkerFor`, not inside the switch — so the basename branch cannot route around it. `format.go:82` applies the identical sanitizer even though `formatInPlace`'s switch already allowlists `ext`, which is the right call for keeping the two from drifting. Content never touches argv: it goes over stdin and the guest reads an exact byte count (`head -c N`) with a `wc -c` equality assertion, which is also what the `exec.go` half-close removal now *requires* — that coupling is correctly documented on both sides. `body.Path` reaches only `filepath.Base` and `filepath.Ext`; it is never used to open, write, or name a file, so path traversal has no sink. `WorkDir` **cannot** be influenced: `ws = "/home/" + guest + "/projects/" + pr.Dir`, `pr.Dir` is enforced against `^[a-z][a-z0-9-]{0,30}$` (`internal/project/store.go:40,102`) and `guest` is derived from the OAuth identity, not from the request body. The `$F` / `${F}.out` / `${F}.err` expansions are all double-quoted; `$F` comes from `mktemp -p .`, so the derived `.out`/`.err` names are unpredictable and the symlink-race window is (a) not attacker-predictable and (b) confined to the requesting user's own workspace inside their own microVM — no boundary crossed. In the updater, `LATEST` is constrained by the anchored `grep -E '^v[0-9]+\.[0-9]+\.[0-9]+$'`, which git tag names cannot escape (no newlines, no shell metacharacters survive the anchor); the residual argument-injection nit on `CURRENT`/`PREVIOUS` is filed above as low.

**Authz/authn** — `internal/httpapi/auth.go` is **unchanged** (`git diff HEAD` empty; last touched by `0192afd`). `authGuard` still exempts only `/api/health`, plus the `isLinkPath` capability branch which independently enforces the constant-time ingress-token check. The rejected `/api/version` exemption left **no residue** — `reports_version()` reads a build-time container label via `docker inspect styrman-server`, which needs no auth, no ingress token, and no network. That label cannot be spoofed by anything a project VM controls: `deploy/docker-compose.yml` mounts `/var/run/docker.sock` into **only** `styrman-caddy` and `styrman-server`, never into project containers (guests run their own nested dockerd), and Docker enforces container-name uniqueness so a running `styrman-server` cannot be shadowed. The new `POST /api/projects/{project}/check` route is registered inside `RoutesWithAuth` alongside `/format` and resolves through `gitContext` → `getProjectFor` → `s.who(r)` → the caller's own per-user `projects` store, so a project ID guessed from another user's namespace 404s rather than resolving. No middleware is skipped and no ID is trusted from the client. Considered and dismissed: `/check` adds no rate limit, but it grants no compute the caller does not already have via their own terminal in their own VM, so it is not a new DoS primitive.

**Crypto** — Nothing hand-rolled introduced. No auth, session, password-hashing, JWT, or OIDC code in the diff. The only cryptographic material in scope is the SSH deploy key, consumed by stock OpenSSH via `GIT_SSH_COMMAND`, and the `openssl rand -hex 32` token/JWT-key generation in `host-setup.sh` — pre-existing, unchanged, and a correct use of a vetted CSPRNG. The existing constant-time ingress-token comparison (`crypto/subtle`) is untouched.

**Dependencies** — `govulncheck ./...` (via `go run golang.org/x/vuln/cmd/govulncheck@latest`, not installed locally): **2 called vulnerabilities**, both in `github.com/docker/docker@v28.5.2+incompatible` — GO-2026-4887 (CVE-2026-34040, Moby AuthZ-plugin bypass on oversized request bodies) and GO-2026-4883 (CVE-2026-33997, off-by-one in plugin privilege validation). Both are **`Fixed in: N/A`** on the `+incompatible` line (fixed only in `github.com/moby/moby/v2 ≥ 2.0.0-beta.8`), both are daemon-side issues, and both are flagged solely through package-`init` reachability (`orchestrator.init calls client.init, which calls api.init`) with no real client call path — pre-existing, not introduced by this diff, and not actionable without a module-path migration. Worth a TODO row, not a blocker. `npm audit` in `web/`: **found 0 vulnerabilities**. One new npm dependency, `@codemirror/lint ^6.9.7` — justified: first-party CodeMirror, required for `lintGutter`/`linter`, no stdlib or existing-dep equivalent, and it is the smallest thing that does the job. No new Go dependencies (`internal/conversation/store.go` deliberately hand-rolls natural sort on `unicode`/`utf8` rather than pulling `x/text/collate`, and documents the tradeoff — correct stdlib-first call, and the ordering change carries no security weight). `go build ./...` clean; `go test ./internal/httpapi/... ./internal/conversation/...` pass.

**Frontend (surface 5)** — Clean, no XSS. Checker diagnostics reach `@codemirror/lint` as `Diagnostic.message`, a plain string; `dist/index.js:423` passes it as a child of `crelt(…, "cm-diagnosticText", …)`, which appends it as a **text node** — a hostile diagnostic containing markup renders as literal text. `renderMessage` (the only HTML-capable path) is not used. `d.line`/`d.col` are clamped to the document in `CodeEditor.tsx` before becoming positions, so a checker reporting a line past EOF cannot throw inside CodeMirror. `checkNote` is a JSX text child (`FileEditor.tsx:280`), React-escaped. `FileEditor.tsx:141` markdown preview is unchanged in substance and still safe: `micromark(text, { allowDangerousHtml: false })` escapes raw HTML and its `sanitize-uri` protocol allowlist drops `javascript:` hrefs, so the `.replaceAll("<a href=", …)` rewrite can only match generator-emitted anchors — a literal `<a href=` in the source is already `&lt;a href=`, and `<` inside an emitted attribute value is escaped, so the replacement cannot break out of an attribute. `dangerouslySetInnerHTML` at `:378` is the only such usage in `web/src` and its comment accurately states why it is safe. No `eval`, `new Function`, `innerHTML`, `srcdoc`, `postMessage`, or `window.open` in the new/changed components; the two `href=` uses go through `api.downloadUrl`, which `encodeURIComponent`s the path.
