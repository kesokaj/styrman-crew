## Status: COMPLETE

## Verdict: FINDINGS (low only — the fix holds)

The fix holds. authGuard now judges a request by `routePath(mux, r)`, the path part of the pattern `mux.Handler(r)` returns. That is the same lookup `ServeMux.ServeHTTP` runs, on the same mux instance (server.go:455, the only production caller). In go1.25.0 that lookup returns one of three things:
- a registered pattern;
- for a redirect, the redirect target's pattern;
- `""` when nothing matches.

So the link exemption (ingress token only, no identity) now reaches only `serveLink`, `redirectSlash` or a 301 `RedirectHandler`. No API, WS or SPA pattern starts with `/link/`, `/shared/`, `/proxy/` or `/p/…/port/`. Addendum2's crafted `…/terminals/..%2F…%2Flink%2Fx` is refused with 401 without an identity. So is the same trick through the `/ws/term/{project}/{term}` and `/ws/browser/{project}` wildcards. Before this fix those requests failed closed only inside the handler.

Real link, shared and preview routes behave as before, including `<token>.preview` hosts rewritten to `/link/{token}/…`. A non-styrman Google user still reaches only preview and shared routes. `/api/health` stays open. Unclean paths still get only a 301, and unmatched paths now need an identity.

What remains is low:
- the `/api/health` exemption is still judged on the decoded path, though it fails closed;
- the non-user half of the fix had no test that could fail at 57de009 (closed in 96c5f95, after the range);
- two comments are stale.

## Findings
- **[low / confidence: high]** `internal/httpapi/auth.go:28`: the `/api/health` exemption is the last authGuard decision keyed on the decoded `r.URL.Path`.
  - **Contradiction.** It goes against `routePath`'s own doc comment (`internal/httpapi/budget.go:140-141`: "the one thing every guard may judge a request's kind by").
  - **Weakness.** `GET /api%2Fhealth` decodes to `/api/health` and skips the identity check. Its route is the `GET /` SPA catch-all, because the encoded slash keeps `api/health` in one segment.
  - **Why it fails closed today.** Two checks stop it: the catch-all 404s any decoded `/api/` path (`server.go:606-609`), and it refuses an unauthorized identity (`server.go:614`).
  - **Risk.** This is not a bypass. It is a latent one, the same class this range closes: if the catch-all ever changes, the guard alone does not hold. It predates the range.
  - **Remediation.** Exempt only when `routePath(mux, r) == "/api/health"`. That keeps `GET`/`HEAD /api/health` open and sends the encoded form to the identity check.
  - **Test.** Through `RoutesWithAuth("header")`: an anonymous `GET /api%2Fhealth` gets 401, and `GET /api/health` gets 200.
- **[low / confidence: high]** `internal/httpapi/auth.go:77`: at 57de009, no test could fail on the non-user half of the fix.
  - **Gap.** Put `r.URL.Path` back on this line and every test at 57de009 stays green. No test there sends a non-styrman email on a path whose decoded form reads as preview or shared while its route does not. `TestAuthGuard` covers only `/api/projects` and `/api/health`.
  - **Impact of that revert.** None today: the catch-all would still 404 the unauthorized identity (`server.go:614`).
  - **Closed after the range.** 96c5f95 adds `TestANonUserReachesOnlyPreviewAndSharedRoutes`, where `/proxy%2F<pid>%2F3000/x` → 403 "not authorized". I read that test and ran it green, but I did not mutation-check it.
  - **Remediation.** None beyond confirming that mutation in 96c5f95's own review.
- **[low / confidence: high]** Describing text: two comments are stale.
  - `internal/httpapi/auth.go:42` cites "ADR-086 amendment 2" for authGuard's change. DECISIONS.md:2980-2982 and plan D29 record it as amendment 3; amendment 2 is csrfGuard/budgetGuard.
  - `internal/httpapi/server.go:610-613`, the catch-all comment, still says a preview-only guest reaches it through "a malformed /proxy/… that didn't match the proxy routes". Since 57de009, authGuard refuses that request (its route is `/`), so the comment describes a flow that no longer exists. The check below the comment is still worth keeping as defense in depth.
  - **Remediation.** Cite amendment 3. Reword the catch-all comment as defense in depth: authGuard admits a non-user only to preview and shared routes, so an unauthorized identity here is unexpected.

## Checked
- **Route lookup (go1.25.0 source read).** I read `findHandler` and `matchOrRedirect` from the local toolchain.
  - Outside CONNECT, there are four outcomes:
    - (a) a match returns the matched pattern;
    - (b) a trailing-slash redirect returns the slash-appended path's pattern, with a `RedirectHandler`;
    - (c) an unclean path returns the cleaned path's pattern (or `""`), with a `RedirectHandler`;
    - (d) a 404 or 405 returns `""`.
  - The CONNECT trailing-slash case would return the decoded `u.Path`. But every registration names its methods (GET/HEAD/POST/PUT/PATCH/DELETE/OPTIONS) and none names CONNECT, so CONNECT always gets `""` and needs an identity.
  - I read the whole `newMux` table (`server.go:460-603`). Only the tunnel registrations satisfy `isLinkPath`/`isSharedPath`/`isPreviewPath`:
    - `/link/{token}[/]`
    - `/shared/{token}[/]`
    - `/proxy/{project}/{port}[/]`
    - `/p/{project}/{term}/port/{port}[/]`
  - No pattern is host-qualified.
- **Nothing rewrites the request between authGuard and the mux.**
  - `csrfGuard` (`server.go:712-735`) and `budgetGuard` (`budget.go:217-253`) only read the URL and Host.
  - `identity.WithUser` only adds context.
- **previewHostRewrite (`server.go:649-690`).**
