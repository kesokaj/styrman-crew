## Status: COMPLETE

## Verdict: FINDINGS (three low; no medium or high)

**The medium finding is fixed.** Round 1's medium finding (`/opt/agy` 0777) is fixed, and the fix is correct and complete for the threat it named:
- **Image:** `/opt/agy` is built `0755` root-owned (`image/Dockerfile:151`).
- **Boot:** the entrypoint chowns only the directory to `UID_:GID_` on every boot (`image/entrypoint.sh:67`). That runs after the uid-mismatch FATAL and before the minimal-mode branch, so no uid other than the project user can rename into the directory, in project VMs and in the setup VM alike.
- **Group:** mode 0755 leaves the group without write. That matters here, because `groupadd -g "${GID_}" … || true` (`:46`) can leave the user's primary group a pre-existing system group.
- **Failure:** a failed chown fails closed. The directory stays root 0755: `agy update` breaks, and nothing opens.
- **Test:** the new Tier 2 check pins the owner, the mode and "nobody cannot write", with a positive control in front of the negation. ADR-080 and BUG-086 record that the must-fail state was observed on the 0777 image.
- **Release exposure:** no tag contains 11e4f9a (the newest tag is v1.39.0), so no released container ever carried the 0777 directory.

**The low finding is fixed.** Round 1's low finding (Claude Code is a run-time float) is fixed in the Dockerfile pin note, the runtime-image spec and ADR-080.

**The bridge refactor is clean.** `applyControl` in `internal/terminal/bridge.go` is behaviour-identical to the inline code it replaced and leaves no orphaned declaration.

**What remains is low:**
1. ADR-077's heading still has no supersession marker, so its "mode 0777 … opens no boundary" reads as current where it was written.
2. The new check proves the directory, not the binary it protects.
3. Round 1's js-yaml advisory, outside the range, is still open.

## Findings
- **[low / confidence: high]** `.agents/docs/architecture/DECISIONS.md:2761` (ADR-077 heading), with `:2765` (Decision (2)) and `:2769` (Consequences): the reversed security claim still stands unqualified where it was made.
  - **What it still says:** "the directory mode 0777 … The mode opens no boundary". It also still says a newer Claude is "the user's own choice inside their VM".
  - **What was corrected:** round 1 named this location among the four restatements to correct. The other three were rewritten: `image/Dockerfile:129-140`, `image/README.md:22` and `specs/styrman/runtime-image.md:66-71`. ADR-077 itself is corrected only by ADR-080, thirty lines below it.
  - **The file's own convention:** a superseded ADR is marked on its heading line. ADR-062 (`:2351`) and ADR-073 (`:2723`) both read "— superseded by ADR-074". ADR-077's heading reads "— Accepted" only.
  - **Who is misled:** a reader who reaches ADR-077 directly takes 0777 and "opens no boundary" as current. That includes `sh-agent search --refs ADR-077`, the spec's "ADR-077" pointer, and BUG-080's record. That reasoning is exactly what BUG-086 records as the defect.
  - **Remediation:** append "— directory mode superseded by ADR-080 (2026-10-02)" to the ADR-077 heading, as ADR-062 and ADR-073 do. This is a documentation fix; no code is involved.
- **[low / confidence: low]** `.agents/docs/testing/styrman/integration.sh:261-262`, with `image/Dockerfile:151-152`: the new check proves the directory, not the binary it protects.
  - **What is asserted:** `stat -c '%U %a' /opt/agy` and `runuser -u nobody -- test -w /opt/agy`. Nothing in the image or the tests asserts the mode of `/opt/agy/agy` itself.
  - **Where that mode comes from:** at build, Google's installer sets it and the RUN step `mv`s it unchanged. After an update, `agy update`'s own writer sets it, under the project user's umask.
  - **The gap:** a group- or world-writable binary can be overwritten IN PLACE by another uid. That is BUG-086's outcome by a second route, and the check stays green. A group-writable updated binary is the plausible shape, because its group is the user's primary group, which can be a pre-existing system group (see the verdict).
  - **Confidence:** low, because the file's real mode was not observed. No verifier, change or bug record states it, and docker was excluded from this review. This is a coverage gap, not a demonstrated hole.
  - **Remediation:** extend the check with `[ -z "$(docker exec ${CN} find /opt/agy -perm /022 -print)" ]`. It covers the directory, the binary and anything an update leaves behind. Optionally add `chmod go-w /opt/agy/agy` after the `mv` in the image's RUN step.
- **[low / confidence: high]** Pre-existing and outside the range; carried from round 1, which 39ccf89 left open by name: GHSA-2883-xcg3-v3hh, a js-yaml CPU denial of service on empty merge sources.
  - **Package:** `js-yaml` 4.0.0-4.3.1 in the web build chain (`node_modules/js-yaml`, via `@tanstack/react-start -> @tanstack/start-plugin-core -> xmlbuilder2`). npm rates it high.
  - **Re-run:** `npm audit` this round gave the same single result, rc=1.
  - **Exposure:** minimal. It is a build tool only, the shipped SPA is static, and exploiting it needs attacker-controlled YAML at build time.
  - **Remediation:** a separate dependency change (`npm audit fix`, which npm reports as available).

## Checked
- **Fix 1: the agy directory (BUG-086, ADR-080).**
  - **Image.** `image/Dockerfile:151` creates the directory with `install -d -m 0755 /opt/agy`; the `mv` and the `/usr/local/bin/agy` symlink are unchanged.
  - **The chown.**
    - `image/entrypoint.sh:67` chowns the directory only.
    - `UID_` and `GID_` are `:?`-guarded environment values from the server (`:9-10`), and the chown runs after the `id -u` mismatch FATAL.
    - The script uses `set -uo pipefail` without `-e`, so a failed chown logs a WARN and leaves the directory root 0755.
    - The chown runs before the minimal-mode exit at `:354`, so the setup VM gets it too.
    - It runs without `-h`. That is fine: `/opt` is root 0755, so only root, or the project user through sudo (already root-equivalent), could plant a link at `/opt/agy`. No other uid has a path to it.
  - **No boot-time `chmod`.** This is not a gap. The directory and the entrypoint come from the same image, and no release carried 0777, so no older container meets the new entrypoint.
  - **No root-run agy.** The entrypoint's only agy call (`:255-256`, `agy mcp add`) runs under `runuser -u "${USERNAME}"`, and `styrman-setup` runs agy interactively as the user. The Dockerfile's "nothing runs agy as root after this build step" holds for the boot path. Even if it did not, the project user has passwordless sudo, so it would grant nothing new.
  - **Tier 2, both directions.** Two checks pin both sides:
    - The owner side is `integration.sh:254-255`: the user can write the directory, and `agy` resolves to the regular path `/opt/agy/agy`.
    - The new check at `:261-262` requires `stat -c '%U %a'` to equal `${ME} 755`. A 0777 directory fails it, so does a root owner, and so does an added setgid or sticky bit (`%a` prints 2755 or 1755).
    - `runuser -u nobody -- true` runs before the negated `test -w` in the same `&&` chain, so a docker or runuser failure cannot read as "cannot write".
    - The must-fail state is taken from ADR-080's Context and BUG-086 ("`runuser -u nobody -- test -w /opt/agy` succeeded" on the 0777 image). It was not re-observed here, because docker was excluded.
  - **Restatements.** A grep of the tree (excluding `web/dist` and the dated trail records) covered "opens no boundary", "0777", "world-writable", "ONE thing that floats" and "the user's own choice inside". Every living hit is corrected: `image/Dockerfile:52,134`, `image/entrypoint.sh:62`, `image/README.md:22`, `specs/styrman/runtime-image.md:69` and `integration.sh:257`. The plan's paragraph (`plans/2026-10-02-tool-updates-freeze-harness-v2.md:113-119`) is marked "SUPERSEDED by D21". ADR-077 is finding 1.
