# Security review — 1fe28a0-4460e1b   (2026-10-02)

Range reviewed: 1fe28a0..4460e1b (11e4f9a image pins / harness v2.3.2 / in-project claude+agy updates, ADR-077/078; 4460e1b terminal ping/pong liveness + "Use here" reclaim, ADR-079, BUG-085; diff `git diff 1fe28a0...4460e1b`)

## Status: COMPLETE

## Verdict: FINDINGS

The worst problem is in the runtime image. It now ships `/opt/agy` as a world-writable directory (0777, no sticky bit) that holds the `agy` binary, and `/usr/local/bin/agy` resolves to that file. Any UID inside a project microVM can rename a file of its choosing over `/opt/agy/agy`, not only the project user. The next `agy` the project user runs then executes it. That user has passwordless sudo (`image/entrypoint.sh:56`) and the brokered git/gh/gcloud/claude/agy credentials, which are shared across all of the user's projects. ADR-077 and the Dockerfile comment say the mode "opens no boundary" because the project user is root in its VM. That holds for the project user only. The other UIDs in the VM are the boundary this mode removes: apt's `_apt` fetchers, which also run during the boot-time apt restore, and the workers of any daemon a user installs and exposes through a port preview or public link. The second finding is documentation. Since ADR-077, Claude Code updates itself unattended from npm in every project, yet the pin note and the runtime-image spec still describe it as pinned and agy as "the ONE thing that floats". The bridge's ping/pong, the frontend reclaim and liveness logic, and the `styrman-ctl` CLOUDFLARE_API_TOKEN fill are clean. The new image pins I could check match the publishers' own sums.

## Findings
- **[medium / confidence: medium]** `image/Dockerfile:141` (`install -d -m 0777 /opt/agy`): a world-writable, non-sticky directory holds an executable that is on every PATH (`/usr/local/bin/agy` -> `/opt/agy/agy`, `image/Dockerfile:143`). It is also on sudo's `secure_path`, so `sudo agy` resolves to it.
  - **Weakness:** POSIX rename semantics let any UID in the microVM replace the binary. Nothing at boot narrows the mode: `/opt/agy` appears nowhere in `image/entrypoint.sh` or `image/configs/`.
  - **Exploitation in principle:** a process running as a non-project UID is compromised. Examples are apt's `_apt` download sandbox (which also runs during the ADR-028 boot-time package restore) and an apt-installed daemon's worker (`www-data`, `postgres`) reachable through a port preview or public preview link. That process plants a binary, which then runs as the project user the next time `agy` starts. From there it gets sudo to root in the VM and every brokered credential of that user.
  - **Precondition:** a separate compromise of another UID. That is why this is medium, not high. Confidence that the directory permits the replacement is high; the impact rests on that precondition.
  - **The claim it contradicts:** "The mode opens no boundary" appears at `image/Dockerfile:127-130` and in ADR-077 Decision (2) (`.agents/docs/architecture/DECISIONS.md:2765`). The same restatements are at `image/README.md:22` and `.agents/docs/specs/styrman/runtime-image.md:67`. It is true only for the project user.
  - **Remediation (keeps the ADR-077 layout and behaviour):** build the directory `0755 root`. At boot the entrypoint already knows `UID_`/`GID_`, so it can run `chown -h "${UID_}:${GID_}" /opt/agy /opt/agy/agy` (and `chmod 0755 /opt/agy`) before `ready`. `agy update` still works because its own user owns the directory, and no other UID can rename into it. A sticky bit is not a fix: it would stop the user's updater from replacing the root-owned file.
  - **Test:** add a Tier 2 check that `/opt/agy` is not group- or world-writable and is owned by the project user, beside the existing "project user can write agy's directory" check in `.agents/docs/testing/styrman/integration.sh`. Correct the "opens no boundary" sentence in all four places.
- **[low / confidence: medium]** `image/Dockerfile:47-53` (pin note), `.agents/docs/specs/styrman/runtime-image.md:61-65` ("claude … pinned") and ADR-077 Consequences (`DECISIONS.md`, "the user's own choice inside their VM"):
  - **Weakness:** Claude Code's run-time version is no longer the pin, and no user action is involved.
  - **Why:** ADR-077 creates `~/.npm-global` on every boot, and `image/skel/bashrc:25` puts it first on PATH. No `DISABLE_AUTOUPDATER` or `autoUpdates` setting exists anywhere in `image/skel` or `image/configs`. So Claude's own auto-updater, which is on by default and which Tier 2 now asserts usable through `claude doctor`, installs npm's latest `@anthropic-ai/claude-code` into every project home, beside the brokered credentials. That code runs instead of the pinned `CLAUDE_CODE_VERSION`.
  - **What the docs claim:** the pin note still says "Claude Code is pinned by npm version … The ONE thing that floats is the Antigravity CLI". The 2026-09-22 review filed the same pattern for agy: a note that reads as more coverage than it gives.
  - **Remediation:** record Claude as a second run-time float in the pin note and the spec. Say what it trusts (the npm registry and the publisher's account, unattended, per project) and that the image pin governs only the first run and the fallback after a home is reset. Optionally set `autoUpdatesChannel: "stable"` if release churn matters. This is not a code defect: the operator chose the posture, but its description is wrong.
  - **Confidence:** medium, not high, because the harness v2.3.2 content was not examined and could in principle set the updater off.
- **[low / confidence: high]** Pre-existing, outside this range (`web/package-lock.json` unchanged): `npm audit` reports GHSA-2883-xcg3-v3hh (high in npm's rating), a js-yaml CPU denial of service on empty merge sources.
  - **Affected version:** `js-yaml@4.3.1` (fixed in >=4.3.2), reached via `@tanstack/react-start@1.168.49 -> @tanstack/start-plugin-core@1.171.39 -> xmlbuilder2@4.0.3`.
  - **Exposure:** this is a build-tool chain. The shipped SPA is static and served by the Go binary, so exploitation needs attacker-controlled YAML at build time, and practical exposure is minimal.
  - **Remediation:** bump it in a separate dependency change (`npm audit fix`, which reports a fix available). It is recorded so it is not lost; nothing in this range introduced it.

## Checked
- **Secrets — clean.**
  - **Scan:** the 3,202-line non-dist diff for GitHub, Google API/OAuth, Anthropic, AWS and Slack token shapes, PEM private keys, and assignments of `CLOUDFLARE_API_TOKEN`/`GOOGLE_CLIENT_SECRET`/`GH_TOKEN`/`STYRMAN_INGRESS_TOKEN`. There were no token hits. A planted control string matched (1), so the scan is live. The only assignment hits are test fixtures (`GOOGLE_CLIENT_SECRET=s3cret` and empty values in `internal/config/styrman_ctl_optional_fill_test.go`).
  - **Build token:** the image build's GitHub token remains a BuildKit secret mount (`--mount=type=secret,id=gh_token`), never an ARG/ENV.
  - **CLOUDFLARE_API_TOKEN** (`deploy/styrman-ctl` OPTIONAL_FILL):
    - It is never echoed: the dry-run plan prints the key only, and both refusal messages name the key, never the value.
    - It is written through `env_set` (chmod 600 temp file, atomic `mv`, symlink target refused).
    - The `--env-file` source passes `private_file` first (`deploy/styrman-ctl:471`).
- **Injection — clean.**
  - **CLOUDFLARE_API_TOKEN value:** validated by the existing `validate` rule, which refuses whitespace, `$`, `{`, `}`, backslash and control bytes. `env_set` also refuses newline and backslash, and the value reaches awk via `ENVIRON`, never `-v`. No script sources `.env`: the only grep hits are comments in `deploy/host-setup.sh`.
  - **Entrypoint:** the moved `sh-agent install` output is still filtered (`tr -cd '[:print:]\n' | cut -c1-200`) before it is logged. The stamp still travels as `sh -c` arguments. Every new step runs under `runuser -u "${USERNAME}"` and a timeout.
  - **Bridge:** `classifyControl` unmarshals into a fixed struct. Unknown types are ignored, client data is never reflected, and a client `{"type":"pong"}` gets no reply, so two endpoints cannot loop.
- **Authz/authn — no finding.**
  - **Server:** no new endpoint or middleware change. The ping is answered inside the already-authorized `serve` read loop with a constant 15-byte frame (no amplification; a resize per frame was already costlier). The reply write is bounded at 5 s under `hctx`, which `RevocationWatch` cancels. coder/websocket v1.8.15 allows concurrent `Write` with the stream goroutine. A ping no longer counts as idle-reaper activity, which tightens resource control.
  - **Frontend (`TerminalPane.tsx`, `termLiveness.ts`):** text frames are no longer written to the xterm. Keystrokes typed while a pane is closed for good are dropped, so a reclaimed pane cannot replay them. Wake and reclaim reconnects never carry boot intent. No `innerHTML`, and no test hook ships: the e2e wraps `WebSocket` via Playwright `addInitScript` only. A reclaim crosses no user boundary, because terminals are per-user and the server's authorization is unchanged.
- **Crypto — no hand-rolled primitives.**
  - **Harness download:** the verification in `image/Dockerfile` is unchanged in the range; only `HARNESS_VERSION` moved, v1.6.0 -> v2.3.2. It runs `ssh-keygen -Y verify` against the pinned `HARNESS_SIGNER` with namespace `sh-agent-release`, requires the `# styrman-harness <version>` header, runs `sha256sum -c`, and checks the binary's self-reported version. This consumes OpenSSH and coreutils as designed.
