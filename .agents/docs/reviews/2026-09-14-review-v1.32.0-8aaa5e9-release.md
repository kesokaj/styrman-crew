# Review — v1.32.0..8aaa5e9 release gate (v1.33.0)

Range reviewed: v1.32.0..8aaa5e9

## Verdict: APPROVE WITH NITS

Nothing in the range blocks the release. The worst item is in the release
gate itself: `deploy/verify-commit.sh`'s new 429 detector matches a bare
`429` anywhere in the captured build log, so a REAL build failure whose log
happens to contain those three digits (a hex digest substring, a `429ms`
timing) is announced as "Docker Hub rate limit … not a defect in the commit"
AND has its `tail -n 20` diagnostic suppressed. The gate still exits 1 either
way, so no bad tag can be signed on it — it misattributes a cause and hides
the evidence, which is why it is low and not high. The two Phase 2
refinements (main.go's read-error classification, the compose passthrough)
are correct and their documentation matches the code. The vendored harness
mirror is byte-identical to upstream cceee54 (verified, see Prior coverage).

## Findings

- **[low / confidence: high]** `deploy/verify-commit.sh:40` — the 429 test is
  `grep -qiE 'toomanyrequests|too many requests|429'`. The bare `429`
  alternative is an unanchored three-digit substring: a 64-char hex digest
  contains it about 1.5 % of the time (the log prints one per pinned `FROM`,
  three for the runtime image), and BuildKit timings (`429ms`) or a Go error
  at line 429 match too. On such a false positive the operator is told the
  failure is "not a defect in the commit" and the `tail -n 20` of the log is
  NOT printed, so the actual error is never shown. Fix: drop the bare `429`
  alternative (`toomanyrequests|too many requests` already covers both the
  daemon string and the HTTP reason phrase BUG-056 observed), or require
  `429 Too Many Requests`; and print the log tail in BOTH branches, since the
  tail costs nothing and is the only evidence either way.
  - Confirmed separately: a `-q` build DOES carry the text. BUG-056's own
    recorded output (`… unexpected status from HEAD request … 429 Too Many
    Requests`) came from the pre-existing `docker build -q … >/dev/null`
    runtime-image step, i.e. from stderr, which `build_image` now captures.
    The detector's positive path works; only its over-breadth is at issue.

- **[low / confidence: medium]** `deploy/verify-commit.sh:203` — the server
  build's log is written INSIDE its own build context:
  `build_image "${WT}/.verify-server-build.log" … .` runs with cwd `${WT}`, so
  the context is `${WT}` and the log sits at its root. The repo `.dockerignore`
  excludes `.git`, `.agents`, `.claude`, `**/*_test.go` — not `*.log`. Two
  consequences: (a) the gate's whole premise is that it builds exactly what
  the updater will build from the commit, and this adds a file to the context
  that the commit does not contain (it reaches the builder stage through
  `deploy/Dockerfile.server`'s `COPY . .`); (b) the shell creates the file
  before `docker build` starts and docker writes into it while BuildKit
  transfers the context — a file changing size mid-transfer is a known source
  of context errors. With `-q` the file is usually still empty at transfer
  time, which is why this is low rather than medium. Fix: put both logs
  outside the worktree — e.g. `LOGDIR="$(mktemp -d)"` next to `WT`, removed by
  the existing `cleanup` trap. The runtime build (context `image/`, log at
  `${WT}/`) is already outside its context and needs no change.

- **[low / confidence: high]** `.agents/docs/deploy/remote.md` (Docker Hub
  section, added in 7e484ea) — "Hub allows 100 anonymous pulls per 6 h per IP"
  contradicts the record it cites: BUG-056 documents the observed header
  `x-ratelimit-limit: 100;w=3600`, i.e. 100 per HOUR, and its own text says
  "100/h". The same paragraph's "40/h authenticated" is likewise per hour. An
  operator budgeting gate runs against a six-hour window when the real window
  is one hour will under-run the gate (or over-wait); pick one and make the
  bug record and the deploy guide agree, citing the header as the evidence
  (BUG-034's rule). Everything else in that section checks out against the
  code: `deploy/update/styrman-update:228-247` honours a `DOCKER_CONFIG` only
  under `/run` (plus root-owner and no-group/world-write assertions) and
  otherwise substitutes a fresh `mktemp -d` removed by its EXIT trap, and
  `deploy/update/styrman-update.service:26-28` is exactly the
  `RuntimeDirectory=styrman-update` / mode 0700 / `DOCKER_CONFIG=%t/styrman-update/docker`
  the doc describes — so "the updater builds anonymously by design" is
  accurate.

## Reviewed and clean (no findings)

**Phase 2 deltas (mine to review, per dispatch).**
`cmd/styrman/main.go:38-64` — the four-branch switch is correct and correctly
ordered: `errors.Is(ferr, fs.ErrNotExist)` → Warn+continue, any other read
error → Error+`os.Exit(1)` unless `STYRMAN_ALLOW_IP_FORWARD=1`, forwarding-on
→ same. `errors.Is` reaches through `IPForwardOff`'s `fmt.Errorf("read %s: %w", …)`
to `*fs.PathError` to `ENOENT`, so the ErrNotExist branch is reachable; the
imports (`errors`, `io/fs`) are present. The guard sits after `config.Load`
and before any `os.MkdirAll`, so a refusal has no filesystem side effect, and
it is gated on `cfg.SelfContainer != ""` (`STYRMAN_SELF_CONTAINER`,
`internal/config/config.go:183`), leaving host-mode dev exempt as documented.
`deploy/docker-compose.yml:110` — `STYRMAN_ALLOW_IP_FORWARD=${STYRMAN_ALLOW_IP_FORWARD:-}`
defaults to empty, and empty is not `"1"`, so the unset case is refuse-on-forwarding;
the `sysctls: net.ipv4.ip_forward=0` block it references is really there
(`deploy/docker-compose.yml:82-83`), which the Phase 2 review had listed as
unexamined. The docs match the refined code: `api.md`'s new row states
"A MISSING sysctl file warns and continues; any other read error refuses like
forwarding-on", and its claim that a tripped guard rolls the deploy back is
substantiated — `styrman-update`'s `reports_version` requires the container
`running` and `healthy`, which a server that `os.Exit(1)`s at boot cannot be.

**b21a3c1 — `web/e2e/run.sh`.** The hoist is behaviour-preserving:
`MOUNT_SOURCES_FMT=$'{{range .Mounts}}{{.Source}}\n{{end}}'` is ANSI-C quoting,
so the variable holds the same literal newline the inline format did, and
`--format "${MOUNT_SOURCES_FMT}"` is quoted at use. It is assigned at line 28,
before `cleanup()` is defined and well before `trap cleanup EXIT`, so the trap
can never fire with the variable unset. The `|| continue` and `|| true` guards
BUG-024 requires are intact on both lines. The eight `.claude/agent-memory`
deletions are confined to that tree — `git show --stat b21a3c1` lists no
deletion outside it, so no repeat of BUG-006 — and TODO.md going to headers is
the Definition of Done's own requirement, with the `changes/` entry as the
record.

**7e484ea — `build_image` control flow.** Verified empirically in the
scratchpad, not by reading: `exit 1` inside `( cd "${WT}" && build_image … )`
exits the subshell, the parent's `set -e` aborts on it, and the parent's EXIT
trap runs exactly once (bash resets traps in subshells). `cleanup` uses
`git worktree remove --force`, so the untracked log files in the worktree do
not block removal. `if ! docker build …` correctly suspends errexit for the
test without swallowing anything.

**3b88baa — the two new rules.** `.agents/rules/no-live-workarounds.md` and

**641ad79 — the vendored mirror.** `VENDORED.md`'s rewritten paragraph is

## Criteria

1. **Dead code — pass.** No orphaned exports, commented-out blocks or
   unreferenced files introduced. The range's largest deletion (eight
   `.claude/agent-memory` files, 1 580 lines) is dead-trail removal in the
   right direction; `git show --stat` confirms nothing outside that tree went
   with it.
2. **Flow tracing — pass.** `main.go` → `config.IPForwardOff` →
   `IPForwardProc`, and the override name traced to every caller that must
   honour it: `deploy/docker-compose.yml` (env passthrough + the sysctl it
   asserts), `api.md`, `guide.md`, `AGENTS.md`. The mechanism-reaches-every-caller
   rule's "which version runs first after this ships?" question is satisfied
   in the safe direction — nothing needs enabling; a deploy that trips the
   guard fails `reports_version` and rolls back. `build_image`'s failure path
   traced through subshell → parent `set -e` → EXIT trap, confirmed by
   execution.
3. **Standards conformance — pass.** Go: `%w` wrapping, no discarded errors,
   `slog` structured fields, gofmt-shaped. Shell: `set -euo pipefail` intact,
   `local` in the new function, quoted expansions, no side-effecting function
   inside `$(…)` (BUG-010), no verification piped inside a chain that leads to
   a commit (`.agents/rules/verify-bare.md`). `.agents/docs` frontmatter
   (`owner:`/`date:`) present on the new records.
4. **Directory layout — pass.** New rules under `.agents/rules/`, new records
   under `.agents/docs/{changes,retros,reviews,testing}/`, the gate helper
   inside `deploy/verify-commit.sh` itself, the vendored mirror untouched
   except as a verbatim refresh (the project standard).
5. **Simplicity (DIY-except-security) — pass.** No new dependency in either
   module; `IPForwardOff` is 6 lines of stdlib; `build_image` is a plain
   function, not a framework. No hand-rolled auth/crypto/session code anywhere
   in the range.
6. **Decoupling — pass.** `IPForwardOff` takes its path as a parameter, so it
   is testable without `/proc` and the boot policy stays in `main`; the gate
   helper is local to one script; the vendored mirror remains a third module
   nobody edits in place.
