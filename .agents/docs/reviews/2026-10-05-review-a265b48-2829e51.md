# Review — a265b48-2829e51   (2026-10-05)

Range reviewed: a265b48..2829e51

## Status: COMPLETE

## Verdict: APPROVE WITH NITS

Nothing broken. The 30 s read deadline set in `acquireSlot` does not harm keep-alive GETs: Go's serve loop resets the conn read deadline after every request (`net/http/server.go` ~1984/2136, `abortPendingRead` 748-752). The new test is sound and passes here (1.5 s). The worst point is that the fix bounds a slot's hold to 30 s but does not stop an authenticated client from re-taking slots in a loop, so the lockout in finding 1 of the earlier review is shortened, not removed; the commit message and changes entry say "no longer holds".

## Findings
- **[medium / confidence: medium]** `internal/httpapi/explorer.go:488-489` — residual of the original finding. The semaphore is global, not per-tenant. A client that opens 8 trickling PUTs and re-sends each as it times out (30 s apart, staggered) keeps the 8 slots taken apart from a window of about one RTT per slot, so other tenants mostly still get 429. The deadline turns "forever" into "30 s per request", which is a real improvement but not "no longer holds an editor slot". Fix: say "bounded to 30 s" in the changes entry and commit text, and queue per-tenant slot accounting (or an idle-based read deadline plus a per-user cap) as the actual remedy. Not a regression.
- **[low / confidence: high]** `internal/httpapi/explorer.go:489` — the deadline is absolute from slot acquisition, not idle-based. A legitimate max-size body (8 MB cap) over an uplink below roughly 2.2 Mbit/s cannot arrive in 30 s; `Decode` fails and the handler answers 400 with a decode error, which reads as "bad request", not "too slow". Typical editor files are small, so rare. Fix: document the limit in api.md, or map a timeout error from the body read to 408.
- **[low / confidence: high]** `.agents/docs/specs/styrman/api.md:167` — the GET `.../file` row now says "a 30 s deadline to send the body", but a GET has no body. The deadline applies to PUT, `/format` and `/check`, which the sentence already lists. The two history rows (api.md:193 and the search row) take the same `acquireSlot` and now get a read deadline too, but neither mentions any deadline (the write deadline was already unstated there). Reword so the body deadline sits on the PUT row.
- **[low / confidence: medium]** `internal/httpapi/write_deadline_test.go` (new test) — covers only `PUT /file`. `/format` and `/check` take the slot before their body read too, and no test pins the deadline there; they share `acquireSlot`, so the risk is small. The testing README's test list does not name the new test, though no rule requires it.

## Judgement on the questions asked
- GET on keep-alive: the deadline is reset by the serve loop (idle timeout or zero) before the next request is read, and `readRequest` sets a fresh one. A GET with no body has a background read pending; at 30 s it times out and cancels the request context. That is the same instant the 30 s write deadline kills the response write, so no behaviour is lost. Source read only; no keep-alive test was run.
- Large bodies that arrive within 30 s: unaffected. Slower ones fail (see low finding 2).
- Test: the positive control (`len(fileSlots)==1`) proves the slot was taken before the wait. `httptest.NewServer` has no server timeouts, so without the deadline the slot stays held (the author's mutation, per the Outcome, left it held at 8 s). I did not re-run the mutation. 1 MiB declared and none sent is a faithful trickle.
- Doc edits: the deploy.md token scope (both repos) matches the ADR-074 mechanism it cites; the e2e usage comment is fine; api.md is as in finding 3.
