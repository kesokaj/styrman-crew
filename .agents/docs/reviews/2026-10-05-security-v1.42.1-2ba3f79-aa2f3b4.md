# Security review — v1.42.1-2ba3f79-aa2f3b4   (2026-10-05)

Range reviewed: 2ba3f79..aa2f3b4 (one commit, aa2f3b4; 23 paths). This is the release-gate review for v1.42.1, and it answers `2026-10-05-security-v1.42.1-v1.42.0-2ba3f79.md`. The working tree equalled aa2f3b4 when the review began. HEAD moved to 4001374 while it ran (see Not examined).

## Status: COMPLETE

## Verdict: FINDINGS

The previous HIGH is fixed in principle. Nothing in the platform runs at -1000 any more. A runaway host-side git now hits the server container's 4 GiB memory cap, and the kernel kills git inside that cgroup: not the server, and nothing outside the container.

The worst problem now comes from that same cap. The server is PID 1 of a container capped at 4 GiB, and the history search makes several whole copies of a guest-written 4 MiB transcript tail for every file it scans, with no limit on concurrent searches. One tenant running about 100-250 concurrent searches against its own project can push the server over the cap. The kernel then kills the server and the container restarts, so every tenant's terminals, API and previews drop. The tenant can repeat this at will. Before the cap, the same load used a few GiB of a 62 GiB host and nothing was killed.

Second, the token fix replaced `sudo GH_TOKEN=…` with `sudo --preserve-env=GH_TOKEN`. As far as I can tell from sudo's source, sudo logs that form the same way. The docs and the FATAL hint now recommend a form that, by that reading, lands in the log they warn about. The argv (`ps`) exposure is fixed.

The dockerd medium is fixed in code but is not live yet. Measured on dave: dockerd is at -500, the start limit is 3 per minute, and there is no new drop-in. It takes effect with the post-release root re-run of `host-setup.sh`, as ADR-085 says. The drop-in write path is safe.

## Findings

- **[medium / confidence: medium (mechanism read in code; the concurrency threshold is estimated, not measured — no memory experiments on production)]**
  - **Where:**
    - `deploy/docker-compose.yml:164` (`mem_limit: 4g`)
    - `deploy/Dockerfile.server:27` (exec-form `ENTRYPOINT`, so the server is PID 1; no `init:` in compose)
    - `internal/history/history.go:104-113` (the caps and the "guest-writable" comment)
    - `internal/history/history.go:150-190` (`searchOne`)
  - **The weakness:** the cap turns server memory growth that a tenant drives into an OOM kill of the whole control plane.
  - **Mechanism:**
    - Each in-flight `Search` scans up to 50 transcripts.
    - For each transcript, `searchOne` holds the 4 MiB tail `buf` and then makes up to four whole-tail copies:
      - `string(buf)`;
      - `ansiRe.ReplaceAllString`;
      - `strings.ReplaceAll` (a PTY transcript is full of `\r\n`, so this one copies);
      - `strings.ToLower`.
    - That is about 8-12 MiB live and about 20 MiB allocated per file.
    - Nothing in `internal/history` limits concurrent searches per user or server-wide. The handler was not traced.
    - The logs directory is guest-writable, so a tenant can plant 50 files of at least 4 MiB each. Mixed case and CRLFs defeat the no-copy fast paths.
    - There is no `GOMEMLIMIT` anywhere in `deploy/`, `cmd/` or `internal/` (grep). The Go heap therefore grows to about twice the live set before it is collected.
    - `memory.oom.group` is 0 (measured), so the cgroup OOM killer picks the largest process in the container: the server itself.
  - **Scenario:**
    - A tenant keeps about 100-250 searches in flight. They are CPU-bound and each takes seconds, so about 2 requests per second sustains that.
    - The heap passes 4 GiB and the server is OOM-killed.
    - The container exits and `unless-stopped` restarts it, with Docker's back-off.
    - Every tenant's sessions drop, and the tenant can repeat this to keep the server in a crash loop.
    - Before this range, the same load cost about 2-4 GiB of a 62 GiB host and killed nothing.
  - **Remediation:**
    - Add a server-wide semaphore, a per-user limit, or both, on `Search` and on any handler that holds multi-MiB buffers, and answer 429 when it is full.
    - Stream the scan (`bufio` over the tail, case-folding per chunk) instead of making five whole-tail copies.
    - Set `GOMEMLIMIT` (for example 3GiB) in the `styrman` service's environment.
    - Test: run N concurrent searches over 50 planted 4 MiB transcripts, and assert 429s or a bounded heap (`runtime/metrics`). Do a must-fail run without the semaphore.

- **[low / confidence: medium (from the sudo source as I know it, not executed — running sudo was outside "measure settings only"; dave runs sudo 1.9.16p2)]**
  - **Where:**
    - `deploy/host-setup.sh:307` (FATAL hint)
    - `.agents/docs/deploy/remote.md:80-88`
    - `.agents/docs/specs/styrman/deploy.md:254-263` and `:340-344`
    - `.agents/docs/changes/2026-10-05-1455-oom-order-revised.md:39-42`
    - The form came from the previous review's own remediation (`reviews/2026-10-05-security-v1.42.1-v1.42.0-2ba3f79.md:109-110`). That advice was wrong.
  - **The weakness:**
    - sudo's front end puts each `--preserve-env=NAME` variable into the same `env_add` list as a command-line `NAME=value` assignment, as `NAME=value`.
    - The sudoers plugin checks that list. That is why sudo(8) says the policy "may return an error" for `--preserve-env=list`.
    - The plugin also writes that list into the accept log line as `ENV=…`.
    - So, by this reading, the new runnable line writes `ENV=GH_TOKEN=<token>` to the auth log or journal, just like the form the text says "lands in sudo's log".
    - What is fixed: the token is no longer in sudo's argv, which any local user can read from `/proc/<pid>/cmdline` while it runs.
    - `export GH_TOKEN=$(gh auth token)` also leaves the operator's broad `gh` token in that shell's environment for every later command. Before, it was scoped to one call.
  - **Remediation:**
    - Make the token-file forms the runnable lines: `sudo deploy/styrman-ctl install --gh-token-file <600 file>`, or `/etc/styrman/gh-token` (root, 600), which `host-setup.sh:301-306` already reads.
    - Or pass the token on stdin into the root shell: `gh auth token | sudo bash -c 'read -r GH_TOKEN; export GH_TOKEN; exec bash deploy/host-setup.sh --user "$1"' _ "$USER"`.
    - Correct the "lands in sudo's log" sentences.
    - Confirm off production with a canary. In a throwaway container with sudo and `Defaults logfile=<scratch file>`, run `DUMMY=canary sudo --preserve-env=DUMMY true`, then look for `ENV=DUMMY=canary` in that file.

- **[low / confidence: high (by reading)]**
  - **Where:** `internal/gitrepo/gitrepo.go:65`, `internal/gitrepo/oom_test.go:17-48`, `.agents/docs/testing/styrman/README.md:8` ("the host-side git child is set back to its own OOM score").
  - **No test covers the line that does the reset, and a failure is silent:**
    - `TestSetOOMScoreAdjWritesTheChild` calls `setOOMScoreAdj` directly on a `sleep` child.
    - `TestGitStillRunsWithTheReset` only checks `IsRepo` after `EnsureRepo`.
    - Deleting line 65 leaves both tests green. The change entry's "red against a stub" covers the helper, not the call in `git()`.
    - The write's error is thrown away (`_ =`). If the write ever fails in the container (a read-only `/proc`, `hidepid`, an LSM change), nothing says so.
  - **Why it should work:** kernel rules say the write succeeds. Raising a score needs no privilege as long as it stays at or above `oom_score_adj_min`, which is -999 here, and the server's uid owns the git child.
  - **What is unverified:** this was not measured inside a real v1.42.1 container, because v1.42.1 is not deployed yet.
  - **Impact is small:** the 4 GiB cap bounds git either way, and inside the cgroup the larger -999 process (git) is still the one killed.
  - **Remediation:**
    - Add a test for the call itself:
      - Raise the test process's own score to 100 (allowed).
      - Run `git()` with a `git` shim on `PATH` that sleeps briefly and prints `/proc/self/oom_score_adj`.
      - Assert `0`, and do a must-fail run with line 65 removed.
    - Log a Warn once when the write fails.
    - After the deploy, add a live check of a git child's score inside `styrman-server`.

- **[low / confidence: low (not load-tested)]**
  - **Where:** `deploy/docker-compose.yml:59-65` (Caddy `mem_limit: 1g`; no `GOMEMLIMIT`).
  - **The weakness:** the internet-facing ingress now restarts at 1 GiB instead of drawing on host memory.
    - Under cgroup v2, kernel socket buffers count against the container's limit, alongside goroutines and TLS/bufio buffers.
    - An unauthenticated connection flood that reaches 1 GiB OOM-kills Caddy.
    - Every tenant's sessions drop until Caddy restarts, and a sustained flood keeps it in a crash loop.
  - **Context:** measured peak since start is 45 MB (`memory.peak`), so the cap is ample for normal use. The cap is better than ADR-084's unbounded -1000, but it lowers the bar compared with v1.42.0, which runs live at score 0 with no limit.
  - **Remediation:**
    - Set `GOMEMLIMIT` (about 800MiB) on the caddy service.
    - Confirm the ingress's read-header and idle timeouts, and add a connection cap.
    - Load-test off production.

- **[low / confidence: high (mechanism), low (exposure)] Pre-existing, in a file this range touched, outside its changed lines.**
  - **Where:** `.agents/docs/testing/styrman/README.md:219-235` (the updater self-install test procedure).
  - **The weakness:**
    - The procedure has the operator write `sed` output to `/tmp/self-install-funcs.sh`, then has root `source` that file.
    - With /tmp sticky and `fs.protected_regular` on, another local user who creates that name first makes the operator's write fail. Root then sources the planted file.
  - **Remediation:** write it under `.agents/scratch/` or a root-owned `mktemp -d`, and source only a file root has just created.

## Prior findings, re-checked at aa2f3b4

1. **High (-1000 inherited by host-side git, host hang): fixed in principle, not yet live.**
   - **The fix:**
     - Compose sets both services to `oom_score_adj: -999` with `mem_limit` 4g / 1g (`docker-compose.yml:64-65`, `:163-164`), pinned by `compose_oom_test.go`.
     - The only host-side exec in non-test server code is gitrepo's `git` (grep for `exec.Command`: one hit).
     - `RootRemoveContents` (`orchestrator.go:1416-1437`) runs `find -delete` through `docker exec -u 0` inside the same container. The same cap bounds it, and it keeps -999. Acceptable.
     - git's growth now hits the container's `memory.max` and causes a cgroup-local OOM (`memory.oom.group` 0). git is the victim: at score 0 after the reset, or as the larger -999 process if the reset failed. The server survives, and nothing outside the cgroup is touched.
     - No platform process runs at -1000.
   - **Not live yet:** the running containers are 1.42.0, with `Memory=0` and `OomScoreAdj=0` (measured).
   - **Can a tenant get around the reset? No, as far as these paths go:**
     - With the exec keys neutralised, these two git commands start no children.
     - The pid cannot be reused before `Wait`, because the zombie holds it.
     - Only code execution inside git could lower the score again.
   - **Small residuals:**
     - git runs at -999 for the moment between `Start` and the write. The cap bounds that too.
     - `kernel.panic` is left to the operator (ADR-085, Rejected). That is acceptable now that nothing is unkillable.

2. **Medium (dockerd at -500 dies first): fixed in code. Live only after the post-release root re-run of `host-setup.sh`.**
   - The updater never runs `host-setup.sh`, and ADR-085's Consequences say so.
   - **Measured on dave today:**
     - dockerd (pid 843) at -500.
     - `StartLimitBurst=3`, `StartLimitIntervalUSec=1min`.
     - `DropInPaths` lists only `limits.conf`.
   - **The drop-in write (`deploy/lib/docker-oom.sh:29-41`) is safe.** The symlink/TOCTOU concern is refuted:
     - `/etc/systemd/system` and `docker.service.d` are root:root 0755 (measured), so no non-root actor can plant a link or race the write.
     - It writes with `mktemp` in the same directory, then `mv -f`. That replaces a planted link instead of writing through it; the test's `symlink` case shows the target untouched.
     - `pidof dockerd` sees only host processes. Tenant dockerds run inside Kata guests, so none of them can be given -999.
   - **A correctness nit, not security:** `daemon-reload` runs only on `changed`.
     - A run interrupted after the write but before the reload is never reloaded by a later re-run, which reports `unchanged`.
     - The running dockerd's score is set directly, but `StartLimitIntervalSec=0` waits for the next reload.
     - Running `systemctl daemon-reload` every time (it is idempotent) closes this.

3. **Low (token on sudo command lines): partly fixed.**
   - The argv form is gone from the runnable lines and from the FATAL hint.
   - The replacement is, by my reading, logged by sudo the same way (second finding above).
   - The closed plan line (`plans/2026-10-05-project-resources.md:406`) stays as written, by decision.

4. **Low (`docker ps` gate fails open): fixed at `.agents/docs/testing/styrman/integration.sh:540`.**
   - `running=$(docker ps …) && ! grep -qx … <<<"$running"` fails closed when `docker ps` fails.

   - The same fail-open shape remains elsewhere, all pre-existing and test-only, run as the operator uid against the suite's own VM:
     - at `:683`, before the host-side `sed -i` and `rm -f` into the guest-writable test home at `:686-687` (low);
     - at `:600`, `:643`, `:661` and `:727`, before assertions only.
