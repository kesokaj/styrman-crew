## Verdict: FINDINGS

Nothing in this range weakens the running product, and the two changes that
touch the security posture (the `ip_forward` boot assertion reaching its
override, and the vendored harness's symlink/name guards) both move it
forward. The worst problem is in the **release gate itself**: the new 429
classifier in `deploy/verify-commit.sh` matches the bare digits `429`
anywhere in a `docker build` log — layer digests, byte counts, timestamps —
and in that branch it **suppresses the log tail** and tells the operator the
failure is "not a defect in the commit". A genuine build break whose output
happens to contain those three digits is therefore reported as a rate limit,
with the real error hidden, on the one gate whose entire reason for existing
(v1.18.0, ADR-061) is catching a commit that does not build. Everything else
here is low: a deliberate warn-only branch when the sysctl file is absent, a
gate artifact written inside the build context it verifies, and the
advisory-only nature of the root-steps authorization record inside a project
VM.

## Findings

- **[medium / confidence: high]** `deploy/verify-commit.sh:40` — the rate-limit
  classifier is `grep -qiE 'toomanyrequests|too many requests|429'` over the
  whole captured build log. The third alternative is three unanchored digits
  and matches a substring of any hex layer digest, byte count, duration or
  port in the log; a `docker build -q` failure prints many. When it matches,
  the branch prints only `FAIL: Docker Hub rate limit … not a defect in the
  commit` and **does not** run the `tail -n 20 "${log}"` that the else branch
  runs, so the actual compiler/Docker error never reaches the operator. The
  documented remedy for that message is "wait for the window" and re-run
  (`.agents/docs/deploy/remote.md`, Docker Hub), i.e. the gate actively steers
  a real defect toward a retry. Exploitable in principle only as a
  release-integrity failure, not by a remote party — but this is the gate that
  guards what the auto-updater builds on the production host. Remediation:
  drop the bare `429` alternative and match Docker's actual wording
  (`toomanyrequests`, `You have reached your pull rate limit`,
  `429 Too Many Requests` / `[Tt]oo [Mm]any [Rr]equests`), and print the log
  tail in **both** branches so no failure is ever classified into silence.

- **[low / confidence: high]** `deploy/verify-commit.sh:200-202` — the server
  build's log is written to `${WT}/.verify-server-build.log`, i.e. *inside*
  the detached worktree that is that same build's context (`docker build … .`
  from `cd "${WT}"`). Neither `.dockerignore` nor `image/.dockerignore`
  excludes `*.log` or `.verify-*`, and `deploy/Dockerfile.server:13` is
  `COPY . .`, so the gate's own artifact enters the builder stage of the build
  it is verifying. Impact is bounded and I confirmed the bound: the final
  stage copies only `/out/styrman` (`deploy/Dockerfile.server:22`), so nothing
  ships; the file is empty at context-send time; the worktree lives in a
  `mktemp -d` (mode 0700) under `$TMPDIR`, outside the repo, and `cleanup()`
  does `git worktree remove --force` then `rm -rf`, so it does not persist;
  and no step of the gate asserts worktree cleanliness (`git status` appears
  nowhere in the script), so no check is perturbed. What remains is that the
  gate no longer builds byte-identical context to the updater's — the precise
  property ADR-061 exists to prove. Remediation: write both logs beside the
  worktree (`${WT}.server.log`) rather than inside it, or add `.verify-*.log`
  to `.dockerignore`. The runtime build is already fine (its log is outside
  the `image/` context).

- **[low / confidence: high]** `cmd/styrman/main.go:50-51` — the R12
  no-routing assertion has exactly one branch that degrades to a warning
  *without* requiring `STYRMAN_ALLOW_IP_FORWARD=1`: `errors.Is(ferr,
  fs.ErrNotExist)`. Every other outcome (forwarding on, EACCES, EIO, a
  directory where the file should be) refuses. This is the recorded
  trade-off from the phase-2 review ("an exotic kernel must not take the
  service down over it") and I am not asking for it to be reversed — but the
  guarantee the guard advertises is silently absent on that path, with a
  single `Warn` line in a container log nobody tails, and the one actor who
  could make `/proc/sys/net/ipv4/ip_forward` vanish (a host-root operator
  masking `/proc`) is the same actor the compose `sysctls:` block trusts. Not
  reachable by a tenant or a project VM. Remediation: none required; if the
  branch is kept, make it observable — surface it the way a tripped guard is
  surfaced, so "unknown" is never mistaken for "asserted".

- **[low / confidence: medium]** `deploy/docker-compose.yml:110` — the new
  `STYRMAN_ALLOW_IP_FORWARD=${STYRMAN_ALLOW_IP_FORWARD:-}` passthrough is
  **fail-closed for every accidental value**, which I checked directly against
  the consumer: `main.go` compares `os.Getenv(…) != "1"` exactly, so unset,
  empty, `true`, `yes`, `0`, `1 ` (trailing space) and a misspelled key all
  leave the guard armed; compose's `:-` default yields the empty string, never
  `1`. A `.env` typo cannot weaken it. The reachable weakening is the
  deliberate one: compose resolves interpolation from the **shell environment
  in preference to `deploy/.env`**, so an exported `STYRMAN_ALLOW_IP_FORWARD=1`
  left over from a debugging session — or a line added to `deploy/.env` to get
  past one bad boot — disables the assertion permanently, with only a `Warn`
  at each start and nothing that re-raises it. The updater path is clean:
  `deploy/update/styrman-update` sets no such variable and runs under a
  systemd unit whose `Environment=` lines do not include it. Remediation:
  have `/preflight` read the knob's effective value on the host and fail the
  deploy row when it is `1` without a dated waiver — this is exactly the case
  `.agents/rules/no-live-workarounds.md` was written for.

- **[low / confidence: medium]** `image/harness/context/dev-setup.md:8` — the
  root-steps sentence now conditions `sudo -n` on the project's
  `.claude/settings.json` recording the standing permission, and this file is
  rendered into every project VM's `AGENTS.md`. **Net effect for a VM user who
  already holds sudo: no change in capability** — they can run `sudo` directly
  whatever the sentence says — and the change is strictly a *narrowing* versus
  v1.32.0's unconditional wording, so the default improves. The residual: the
  "authorization record" lives in the project's own working tree, which inside
  a VM is tenant-writable and can arrive wholesale from a cloned repository.
  A hostile repo that ships a `.claude/settings.json` re-opens the sentence's
  permission for an agent operating on that repo's content, so the gate is
  advice to the model, not enforcement. Blast radius is that tenant's own
  microVM: the Kata boundary holds, the host is not reachable, and the
  credentials exposed (brokered git/gh/ssh/claude/agy/gcloud) are already the
  tenant's own. Upstream recorded the same residual verbatim
  (`styrman-harness` review, Outcome, last bullet: "`.claude/settings.json` as
  the authorization record for root steps is the harness's existing
  convention"). Remediation: none in this repo; if the record is ever to be
  load-bearing it has to come from outside the tree being worked on.

- **[low / confidence: medium]** `image/harness/internal/harness/inventory.go`
  (blast radius of the mirror, not a defect introduced here) — upstream's
  fix 3 validates a skill/agent frontmatter `name:` to a single local
  identifier-like segment, which closes the injection path through the name.
  The `description:` is still rendered verbatim into the consumer's
  `AGENTS.md` (`cell()`, `inventory.go:325`), bounded to 140/160 characters.
  I confirmed `cell` collapses all whitespace (`strings.Fields` — so no
  newline can break the row) and escapes `|`, so it cannot forge table
  structure; what it cannot do is stop 140 characters of adversarial prose
  reaching the model's global context when `sh-agent` is pointed at a cloned
  repo's `.agents/` tree inside a VM. Inherent to the feature (a description
  exists to be read by the model) and contained to the tenant's own VM.
  Recorded so the surface is on the record, not as a demand.

- **[info / confidence: high]** `image/harness/internal/harness/inventory.go:47-77`
  — the `validName` doc comment is split across the wrong two functions: the
  block that explains the parse boundary ("validName is the parse boundary for
  a frontmatter `name:` …", ending "Refused with the file named, so an author
  sees it at `sh-agent install`") is attached to `identLike`, and `validName`
  carries the orphaned fragment `// time rather than finding a file written
  beside their home.`. Cosmetic, no behavioural effect, byte-identical to
  upstream `cceee54` — belongs in the upstream repo, flagged here only because
  a description that names the wrong function is read as a guarantee about it.

## Outcome

  release code review raised the same finding as its #1): the regex is
  `toomanyrequests|too many requests`; the tail is printed in both
  branches; re-exercised with a fake `docker` (a digest containing
  `4291f00` now takes the generic branch). Rides in the release commit,
  re-verified by `deploy/verify-commit.sh` on that commit.
- **2 [low/high] build log inside the build context — FIXED**: logs live
  in a separate `LOGDIR` under `$TMPDIR`, removed by `cleanup`.
- **3 [low/high] `fs.ErrNotExist` degrades to a warning — REBUTTED, no
  change.** The branch logs `ip_forward state unknown — cannot assert the
  no-routing guarantee (R12)` at Warn, so "unknown" is distinguishable from
  "asserted" (which logs nothing) in the same log the health check reads;
  the trade-off (an exotic kernel without the sysctl file must not take
  the service down) is stated in the code comment and the env table. The
  only Linux kernels lacking the file have no IPv4 forwarding at all.
- Carried, not this release's: `npm audit` 1 high (js-yaml, build-time
  only) — pre-existing, in the gate report's "What was not checked".
