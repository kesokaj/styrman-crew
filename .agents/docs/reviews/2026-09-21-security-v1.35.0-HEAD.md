# Security review — release gate v1.36.0 (v1.35.0..HEAD)   (2026-09-21)

Range reviewed: v1.35.0..5478667b017edaeb69b3c72f1a06796d5e47a0eb

## Status: COMPLETE

## Verdict: FINDINGS (worst: low — no blocker found)

Nothing in this range is an escalation path, no secret is committed, and the
signature chain the image rests on is intact as reviewed before. The recurring
shape is the one this project already has a rule for (`.agents/rules/
mechanism-reaches-every-caller.md`, BUG-035): **two of the previous security
review's accepted fixes landed at some call sites and not at others, and the
prior review's `## Outcome` states one of them more broadly than the code
supports.** `styrman-ctl install --gh-token-file F` hands an operator-named
path straight to a root `docker build` as a `src=` secret without the
`private_file` check the sibling branch three lines below performs, and the
`export GH_TOKEN` that was removed from the two non-root build sites survives
at all three root ones. The retirement also leaves two artifacts of the
deleted channel behind on a live host — a root-owned GitHub token file and a
root clone — that no code removes and no living doc tells the operator to
revoke. Separately, `deploy/vulncheck.sh` dropped the harness module from its
scan and nothing replaced it: the binary now running in every tenant VM has no
vulnerability scan anywhere in this repository's pipeline. Everything else in
the range — the Go deletions, the Dockerfile download block, the entrypoint
guard, the retire step and its tests, the deleted `styrman-ctl` channel block,
the trail markdown — reads clean.

## Findings

- **[low / confidence: high]** `deploy/styrman-ctl:473` — **`--gh-token-file F` reaches a root `docker build` as a `src=` secret with no `private_file` check.** `cmd_install`'s new secret block runs `private_file` on the *installed* `${ETC_DIR}/gh-token` (line 475) but not on the operator-supplied path (line 473); `setup_auto_update`'s own `private_file "${token_file}"` runs only later, and only if auto-update is set up at all (`--skip-auto-update`, or answering `n` at the prompt, skips it). `private_file` (`:507-517`) is the function that refuses a symlink, a non-root/non-operator owner, a group/world-readable mode and a group/world-writable parent directory — every property that matters for a path root is about to read. `image/Dockerfile:152` does `GH_TOKEN="$(cat /run/secrets/gh_token)" gh release download …`, so the file's bytes leave the host as a bearer credential to api.github.com. Scenario (no exploit written): the operator types `sudo styrman-ctl install --gh-token-file /srv/shared/tok`; the path is a symlink, or sits in a directory a second user can write, and root reads and transmits content it never vetted. Corroboration that this is an omission rather than a deliberate relaxation: the channel code deleted in this very range called `private_file "${harness_token_file}"` on its own operator-supplied token path before using it. The prior review's Outcome for its finding 5 reads "`styrman-ctl install` runs `private_file` on it" — true for the fallback branch only. Remediation, one line, no new dependency: `private_file "${gh_token_file}"` as the first statement of that branch, exactly as line 475 does.

- **[low / confidence: high]** `deploy/host-setup.sh:259`, `deploy/styrman-ctl:474`, `deploy/update/styrman-update:681` — **`export GH_TOKEN` survives at the three ROOT build sites while the fix landed only at the two non-root ones.** The previous review's finding 6 ("`export GH_TOKEN` widens a broad developer credential across the whole run") was fixed in `deploy/verify-commit.sh:65-78,211` and `.agents/docs/testing/styrman/ensure-test-image.sh:53-59` — both keep the token in a local, `unset GH_TOKEN`, and set it on the one `docker build` call. Those two are genuinely scoped: I confirmed on bash 5.2.37 that a `VAR=x func` prefix is exported *inside* the function and does **not** persist after it returns, so `GH_TOKEN="${BUILD_TOKEN}" build_image …` does not leak back into the script. The three sites that run as root kept the export, so the token sits in the environment of every child for the rest of a root-run host setup / install / updater tick — including `docker compose up`, the server image build, and everything `host_converge` spawns. `deploy/docker-compose.yml` passes no bare-name environment through (each entry is an explicit `NAME=${VAR}`), so nothing in this diff carries it into a guest: exposure surface, not a leak, which is why this keeps finding 6's severity rather than rising. Remediation: the fixed sites' shape — `BUILD_TOKEN="${GH_TOKEN}"; unset GH_TOKEN; … GH_TOKEN="${BUILD_TOKEN}" docker build …`.

- **[low / confidence: high]** `deploy/update/styrman-update:178-200` (`retire_harness_units`) + `.agents/docs/specs/styrman/deploy.md:281-287` — **the retirement leaves a live GitHub token and a root clone on the host, with nothing that removes them and nothing that tells the operator to revoke the grant.** `retire_harness_units` sheds exactly two unit files and four state files (`harness-version`, `harness-sha`, `harness-failed-version`, `harness-refused`). It does not touch `/etc/styrman/gh-token-harness` — the root-owned 0600 fine-grained token minted for the private `styrman-harness` repository by the deleted `setup_harness_channel` — nor the root clone `/opt/styrman-harness`, nor the now-inert content dir `/var/lib/styrman/harness` (the last is explicitly named as "the operator's `rmdir`" in the script's own comment, the first two are named nowhere). `deploy.md:281-287` lists both paths, but only inside the sentence enumerating what was *deleted from the code*; I grepped `deploy.md`, `.agents/docs/deploy/remote.md`, `deploy/README.md` and the changes entry, and no living doc asks the operator to delete the file or revoke the token at GitHub. The result on the production host after v1.36.0 is a valid credential for a private repository with no consumer, no rotation path and no expiry anyone is watching — the classic orphaned-secret shape, and the one credential in this system whose blast radius is the harness supply chain. Remediation, no new dependency: add `/etc/styrman/gh-token-harness` to `retire_harness_units`'s `rm -f` list (it sits beside the four files already removed, in the same directory the function has just asserted is root-owned and not group/world-writable) and add one line to `deploy.md`'s retirement note telling the operator to revoke that fine-grained token at GitHub and `rm -rf /opt/styrman-harness`.

- **[low / confidence: high]** `deploy/vulncheck.sh:35` — **the code that ships into every tenant VM left the vulnerability scan and nothing replaced it.** The loop went from `for mod in . deploy/caddy/ingress image/harness` to `for mod in . deploy/caddy/ingress`. That is mechanically correct — the module is deleted — but `image/harness` was the module that compiled the `sh-agent` binary every project runs, and the release gate's replacement assertion (`deploy/verify-commit.sh:212-218`) checks only that the binary *reports* the pinned version. So this repository's security gate now scans the server and the ingress and nothing that runs inside a guest. This is narrower than the accepted "harness content is outside the review boundary" risk (ADR-074 consequences): that one is about *reviewing* the instructions; this is about *scanning the Go dependencies* of a binary crew builds into its own image and distributes to every tenant. Remediation, no new dependency: require that the styrman-harness release gate runs `govulncheck ./...` and that a `HARNESS_VERSION` bump in crew cites it — the same place `specs/styrman/versioning.md` step 1 already says the release notes are read.

- **[low / confidence: medium]** `deploy/update/styrman-update:681`, `deploy/host-setup.sh:259`, `deploy/styrman-ctl:474` — **an ambient `GH_TOKEN` outranks the vetted root-owned token file on the root path.** All three order the choice `GH_TOKEN` first, `/etc/styrman/gh-token` second. The updater asserts that file is root-owned and has no group/world access precisely so root never "authenticate[s] with a token another user controls" (`styrman-update:379-384`) — and then a value from the environment silently wins over it. Same seam the review's finding 4 closed for `TRUST_UID` (now `TRUST_UID=0` at `styrman-update:229`) and the seam the script's own `DOCKER_CONFIG` block refuses an inherited value for. Reaching it needs control of root's environment (`sudo -E`, an edited unit), so it is not an escalation on its own; systemd gives the unit a clean environment. Remediation: on the root path prefer the vetted file, or refuse an inherited `GH_TOKEN` the way `DOCKER_CONFIG` is refused.

- **[low / confidence: high]** `deploy/verify-commit.sh:212` — **the release gate's `HARNESS_VERSION` shape check is looser than the prior review credited it with.** `sed -n 's/^ARG HARNESS_VERSION=\(v[0-9][0-9.]*\)$/\1/p'` accepts `v1..6`, `v1.6.0.1` and `v01.6.0`; the earlier review recorded it as enforcing "the canonical `vX.Y.Z` shape". The real content control is `image/Dockerfile:156`'s `grep -qxF "# styrman-harness ${HARNESS_VERSION}"` against the signed `SHA256SUMS` header, which this does not weaken — a non-canonical value simply fails the build. Worth correcting only because this is the gate's sole pin assertion and the record now overstates it. Remediation: the entrypoint's own regex, `^v(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)$` (`image/entrypoint.sh:143`).
