## Verdict: FINDINGS (four low, all pre-existing; none introduced at 12c573e or in v1.42.2)

run.mjs contains no secret, no real token, no credential, no instruction-shaped text, and no production path or hostname written as a literal.

What it lacks is a check that it is talking to the scratch server that run.sh starts:
- Its default target, `http://127.0.0.1:8080`, is the production server's listen address on the host this checkout runs on. Its first act there is an unconditional `DELETE /api/projects/e2e-ui?wipe=true` whose result it never reads.
- Its updater check writes, then deletes, whatever path the inherited `STYRMAN_UPDATE_STATUS_FILE` names.
- Its screenshots go to a fixed shared `/tmp` path.

On the run.sh path all three are harmless: port 18090, a mktemp state dir, and a status path exported from that dir. On a bare `node web/e2e/run.mjs`, which is the invocation the file's own usage line documents, production's header auth is the only layer between the suite and production.

The one thing that can affect production on the normal run.sh path sits in the harness, outside the named range. run.sh's EXIT trap sweeps away every `sdb-`/`lan-` Docker network created during the run, production's included, unless a running container holds it.

Every finding line predates v1.42.1. `git blame` at 12c573e puts them in v1.0.0, v1.25.0 and v1.41.0. 12c573e's own change (:404-413) adds none.

## Findings

- **[low / confidence: medium]** `web/e2e/run.sh:87-95`. This is the harness, outside the named range, unchanged since 5481ea2 (first tag v1.25.0). The run.mjs-to-run.sh link is run.sh:66-69: run.mjs leaves projects behind, and this sweep exists to clean up after it.
  - **Weakness:** the EXIT trap removes every network on the host's shared Docker daemon whose name matches `^(sdb|lan)-` and whose `.Created.Unix` is at or after `RUN_START`.
    - Its own comment (:79-81) names the timestamp as "the guard that protects production", on the grounds that production's networks predate the run. That holds only for networks that already existed when the run started.
    - Production's server creates `sdb-<hash>`/`lan-<hash>` networks on the same daemon (run.sh:52-53 reasons about production's containers there):
      - at project create;
      - at every network-mode toggle, which rebuilds the network.
    - A production network created during the run is removed if no running container holds an endpoint on it when the trap runs. Runs last minutes: 210 s rebuild budgets and 120-180 s clone waits. Two cases qualify:
      - a project that has been stopped since;
      - a boot caught between `network create` and container start.
    - Docker refuses to remove only networks with active endpoints, and a stopped container holds none.
  - **Why exploitable in principle:** no attacker is needed, only a coincidence on the documented path, because the suite runs on the production host. A tenant can make it likelier by creating and stopping projects, but cannot see when the suite runs.
  - **Impact not traced:** whether the project heals on its next start or fails to start depends on the orchestrator's start path. `internal/orchestrator/orchestrator.go:994` creates networks and `:1629` checks for NotFound on some path; neither was followed.
  - **Remediation, docker CLI plus one Go option, no dependency:**
    - Label the networks the server creates with its state dir (`Labels` in the `NetworkCreate` options at orchestrator.go:994).
    - Filter the sweep on that label (`docker network ls --filter label=…=${STATE}`), the same way :37-64 already scopes containers by mount sources under `${STATE}/`.
    - Drop the time window as the production guard.
    - Must-fail test: create an `sdb-x` network after `RUN_START`, attach a stopped container, and assert the network survives the trap.

- **[low / confidence: medium]** `web/e2e/run.mjs:16` (the default `--base`; the usage line at `:7` documents the bare run) together with `:56`. Present since 2a6d457 (v1.0.0).
  - **Weakness:** `BASE` defaults to `http://127.0.0.1:8080`. On the production host that is production's own listener:
    - `deploy/docker-compose.yml:92` sets `STYRMAN_ADDR=0.0.0.0:8080`;
    - `:20` sets host networking, which by its comment belongs to the server.
  - The suite's first network act is `DELETE ${BASE}/api/projects/e2e-ui?wipe=true` (`:56`). Its result is discarded (`.catch(() => {})`, status never read), and the run carries on against the same target with:
    - project creates (`:165`, `:1948`, `:2006`);
    - a share to an outside address and a public link (`:900-953`);
    - LAN-mode enable (`:1639`);
    - resource changes (`:1845`, `:1872`);
    - wipes by name (`:1946`, `:1992`, `:2004`, `:2046`).
  - Nowhere does it check that the target is a scratch server.
  - **Why exploitable in principle:** today production refuses all of these requests.
    - `STYRMAN_AUTH=header` (compose `:96`) requires the ingress token (`internal/config/config.go:228`; AGENTS.md: `X-Styrman-Ingress` together with `X-Caddy-Email`), and run.mjs sends neither.
    - That is one layer, and it belongs to the server, not to the test.
    - If that layer ever failed open, or `--base` named any auth-none server holding real data (auth none makes the caller an admin, `:1453`), the suite would wipe the named projects, publish a public link and switch a project to LAN mode there.
    - Production's refusal was read from config, not probed. Sending these requests to production was out of bounds for this review.
  - **Remediation, node built-ins only:**
    - Remove the default, so a missing `--base` exits with the usage text. Alternatively, default to run.sh's `127.0.0.1:18090`.
    - Before `:56`, refuse to go on unless the target proves it is the scratch server: run.sh exports `STYRMAN_E2E_STATE=${STATE}`, and run.mjs requires the state dir the server reports (Settings renders "State dir", `:1444`) to equal it. Refuse any state dir outside `/tmp/styrman-e2e-*`.
    - Must-fail test: run run.mjs against a server whose state dir is not scratch and assert it exits before any DELETE.

- **[low / confidence: medium]** `web/e2e/run.mjs:1457-1486`, since 5571b57 (first tag v1.41.0).
  - **Weakness:** the check writes to, and later deletes, a path it takes from its environment without asking whose file it is:
    - `:1457` takes the path from the inherited `STYRMAN_UPDATE_STATUS_FILE`.
    - `:1463` runs `mkdirSync(dirname(file), { recursive: true })`.
    - `:1464` runs `writeFileSync` with a fabricated record: `result: "failing"`, `code: "fetch-auth"`, `deployed: "v1.38.0"`.
    - `:1486` runs `rmSync(file, { force: true })` in a `finally`.
  - Two checks are missing:
    - nothing confirms the path is the run's scratch path;
    - nothing confirms the file did not exist before the plant. `:1460` checks that the page shows no notice, but that reflects the path the server reads, not the path this process writes.
  - **Why exploitable in principle:**
    - run.sh exports the scratch path (run.sh:124), so the run.sh path is safe.
    - Production's value of the same variable is `/etc/styrman/status/updater.json` (compose `:130`).
    - Run directly, with that value in its environment, by an account that can write there, the check replaces the real updater status with a fabricated "failing since now" record and then deletes it.
    - Until the next updater tick, that erases the admin's notice of whether auto-updates, the path security fixes take, are landing.
    - The variable is set in the compose service and not in an operator's shell, so the precondition is narrow.
  - **Remediation, node built-ins only:**
    - Refuse to plant when `existsSync(file)`, so the test never overwrites or deletes a file it did not create.
    - Require the path to lie under the run's scratch root (`STYRMAN_E2E_STATE`, as in the finding above), in line with ADR-052's "never a default that aliases /var/lib/styrman, /etc/styrman".
    - Must-fail test: pre-create the file and assert the check refuses and leaves it byte-identical.

- **[low / confidence: medium]** `web/e2e/run.mjs:17` and `:86`, since 2a6d457 (v1.0.0).
  - **Weakness:**
    - `--shots` defaults to the fixed path `/tmp/styrman-shots`.
    - `:86` writes `${SHOTS}/<name>.png` under 16 fixed names (`01-home` … `11-clone-failure-badge`, `browser-fixture`, `99-failure`).
    - run.sh never passes `--shots` (run.sh:142), so every run uses the fixed path, and nothing ever removes it.
  - **Why exploitable in principle:**
    - Any other local account can create `/tmp/styrman-shots` first. It is their own directory and not sticky, so `fs.protected_symlinks` does not apply.
    - They can then plant `<name>.png` symlinks.
    - The run writes PNG bytes through those links into any file the operator can write. Clobbering `~/.ssh/authorized_keys`, for example, locks the operator out; it does not give code execution.
    - The planter can also read every screenshot: terminal output, transcripts, and the Settings page with the host state dir.
    - Precondition: a second local account on the host. Tenants live inside microVMs and cannot reach the host's `/tmp`.
    - That Playwright creates the parent directory and writes through a symlink is its documented behaviour; it was not measured here.
  - **Remediation, node built-ins only:**
    - Default to `fs.mkdtempSync(path.join(os.tmpdir(), "styrman-shots-"))`, which is 0700 and unpredictable, and print the path at the end. Alternatively, default to a directory under the repository's gitignored `.agents/scratch/`.
    - Refuse a `--shots` directory that already exists and is not owned by the current user.
