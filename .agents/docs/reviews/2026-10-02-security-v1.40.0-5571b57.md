# Security review — v1.40.0-5571b57   (2026-10-02)

Range reviewed: v1.40.0..5571b57 (`git diff v1.40.0...5571b57`, three commits: b03bc91 handoff, 837b3b9 Phase 1, 5571b57 Phase 2)

## Status: COMPLETE

## Verdict: FINDINGS

Nothing high or medium. The root-written status file is sound where it runs in production. Every value is drawn from a closed set or matches a tag pattern before root writes it, and the server decodes and checks every field again. The settings key goes to admins only, and the page builds its own sentence (React text, never HTML). No guest can reach the file or its directory. The worst item is a policy gap, not code: ADR-082 makes a second SSH key a release signer, and a tag that key signs is built and run as root on any host that lists it. Where that key lives and how it is protected is not recorded, the NUC's own list is unchecked, and only truncated fingerprints are written down (low). The second item is defense in depth. The status writer checks only the final directory, and the parent only when it creates the directory, so on its own it does not enforce the "root never writes below a lower-privileged owner" rule (BUG-009). That protection comes from the pinned `/etc/styrman/status` path (low). Separately, the working tree changed during this review: another actor left uncommitted edits to `internal/orchestrator/ports.go` (`GuestGoingAway` now loops on `TryLock` until ctx is done), its test, `web/e2e/run.mjs` and `web/src/lib/updaterNotice{,.test}.ts`. This review covers commit 5571b57 only, and those edits need their own review (see Not examined).

## Findings
- **[low / confidence: medium]** `.agents/docs/architecture/DECISIONS.md:2811-2819` (ADR-082), restated in `.agents/docs/specs/styrman/versioning.md:283-290` and `.agents/docs/deploy/gcp.md`. The ADR accepts a second release-signing key, "the Mac key". On a host whose `allowed_signers` lists it (the GCP VM does), a tag signed with that key is checked out, built and run as root (`verify_tag` is the only gate on the update channel). Each extra signer adds a way to compromise that host. The ADR records neither where the Mac key's private half lives nor whether it is passphrase-protected or hardware-backed (`sk-ssh-ed25519`/Secure Enclave). Both keys appear only as truncated fingerprints (`SHA256:XeeDl8Y8…`, `SHA256:5HpYQJjpG+…`), so an operator cannot check a host's `allowed_signers` against the repository. Whether the NUC lists the Mac key is stated as unchecked. That direction fails safe: a tag is refused, now shown as `signature`. Remediation: record both full public fingerprints (they are not secret), each key's custody and protection, and the revocation step ("remove the line from every host's `allowed_signers`", plus which hosts list which key). Prefer a hardware-backed or passphrase-protected key for any signer that lives on a laptop. Or drop to one signer when the GCP VM is next reachable.
- **[low / confidence: high]** `deploy/update/styrman-update:93-151` (`status_dir_ok` / `write_status`; `dir` is derived at `:114`, `mktemp` and `mv -f` at about `:140-145`). Root's write target comes from `STYRMAN_UPDATE_STATUS_FILE` and gets weaker checks than `STATE_DIR` gets at `:383-402`. The path is not canonicalized, not required to be absolute (a relative value resolves against the cwd when the trap fires, which is `DEPLOY_DIR` after `cd`), and not refused under `/var/lib/styrman`. Only the final directory is checked (real directory, root-owned, not group/world-writable), plus its immediate parent when it creates the directory. No ancestor above that is checked. Suppose an ancestor were owned by a lower-privileged uid, such as a privileged hand run or test with a scratch `STYRMAN_ETC_DIR` under an operator-owned tree. Between `status_dir_ok` and `mktemp`/`mv`, that owner could swap a path component, and root would then create a 0644, root-owned, fixed-name, fixed-content `updater.json` in a directory of the owner's choosing. That is the BUG-009 shape, with minimal impact because the name and content are fixed. It does not apply in production. The unit pins `/etc/styrman/status/updater.json`, and `/etc/styrman` is root 0700 (`host-setup.sh:405-407`, `styrman-ctl:614`). `styrman-ctl` refuses `STYRMAN_ETC_DIR` unless `STYRMAN_CTL_TEST=1` (`styrman-ctl:44-47`). Remediation: run `realpath -m` on the path, require an absolute path, and refuse `/var/lib/styrman/*`, as for `STATE_DIR`. Or walk every ancestor from `/` (root-owned, not a symlink, not group/world-writable), like `realBelow`. Add a hook test that plants a non-root-owned ancestor and asserts `WARN: status not written`.

## Outcome
(Written by the main agent, 2026-10-02, in the commit that fixes these.)

ADR-082 gains a "Keys, custody and revocation" paragraph: both full fingerprints (read from the v1.39.0 and v1.40.0 tag signatures), where each key lives, and the revocation step (delete its line from each host's `/etc/styrman/allowed_signers`). **left: operator**: how the Mac key is protected on the Mac (passphrase, hardware) is the operator's to record, and whether the NUC's `allowed_signers` lists it needs root on the NUC.
