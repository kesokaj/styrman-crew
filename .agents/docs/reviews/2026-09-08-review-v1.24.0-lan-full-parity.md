# Review — v1.24.0 LAN full parity (ADR-066)   (2026-09-08)

Range reviewed: v1.23.0..HEAD

## Verdict: REQUEST CHANGES

Two defects break the feature on hosts that are not this production box. The credential
broker's new fail-closed gate has a guard that can never fire — `config.Load` cannot
produce an empty `FirewallRunDir`, so `netpol.Enabled()` is always true — which means
every deployment without a fresh root status file (the documented local dev run, a fresh
R11 install before `deploy/firewall/install.sh` has run, `web/e2e/run.sh`, or a
production host whose timer has stalled past `StaleAfter`) silently stops serving the
SSH key to **every** project, breaking R3's "sign in once, every project stays signed
in". Separately, `install.sh` writes a malformed `INGRESS_BRIDGE=` line into a
*fresh* conf, which the firewall script rejects as a grammar error and which therefore
closes every LAN allowance on that host — an R11 (reproducible installation) defect.
Both fail closed, so neither is an exposure; both are reproduced below. The shell
rule-family generalization itself is sound: the three regexes are genuinely disjoint,
the key round-trips are consistent, and the delete-by-spec path is correct.

## Findings

- **[high / confidence: high]** `internal/httpapi/network.go:304` — the guard
  `if !s.netpol.Enabled() { return p.LanAccess, nil }` is unreachable.
  `netpolicy.Dir.Enabled()` is `statusPath != ""`, set from `cfg.FirewallRunDir`, which
  `config.Load` fills with `envOr("STYRMAN_FIREWALL_DIR", "/run/styrman-firewall")` —
  and `envOr` maps *both* unset and explicitly-empty to the default. So the branch is
  dead outside tests, and the protection its own comment claims ("without that guard
  every local dev run would read as 'cannot confirm' and silently withhold the SSH key
  from every project") does not exist. Concrete failure: on any host where
  `/run/styrman-firewall/status` is absent or older than `StaleAfter`,
  `netpolicy.Exposed(false, id, nil, now)` returns `true` for every project,
  `Broker.files` drops every `~/.ssh/*` credential, and git-over-SSH push stops working
  in all projects — including the documented `STYRMAN_IMAGE=… go run ./cmd/styrman/`
  local run (`.agents/docs/deploy/local.md`) and the whole window of a fresh R11 install
  before `deploy/firewall/install.sh` has run. R3 is the requirement broken. Fix: probe
  whether the host half is actually installed (status path has ever existed / a distinct
  `Installed()` on `netpolicy.Dir`) rather than whether a config string is non-empty, and
  add a `TestServerLanExposed` case with a `FirewallRunDir` that never contains a status
  file asserting the key is still served when no project has ever had LAN access.
  Note `TestServerLanExposed` (`internal/httpapi/lanprune_test.go:104`) currently pins the
  opposite behaviour ("no status file must read as exposed"), so decide which contract is
  intended — today the code and its comment disagree, and only one of them is tested.

- **[high / confidence: high]** `deploy/firewall/install.sh:209` — the fresh-conf writer
  emits a corrupt `INGRESS_BRIDGE` line. `"${INGRESS_BRIDGE:+INGRESS_BRIDGE=${INGRESS_BRIDGE}$'\\n'}"`
  has a doubled backslash inside double quotes, so ANSI-C quoting decodes `\\n` to a
  literal backslash followed by `n` rather than a newline. Reproduced by running the
  exact line: the conf gets `INGRESS_BRIDGE=br-0123456789ab\n`. `read_conf`'s grammar
  regex at `deploy/firewall/styrman-firewall.sh:419` does not match that value, so the
  script takes the `conf_fail "conf: unparseable line"` branch — which closes **every**
  allowance, not just the published-port family: plain `LAN_CIDRS` access for all
  projects goes away and `netpolicy.Availability` returns "host firewall config error",
  so no project can be enabled at all. Reachable exactly on `sudo bash
  deploy/firewall/install.sh --lan-allow-published-ports 1` with no existing conf, i.e.
  the R11 fresh-host path; production is unaffected because it has an existing conf and
  takes the in-place `UPDATES` branch, which is correct. `deploy/firewall/test.sh:69`'s
  `write_conf_pub` uses the correct single-backslash `$'\n'`, which is why the suite
  never caught it — it exercises its own writer, not the installer's. Fix: drop the
  `$'…'` and let the surrounding `printf '%s\n' "${body}"` terminate the line, i.e.
  `"${INGRESS_BRIDGE:+INGRESS_BRIDGE=${INGRESS_BRIDGE}}"`; add a check that runs
  `install.sh --lan-allow-published-ports 1` against an absent conf and then runs the
  firewall script over the result.

- **[medium / confidence: medium]** `deploy/firewall/styrman-firewall.sh:586` (and the
  same shape at `:660`) — `done < <(ipt -S "${chain}" 2>/dev/null || true)` swallows a
  read failure. If `iptables -S` fails (lock contention past `-w 5`, netlink error),
  `scan_current` sees an empty chain, so `PURGE` and `MALFORMED` stay empty and nothing
  is revoked — while `reconcile`'s insert pass iterates `DESIRED` independently and still
  installs everything. That is precisely the "loosening without tightening" shape the
  file's own comment at lines 227–231 says it must never have, sitting on the read that
  gates all revocation rather than on the `CHAINS` construct that comment guards.
  Downstream: `count_applied` swallows the same failure, so the status file reports the
  project as not applied, `netpolicy.Exposed` reads "not exposed", and the broker
  re-serves the SSH key while the RETURN may still be live in the kernel — the exact
  pairing ADR-066 part 4 exists to prevent. Bounded to one 60 s tick by the timer, and no
  `error=` line is written, so nothing surfaces. Fix: capture the output and the rc
  separately, treat "chain missing" (the reason `|| true` is there) differently from a
  read failure, and on a read failure record an `error=` and skip the insert pass for that
  chain rather than proceeding half-blind.

- **[medium / confidence: high]** `internal/httpapi/network.go:266` vs
  `internal/credbroker/broker.go:57` — the "is this credential host-reaching" predicate is
  implemented twice and has already drifted. `credbroker.isHostReachingFile` strips `~/`,
  `$HOME/` **and** `./`; `pruneHostReachingCreds` strips only the first two. A file
  credential stored as `./.ssh/id_ed25519` — accepted by `credstore.validRelPath`, which
  only rejects absolute paths and `..` segments — is therefore withheld by the broker but
  *not* removed from the project home by the prune, so enabling LAN leaves a live copy of
  the SSH key inside the guest. This directly contradicts the prune's own doc comment
  ("this prunes exactly what the broker withholds rather than a hardcoded guess that
  could drift from it") — it *is* a second hardcoded guess. Fix: export one predicate
  (e.g. `credstore.IsHostReaching(path)`) and call it from both sites; add a case with a
  `./.ssh/…` path to `TestPruneHostReachingCreds`.

- **[low / confidence: medium]** `deploy/firewall/install.sh:44` — `--ingress-bridge` is
  accepted unvalidated and then interpolated into `sed "s|^${k}=.*|${kv}|"` in the
  in-place conf updater. A value containing `|` corrupts the substitution or injects a
  sed flag; a value of any other wrong shape lands in the conf and only fails at runtime.
  The *derived* path (`derive_ingress_bridge`) checks shape and existence; the explicit
  one does not. Root-run with operator-supplied arguments, so impact is small, but the
  asymmetry is unnecessary. Fix: apply the same `^br-[0-9a-f]{12}$` check to the flag.

- **[low / confidence: high on the facts, low on the impact]**
  `web/dist/client/_shell.html` — modified in this range (commit 2321b99) and classified
  binary by git: `git diff --numstat` reports `-  -`, `file` reports `data`. Cause is a
  raw NUL at byte offset 7417, inside the serialized router payload
  `{i:"__root__\x00",u:…}`. It is pre-existing (the same byte is present at v1.23.0) and
  it is generated output from `npm run build`, not a hand-written heredoc — but
  `.agents/rules/writing-files.md` (BUG-007) makes an unreadable *changed* file a stop
  sign rather than something to skip, so it goes on the record: every reviewer of this
  range, including this one, read "Binary files differ" for a shipped, `go:embed`ed
  asset. Possible functional edge, low confidence: the HTML tokenizer replaces U+0000 in
  script data with U+FFFD, so the byte the browser parses is not the byte shipped; the
  site works today, so this is a note, not a claim. Fix, if wanted: teach the build (or a
  post-build step) to reject a control byte in `web/dist/client/**`, so the artifact stays
  reviewable.

## Answers to the four questions asked

1. **Does the generalized reconcile stay correct for three families?** Yes, on the paths
   examined. `fam_key_lan/lanhost/lanpub` and `desire_lan/lanhost/lanpub` and
   `rule_args_lan/lanhost/lanpub` agree field-for-field on all three arities; the key's
   first field is always the tag and its last always the uuid, which is all the generic
   code assumes. `CHAINS` is deduplicated into a real array (not a command substitution),
   `scan_current` walks each *distinct chain* once so the two families sharing
   `STYRMAN-FWD` see one consistent `first_drop`, and `WANT_COUNT`/`APPLIED_COUNT` sum
   across families so `lan=` keeps its all-or-nothing meaning. The residual is the
   swallowed `-S` failure above, which is not specific to the generalization.
2. **Are the three regexes disjoint, and what happens to a line matching two?** They are
   disjoint by construction and a two-match line is impossible. `lanhost` is bound to a
   different chain and is skipped by the `FAM_CHAIN[$tag] = $chain` filter. Within
   `STYRMAN-FWD`, `lan` requires `-o <dev> -m comment` immediately after `-i`, while
   `lanpub` requires `-m conntrack --ctstate DNAT -m comment` there and carries no `-o`;
   `iptables -S` renders `-o` before the matches, so no single rendering satisfies both.
   The `FAMILY_TAGS`-order "first match wins" is therefore not an ordering dependency, and
   the file's comment at lines 206–208 is accurate. A line carrying the `styrman-lan`
   comment prefix that matches no family becomes `MALFORMED`.
3. **Is the delete-by-number path safe under a concurrent writer?** Adequately. Purges go
   through `ipt -D "${CHAIN}" "${ARGS[@]}"` — delete by full spec, BUG-013's rule.
   `delete_malformed` is the only positional delete, and it re-reads the chain
   immediately before and requires the exact line text at that number, refuses to delete
   anything ending `-j DROP` by number at all, and runs under the `flock` that serializes
   this script against itself. The theoretical window between the re-read and `-D` remains,
   but `STYRMAN-IN`/`STYRMAN-FWD` have no other writer (dockerd writes `DOCKER-USER`, not
   these chains), so I did not find a concrete failure. Not a finding.
4. **Are the broker's failure modes closed?** Yes on the paths inside `credbroker`: a nil
   checker withholds, an error from the checker withholds, and `netpolicy.Exposed` treats
   nil/stale status and the disable window as exposed. The hole is one level up — the
   dead `Enabled()` guard (finding 1) makes "closed" the answer in cases the authors
   believed were excluded, and the drifted prune predicate (finding 4) leaves a
   materialized copy behind in one case. Note the same union is recomputed in `lanView`
   *without* even the dead guard, so `credentialImpact` is emitted for projects whose key
   the broker would actually serve; the UI hides it behind `on &&`, so no user-visible
   contradiction today.
5. **Can `web/e2e/run.mjs`'s planted file leak outside the scratch area?** No.
   `STYRMAN_E2E_FW_DIR` is set only by `web/e2e/run.sh:69` to `${STATE}/fw`, where
   `STATE` is a fresh `mktemp -d`, and it is the same directory the test server's
   `STYRMAN_FIREWALL_DIR` points at (run.sh:58). The block is skipped entirely when the
   variable is unset, so a direct `node run.mjs` against a real server plants nothing.
   `mkdirSync` is `recursive` under that scratch path and the cleanup is
   `rmSync(join(FW,"status"), { force: true })` — one named file, no recursive delete,
   which is what `.agents/rules/writing-files.md` asks for. A throw between plant and
   cleanup leaves the fake status in the scratch dir only.

## Criteria

1. **Dead code — fail.** `internal/httpapi/network.go:304`'s `!s.netpol.Enabled()` branch
   is unreachable in every configuration `config.Load` can produce (finding 1). Nothing
   else is orphaned: `BridgeNameForNetwork` has its one caller, `preferOverride` is used
   by `LocalNetwork.tsx` and covered by `lan.test.ts`, the new `hostFirewallView` fields
   are all rendered, and no commented-out blocks were introduced.
2. **Flow tracing — fail.** Findings 1, 3 and 4 are all flow defects: a guard that does
   not gate what it claims, a swallowed read that decouples revocation from insertion,
   and a policy predicate that exists twice and disagrees. What does trace cleanly:
   `credbroker.New`'s new parameter is updated at its single call site
   (`cmd/styrman/main.go:182`); `MinScriptVersion` 3→4 matches `STYRMAN_FW_VERSION=4` and
   `test.sh` §2, and `TestMinScriptVersionMatchesScript` pins the pair; the PUT's rollback
   still restores the exact `(value, timestamp)` pair (BUG-018 not reintroduced); the
   throttled-kick path for no-op PUTs is intact (BUG-015); `preferOverride` fixes the
   latching equality test and its `d >= o` ordering with a NaN fallback is correct
   (BUG-020); `netpolicy.Derive` still reports "cannot confirm" rather than "off" on an
   unreadable status (BUG-014); `hostAddrs`/`lanCidrs` stay admin-gated behind
   `v.Host` while `credentialImpact` — which describes the owner's own project — does not
   (BUG-017's leak rule respected).
3. **Standards conformance — pass with one exception.** `gofmt -l internal cmd` is empty,
   `go vet ./...` is clean, `bash -n` passes on both shell files. The exception is the
   project rule `.agents/rules/writing-files.md` / BUG-007: a changed file in this range
   is binary to git (finding 6). Minor, not a finding: the blank line added at
   `internal/httpapi/network.go:311` detaches `kickLAN`'s doc comment from its function.
4. **Directory layout — pass.** `internal/netpolicy/status.go` sits beside
   `status_test.go`; `internal/httpapi/lanprune_test.go` is a new file whose name cannot
   collide, and `git diff --stat` shows zero deletions on it and on the other Go test
   files, which is the check BUG-005 asks for; firewall assets stay under
   `deploy/firewall/`; frontend changes are confined to `web/`; no stray files at the root.
5. **Simplicity, DIY-except-security — pass.** No new dependencies in either Go module or
   in `web/`; everything is stdlib plus what was already vendored. No hand-rolled auth,
   crypto, hashing, sessions or JWT/OIDC — the LAN gate is an authorization decision over
   existing identity, and it is enforced by root's iptables, not by new crypto. The one
   place complexity was deliberately bought is the shell rule-family table, and it earns
   it: three families, one reconcile, one place for a delete-by-spec fix to land. The
   `LanChecker` interface has one production implementation but a real test double and a
   genuine reason to exist (the orchestrator cannot answer the question), so it is not
   speculative abstraction.
6. **Decoupling — pass, with one seam to tidy.** `LanChecker` is declared in the package
   that consumes it, sized to one method, and keeps the orchestrator free of any view of
   `Project.LanAccess`; `netpolicy` stays a pure derivation package with the I/O in `Dir`;
   the server↔root contract remains name-only markers in and a key=value status file out,
   with `ingressBridgeMismatch` added as the one cross-check that needs the daemon and is
   correctly placed on the server side. The seam that needs tidying is the duplicated
   host-reaching predicate (finding 4) — two packages independently encoding one policy is
   exactly the coupling that drifts, and it already has.

## Not findings (checked, sound)

- `validate_cidrs` enforces /16../30, zero host bits, and non-overlap with 172.16/12,
  169.254/16, 100.64/10, 198.18/15, loopback, 0/8, 224/3 **and** the connected route of
  every Docker bridge discovered at runtime — R12's constraints hold.
- `conf_fail` clears `LAN_CIDRS`, `LAN_HOST_ADDRS`, `LAN_PUB_SUBNETS` and both allow
  flags together, so no partially-trusted conf exists.
- `rule_args_lanhost` omitting `-o` is correct (`STYRMAN-IN` packets are never forwarded)
  and it still pins `-s` to the bridge subnet against a spoofing guest under loose
  `rp_filter`.
- `rule_args_lanpub`'s positive `-d` allowlist plus `-m conntrack --ctstate DNAT` is the
  right shape given iptables accepts only one `--out-interface`; a direct (non-DNAT)
  connection into a bridge subnet still falls through to the 172.16/12 DROP.
- `files.Remove`/`files.Exists` go through `openRoot`, so the prune cannot be aimed out of
  the tenant tree by a planted `~/.ssh` symlink, and `TestPruneRefusesToFollowAPlantedSymlink`
  proves it (BUG-002/003 guards intact).
- `ingressBridgeMismatch` holding `ingressBrMu` across a 3 s `NetworkInspect` serializes a
  project listing behind one call at most once per minute — bounded, not a defect.
