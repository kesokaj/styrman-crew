## Answers to the five questions the dispatch asked

**`uploadErr` as a closure — correct.** It closes over the *variable* `saved`, and
`saved = append(saved, name)` rebinds that same variable, so both call sites serialise the list
as of the failing part. No captured-copy bug. `writeJSON` sets `Content-Type` and the status
before encoding, so the shape on the wire is `{"error":{"message":…},"saved":[…]}` — a superset
of `writeErr`'s, which is what the client's widened body type expects.

**The `project.ErrNotFound` remap it skips — does not matter today, see R4-4.** Both call sites
pass freshly constructed static errors (`errors.New("path is managed by styrman")`,
`errors.New("cannot save upload")`), neither of which can wrap `project.ErrNotFound`, so the
remap at `server.go:1090-1092` is unreachable from `uploadErr`. It is a latent trap, not a defect.

**`throw r.error` inside `tryUI` — toasts correctly.** `ApiError extends Error`
(`api.ts:208-214`), `tryUI` does `toast("error", (e as Error).message || "Request failed")`
(`api.ts:200-206`), and `.message` is the server's `error.message` with `res.statusText` as the
fallback — byte-identical to the string the old throwing path produced. The only behavioural
change is ordering: the eviction and the re-list now run *before* the toast, which is the point.
(`ApiError` is not exported, so the inferred return type of `uploadFiles` names a module-private
class. Harmless while `declaration` is off; it would also block any `instanceof ApiError` narrowing
a future caller wanted.)

**The Go test's fixture assumptions — both hold.** `".ssh"` is not a filesystem fact: it is a
hardcoded arm of `managedHomeTarget`'s switch (`explorer.go:106-111`), a pure function of the
scope flag and the string, so nothing about the fixture's home layout can make the trigger
flaky — and if that list ever loses `.ssh` the test fails loudly on the `w.Code != 400`
assertion rather than silently degrading into a success-path test. `makeProject` does create a
usable home: the test's follow-up `GET .../home/file?path=a.txt` returns 200, which it could not
if `scopeFor` had no home root to resolve. Verified by running it: **PASS**, and the whole
`go test ./...` is green.

**The e2e check — robust, and correctly ordered.** `setInputFiles` is one of the few Playwright
actions whose actionability set is *Enabled only*, not Visible, so `className="hidden"` on the
input (`FileExplorer.tsx:251-262`) is fine; and `panel().locator('input[type="file"]')` cannot
strict-mode-collide because that is the only file input in `web/src`. State entering the check is
exactly what it asserts in its own first line (`editor-path` naming `two.txt`): the preceding
"discard-and-open" check leaves the pane on project-scope `two.txt` at the workspace root, so
`scope.kind`/`path` make `inDir("two.txt")` agree with the pane's identity. Ordering is right on
both sides — it sits *after* the cap check (which reloads the page, and must precede every
dirty-editor check because of the new `beforeunload` handler) and it does not depend on the
pre-cap chips, since `two.txt` is added to recents after the cap check by "discard-and-open".
`chipLabel` yields the bare `two.txt` because no other recent (`one.txt`, `junk0..5`) shares that
basename. Nothing later depends on `two.txt`'s contents. `Buffer` is a Node global and `run.mjs`
is harness code, so the plain-V8 rule does not apply.
