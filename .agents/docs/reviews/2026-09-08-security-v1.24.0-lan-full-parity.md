# Security review — v1.24.0 LAN full parity (ADR-066)   (2026-09-08)

Range reviewed: v1.23.0..HEAD

## Verdict: FINDINGS

The worst problem is that `LAN_ALLOW_HOST=1` grants every LAN-enabled project unrestricted
L3 reach to **every** service listening on the host's uplink address, and the one
precondition the project itself states for that grant — "a deployment that sets it MUST NOT
accept password authentication on the uplink" (R12, ADR-066 part 5) — is enforced by
nothing in code. Not by `install.sh --lan-allow-host 1`, not by `validate_allow_host` in the
root script, not by `netpolicy.Availability` on the server. The project's own ADR text
records that this host runs `sshd` on `0.0.0.0:22` with `passwordauthentication yes`
alongside `/etc/sudoers:50 %sudo ALL=(ALL:ALL) NOPASSWD:ALL`, so on that host a single root
command would hand an untrusted in-guest agent an unrate-limited root-credential-guessing
surface reachable from inside the microVM whose whole purpose is to prevent that. Production
has **not** opted in (documented in `deploy/remote.md`), so this is a latent grant behind a
deliberate root action rather than a live exposure — but the guard rail is a paragraph in a
markdown file, and the code path that writes the key does not read it.

Against the two questions the coordinator asked directly: **no**, neither new reach can be
widened by anything a guest controls (the marker grammar is a name, the destinations come
from root's own `ip route`/`ip addr` view and a root-owned conf, `-s` is pinned to the
bridge subnet so a NET_ADMIN guest cannot spoof past the DROP, and `--ctstate DNAT` cannot
be forged from inside a VM whose dockerd lives in its own netns). The non-root **server**
uid can influence the `lanpub` destination allowlist, but only through the Docker socket it
already holds, which is root-equivalent on this host — a pre-existing equivalence, not a new
one, and worth recording only because the script's header claims root alone decides the
allowed set. And **yes**, `pruneHostReachingCreds` is genuinely confined: it goes through
`internal/files`' `files.Trust` tenant confinement, the sub-root is the project home itself,
`os.Root.Remove` does not follow a final symlink, and `TestPruneRefusesToFollowAPlantedSymlink`
plants exactly that case. The worst a planted symlink achieves is redirecting the delete to
another file inside the same project's own home.

Three defects an independent reviewer found in this same range are **confirmed and already
fixed in the working tree**; I reached two of them independently and they are recorded below
as confirmed-fixed, not as new findings.

## Findings

- **[high / confidence: high]** `deploy/firewall/styrman-firewall.sh:349` (`validate_allow_host`),
  `deploy/firewall/install.sh:40` (`--lan-allow-host`) — the sshd precondition for
  `LAN_ALLOW_HOST=1` is documented and unenforced. `validate_allow_host` checks only that the
  value is `0` or `1`; `install.sh` accepts the flag and writes it with no host inspection;
  `netpolicy.Availability` (`internal/netpolicy/status.go:172`) never considers it. The
  resulting rule is `-A STYRMAN-IN -s <bridge subnet> -d <host uplink addr>/32 -i sdb-<hash>
  -j RETURN` at the head of `STYRMAN-IN`, i.e. a RETURN back into `INPUT`, whose policy on a
  Debian+Docker host is ACCEPT — so it is *every* port, not a port list. Exploitable in
  principle: an agent in a LAN-enabled project opens TCP to the host's uplink address on 22
  and guesses; a success is root via `NOPASSWD:ALL`. Remediation: make
  `install.sh --lan-allow-host 1` refuse unless `sshd -T` reports
  `passwordauthentication no`, behind an explicit `--i-have-hardened-sshd` override; and
  have `validate_allow_host` emit `warn=host sshd accepts password authentication` into the
  status file on every run so Settings → Host firewall shows the condition instead of the
  operator having to remember a runbook.

- **[medium / confidence: high]** `deploy/firewall/styrman-firewall.sh:389`
  (`validate_allow_pub`) + `internal/httpapi/network.go:102` (`ingressBridgeMismatch`) — a
  *wrong-but-valid* `INGRESS_BRIDGE` fails **open**, and the cross-check built specifically
  to catch it is advisory only. Absent, misshapen and nonexistent all fail closed and are
  tested (`deploy/firewall/test.sh` §23). A value that is shape-valid (`br-<12 hex>`) and
  names an existing interface that is *not* the ingress passes every root-side check, and
  `discover_pub_subnets` then leaves the REAL ingress subnet inside `LAN_PUB_SUBNETS` — the
  exact inversion the key exists to prevent, as the code's own comment says. The only
  detection is `ingressBridgeMismatch`, which appends a string to `hostFirewallView.Warnings`
  (admin-only) *after* the fact; `Availability` does not consult it, so enable is still
  accepted and the rules stay installed. Reachable without operator error: Docker routinely
  leaves a stale `br-*` interface behind after an unclean daemon restart, so a conf naming
  the old bridge can satisfy the existence check while the live ingress uses a new one.
  §23 covers absent/stale/invalid but has no wrong-but-existing case. Impact today is bounded
  because nothing is published into the ingress network, so the DNAT match has no target —
  it is the invariant that is broken, not (yet) a reachable service. Remediation: fold the
  mismatch into `netpolicy.Availability` so an enable is refused and the state renders
  `error`, and add a `test.sh` case that points `INGRESS_BRIDGE` at a second existing
  `br-<12 hex>` and asserts the real ingress subnet is not in `lan_pub_subnets`.

- **[medium / confidence: high]** `web/src/components/LocalNetwork.tsx:187` +
  `deploy/docker-compose.yml:20` — the consent dialog states, at the moment the operator
  grants the privilege, that "Other projects, **the ingress** and cloud metadata stay
  blocked". With `LAN_ALLOW_HOST=1` that is false. The Caddy ingress runs
  `network_mode: host`, so it listens on the host's uplink address on 80/443 and the
  `lanhost` RETURN reaches it directly — the `lanpub` family's ingress exclusion covers only
  the DNAT path and is bypassed entirely. That container holds the Docker socket and the
  compose file describes it as "internet-facing, so treat any RCE in it as host root". The
  net *additional* risk is modest (the same listener is reachable from the internet), but a
  security statement shown to obtain consent should not be contradicted by the rules the
  consent installs. Remediation: either carve the ingress's listening ports out of the
  `lanhost` RETURN, or make the dialog say what is actually granted when `allowHost` is true.

- **[medium / confidence: high]** `internal/credbroker/broker.go:52` (`isHostReachingFile`)
  vs `internal/httpapi/network.go:270` (`pruneHostReachingCreds`) — the "host-reaching
  credential" predicate is implemented twice with different normalization, and the two copies
  already disagree. The broker trims `~/`, then `$HOME/`, then `./`; the prune trims only
  `~/` and `$HOME/`. Consequences, both reachable through paths `credstore.validRelPath`
  (`internal/credstore/credstore.go:430`) accepts and `image/configs/styrman-credentials.sh`
  materializes into `$HOME/.ssh/`:
  - `~/./.ssh/id_ed25519` — withheld by the broker, **not pruned** from the project home, so
    the half of the control that removes an already-materialized copy silently does nothing.
  - `~/.//.ssh/id_ed25519` — `isHostReachingFile` reduces it to `/.ssh/id_ed25519`, which
    matches neither branch, so it is **neither withheld nor pruned** while the guest snippet
    still writes it to `~/.ssh/id_ed25519`.
  The doc comment on `pruneHostReachingCreds` claims it "prunes exactly what the broker
  withholds rather than a hardcoded guess that could drift from it" — it is a second
  hardcoded guess, and it has drifted. Remediation: export one predicate that normalizes with
  `path.Clean` on the home-relative form and call it from both sites; table-test the `~/./`,
  `~/.//`, `$HOME/.ssh/…` and bare `.ssh/…` spellings.

- **[low / confidence: high]** `deploy/firewall/install.sh:185-187` — the new in-place conf
  update writes `${CONF}.new.$$` into `${ETC_DIR}` and `mv -fT`s it over the conf **without**
  any of the `${ETC_DIR}` assertions the create branch performs at lines 214-216 (`-L`,
  owner `0`, `-perm /022`). It validates the conf *file* (symlink, root-owned) but never its
  parent, and a `>` redirection follows a symlink pre-planted at that exact name. This is
  BUG-009's shape — root code writing below a directory it has not just asserted. Not a live
  hole on a host this installer created (`/etc/styrman` is root-owned 0700 there), so it is
  defense-in-depth. Same block: `sed "s|^${k}=.*|${kv}|"` interpolates `${kv}` unescaped and
  `--ingress-bridge` is the one CLI value with no shape validation, so `|`, `&` or `\` in it
  corrupts the conf (root-operator input; the script then fails closed).

- **[low / confidence: high]** `internal/httpapi/network.go:150` — `credentialImpact` is
  deliberately **not** admin-gated, and `netpolicy.Exposed` returns `true` whenever root's
  status is missing or stale *regardless of the record*. So `GET /api/projects/{id}/network`
  returns `credentialImpact: "ssh-key-withheld"` to a non-admin owner of a LAN-**off**
  project whenever the host firewall's status file is unreadable or its timer has not run for
  three minutes. That is a signal about the operator's host state crossing to a tenant —
  BUG-017's class again ("grep every field a handler returns for the same invariant already
  enforced elsewhere"). The UI only renders it when `on`, so nothing is displayed today, but
  it is on the wire. Remediation: gate the field on `p.LanAccess`.

- **[low / confidence: medium]** `deploy/firewall/styrman-firewall.sh:365`
  (`discover_pub_subnets`) — the `lanpub` destination allowlist is derived from
  `ip -o -4 route show scope link` filtered by *interface naming convention*
  (`docker0`, `br-<12 hex>`, minus `sdb-*`, minus the ingress). Its inputs are therefore
  whatever the Docker daemon has created, and the non-root server uid drives that daemon
  through `/var/run/docker.sock`. A network created with
  `com.docker.network.bridge.name=br-<12 hex>` and an arbitrary subnet enters the allowlist
  on the next tick. This confers nothing new — socket access is already root-equivalent on
  this host — but it does mean the script header's claim that "root decides what 'local
  network' means" holds for `LAN_CIDRS` and not for this family. Worth stating in the ADR so
  a future reader does not rely on a property that is not there. Related, lower confidence:
  a `br-<12 hex>`-named bridge that is *not* a Docker network (or a Docker network with a
  custom non-`br-` bridge name) is misclassified in both directions by
  `is_docker_bridge_name`, which also feeds `validate_cidrs`' deny list — a custom-named
  Docker bridge whose subnet overlaps `LAN_CIDRS` would not be denied. Pre-existing, not
  introduced here.

### Confirmed and already fixed in the working tree (not new)

- `internal/httpapi/network.go` guarded on `netpol.Enabled()`, unreachable because
  `config.envOr` substitutes the `/run/styrman-firewall` default for an empty value — I
  reached this independently and had it queued as a low finding (the dead branch is the
  fail-**open** one, so the live behaviour was fail-closed but platform-wide key withholding).
  Now guarded on `Dir.Installed()`, which stats the run dir. The direction to watch on
  re-review: `Installed()` must not make "the run dir vanished" read as "no LAN feature",
  which would be BUG-014 inverted onto the credential side.
- `deploy/firewall/install.sh:209` wrote `INGRESS_BRIDGE=…$'\n'` with a literal backslash —
  reached and reproduced independently (`printf` run, and the grammar regex at
  `styrman-firewall.sh:419` confirmed to reject it, taking `conf_fail` and closing every
  allowance). Fails closed. Now built as a separate line.
- `ipt -S "$chain" 2>/dev/null || true` swallowing a failed chain read, so a failure revokes
  nothing while the insert pass still installs everything — loosening without tightening.
  I had not reached this one; it is the same BUG-010 shape the `CHAINS` array comment already
  guards against elsewhere in the file, and the fix belongs in `scan_current`,
  `delete_malformed` **and** `count_applied`, all three of which use the identical construct.

## Not examined

Named honestly so the gate report does not imply coverage it does not have:

- **No dynamic verification of the firewall.** `deploy/firewall/test.sh` and
  `.agents/docs/testing/styrman/integration.sh` were read, not run — both need root and a
  live Kata/iptables host. Every rule-ordering and reachability claim above is from reading
  the script and the rendering the regexes pin, not from observed packets.
- **The actual FORWARD-chain outcome of `lanpub`.** A RETURN out of `STYRMAN-FWD` lands back
  in `DOCKER-USER` and then meets `DOCKER-ISOLATION-STAGE-1/2`, which on Docker 28 may drop
  cross-bridge forwarding before the DNAT ACCEPT. Whether the family functions at all is
  therefore unverified here; the integration script asserts it does. Either way it fails
  closed, so this does not change any finding.
- **`route_localnet` on the `sdb-*` bridges.** If Docker sets it, a guest could reach
  `127.0.0.1`-published ports through the DNAT path — wider than the LAN-peer parity the ADR
  claims. Not checked on a live host; no port is published on loopback in
  `deploy/docker-compose.yml`, so it is theoretical today.
- **The vendored Caddy ingress source** (`deploy/caddy/ingress/`) beyond confirming it is
  unchanged in this range and that its tests pass. Header-stripping behaviour for
  client-supplied `X-Caddy-Email` / `X-Styrman-Ingress` was not re-verified, and it matters
  to the ingress-reachability finding above.
- **`web/dist/client`** — rebuilt bundles, reviewed only as the diff of their sources
  (`web/src/lib/lan.ts`, `web/src/components/LocalNetwork.tsx`, `web/src/lib/api.ts`).
  `git diff --numstat` shows text for every source file changed; no `- -` rows outside
  `dist` (BUG-007 check).
- **`web/e2e/run.mjs`'s 90 new lines** and the frontend test suite were not run.
- The prior per-phase reviews in `.agents/docs/reviews/2026-09-08-security-lan-phase*.md`
  and `-phase1-refactor.md` were not re-audited for findings that were accepted then and
  might read differently now.

## Checked

- **Secrets** — clean. Every added line in the range grepped for
  `password|secret|token|key|BEGIN … PRIVATE|AKIA|ghp_|sk-`; every hit is prose in ADRs,
  deploy docs, comments or UI copy about the sshd/SSH-key policy. No `.env`, `*.pem`,
  `*.key` or credential JSON in the diff. `deploy/vulncheck.sh` still shadows `deploy/.env`
  with `/dev/null` before running a downloaded tool.
- **Injection** — the root script's inputs are a root-owned conf validated against a strict
  grammar per line, and marker **filenames** matched against a UUID regex with contents never
  read; rule arguments are rebuilt from regex captures and passed as an argv array, never a
  string. `install.sh`'s `sed "s|^${k}=.*|${kv}|"` interpolates an unvalidated
  `--ingress-bridge` into a replacement (low finding above). Go side: no SQL, no exec of user
  data; `files.Remove`/`files.Exists` normalize with `cleanRel` (`path.Clean("/"+rel)`) and
  run through `os.Root`.
- **Authz/authn** — `PUT /api/projects/{id}/network` resolves the project *before* the admin
  check and 404s a foreign project ahead of any authorization signal; enable requires
  `requireAdmin`, disable does not (tightening is never refused, correct).
  `hostFirewallView` — LAN CIDRs, host addrs, pub subnets, ingress bridge, root's raw
  warnings — is admin-only, and `lanFor` substitutes generic text for non-admins on
  `error`/`unavailable`. The one non-admin field added in this range, `credentialImpact`,
  leaks host-firewall health (low finding above). Nothing else in the range moves a
  capability across the admin line.
- **Crypto** — nothing hand-rolled and nothing added. `config.BridgeNameFor`'s SHA-1 is a
  non-security name derivation (Docker's own bridge-naming scheme), matched by the script's
  `sha1sum | cut -c1-11` and pinned by a golden vector shared between
  `internal/config/bridgename_test.go` and `deploy/firewall/test.sh`.
- **Dependencies** — no dependency changes at all in this range: `go.mod`, `go.sum`,
  `web/package.json`, `web/package-lock.json` and `deploy/caddy/ingress/go.{mod,sum}` are
  untouched. `bash deploy/vulncheck.sh` (pinned `golang:1.25.13-trixie`, all three modules)
  exits 3 with exactly the two accepted, no-fix-available `github.com/docker/docker`
  advisories — GO-2026-4887 and GO-2026-4883, in both the server (v28.5.2) and ingress
  (v27.5.1) modules; `image/harness` clean. A bare `govulncheck ./...` on this workstation's
  go1.25.0 reports 31 stdlib findings that the shipped build does not have — the exact
  discrepancy `vulncheck.sh` exists to avoid, so the pinned run is the one that counts.
  `npm audit --omit=dev` in `web/`: 0 vulnerabilities. `go vet ./...` clean;
  `go test ./...` and `(cd deploy/caddy/ingress && go test ./...)` pass.
- **GCP surface** — not applicable and untouched: self-hosted single host, no IAM binding,
  no service account, no Cloud Run, no `--allow-unauthenticated`, no key file. Secrets reach
  the server as compose env from a gitignored `deploy/.env`, unchanged in this range.
