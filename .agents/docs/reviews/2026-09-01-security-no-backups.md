# Security review — no-backups + token-auth updater   (2026-09-01)

Scope: uncommitted working tree against `HEAD` = `cbd8b05` (v1.16.1). Diff removes the whole
backup feature (Go package, 5 HTTP routes, cadence goroutine, config knobs, frontend, host
restic layer) and replaces the auto-updater's SSH deploy key with a fine-grained GitHub token
fed through an inline git credential helper. Blast radius followed: `deploy/update/styrman-update`
(runs as root, builds and runs what it fetches), `deploy/host-setup.sh` (the operator-facing
secret-provisioning procedure), `internal/httpapi/server.go` (delete/boot lifecycle and route
table), the live host's `/etc/styrman` + systemd units, and the residual on-disk data the removed
feature leaves behind.

## Verdict: FINDINGS

Nothing high. The worst item is not in the code that was written but in the data the removal
left behind: a 10 MB unencrypted `tar.gz` of a project workspace **and its per-project home**
still sits at `/var/lib/styrman/backups/…` on the live host, and every code path that could
list or delete it was deleted in this change. `server.go:801-803` states plainly that the
per-project home holds "docker disk, transcripts, apt manifest, dotfiles, **any creds**" — so
this is orphaned credential-bearing residue with no lifecycle and no product-side way to remove
it. Second: wipe-delete lost its pre-wipe safety net while the UI checkbox that triggers it is
still **pre-checked**, so the default "Delete project" is now permanent destruction of the
workspace and its git history. The token credential helper itself is sound in the ways that
matter most — the token never enters argv, `.git/config`, or the remote URL, and the
`-c credential.helper=` reset genuinely clears file-scoped, URL-scoped and env-inherited
helpers (verified empirically against git 2.47.3) — but the helper answers with the token for
**any** host and protocol, and the reset is skipped entirely when the token file is absent.

## Findings

- **[medium / confidence: high]** `internal/backup/` (deleted) + live host `/var/lib/styrman/backups/ostling-simon/bb217d96-…/20260901T185113Z.tar.gz` — the removal deletes the *code* but not the *data*. Read-only listing confirms one 10 159 661-byte archive plus its `.json` metadata, mode `0600`, owner `kesokaj`, inside a `0700` dir. The archive format (`git show HEAD:internal/backup/backup.go`) is a plain `tar` + `gzip` stream with **no encryption**, and its sources were the workspace *and the per-project home* — the same home the delete path documents as holding harvested credentials (gcloud, claude, ssh, agy per ADR-030/032). Exploitable in principle: any future path that reads the state dir as a lower-privileged actor, any host-level backup/copy/imaging of `/var/lib/styrman`, or a container that ever gets `/var/lib/styrman` bind-mounted (the server container already does — `deploy/docker-compose.yml:120`) can read plaintext credentials that outlived both the project and the feature. Remediation: shred the tree as part of this change (`shred`/`rm -rf /var/lib/styrman/backups` on the host, operator-run since ADR-052 bars me from touching it), and add one line to the changelog/host notes telling other operators to do the same — a removal that leaves secrets behind is not a removal.

- **[medium / confidence: high]** `web/src/components/DeleteProjectDialog.tsx:23` + `internal/httpapi/server.go:785-800` — `useState(true)` means the "Also delete its files on disk — workspace, git history, docker disk, and transcripts" checkbox is **checked by default**, and the pre-wipe safety backup that used to fail-closed in front of it is gone. The only remaining gate is typing the fixed word `delete`, which is the same keystroke for the recoverable and the unrecoverable variant. This is a data-destruction risk, not an attacker path (CSRF is separately covered: `csrfGuard` at `server.go:459-466` is unchanged and rejects cross-origin mutating requests, and `DELETE` triggers a CORS preflight regardless). Remediation: flip the default to unchecked so the destructive variant is an opt-in, and require typing the **project name** rather than a constant when `wipe` is set. If the operator prefers the current default, record that as an explicit accepted risk — the code comment does record the removal honestly, which is good, but the UI default contradicts the "irreversible" framing.

- **[medium / confidence: high]** `deploy/update/styrman-update:157-158` — the inline credential helper is unconditional on host and protocol. Verified: feeding `protocol=https host=evil.example.com` (and even `protocol=http`) to `git credential fill` with exactly these arguments returns `username=x-access-token` and the token. In practice the only credentialed operation is `git fetch origin` against the URL in `/opt/styrman/.git/config` (root-owned, currently `https://github.com/kesokaj/styrman-crew.git`), but git re-queries the helper for the *new* host on an HTTP redirect and this helper will answer — so a GitHub-side redirect, a TLS-MITM with a mis-issued cert, or any future edit of the origin URL turns into token disclosure to a third party. Remediation (verified working): scope the helper to the host — `-c "credential.https://github.com.helper=!f() { … }; f"`. With that form the same probe against `evil.example.com` fails with `could not read Username`, and github.com still succeeds.

- **[low / confidence: high]** `deploy/update/styrman-update:148-159` — the `-c credential.helper=` reset lives *inside* the `if [ -f "${GH_TOKEN_FILE}" ]` block, so `GIT_CRED_ARGS` is empty when the token file is missing and the stated guarantee ("CLEARS inherited helpers so nothing else … can answer for this fetch") silently does not hold on exactly the path where an ambient helper would matter — a stale `credential.helper=store`, a leftover `~/.git-credentials`, or an inherited `GIT_CONFIG_PARAMETERS` could then authenticate the root fetch with credentials nobody audited, and the fetch would *succeed* rather than fail loudly. Remediation: initialise `GIT_CRED_ARGS=(-c credential.helper=)` before the `if`, and append the token helper inside it.

- **[low / confidence: high]** `deploy/host-setup.sh:381-382` — the documented provisioning command is `sudo sh -c 'umask 077; read -r t; printf "%s" "$t" > /etc/styrman/gh-token'`, and `read -r` leaves terminal echo **on**. The comment promises "never into shell history", which is true, but the token is printed on screen and lands in scrollback, in `script`/tmux logs, and — the sharp edge for this product — in a styrman terminal transcript (ADR-017) if the operator provisions from inside the platform. Remediation: `read -rs t` (and a trailing `echo` for the newline), or `systemd-ask-password`. Same file, no other change needed.

- **[low / confidence: medium]** `deploy/update/styrman-update:158` — `${GH_TOKEN_FILE}` is interpolated **unquoted** into a shell string that git evaluates (`… \"\$(cat ${GH_TOKEN_FILE})\" …`). The `[ -f … ]`, root-owner and mode guards constrain what can reach it, and `STYRMAN_GH_TOKEN_FILE` is only settable by editing the root-owned unit (`styrman-update.service` has no `EnvironmentFile`), so this is not attacker-reachable today — it is defence-in-depth on a credential path plus a plain functional bug for any path containing spaces or glob characters. Remediation: quote it — `\"\$(cat '\''${GH_TOKEN_FILE}'\'')\"` or, cleaner, export the path in the helper's environment instead of splicing it into the string. Not exploited, not demonstrated.

- **[low / confidence: high]** `deploy/update/styrman-update` (deployment gap, verified on host) — `deploy()` rebuilds images and restarts the stack but never reinstalls `/usr/local/bin/styrman-update` or its units; those come only from a manual `host-setup.sh` run. The host is therefore still running the **old** deploy-key script (journal, 21:27:26: *"install a read-only deploy key at /etc/styrman/deploy-key"*), and since the key was already revoked the timer now fails every 5 minutes. Consequence: **the host currently receives no updates at all, security patches included**, and none of the new token guards (root-owner, mode) are actually in force until the operator both mints the token and reinstalls the script by hand. Deliberate per the operator's plan, but it is a live patch-delivery outage and belongs in the release notes with the exact recovery order (install script → mint token → `--check`).

- **[info / confidence: high]** Trust-model delta, honest accounting. **Better:** no private key material on the host at all; the credential is scoped to one repository at `Contents: Read-only` (the old deploy key was per-repo but not per-permission-bit in the same way), it expires, it is revocable from the GitHub UI in one click with an audit trail, and the whole known_hosts/TOFU problem — which cost two prior review cycles — disappears. **Worse:** a bearer token has no possession binding, so a single read of `/etc/styrman/gh-token` yields full repo-read from *any* machine on the internet with no host-key, client-cert or IP anchor, whereas an SSH key at least required the attacker to also reach GitHub over SSH with an identity GitHub can correlate; and the trust anchor moved from one pinned host key to the whole public CA set, which is what makes the unscoped-helper finding above matter. **Net:** roughly neutral, tilting positive because of expiry + one-click revocation — provided the helper is host-scoped and the expiry is short and calendared. Note also that "Contents: Read" means read of *everything* in the repo, so any secret ever committed is in the token's blast radius.

- **[info / confidence: high]** Not a constitution violation. The inline helper is *configuration of git's documented credential-helper interface*, not a hand-rolled auth/crypto construction: no protocol, no token minting, no signature or hash implemented locally. Called out explicitly so a later reader does not have to re-litigate it. The tag-signature path (`verify_tag`) is likewise unchanged by this diff and still uses `git verify-tag` with an SSH allowed-signers file.

## Checked

- **Secrets** — No credential values printed anywhere in this review. Token never enters argv, `.git/config`, the remote URL, or `GIT_CONFIG_PARAMETERS` (only the helper *string*, i.e. the file path, propagates); verified `/opt/styrman/.git/config` carries only `url = https://github.com/kesokaj/styrman-crew.git` and no helper line, and `/root/.gitconfig` has no helper/token/password entry. `git -c … clone` in the printed instructions is correctly placed *before* the subcommand, so nothing is persisted into the new repo's config. Rebuilt `web/dist` bundle scanned for `ghp_`/`github_pat_`/`gho_`/`AIza`/`sk-ant-`/PEM headers — clean. Host `/etc/styrman` (read-only listing) now holds only `allowed_signers` (0644 root, public keys — fine) and `update/`; `deploy-key`, `deploy-key.pub`, `known_hosts`, `restic-pw`, `backup.env`, `backup-sa.json` are all gone, dir is `0700 root:root`, and `gh-token` is not yet present (updater failing loudly, as designed). Residual credential-bearing archives under `/var/lib/styrman/backups` — see finding 1; listed read-only only, nothing touched (ADR-052).
- **Injection** — One unquoted interpolation of an operator-controlled path into a git-evaluated shell string (finding 6); not attacker-reachable, no exploit produced. `wipe` is a strict `== "true"` string compare. The removed `FromBackup` path deleted `projectIDRe`/`backupIDRe` validation *and* the code that needed it — net reduction in parsing surface, including a `tar` extractor with `..`/symlink-parent defences that no longer has to be correct. No new external input is parsed by this diff.
- **Authz/authn** — All five backup routes confirmed unregistered: `go build ./...` clean, and `grep` for `restoringState|doBackup|backupIDRe|errBackupBusy|seedFromBackup|BackupMeta|fromBackup|/backups` across `internal/`, `cmd/`, `web/src/` and the rebuilt `web/dist/assets/*.js` returns nothing. No orphaned authz assumptions: the removed handlers were the only users of the `restoring`/`backingUp` maps, `tryAcquire` moved intact to `credharvest.go` with the same `deletingMu`-guarded compare-and-set semantics, and its one surviving caller is the credential push. No surviving archive-touching code exists, so the removed restoring-guard cannot leave a boot/delete interleave: `ensureFor`, `startProject` and `deleteProject` now interlock only through `deleting`, which is unchanged. `csrfGuard` and `authGuard` ordering untouched. `go test ./internal/httpapi/...` passes.
- **Crypto** — Nothing hand-rolled; see the info finding. Trust anchor changed from a pinned SSH host key to public-CA TLS, which is the accepted cost of the token decision. Removed backups were unencrypted `tar.gz`, so their disappearance from the product is a net crypto/exposure improvement — once the residue is shredded.
- **Dependencies** — No new dependencies (the diff only removes code; `go.mod` unchanged). `govulncheck ./...` on the working tree: **31 findings**, versus **33** on a `git worktree` of `HEAD` — the removal reduced reachability by two, and introduced none. 29 of the 31 are Go stdlib findings attributable to the **local toolchain** `go1.25.0`; production builds from `deploy/Dockerfile.server:9` = `golang:1.25.13-trixie`, which is at or above every "Fixed in" version listed (max `go1.25.13`), so the shipped binary carries none of them — the local toolchain should still be bumped so this scan is meaningful. The remaining two are `GO-2026-4887` (moby AuthZ plugin bypass on oversized bodies) and `GO-2026-4883` (off-by-one in plugin privilege validation) in `github.com/docker/docker@v28.5.2+incompatible`, both `Fixed in: N/A`, both pre-existing at HEAD, and both daemon-side defects surfaced through the client module rather than client-exploitable — track the daemon version, no action in this diff. `npm audit` in `web/`: **0 vulnerabilities** (prod and full).
