## Verdict: REQUEST CHANGES

One high-severity finding. `orchestrator.Logs` buffers a project's whole console tail into an unbounded `strings.Builder` while its own comment asserts the opposite ("the tail option bounds the window to <=2000 lines, so buffering it all … is safe"). Docker's `Tail` bounds *lines*, not bytes, and the guest is root inside its own microVM — it picks the line length. This is the exact threat the file next door (`exec.go`) defends with `cappedBuffer` and rates H4/H7 ("without a cap one project could OOM the whole shared server"), and the Ops-panel dialog re-requests it every 30 s. Everything else is medium and below.

The tree is genuinely well built — comments carry real reasoning, threat models are stated, error paths are deliberate. The recurring weakness is the one this audit was told to weight: **a load-bearing comment that asserts a property the code does not have.** Nine of the findings below are that class, and two of them (the `Logs` safety claim and the `usernameFromEmail` "would be a cycle" justification) are load-bearing enough that the next engineer stops checking.

## Criteria roll-up

1. **Dead code — FAIL (3, all small).** `Orchestrator.LastActivity` (no callers, doc points at machinery deleted in ADR-035), `Project.Agent` (no reader or writer anywhere), `Project.GitInit` (constant `true`, never read). All three are clean deletions. No commented-out blocks, no orphaned files, no unreachable branches found; `go mod tidy` is a no-op and `go vet` is clean.
2. **Flow tracing — FAIL (1 high).** `orchestrator.Logs` buffers guest-controlled bytes without a cap while asserting it is safe to do so. Everything else traced cleanly: callers updated, types agree, errors propagate with `%w`, every goroutine in the WS bridge and the reaper has a defined exit, resources close on all paths, and no caller reaches a stub.
3. **Standards conformance — FAIL (12).** Go: error classification by `err.Error()` substring on the self-attach and rename paths, sentinel `==` comparisons, swallowed writer `Close`, a hand-rolled sort. TypeScript: the whole HTTP boundary cast unvalidated, `as Error` on unnarrowed catches, one import-time storage read. Testing: **zero** frontend unit tests and no runner; `internal/identity` untested despite owning the tenancy key; `orchestrator` at 3.0 % and `terminal` at 8.5 %.
4. **Directory layout — FAIL (2).** ~235 lines of migration + janitor business logic in `cmd/styrman/main.go`, and a 1,013-line route file holding nine components that belong in `web/src/components/`. Everything else lands where an unfamiliar engineer would look.
5. **Simplicity, DIY-except-security — FAIL (4), security exemption PASS.** No hand-rolled auth, crypto, hashing, sessions, or JWT anywhere — OAuth is `caddy-security`, the ingress token uses `crypto/subtle`, tokens come from a proper store; dependency set is minimal and justified. The failures are duplication (seven copies of atomic-write, only one durable) and reproducibility (unpinned Caddy/plugin/base images against R11; the server image embedding a possibly-stale committed `web/dist`).
6. **Decoupling — FAIL (3).** Interfaces are small and consumer-declared, no cross-package reach-ins, no grab-bag `util`. The failures are a "single source of truth" helper that four other sites bypass (with a divergent rule, on the broker's tenant-resolution path), a route-pattern string used six times as an implicit scope contract, and one god-file. Two engineers on credentials and backups would collide in `settings.tsx`.
