## Status: COMPLETE

## Verdict: REQUEST CHANGES (design needs revision before Phase 1/2 start — two concrete correctness gaps, one unverified external-format assumption that the plan's own safety guard depends on, and one added-scope item without an operator D-row)

The plan is unusually well specified for a cold-reader — Interfaces, Failure modes and Decisions sections are concrete and traceable to actual code — but it has one literal interface bug (the new Dockerfile `RUN` writes to `/styrman/bin/` before that directory is created anywhere in the build, given the stated placement), one BLOCKING ambiguity in where the new host-side harness-unit-removal step must sit relative to `host_converge`'s unrelated firewall guards (get this wrong and the removal silently never fires on some hosts, reproducing the exact BUG-064 shape the plan cites to justify making it unconditional), and one BLOCKING unverified assumption about the new `sh-agent` binary's `state.json` format that the plan's own "never-downgrade" safety guard (D4) is built on, with no verification step anywhere in the plan that would catch it being wrong before release.

## (1) Gaps

- **G1 — `image/Dockerfile:37-48` vs the plan's Interfaces block — the new RUN's destination directory does not exist yet at the stated insertion point.** The plan places the download/verify RUN "after the apt step that installs `gh`" (lines 37-48 today) and its last line is `install -m 755 sh-agent-linux-amd64 /styrman/bin/sh-agent`. Plain `install` (no `-D`) requires the destination directory to already exist; today `/styrman` is first created by `mkdir -p /styrman` at line 142, and `/styrman/bin` is only implicitly created later by the harness-builder `COPY --from=harness-builder /out/sh-agent /styrman/bin/sh-agent` (line 164) — which the plan deletes. As literally given, the first `docker build` attempt in Phase 1's own verify step fails with "cannot create regular file '/styrman/bin/sh-agent': No such file or directory", before the download/verify logic is ever exercised. Fix is trivial (`mkdir -p /styrman/bin` in the new RUN, or move the RUN after line 142/146) but the plan as written does not say which, and the literal interface block will not build. Confidence: high (verified `install --help` behaviour and the exact current line numbers). Severity: low (self-correcting on first build, but wastes a cycle and is worth fixing in the plan text before Phase 1 starts).

- **G2 — BLOCKING — `deploy/update/styrman-update:807-896` — the plan does not say whether the new harness-unit-removal step sits inside or outside `host_converge`'s existing firewall-specific early-return guards.** `host_converge` today returns early (doing nothing) when `STYRMAN_FW_INSTALL_BIN`/`STYRMAN_UPDATER_UNIT_DIR` are unset, when `REQUIRE_SIGNED != 1`, when the firewall bin/unit dirs are missing/untrusted, or when no verified deployed SHA is recorded (lines 808-832) — all firewall concerns, unrelated to the harness channel. The plan's Interfaces section says only "`host_converge` gains one idempotent step, every tick: … `systemctl disable --now <unit>` … `rm -f` … `rmdir`", and separately, in Failure modes, explicitly invokes BUG-064 to justify making the step unconditional/idempotent rather than gated on "something changed". But if an implementer adds the new removal logic in the natural place — inside the function, after the existing guards, next to the old install-unit-pair block it replaces (lines 843-869) — then on any host where `REQUIRE_SIGNED != 1` (an explicitly supported opt-out state, line 812) or where the firewall dirs are untrusted, the function returns at line 814 or 823 and the harness-unit removal never runs, on any tick, ever. That reproduces exactly the BUG-064 failure mode (a step that should be unconditional silently depends on an unrelated precondition) the plan cites as its own justification. Two implementers reading only the plan text would plausibly place the step differently — one nested where the old block was, one factored out to run before any guard — with materially different host behaviour. The plan needs to say explicitly: the removal step runs before (or independent of) the firewall-specific guards. Confidence: high (read the actual guard code and the two call sites at lines 1015/1055/1083). Severity: medium (only matters on a host with signing off or an untrusted firewall dir, but that is an existing, supported, documented state).

- **G3 — BLOCKING — an unverified assumption about the NEW `sh-agent` binary's `~/.config/sh-agent/state.json` format underlies the plan's D4 safety guard, and nothing in the plan's verification would catch it being wrong.** The plan's entrypoint pseudocode reads: `HOME_REL = the \`embedded:vX.Y.Z\` release in ~/.config/sh-agent/state.json, "" if none/other`, extracted via `sed -n 's/^ *"repo": *"embedded:\(v[0-9][0-9.]*\)".*/\1/p'`. This assumes the new, not-yet-shipped `sh-agent` release binary writes a `"repo"` key whose value is literally the string `embedded:vX.Y.Z` after an in-project `sh-agent update`. I checked the CURRENT mirrored source (`image/harness/internal/harness/state.go:16` and `apply.go:84`, `cmd/sh-agent/main.go:105`): today `Repo` is populated from a filesystem path (`harness.FindRepo(*repoFlag, home)`), with no `embedded:` prefix convention anywhere in this mirror — because this mirror predates the operator's rebuild that the plan's `## Why` describes ("the operator rebuilt styrman-harness around one delivery mechanism"). The recon this plan cites explicitly flags this as **not examined** ("the private styrman-harness repository itself … its own `sh-agent install`/`update` implementation … was not read"). Nothing in the plan closes that gap: Phase 1's verify only checks `sh-agent version` output; the Tier 2 "never-downgrade" edge case (Phase 3, and the E2E criteria list) explicitly **plants** the newer-release condition synthetically ("manifest planted newer … from the host as the owner") rather than producing it by actually running `sh-agent update` inside a project — so the test validates the sed pattern against itself, not against the real binary's output. The Risks/Assumptions section addresses a neighboring assumption (resync-by-manifest behaviour, citing the harness's own README) but does not list this state.json field-format assumption at all. If the real format differs even slightly (different key name, nesting, or value shape), `HOME_REL` silently resolves to `""` every time, the `else` branch always runs `sh-agent install`, and D4's stated purpose — "an image carrying an older harness than the home would otherwise downgrade it silently" — is exactly what happens, invisibly, with no test or verify step positioned to notice before release. Confidence: high on the code trace (state.go/apply.go/main.go read directly); high on this being unverified anywhere in the plan. Severity: high — this is the one thing the plan explicitly built beyond "run install" specifically to prevent silent data loss of a user's forward progress, and it rests on an assumption from a private repo this plan cannot see.

## (2) Scope

- The never-downgrade guard (D4) is scope beyond the operator's literal request in `## Why` ("Only add sh-agent binary to the runtime and run install. That's it, don't complicate things."). The plan is honest about this — D4 is attributed `by: implementer`, not `by: operator`, and the plan's own words call it "the one addition beyond 'run install'". Per the review framework's own rule ("Each is a gap unless a D-row says who asked for it"), an implementer-attributed D-row is not an operator ask, so this is scope the plan adds on its own judgment. Given the operator's demonstrated pattern in this same conversation of trimming implementer additions as "excessive" (see the plan's own Rejected list: a pin file, a build wrapper, a `bump-pins.sh` refresh, and splitting off `harness-migrate.sh`/vulncheck work were all offered and struck), and given G3 above shows this specific addition is the plan's only real unverified-external-format risk, this is worth a one-line confirmation with the operator before Phase 1, not an assumption that "don't complicate things" tacitly excludes it. Everything else in scope (Dockerfile download+verify, entrypoint reshape, deleting the channel end to end, Tier 2 rewrite, R5/ADR) traces directly to the operator's quoted words or to a named consequence of removing the channel — no other unrequested surface found.

## (3) Readiness

Questions a first-pass implementer would have to ask (or guess) before starting:

1. **BLOCKING** — Where exactly (relative to the firewall-specific early-return guards) does the new harness-unit-removal step live in `host_converge`? (G2)
2. **BLOCKING** — What is the actual field/format the new `sh-agent` binary writes into `~/.config/sh-agent/state.json` to record an `embedded:`-sourced install, and does the given `sed` pattern match it? Is there any way to check this before Phase 3 plants a synthetic fixture that only tests the assumption against itself? (G3)
3. **NON-BLOCKING** — Should the D4 never-downgrade guard be built at all, given the operator's "don't complicate things" instruction and D4's `by: implementer` attribution? A reasonable implementer could decide to keep it (it is a sound safety property) or ask first; either is defensible, but it is the plan's only piece of added, unrequested logic and the source of G3's risk, so flagging it is worth the one line even though it is not strictly blocking.
4. **NON-BLOCKING** — Exact placement of the new Dockerfile RUN relative to `mkdir -p /styrman` (G1); any competent implementer fixes this on the first failed build.
