## Verdict: FINDINGS

Nothing high or medium; two lows. The swap race from my earlier finding 1 is closed: in an independent probe through the gated `__write-status` hook, a 0777 ancestor that 57179a4's script wrote below is now refused, and the 0755 control is still written. The worst remaining problem is the new per-tick `Status` in `GuestGoingAway`. While a lifecycle change holds the project's lock, every parked request whose exec failed now makes about 10 `ContainerInspect` calls per second against the dockerd all tenants share. No per-user cap or server-side deadline bounds how many requests one tenant can park. The second low is a hole in the new walk: `read` stops at the first newline, so a status path with a newline in an ancestor's name is checked against a different, truncated path. A status file was written below a 0777, non-sticky ancestor that way. Production is not reachable: the path is pinned by root-owned config. The sticky-bit allowance is sound (see Checked).

## Findings
- **[low / confidence: medium]** `internal/orchestrator/ports.go:136-160` (`GuestGoingAway`), reached from `internal/httpapi/proxy.go:26` (`GET /api/projects/{id}/ports`) and `internal/httpapi/browser.go:95` (`browserExec`: browser REST status, start and stop, and the WS relay).
  - **What changed:** at 57179a4, a waiting request cost one `TryLock` per 100 ms tick and two `Status` calls in total. Now each tick also calls `o.Status`, which is one `ContainerInspect` on the host daemon (`orchestrator.go:150-163`).
  - **When it runs:** after an exec into the project's running container fails, while the container is still running with the same id and another goroutine holds the project's lock. It stops when the guest is gone, the lock is free, or the request context ends.
  - **No bound below that:** `http.Server` sets only `ReadHeaderTimeout`. A grep of `internal/httpapi` and `cmd/styrman` finds no semaphore, rate limit or per-user in-flight cap for `/ports` or the browser REST endpoints. Only the relay has one (8 per user, 32 per server). No limit directive was found in `deploy/caddy`.
  - **What one tenant can do:** start their own project. A cold start holds the lock through `waitReady`, up to 90 s, and a mode toggle has a 3-minute context. In that window, park N `/ports` requests whose scan fails, for example during the boot itself, or from inside a guest the tenant controls (not verified). That gives about 10·N inspects per second, up to about 900 per request, against the shared daemon. The tenant can repeat it on every stop and start. All tenants feel the load, but nothing crosses tenants: the lock key is the caller's own project.
  - **Why only low:**
    - Only authenticated, allowlisted users can do this, and it costs availability only.
    - An inspect is cheap.
    - The same tenant could already flood `/ports` without any wait, and each such request costs a Kata exec, which is heavier. This change makes the server generate the load from idle, parked connections. It does not raise a ceiling that was enforced.
  - **Remediation:**
    - **Coalesce:** one poller per project. Use a singleflight keyed on `key(user, project)` around `gone()`, or cache the `Status` result for one tick across waiters.
    - **Back off:** keep 100 ms for the first second, then step up to 1 s.
    - **Cap the wait on the server:** `context.WithTimeout` at about the page's own 20 s abort (`web/src/lib/api.ts:376`), so a client that never gives up cannot hold a request for the whole lifecycle change.
    - **Cap in-flight requests per user** for `/ports` and the browser REST endpoints, like the relay's 8. This also bounds the older exec flood.
    - **Test:** N concurrent waiters must cause about one inspect per tick, not N.
- **[low / confidence: high]** `deploy/update/styrman-update:109` (`IFS='/' read -ra parts <<< "${1#/}"` in `status_ancestors_ok`), with `:148` and `:154` (`$(dirname -- …)`).
  - **What is wrong:** `read` consumes only up to the first newline, so every component after a newline in the walked path is never checked. The canonical check at `:144` does not stop this: `$(…)` strips only trailing newlines, so a path with an embedded newline still compares equal to its own `realpath -m`. And `$(dirname -- …)` strips a newline that ends a directory name, so `:148` and the parent check at `:154` can be pointed at a sibling directory.
  - **Shown, not inferred:** run in a user-namespace chroot under `.agents/scratch/`, through the gated hook, with the HEAD script (`cmp`-identical). `STATUS_FILE=$'/ok\nevil/status/updater.json'`, where `/ok` is 0755 and `$'/ok\nevil'` is 0777 without the sticky bit: written, rc=0, no WARN. The walk checked `/ok` instead.
  - **Function-level check:** the real functions under `set -euo pipefail` give `status_ancestors_ok $'/etc\n/nonexistent-x/y'` → 0, and `status_ancestors_ok /nonexistent-x` → 1.
  - **Docs:** `deploy.md` and `versioning.md` now say "every directory above the status directory, from `/` down". That holds only for newline-free paths.
  - **Not reachable in production:** `STYRMAN_UPDATE_STATUS_FILE` comes only from root-owned config: `styrman-update.service:18`, `docker-compose.yml:120` and `styrman-ctl:542`, all `/etc/styrman/status/updater.json`. Anyone who can set it is already root.
  - **Remediation:**
    - Before the canonical check, refuse any `STATUS_FILE` outside a conservative character set, for example `[[ "${STATUS_FILE}" =~ ^/[A-Za-z0-9._/-]+$ ]]`. One line closes the newline and the whole control-character class, and the documented claim then holds as written.
    - Optionally, walk with parameter expansion (`p="${p%/*}"`) instead of `read` and `$(dirname)`.
    - Add a hook test with a newline in an ancestor's name that must WARN and write nothing.

- **Dispatch Q2: is the sticky allowance sound?** Yes.
  - **Kernel rule:** on Linux, an entry in a sticky directory can be unlinked or renamed only by its owner, the directory's owner, or a holder of CAP_FOWNER. The walk requires both the sticky directory and the next component on the path to be owned by root or `TRUST_UID`, so no third party can swap that component.
  - **Probe:** a sticky ancestor whose child is owned by another uid (a bind mount, which shows as 65534) is refused. A sticky ancestor with a trusted child is accepted.
  - **Squatting:** a status directory that is missing is created only under a parent that passes `status_dir_ok` (`:154`), which has NO sticky allowance. So it is never created inside a sticky directory. A directory planted there by another user fails `status_dir_ok` (owner check), as does a planted symlink (symlink check). `mkdir` is not `-p`, so a squat between the check and `mkdir` fails, with a WARN.
  - **Group-writable sticky:** accepted on the same reasoning.
  - **ACLs:** the mode's group bits carry the ACL mask, so `-perm /022` sees a writable named-user entry.
  - **Production:** the path `/`, `/etc`, `/etc/styrman` has no sticky directory. The allowance only serves fixtures under `/tmp`.
