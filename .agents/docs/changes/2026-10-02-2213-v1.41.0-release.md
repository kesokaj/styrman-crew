# v1.41.0 — Settings shows a failing auto-updater; stale keys dropped; the browser view recovers   (2026-10-02)

Release of `plans/2026-10-02-stale-keys-browser-liveness-updater-status.md`.
That plan carried out the v1.40.0 handoff's decisions, which the operator
answered: "go with your recommendations. Fix those then cut a new version".
Gate: `reviews/2026-10-02-preflight-v1.41.0.md` (SHIP). MINOR: it adds
behaviour and nothing an existing deployment must react to. Docker creates the
new mount's directory by itself.

## What ships
- **Updater status in Settings** (ADR-081). Each real updater tick records how
  it ended in `/etc/styrman/status/updater.json`: one validated line, codes
  and release tags only. The server reads it through a read-only mount, and
  admins see a notice when auto-update is failing, has not run for an hour, or
  its status cannot be read. Phase 2's entry has the details.
- **Stale keystrokes dropped.** Keys typed while a terminal reconnected are
  sent only if the oldest is under 30 s old; otherwise the whole queue goes.
- **The browser view recovers.** A relay socket that went silent without
  closing is noticed by a CDP probe and reconnected.
- **BUG-088.** The Ports panel and the browser view's status answered with a
  500 while a project's network mode was switched or the project stopped. They
  now answer "no ports" / "not running". The check waits out a stop in flight,
  asking Docker every 100 ms for up to 20 s.
- **ADR-082.** Two keys sign release tags. The ADR holds both full
  fingerprints, where each key lives, and how to revoke one.

## Learnings for the local host
- This host takes the tag only after BUG-084's token is replaced. From then
  on, a failing updater shows in Settings instead of going unnoticed.
- `t.TempDir()` is group-writable under this host's umask 002. Tests of code
  that refuses writable ancestors need 0755 fixtures.

## Deploy

tick, the NUC after its token is replaced. The first updater status appears
