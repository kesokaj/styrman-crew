# v1.17.2 — fixing all 15 confirmed findings from the v1.17.1 max code review

Date: 2026-09-02. HEAD at the start of this work was `36210ff` (v1.17.1); this tree becomes
v1.17.2. Source: the vendor `/code-review` at effort `max` over v1.17.1
(`.agents/docs/reviews/2026-09-01-code-review-v1.17.1-max.md`, 15 CONFIRMED findings, ranked
correctness-first — nothing applied at review time, fixes are this separate change set). Every
finding is addressed below; nothing was left silently unfixed.

## Fixes, mapped to the source findings

1. **[finding 1, data corruption]** `FileEditor.tsx`'s render-phase reset and the `CodeEditor`
   remount key were both keyed on `file.path` alone, so opening the same-named file in the
   *other* scope (one click via a Recent chip) kept the previous scope's buffer on screen with
   no dirty guard — Ctrl+S silently overwrote the wrong file (no backup layer, ADR-055). Both
   `docKey` and `docIdentity` are now one `${scope.kind}:${scope.project}:${file.path}` const,
   used for the reset and for `key={st.docIdentity}` on `CodeEditor`.
2. **[finding 2, pre-existing data loss]** `FileExplorer`'s "New file"/"New folder" now reject a
   name that already exists in the loaded listing (`createError`). This is client-side only —
   the `PUT .../file` endpoint is still `O_CREATE|O_TRUNC` with no create-only variant, so a raw
   API caller (or the UI itself racing a guest-side create) can still truncate. Accepted and
   recorded in `guide.md` rather than silently left unstated; a real fix needs an `O_EXCL`
   server endpoint (TODO).
3. **[finding 3, unsaved-edit loss]** `closeFileInPane`'s scope-aware prune and the pane sweep
   above it used to disagree — the pane sweep matched by path only, so deleting `project:p`
   could clear a pane holding `home:p` and drop its unsaved edits with no prompt. Both loops now
   share one `matches(entry, {scopeKind, path})` predicate.
4. **[finding 4, pre-existing unsaved-edit loss]** `p.$project.$term.tsx` now installs a
   route-level `useBlocker`, wired to `pane.dirty`, plus a `beforeunload` handler while dirty,
   with a "Discard and leave" confirm dialog on a blocked navigation. `ignoreBlocker: true` is
   set on the three navigations that follow a destructive action (delete terminal, delete all
   terminals, delete project) so the prompt cannot strand the user on a route whose terminal or
   project no longer exists — a hole the round-1 review caught before ship.
5. **[finding 5, file resurrection]** `EditorPane`'s load effect now reverts the store to
   `loaded.req` (or `null`) when `readFile` rejects (a stale Recent chip, a guest-side `rm`),
   instead of leaving the store pointed at a path the pane no longer shows — the bug that let a
   later Save recreate a deleted file.
6. **[finding 6, pre-existing stale overwrite]** The server (`internal/httpapi/explorer.go`) now
   reports the parts it saved on **every** exit, success or failure — a mid-stream error returns
   its error body plus `saved` with whatever landed before the failing part (new handler test
   `TestUploadReportsSavedPartsOnFailure`, `internal/httpapi/explorer_files_test.go`). This took
   two passes to actually be true on every exit: round 4's reviewer caught that the `mr.NextPart()`
   error branch (the one a truncated multipart body or the endpoint's own 512 MiB cap actually
   trips) still called the old `writeErr` and dropped `saved` — a one-word fix
   (`writeErr`→`uploadErr` at that call site) closed it, and the handler test gained an
   all-parts-skipped case asserting the wire shape is `"saved":[]`, not `null`, on a fully
   successful-but-empty upload. The client (`api.uploadFiles`) no longer throws on a failed
   upload — it returns `{ saved, error? }` — and `FileExplorer`'s `upload()` calls a new
   `evictFromPanes()` (panes only; the Recent chip is **kept**, since the file still exists) for
   exactly the server-reported base names under the upload directory, on success and failure
   alike, then rethrows `error` if present. An earlier round's "evict by the dropped file names on
   failure" heuristic — which cleared panes for files the server had never touched, and
   over-cleared an entire folder on a failed directory drop — was deleted rather than kept
   alongside it. `closeFileInPane` (used for delete/rename) is now `evictFromPanes` plus a recents
   prune; upload only needs the former. The e2e check added for this finding exercises only the
   success path (see Honest coverage below) — the failure branch is covered by the Go test alone.
7. **[findings 7 and 9, ops + security surface]** — the `styrman-update.service` line that
   hard-coded `DOCKER_CONFIG=/etc/styrman/update/.docker` a second time (redundant with, and
   contradicting, the "ONE pin" ADR-052 comment) is gone. `DOCKER_CONFIG` is now a per-run
   `RuntimeDirectory=styrman-update` tmpfs (`%t/styrman-update/docker`, mode 0700, wiped by
   systemd after the oneshot) under the unit, and `mktemp -d` + an `EXIT` trap for hand-runs
   outside systemd — now the only `EXIT` trap in the script, commented as such ("anyone adding
   another EXIT trap must chain this cleanup, not replace it"). An inherited value is honoured
   only when it is under `/run` **and** its nearest existing ancestor is root-owned and not
   group/world-writable (`stat -c %u` = 0, `find -maxdepth 0 -perm /022` empty) — anything else,
   including a `/run/*`-shaped path that fails either assertion, hard-fails rather than silently
   falling back. This closes the gap a bare path-shape check left open (round 2's `/run/*` case
   still trusted the shape alone; `/run/lock` is `1777` and `/run/user/<uid>` is uid-owned, so
   either would have passed a shape-only test). The leftover `/etc/styrman/update/.docker`
   directory from the 2026-09-01 fix was removed from the host.
8. **[finding 8, test theatre]** The "recent strip reopens a file" e2e check now asserts a REAL
   reopen: the previously-open document goes `detached` and the toolbar's `editor-path` testid
   names the new file, closing the gap where a lax `text=hi` substring match was already
   satisfied by the still-open Dockerfile buffer (`RUN echo hi`).
10. **[finding 10, validation]** `sanitizeRecents` is now the one constructing parser used on
    both read (`loadRecents`) and write (`noteRecent`) — canonicalises relative paths (rejects
    absolute paths, `.`/`..` segments, control characters, and anything over 512 chars),
    first-wins dedup on `${scopeKind}/${path}`, caps the array. Previously the validator ran on
    read only and `noteRecent` persisted whatever it was given unvalidated.
11. **[finding 11, UX]** Chip labels now disambiguate: home-scope chips get `~/<path>`; project
    chips show the basename, or `parent/basename` when two open files collide on basename. The
    collision walk-up is one parent level only (round-1 review nit, not re-fixed this round — see
    Honest coverage below).
12. **[finding 12, a11y contrast]** Dropped `opacity-75` from the inactive-toggle badge (now
    5.8:1 on `--bg-raised`, verified numerically against the review's measured colors) and
    switched the highlighted row's descendants to `text-on-accent-soft` so the size label/icon
    read correctly against `bg-accent-soft`.
13. **[finding 13, a11y]** The Editor toggle's `aria-label` stays pinned to `"Editor"` (so the
    accessible name never churns), and a `.sr-only` child span now carries
    `aria-describedby`-linked text — basename plus ", unsaved changes" when dirty — so the badge
    and the unsaved-edit dot are no longer invisible to assistive tech.
14. **[finding 14, process/DoD]** The remedy is this release's own gate history: five
    independent rounds (below), all with real artifacts on disk, not a self-verified claim.
15. **[finding 15, UX]** The Recent strip now renders below the file listing instead of above
    it, so opening the first file no longer shifts the listing under a stationary pointer (the
    double-click hazard the source review hit-tested in Chromium).

## Honest coverage statement

Findings 2, 4, 5, 11, 12, 15 remain e2e-uncovered by design or by tooling limits, not by
oversight. (Finding 6 was in this list through round 2 — the round-3/4 rework plus the Go test
`TestUploadReportsSavedPartsOnFailure` closed the *server* and *client-decoding* gap. The new e2e
check, `"upload over the open file evicts its pane, keeps its chip"`, covers only the success
path, per the round-4 review — no browser-level check exercises the client's failure branch
[evict `r.saved`, then surface `r.error`]; that branch is covered by the Go test's assertion of
the wire shape alone, not by anything exercising `FileExplorer.upload()`'s catch/rethrow. Noted
as an accepted residual below, not silently claimed as full coverage.)

- **2** — client-side `createError` only; no e2e case exists for "New file" against an existing
  name, and the residual (raw API callers still truncate) is a server-side gap, not something
  this suite's browser-only harness can close.
- **4** — no e2e case names "Discard and leave" (the route blocker's confirm label); the suite's
  one similar wait is `EditorPane`'s own in-pane dialog (`"Discard and open"`), a different code
  path.
- **5** — no e2e case forces a `readFile` rejection (a stale chip / guest-side `rm` mid-session).
- **11** — no e2e case seeds a same-basename collision across two directories.
- **12** — contrast ratios are not Playwright-assertable without a dedicated color-contrast tool,
  which this suite doesn't have; a pre-existing tooling gap, not new to this release.
- **15** — the source review itself calls this e2e-invisible: Playwright re-resolves the target
  element per click, so a pointer-position regression across a re-render cannot be caught by
  this harness.

Finding 10 is covered for its cap dimension only (mutation-verified red); the canonicalisation
half (dot-nav, control chars, length) has no e2e fixture feeding a non-canonical path through
`sanitizeRecents`.

**Accepted residuals**, recorded rather than silently carried:

- `chipLabel` disambiguates one parent level only — `x/a/n.txt` and `y/a/n.txt` still render two
  identical `a/n.txt` chips (each button still carries the full path in `title`/`aria-label`).
- `useBlocker`'s `shouldBlockFn`/`enableBeforeUnload` are fresh closures every render, so
  `history.block` tears down and re-registers on every render of the route — correct (never
  stale), but accidental correctness rather than intentional.
- The Recent strip is now last in DOM/tab order (moved below the listing for finding 15), so a
  keyboard user tabs through every listing entry to reach the chips.
- The updater's `EXIT` trap (`rm -rf "${DOCKER_CONFIG}"`) is the script's only `EXIT` trap — now
  commented as such in the script itself (round 3), so a future second `trap ... EXIT` is a
  documented hazard, not a silent one.
- The `"recents list is capped on read"` e2e check overwrites the real
  `styrman.recentFiles.<project>` localStorage key with 20 junk entries mid-suite and never
  restores it — an ordering landmine (nothing after it in the suite uses the strip today, so it
  passes, but it's a trap for the next check that does; a future check must run before it in the
  editor section, not after). Now commented in `run.mjs` itself (round 3) alongside a sharper
  note: because this release's `beforeunload` handler fires while a pane is dirty, the check's
  `page.reload()` is only safe because it runs before the suite's one dirty-editor check — moving
  it later would turn that reload into a native unsaved-changes dialog.
- `createError` is client-side/TOCTOU: it checks the last-loaded listing, not the filesystem at
  write time, so a create racing a guest-side `touch` of the same name can still land past it.
- A guest-side `rm` of an open file's chip is not actively pruned by this release's fixes either
  — a stale chip just fails to reopen (pre-existing, accepted in the 2026-09-01 entry, unchanged
  here).
- `web/src/lib/api.ts`'s `uploadFiles` is the one API call that bypasses `request()`, so it gets
  neither `request()`'s 401/OAuth-redirect handling nor its abort timeout (round-4 review, low).
  Two consequences: an ingress-redirected upload (expired session redirected to the OAuth portal)
  reads as `res.ok`, `res.json()` fails, and the `.catch(() => ({}))` fallback makes `upload()`
  report a clean, silent success for an upload that never happened; a plain 401 surfaces as a raw
  toast instead of running `reAuthOnce()` like every other call does. TODO.
- `govulncheck` on this host measures the go1.25.0 toolchain installed here, not the pinned
  `golang:1.25.13-trixie` the image actually builds with (round-3 security delta) — the shipped
  artifact is unaffected (every stdlib fix the host-toolchain scan surfaces is ≤ 1.25.13, verified
  against the tag history), but the gate itself is measuring the wrong thing, and a 31-finding
  noise floor is where a future real advisory would hide. TODO.
