## Reviewer: approve with nits — and one of the nits was a real bug of mine

`reviews/2026-09-09-review-adr-067.md`, three findings, all fixed:

1. **[medium] The client timeout I added in BUG-022 was still short.**
   `setProjectLan` got 150 s by copying `startProject`/`stopProject`. But the
   SERVER bounds a rebuild at `lanRebuildTimeout = 3 * time.Minute`; 150 s is
   correct for start/stop only because *their* server budget is 2 minutes. A
   150–180 s rebuild would abort in the client while succeeding on the server:
   BUG-022's exact failure, in a narrower window. Now 210 s, paired with the
   Go constant by name in a comment, and the two e2e PUTs raised to match.
   Recorded in BUG-022 as the second attempt, with its prevention rule
   sharpened: derive a client timeout from the server's bound for *that*
   request, never from a neighbour's number.
2. **[low]** A dead `if err == nil {}` left behind when `kickLAN` was deleted.
3. **[low]** A stale ADR-065 comment describing a pending-state derivation
   that no longer exists.

## Security: 0 high, 3 medium, 4 low — and one medium was a fail-open

`reviews/2026-09-09-security-adr-067.md`. The primary question put to it —
can a LAN project obtain another *user's* broker credentials? — came back
"no path found, by reading, not measured": `containerHoldsIP` requires the
source address to be one the resolved container actually holds, and the
broker serves per-user secrets, so a project reaching any broker address is
served its own. Cross-tenant would need a forged source whose TCP handshake
completes, and the SYN-ACK routes out the victim's bridge. **Broker
reachability itself was not tested** — it only starts when the server is
containerized — and the test that settles it is specified in the report.
That test is owed.

The three mediums:

1. **Revocation failed open — FIXED.** On a LAN→sandbox toggle the record was
   written *before* the rebuild. If `Stop` then failed, the container kept
   running on the `lan-` bridge while the record — and the switch, the badge,
   the API — said sandbox. Nothing would ever reconcile it: the mismatch heal
   in `EnsureRunning` fires for STOPPED containers only. Now a failed `Stop`
   rolls the record back so what is reported is what is in force, at WARN;
   a failed rollback logs at ERROR. The other branch — `Stop` succeeded,
   restart failed — deliberately keeps the new record, because the container
   is down and the next start applies it.

   Testing it needed a seam: `internal/httpapi` gained `modeRuntime`
   (Status/Stop/EnsureRunning), set from the orchestrator in `New()` exactly
   as `guestRuntime` was in v1.22.0, and `network.go` goes through it. Two
   tests in `network_test.go` (appended, not rewritten):
   `TestNetworkFailedRevocationRollsBackTheRecord` — mutation-checked, it
   fails when the rollback is made a no-op — and
   `TestNetworkFailedRestartKeepsTheRecord` for the branch that must not
   roll back. Recorded as **BUG-028**.
2. **sshd password auth — operator's, and real.** ADR-066 enforced
   password-auth-off as a gate; ADR-067 deleted the gate (operator decision).
   Live on this host: `passwordauthentication yes`, listening `0.0.0.0:22`.
   Any project put in LAN mode reaches it. `deploy/remote.md` says so as
   advice; ADR-067's new amendment says so as a recorded cost.
3. **The broker's bridge-only binding now rests on one layer** (Docker's
   per-bridge DROP) instead of two (that plus the host firewall's guest→host
   drop). Not a defect, but not in ADR-067's text either. Now it is — see the
   amendment.

The lows are recorded in the report and not acted on here.

## ADR-067 amended

`DECISIONS.md` gains a third ADR-067 amendment (append-only) recording what
the live run measured and the security review confirmed: LAN mode reaches the
host at *every* address it holds, including its gateway addresses on other
projects' bridges; the broker's binding now has one layer; sshd is reachable
with whatever auth the host allows; a failed revocation fails closed; and the
broker test is owed.
