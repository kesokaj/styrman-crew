## Why deploy promptly

`/format` is live on v1.14.2 right now returning `{"content":""}` for every
request, and the editor pushed that empty response straight into the
buffer — Format then Save wiped the file. This release fixes it (see
§1 of the syntax-check-and-autoupdate entry). That bug alone is the
argument for shipping this release rather than polishing it further.

## Four remediation rounds ran inside the gate

Worth recording plainly: three of the four rounds were cases of code
asserting a security property it did not actually have, not new defects.

1. `git verify-tag` alone does not pin the signer — with PGP it exits 0 for
   a good-but-untrusted signature and never compares the signer to the
   tagger. The trust set was "any key in root's keyring," not "the
   operator," contrary to both the code comment and the earlier changelog
   entry.
2. The allowlist path was read from root's `--global` gitconfig, which is
   unreadable under the shipped systemd unit (`ProtectHome=yes`, no
   `$HOME`) — the timer would have refused every deploy while a hand-run
   `sudo styrman-update` passed. Invisible until the timer was enabled.
3. `deployed-sha` was written but never read, so the rollback path
   re-verified the previous *tag* instead — every existing tag predates
   signing, so the first rollback would have been refused, leaving the box
   stuck on the broken release.
4. The `ssh-keyscan` host-key seeding was the exact unauthenticated TOFU
   mechanism an earlier security review had already rejected, paired with a
   comment claiming that TOFU window was closed.

## Operator action required before enabling the updater

It ships disabled on purpose. Before flipping it on:

- `/etc/styrman/allowed_signers` (root-owned, not group/world-writable).
- Releases signed with SSH (`git tag -s` with `gpg.format ssh`).
- A deploy key.
- `/etc/styrman/known_hosts` seeded from GitHub's **published** host-key
  fingerprints (not `ssh-keyscan`).
- The `/opt/styrman` clone, with its own `deploy/.env`.

Existing tags `v1.14.0`–`v1.15.0` are unsigned or lightweight and would be
refused as-is; releases must be signed going forward.

## Honest limits (from the gate report's "what was not checked")

- The final commit `9d41e55` has had no independent review — verified by
  the preflight gate agent alone.
- The decoy-marker signature bypass was reproduced by the security agent
  but **not** independently reproduced by the preflight gate; the gate's
  own evidence is synthetic tag objects plus a non-regression control.
- The updater has never run end-to-end on this host — every test used
  scratch clones with directory overrides; no real tag has been fetched,
  verified, built, and deployed by it, and the rollback path has never
  executed against a genuinely failing release.
- ARM64 is architecturally out of scope for the runtime image (pinned
  AMD64-only tool binaries and Go toolchain), not a passing check — an
  ARM64 build under QEMU was shown to complete only because it silently
  emulates AMD64 (`go version` inside it reports `linux/amd64`).
- Nothing has been deployed. The live server remains on v1.14.2 and still
  carries the `/format` data-loss bug this release fixes.

## Correction: docs-freshness check was stale when the gate report was written

The preflight gate's Step 4 documentation-freshness check ran and passed
*before* the final two security commits landed (`725ca1d` at 14:20 and
`9d41e55` at 14:46), so the gate report's "docs current" line was already
stale by the time those commits closed the gate. `deploy.md` was left
describing an older implementation of the updater's state-dir path and
rollback behaviour than what actually shipped. The drift was not caught by
any gate — it was found afterwards by the operator asking whether the docs
still matched v1.16.0, and corrected in a follow-up commit.

Process lesson: re-run the docs-freshness check after **any** post-gate
code change, not just after the code gates (reviewer/security/verifier).
A gate report's "docs current" line is only as fresh as the commit it was
computed against, and this release shipped two more commits after that
computation.
