# v1.17.3 — updater self-install + govulncheck in the pinned builder image

Date: 2026-09-02. HEAD at the start of this work was `c83ddba` (v1.17.2); this tree becomes
v1.17.3. Two independent fixes, both closing standing TODO items rather than reacting to a review
report.

## A. The updater installs ITSELF after a health-checked deploy

`deploy/update/styrman-update` deploys the container stack from a verified checkout, but the
script and its two units live outside that stack — `/usr/local/bin/styrman-update` plus
`/etc/systemd/system/styrman-update.{service,timer}`, placed there once by `host-setup.sh`. A
release that touched `deploy/update/*` deployed everything *except* the updater, which kept
running its old copy forever. This bit the operator three times, most recently the v1.17.2
`DOCKER_CONFIG` round-2 fix, which had to be hand-installed on the host a second time.

`self_install()` now runs after `deploy()` reports healthy — on the main path, and again after a
successful rollback (the rolled-back tree's copies must match what the rolled-back tag actually
runs, since the current process keeps executing its own already-open inode either way):

- **Signature-gated first** (security round-1 HIGH, fixed before ship): with the
  `REQUIRE_SIGNED` opt-out engaged, the deployed tree is by definition unverified, and an
  unverified tree must never become the thing that decides whether signatures are checked next
  time. `self_install()` returns immediately, before touching anything, unless
  `REQUIRE_SIGNED=1`. (The rollback path's own "trusted" shortcut is unrelated — it only skips
  *re*-verifying a SHA this host already verified when it first deployed it; it does not affect
  this gate.)
- Targets are read from env (`STYRMAN_UPDATER_BIN`, `STYRMAN_UPDATER_UNIT_DIR`) with **no
  in-script default**, matching the ADR-052 shape used for `STATE_DIR`: the unit sets
  `Environment=STYRMAN_UPDATER_BIN=/usr/local/bin/styrman-update` and
  `Environment=STYRMAN_UPDATER_UNIT_DIR=/etc/systemd/system`; a bare hand-run or a test that
  doesn't set both gets a log line ("self-install skipped: ... unset (the unit sets them)") and no
  install, so a scratch-prefixed test run can never overwrite the real host units.
- Targets are then validated, not just trusted from env: `realpath -m` canonicalizes both paths,
  the binary's basename is pinned to exactly `styrman-update` (refuses a redirected
  `STYRMAN_UPDATER_BIN`), and both destination directories must pass `trusted_dir()` — exist,
  root-owned, not group/world-writable — the same bar every other root-written path in this
  script already meets. The resolved, canonicalized targets are logged before any write.
- **Content comes from the verified git object, never the mutable worktree** (security round 2
  MEDIUM, fixed before ship): the first cut's `cmp`-against-checkout-files design copied whatever
  bytes sat in the working tree minutes after `git checkout --detach --force <tag>` — but that
  checkout directory stays writable, so a local user with write access to it (a group/world-writable
  clone) could swap a file after signature verification and before `self_install()` ran, and the
  install would faithfully ship the swap. `differs()` now compares `git show "${SELF_HEAD}:deploy/update/<f>"`
  — the exact signature-verified object — against the installed copy (`git cat-file -e` for
  presence, `git show | cmp -s -` for content); `atomic_install()` writes `git show`'s output
  straight to the temp file. Worktree edits of any kind are now irrelevant to what gets installed.
  `SELF_HEAD="$(git rev-parse HEAD)"` is resolved exactly **once**, at the top of `self_install()`,
  and every subsequent read in that call resolves against this pinned SHA rather than a bare
  `HEAD` re-read per file (reviewer round-3 low): `HEAD` is the working-tree ref of a live clone,
  and an operator running `git checkout` inside `/opt/styrman` mid-run — however unlikely — could
  otherwise move `HEAD` between the binary read and a unit-file read, installing a mixed set of
  objects from two different commits. Pinning once makes that impossible by construction.
- The deploy clone's `.git` must now be **not group/world-writable**, in addition to the existing
  root-owned check (reviewer/security round-3 low): `self_install()` reads are now decided entirely
  by what `HEAD` resolves to in that repository's object store, so `.git` itself joined the set of
  root-trust inputs this script already asserts a mode bar on (`deploy/.env`, `STATE_DIR`,
  `ALLOWED_SIGNERS`, `GH_TOKEN_FILE`) — an ownership-only check was no longer sufficient once `.git`
  decides what gets installed as root, not just what gets built.
- `atomic_install()` writes the verified object to a fresh `.new.$$` temp file beside the target,
  `chmod`/`chown root:root`s it, then replaces the target with `mv -fT` — atomic rename, new
  inode, so the running bash (which already has its own old inode open) finishes this run
  unaffected and the new copy is what the next timer tick execs. The `-T` (reviewer round 2) makes
  a directory sitting at the target path a hard failure instead of the silent, wrong-but-non-erroring
  behavior of a bare `mv -f`, which moves the source file *inside* an existing directory rather
  than replacing it — verifier reproduced the swallow with a plain `mv -f` before this fix.
  Orphan `.new.*` files from an earlier SIGKILLed attempt are swept for all three targets up front,
  before any install is attempted, not lazily per-file.
- All three files are attempted unconditionally — a failure on one never short-circuits the
  others, so a partially-failed install still gets whatever DID land installed and reloaded.
  `systemctl daemon-reload` runs whenever anything changed, with its stderr captured and logged on
  failure rather than swallowed. The success log ("updater self-installed from the verified tree")
  prints only when nothing failed; a `WARN: self-install incomplete — the next run may still use
  the previous updater` fires instead if any individual file failed. No failure mode here can turn
  an already-healthy, already-deployed release into a reported failure — `self_install()` always
  returns 0.

One-time caveat, stated plainly rather than glossed over: v1.17.3 itself is deployed by the
**v1.17.2** updater script, which does not yet contain `self_install()` — so this release still
needs one last manual reinstall of the script and units on the host. Every release from v1.17.3
onward reinstalls itself automatically, provided signature enforcement stays on.

Closes the 🟡 TODO "The updater does not reinstall ITSELF" (`TODO.md`, added after the v1.17.2
release).

## B. `deploy/vulncheck.sh` — govulncheck against the pinned builder image, not the host toolchain

The 2026-09-01 and 2026-09-02 security passes both ran `govulncheck` against whatever Go this host
happens to have (go1.25.0) and reported 31 stdlib findings that turned out to be pure toolchain
noise — `deploy/Dockerfile.server` actually builds with `golang:1.25.13-trixie`, and every one of
those stdlib fixes lands at or below 1.25.13. The gate was measuring the wrong artifact.

New `deploy/vulncheck.sh`:

- Parses the builder image straight out of `deploy/Dockerfile.server` (`sed` on the
  `FROM golang:... AS builder` line) rather than hardcoding it a second place — one source of
  truth for the toolchain version.
- Runs `go install golang.org/x/vuln/cmd/govulncheck@v1.7.0 && govulncheck ./...` inside that
  exact image, for **both** Go modules in the repo (`.` and `deploy/caddy/ingress`), via
  `docker run` with the repo source bind-mounted read-only (`-v "${ROOT}:/src:ro"`) and named
  volumes for the module cache and build cache (`styrman-vulncheck-cache`,
  `styrman-vulncheck-gocache`) so repeat runs are fast. `go install` + run the binary, not
  `go run` — `go run` was the first cut, and review caught that it collapses govulncheck's exit
  3 ("called vulnerability found") into `go run`'s own exit 1, making a real finding
  indistinguishable from a broken scan; the earlier draft of this entry's "exit = govulncheck's"
  claim was true in intent only, not in the code as first written. `GOTOOLCHAIN=local` is set so
  the scan always runs on the image's own Go and never auto-switches to whatever a `go` directive
  in either module requests — the stdlib measured must be the stdlib that ships. The
  `GOFLAGS=-mod=mod` from the first draft is dropped (unneeded once the tool is a real
  `go install`, not a `go run` against ad hoc requirements).
- The repo is mounted read-only, and the one secret-bearing file inside it — the gitignored
  `deploy/.env`, which holds `STYRMAN_INGRESS_TOKEN`/`STYRMAN_ALLOWED_EMAILS` — is additionally
  shadowed with a `-v /dev/null:/src/deploy/.env:ro` bind, closing a security finding from round 1:
  a container that downloads and builds a tool from the network must never have that file visible
  to it, read-only mount or not.
- Exit status is **worst-wins across the two modules** (reviewer round 2): govulncheck's own per-module
  code (3 when a CALLED vulnerability exists, 0 when clean) is captured each iteration, and the
  running result only ever escalates — an anything-but-0-or-3 code (the scan itself broke) always
  wins outright, and a 3 from an earlier module is never overwritten by a later clean (0) module.
  The first cut let the second module's exit silently replace the first's, so a real finding in
  `.` could be masked by a clean `deploy/caddy/ingress` run; fixed before ship. `r` is now also
  initialized to `0` alongside `rc=0` before the loop starts, matching the reset already done at
  the end of each iteration, rather than relying solely on the `case`'s own `${r:-0}` default
  expansion to cover the pre-loop state — belt-and-suspenders, not a behavior change on its own.
  The script itself still doesn't editorialize about accepted findings — that judgment belongs to
  the security row.

Baseline measured inside `golang:1.25.13-trixie` today: **zero stdlib findings**, and per module
exactly two CALLED findings, both in `github.com/docker/docker@v28.5.2+incompatible` —
GO-2026-4887 and GO-2026-4883, both `Fixed in: N/A`, both daemon-side reachability through `init`.
Accepted, per the same TODO item this closes: no upgrade exists, recheck on every release rather
than block on it. `deploy/caddy/ingress` is the repo's second Go module and this script now scans
both for vulnerabilities.

Closes the 🟢 TODO "Run `govulncheck` inside the builder image" (`TODO.md`, 2026-09-01 whole-project
audit / v1.17.2 security delta). **Partially, not fully, closes** the 🟡 TODO "Add
`deploy/caddy/ingress` to `/preflight`'s verification": vulncheck now covers both modules, but
`/preflight`'s `go vet`/`go test` still only run at the repo root and do not cross into
`deploy/caddy/ingress` as its own module — that gap was caught after this entry's first draft
closed the item too broadly, and it is reopened in `TODO.md`, narrowed to the `go vet`/`go test`
gap specifically (see TODO.md changes below).

## Gates — four rounds

**Round 1** — reviewer REQUEST CHANGES, security FINDINGS (1 high), verifier PASS
(`.agents/docs/reviews/2026-09-02-review-v1.17.3.md`,
`.agents/docs/reviews/2026-09-02-security-v1.17.3.md`,
`.agents/docs/testing/2026-09-02-verify-v1.17.3.md`). The security high is the one described

unverified (`REQUIRE_SIGNED=0`). The reviewer separately flagged the unvalidated
`STYRMAN_UPDATER_BIN`/`STYRMAN_UPDATER_UNIT_DIR` targets, the missing stale-`.new.*` cleanup, the
early-return-on-first-failure shape that could skip `daemon-reload` for units that did land, and
`go run`'s exit-3-swallowing plus the `deploy/.env` mount into a tool-downloading container in
`vulncheck.sh`. The verifier's round-1 PASS predates all of these fixes — it verified the
pre-fix code ran without crashing, not that the design was safe; it is not the release's final
verification record.

**Round 2** — reports appended/added at `.agents/docs/reviews/2026-09-02-review-v1.17.3.md`
(round-2 section), `.agents/docs/reviews/2026-09-02-security-v1.17.3.md` (round-2 section), and
`.agents/docs/testing/2026-09-02-verify-v1.17.3-round2.md`. This closed the round-1 HIGH
(`REQUIRE_SIGNED` gate) plus `trusted_dir()`/`realpath`/basename validation, stale-orphan cleanup,
the never-early-return-plus-trailing-WARN shape, and the `go install`/`GOTOOLCHAIN=local`/
`deploy/.env`-shadow changes to `vulncheck.sh` — but security round 2 carried forward a new

**Round 3** — the git-object-not-worktree fix (`differs()`/`atomic_install()` now read

success-log-only-on-full-success change, plus `vulncheck.sh`'s worst-wins exit logic, all
described above. Its own residual lows — the single unpinned `HEAD` re-read per file, and `.git`'s

`.agents/docs/reviews/2026-09-02-security-v1.17.3.md` (round-3 section), and

**Round 4** — the two round-3 lows: `SELF_HEAD` pinned once via `git rev-parse HEAD` at the top of

## Files changed

- `deploy/update/styrman-update` — new `self_install()` (gated on `REQUIRE_SIGNED=1`), called
  after a healthy main-path deploy and after a healthy rollback; new `trusted_dir()`,
  `atomic_install()`, and `differs()` helpers; `UPDATER_BIN`/`UPDATER_UNIT_DIR` read from
  `STYRMAN_UPDATER_BIN`/`STYRMAN_UPDATER_UNIT_DIR` with no in-script default, `realpath`-canonicalized,
  basename-pinned, and directory-trust-asserted before any write. `atomic_install()`/`differs()`
  source the installed content from `git show "${SELF_HEAD}:deploy/update/<f>"` — `SELF_HEAD`
  pinned once via `git rev-parse HEAD` at the top of `self_install()`, the signature-verified
  object, never the mutable worktree — and install via `mv -fT` into a temp file swept clean for
  all three targets up front. The clone's `.git` gained a new group/world-writable check alongside
  its existing root-ownership check, near the top of the script.
- `deploy/update/styrman-update.service` — added
  `Environment=STYRMAN_UPDATER_BIN=/usr/local/bin/styrman-update` and
  `Environment=STYRMAN_UPDATER_UNIT_DIR=/etc/systemd/system`, pinning the self-install targets the
  same way `STYRMAN_UPDATE_STATE_DIR` is already pinned (ADR-052 shape).
- `deploy/vulncheck.sh` — new script; `go install`+run govulncheck@v1.7.0 (not `go run`, to
  preserve exit 3) for both Go modules inside the Dockerfile-pinned golang builder image, with
  `GOTOOLCHAIN=local`, `deploy/.env` shadowed to `/dev/null` inside the container, a worst-wins
  exit code across both module scans, and `r` initialized to `0` before the loop.
