# v1.21.0 — project home un-nesting and gate fixes     (date: 2026-09-04)

## Summary

v1.21.0 ships **project home un-nesting** (two phases, 2026-09-04), closing the structural risk behind BUG-002/003 and the check-to-mount residual accepted in v1.20.0. The setup VM's home moves from `homes/<user>` to `homes/<user>/base`; the `homes/<user>` directory itself becomes server-only and mounts into no guest, eliminating the cross-tenant symlink-follow and path-redirect opportunities that guest-root could exploit at bind time (ADR-064).

**Project home un-nesting (ADR-064):** At server startup, the operator force-removes setup VMs still bound the old way (single concurrent setup per user; the signal is already enforced), then migrates each tenant's old base home into `base/` through an `os.Root` chroot at the tenant directory. Migration is one-way; a downgrade is explicitly stated in the ADR. Homes from the previous layout are unmounted and moved atomically; operator visibility is zero on success (no UI change), single sign-in interruption on in-progress `styrman-setup` (user retries once, automatic). See phases 1–2: `.agents/docs/changes/2026-09-04-unnest-project-homes-phase1.md` and `-phase2.md`.

**Gate fixes (BUG-005 and others):** Phase 1's test file had overwritten two live tests in the test suite (BUG-005, root-cause in phase 1); both restored. The Docker budget for a failed migration rename was set to 10 s (was unbounded). Failed migration renames log their first error. See `.agents/docs/changes/2026-09-04-v1.21.0-gate-fixes.md` and `.agents/rules/writing-files.md` (new prevention rule).

**Security rounds (Phase 1):** Blocking high finding in round 1 on the chroot sealing logic (ADR-064 consequence) was closed in round 2 with explicit verification; non-blocking items noted for Phase 2 follow-up. See `.agents/docs/reviews/2026-09-04-security-unnest-phase1.md`.
