# v1.24.0 — LAN access becomes full same-network parity (ADR-066)   (2026-09-08)

Gate: `.agents/docs/reviews/2026-09-08-preflight-v1.24.0.md`.
Plan: `.agents/docs/plans/2026-09-08-lan-full-parity.md`.

## What ships

The per-project local-network switch now means what its name suggests. ON is
full same-network parity, **outbound**: the project reaches everything a peer
on the operator's LAN reaches — including the host itself and host-published
Docker ports — with each of those two behind its own root-owned conf opt-in
that **defaults closed**. It stays NAT-only outbound; LAN hosts cannot
initiate connections into a project. Still dropped: every other project and
system bridge, the ingress bridge, cloud metadata, the tailnet, and every
private range outside the configured prefixes.

In exchange, a project that has ever had LAN access is never served the
operator's SSH key by the credential broker again. That is permanent by
design — turning LAN access off cannot un-expose a key the project already
held (ADR-066 amendment).

**Deploying this changes nothing on an existing host.** `LAN_ALLOW_HOST` and
`LAN_ALLOW_PUBLISHED_PORTS` are absent from every existing conf and absent
means no, so converging the script to version 4 grants neither. Opting in is
a human running `deploy/firewall/install.sh --lan-allow-host 1`, and that
command now REFUSES on a host whose sshd accepts password authentication, as
R12 requires.

## How it is built

Three rule families — `lan`, `lanhost`, `lanpub` — share one generic
reconcile keyed by `(tag, chain, regex)`, so a delete-by-spec or ordering fix
lands in exactly one place. The published-port allowance matches only DNATed
connections and takes a POSITIVE destination allowlist of the Docker bridges
that are neither project bridges nor the ingress; the negation the earlier
design assumed (`! -o sdb-+ ! -o <ingress br>`) cannot be written at all,
because iptables accepts one `--out-interface` per rule.

## What the gate cost, honestly

Sixteen findings across three review rounds — eleven fixed, one deleted by
the latch amendment, four subsumed. Three of those rounds saw the previous
round's fixes introduce the next round's worst defect, and most of the
findings were the author's own. Two things came out of it worth carrying:

- The best fix twice over was **deletion, not repair**. The credential
  latch removed a question that had no reliable answer; the rewritten sshd
  gate stopped trying to evaluate `Match` blocks and now refuses on "cannot
  tell". Both are shorter than what they replaced.
- The mechanical gate (`verify-commit.sh`, every suite) was green before all
  three rounds and caught none of the sixteen. It says the tree builds, not
  that it is correct.

Two things are shipped unproven and are named in the gate report's "what was
not checked": **no LAN allowance has ever been applied by the v4 script on
real hardware**, and the published-port path has never been exercised live.
Both need an operator opt-in on a real host to reach.
