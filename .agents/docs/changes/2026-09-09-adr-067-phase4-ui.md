# ADR-067 Phase 4 — the switch says what it actually does

The UI had five states because the old design could be in flight, refused, or
unreportable. There are two now: **Sandbox** and **LAN**.

| file | before | after |
|---|---|---|
| `web/src/lib/lan.ts` | 101 | 65 |
| `web/src/components/LocalNetwork.tsx` | 206 | 133 |
| `web/src/components/LanBadge.tsx` | 22 | 22 (two-state) |
| `web/src/routes/settings.tsx` | — | `HostFirewallSection` (62 lines) deleted |
| `web/src/lib/api.ts` | — | `LanState`, `HostFirewall`, `lanState`, `lanMessage`, `lanChangedAt`, `hostFirewall`, `credentialImpact` deleted |

## What the dialog says now

The old confirm dialog spent three paragraphs on what the host conf had opted
into and on the permanent SSH-key withholding. Both are gone, so it says the
things that are true instead:

- the project becomes an ordinary machine on the network, reaching the LAN,
  **this server including its SSH service**, and its published ports;
- other projects and inbound connections stay blocked either way;
- **applying it rebuilds the project's container** — home and workspace
  untouched, packages replayed, anything living only in the container's
  filesystem lost.

That last one is new and it is the honest cost of the design. The old switch
promised a sub-second toggle; this one takes about as long as a start, and the
UI says so before the click and while it runs.

## `canEnable` is a field, not an inference

`LocalNetwork` used to decide whether the viewer was an admin by testing
whether the reply carried a `host` object. With `host` deleted, the obvious
fix was to thread an `admin` prop down from `SidePanel` — but that repeats
**BUG-019** exactly: *"expose a capability the server already knows as its own
field; don't infer it from a state value reachable through more than one
cause."* So `lanView` gained `canEnable`, set from `u.Admin`, on the GET and
on all three PUT replies. No prop threading, no inference.

## The badge is where a lie would be invisible

`LanBadge` renders from optional fields, so a regression showing "LAN" on
every project would be a false claim about isolation that **`tsc` cannot
catch**. The derivation stays in `lib/lan.ts` — the seam this codebase already
uses for exactly this reason — and `lan.test.ts` asserts both directions:
`lanAccess: true` produces the chip, `false` and *absent* produce nothing.

`preferOverride` was rewritten rather than restored. It used to compare the
monotonic `lanChangedAt`, which is **BUG-020**: equality on a timestamp meant
an out-of-band change never displaced a local one and the switch latched on
the last PUT forever. With one boolean, "caught up" is "the server now says
what we said", and the latch is structurally impossible. The test says so.

## The sweep became a script, and it was lying

Appendix B's sweep was being retyped inline each phase, and on this phase it
reported hits that did not exist and then hits it did not count. It is now
`.agents/docs/testing/styrman/adr-067-sweep.sh`, checked in — and writing it
properly exposed that the inline version had **the BUG-010 defect**: `report`
consumed its input on stdin, so it ran on the right-hand side of a pipe, in a
subshell, and its `fail=1` was set in a child and lost. The script printed
`zero hits` while listing hits.

A check that lies is worse than no check — "silence from your own
instrumentation is not evidence" cuts both ways. It now takes its matches as
an argument, excludes itself, strips comment-only lines (the code that
replaced a mechanism often names it deliberately), and exits non-zero.

Current result: **Go and `web/src` are clean.** The remaining hits are
`integration.sh` and `web/e2e/` — Phase 5's surfaces, correctly still flagged.
