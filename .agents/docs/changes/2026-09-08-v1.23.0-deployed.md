# v1.23.0 deployed and verified live — with one correction to the release entry   (2026-09-08)

Appended rather than edited into `2026-09-08-v1.23.0-release.md`: `changes/`
is append-only, and that entry made a prediction the deploy disproved.

## The correction

The release entry and the v1.23.0 tag message both say the pre-existing
four-versus-six DROP drift on this host is converged by the operator's
`install.sh` run. **It was not: `host_converge` converged it automatically,
before any human touched the host.** The tag message is signed and published
and stays as written; this entry is the record that supersedes it on that
one point.

What actually happened, from the journal:

1. `13:47` — the OLD updater (still the pre-v1.23.0 copy) verified the
   signed tag, rebuilt both images, recreated the containers, health-checked
   them, recorded `deployed-version=v1.23.0`, and self-installed the new
   updater. It has no `host_converge`, so the host firewall was untouched
   this tick and the server booted against a run dir that did not exist yet.
2. `13:53` — the next tick ran the NEW updater. `host_converge` installed
   `styrman-firewall.sh` and its three units from the verified object at
   `7bf0607`, enabled the timer and the path unit, and started the service.
   The base section applied six DROPs, closing the drift that had been live
   since 2026-08-30.

So the delivery gap ADR-065 part (6) exists to close was demonstrated closed
on its first real release, unattended and without a root command from anyone.

## Verified live

- `styrman-server` and `styrman-caddy` on `1.23.0`, server healthy;
  `deployed-version=v1.23.0`.
- `STYRMAN-FWD` carries six DROPs: 10/8, 172.16/12, 192.168/16, 169.254/16,
  100.64/10, 198.18/15.
- `/run/styrman-firewall/status`: `version=3`, fresh `applied_at`, and the
  honest `warn=conf /etc/styrman/firewall.conf missing - no local-network
  prefix configured`.
- `styrman-firewall.timer` and `styrman-firewall.path` both active.
- The integration points the design turns on, observed rather than reasoned:
  the run dir is bound into the server with `rslave` propagation (the
  security fix), `status` is `root:<state gid> 0640` so the server reads it
  by group and no other local uid can, `spool` is operator-owned `0700` so
  the server can write a trigger and only root can drain it, and the server
  created its own marker dirs at `0750`.
- The degradation path proved itself by accident: booting six minutes before
  the run dir existed, the server logged `host firewall spool unwritable —
  changes apply on the 60 s timer` once and carried on. That is the designed
  behaviour, seen in production rather than in a test.

## Still open

The feature is deployed and **inert**, which is the intended state: with no
`/etc/styrman/firewall.conf` the status reports no prefix, Settings shows the
row red, and every enable is refused with 503. Nothing is half-open.

One operator step remains, and it is the only thing between here and the
feature being usable:

```bash
sudo bash /opt/styrman/deploy/firewall/install.sh
```

which writes the LAN definition (discovered from the default route) and
mounts the bounded spool tmpfs — the `rslave` bind means a running server
picks that mount up without a restart. After it, the manual applied-state
check from the plan's Verification section, or the opt-in
`STYRMAN_IT_LIVE_LAN=1` integration block, is the first end-to-end proof
that a real microVM reaches the LAN through the RETURN rule. Until then that
path remains inferred, as the gate report says.
