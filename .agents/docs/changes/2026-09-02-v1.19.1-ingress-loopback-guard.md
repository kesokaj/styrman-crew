# Ingress loopback guard: reject names, require IP literals     (date: 2026-09-02)

## Summary

The Caddy admin API endpoint (`/load`, `/config`) runs in a container with `network_mode:host` holding the docker socket. Access to it is gated by the loopback bind only — the `origins` directive is browser-only defence-in-depth, not authentication.

The `isLoopbackAddr` function checked whether an admin listen address binds loopback only. Its contract was "this address binds loopback and nothing else", but it accepted a bare name (e.g., `"localhost"`) on a case-insensitive string match while IP literals were verified with `IsLoopback()`. A name is resolved by the OS at bind time through /etc/hosts and NSS, so the value the guard checked and the value Caddy actually bound were two different things — the function asserted its contract instead of establishing it.

**Not a live hole:** changing /etc/hosts requires root (already owns the box), `localhost` does resolve to loopback on this host, and the loopback bind itself is what keeps the admin API off the network.

The fix: `isLoopbackAddr` now refuses all names outright (including `"localhost"`), accepting only IP literals verified via `net.ParseIP` and `IsLoopback()`. To prevent the shipped ingress from failing its own guard, `DefaultCaddyAdmin` changed from `"localhost:2019"` to `"127.0.0.1:2019"`. A new test, `TestDefaultCaddyAdminPassesTheGuard`, asserts the shipped default passes the guard, so that combination cannot regress silently.

Pre-flight verification: `CADDY_ADMIN` env var was confirmed empty in the live container, absent from production `.env`, and commented out in `.env.example` — every path falls through to the constant. The Caddy image was built and smoke-tested before tagging (Caddy 2.11.4, all four modules present); `deploy/verify-commit.sh` builds the server image but not caddy independently.

Shipped ALONE rather than stacked into v1.19.0: v1.19.0 already touched the ingress with base-image digest pins, and stacking a guard change would have made a crash loop (if it occurred) hard to attribute.

## Type

bugfix

## Files changed

- `deploy/caddy/ingress/loopback.go` — `isLoopbackAddr` now refuses names (including `"localhost"`) and accepts only IP literals verified with `net.ParseIP` and `IsLoopback()`. Updated doc comments clarify the guard's contract and why names cannot be accepted.
- `deploy/caddy/ingress/config.go` — `DefaultCaddyAdmin` changed from `"localhost:2019"` to `"127.0.0.1:2019"` (IP literal). Updated comment explains why the guard and default had to change together.
- `deploy/caddy/ingress/loopback_test.go` — Added `TestDefaultCaddyAdminPassesTheGuard` to assert the shipped default passes the guard. Expanded `TestIsLoopbackAddr` to cover name rejection: `"localhost"`, `"LOCALHOST"`, `"localhost."` all now correctly fail. Added comment clarifying that the `origins` directive is defence-in-depth, not authentication for `/load`.

## Verification

- Unit tests: `TestIsLoopbackAddr` covers all rejection cases (every interface, non-loopback IPs, bare hosts, non-numeric ports, out-of-range ports, names including `"localhost"` in all cases). `TestDefaultCaddyAdminPassesTheGuard` asserts the shipped constant passes the guard.
- Integration: Caddy image built with all four modules and smoke-tested before tagging (Caddy 2.11.4).
- Preflight: Confirmed `CADDY_ADMIN` is unset in the live container, production `.env`, and `.env.example` — ingress uses the constant on every deployment.
