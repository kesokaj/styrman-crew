# v1.37.0 — the GCP Compute Engine target, and two shared-path fixes it uncovered   (2026-09-22)

Release of the work in `changes/2026-09-21-gcp-compute-engine-target.md` (ADR-075) plus the gate's own fixes. Gate report: `reviews/2026-09-22-preflight-v1.37.0.md` — SHIP. MINOR: a new deploy surface, nothing an existing deployment must react to.

## What ships

- **A GCP target.** `deploy/gcp/vm.sh` (create/status/ssh/stop/start/delete) and `deploy/gcp/install.sh` bring styrman up on a Compute Engine VM by the unchanged host path (`host-setup.sh` → `styrman-ctl install`). Nested virtualization, ssh and scp through IAP with no public port 22, no service account, project-wide ssh keys blocked, the release tag's signature verified on the VM before anything runs from it, and a pre-create refusal when the project's firewall would reach the instance on port 22. Defaults in `deploy/gcp/vm.conf`; secrets are three files outside the repository. Guide: `deploy/gcp.md`.
- **Two fixes to the shared path**, both found by the first GCP bring-up and applied where every host gets them (`.agents/rules/shared-path-learnings.md`, the operator's "take your learnings back to local"):
  - `host-setup.sh` can install Kata on a fresh host again (BUG-070): the zstd asset, `tar --zstd`, and the checksum from the publisher's own release-asset digest, still failing closed without one. Dead upstream for months, invisible because the step is skipped wherever Kata is already installed.
  - `styrman-ctl install --gh-token-file` exports the token for `host-setup.sh` in its own process instead of a command line sudo logs.
- **Records:** BUG-069 (an ssh outage reported as "no /dev/kvm"), BUG-070, BUG-071 (a mutation restore that corrupted a line); the 2026-09-21 retro's two project rules; `testing/guide.md`.

**Two defects the live bring-up found in `deploy/gcp/`, both fixed after the tag** (they are in the scripts run from the operator's machine, not in anything the tag deploys, so they take effect immediately and need no release): **BUG-072** — `styrman-ctl install` carries only its six must-fill keys, so `STYRMAN_HOSTNAME=crew` never reached the host: it served `styrman.gcp.styrman.xyz` while `install.sh` verified `crew.gcp.styrman.xyz`, a name that existed only as a Cloudflare wildcard pointing at the NUC, so a healthy install reported a failure. `install.sh` now delivers the optional keys with `styrman-ctl edit` and reads the hostname back from the host before verifying. **BUG-073** — `vm.sh status` probed `/usr/local/bin/styrman-ctl`, a path nothing creates on any host, so it answered "not installed" forever; it now asks the host which copy it has and validates the answer.

**Still the operator's:** add `https://auth.gcp.styrman.xyz/oauth2/google/authorization-code-callback` to the Google OAuth client, then sign in (the one step no agent can do); and rotate the GCP host's credentials, which were copied from the NUC before the guide required per-host ones (gate report row 5).
