# Recon — replacing image/harness with the styrman-harness sh-agent binary (2026-09-03)

## Question
Map every place styrman-crew builds, seeds, or depends on the vendored `image/harness/` tree, and the constraints/risks of swapping it for `sh-agent install --home DIR` from the separate `styrman-harness` repo.

## Summary
Today the harness is a verbatim vendored mirror (`image/harness/`, synced from `devshell_prompt/harness`, ADR-046) baked into the runtime image and deployed by `image/entrypoint.sh:110-156` running its own `setup.sh` write-once per project home, keyed on `~/.styrman/.harness-version` vs `/styrman/VERSION`. Go and git are already present in the image, so `sh-agent` can run natively — the swap is mechanically straightforward at the entrypoint level. The real risk surface is elsewhere: `internal/httpapi/setup.go:236-248` hardcodes today's Antigravity path `.gemini/config/plugins/harness/agents` for the settings-page agent listing, which does not exist under the new layout (`~/.gemini/config/agents/`, no plugin wrapper, no hooks.json) and will need updating; the ADR-047 PATH-trimming workaround exists specifically because vendored `antigravity/setup.sh` blocks 60s calling `agy -p "/skills"` when no OAuth token exists yet — need to verify `sh-agent install` has no equivalent blocking call, or the R1 5s boot SLA breaks again; and Tier 5 testing (`.agents/docs/testing/styrman/README.md`) is entirely manual/unautomated and directly asserts today's line counts, skill counts, and file paths, all of which change with the new harness.

## Relevant files
- `image/Dockerfile:1-100` — installs `git`, `go` (latest stable, symlinked to `/usr/local/bin/go`), Node 22, `claude` CLI (npm) and `agy` CLI (installer script), `COPY harness/ /styrman/harness/`, `ARG STYRMAN_VERSION`. Go and git are both present — `sh-agent` (a Go binary) could run directly, or be prebuilt and `COPY`'d in.
- `image/entrypoint.sh:110-156` — the seeding block. Reads `HARNESS_VER=$(cat /styrman/VERSION)`, compares to `${HOME_DIR}/.styrman/.harness-version`; if different, `mktemp -d` a user-owned copy of `/styrman/harness`, then `runuser -u <user> -- env HOME=<home> PATH=/usr/bin:/bin:/usr/sbin:/sbin bash <copy>/setup.sh`. **PATH deliberately excludes `/usr/local/bin`** so `agy` is unreachable and the vendored `antigravity/setup.sh` self-check (`agy -p "/skills"`) is skipped (ADR-047) — this is a load-bearing hack tied to the *current* vendored script's shape, not something that automatically carries over.
- `image/harness/README.md`, `image/harness/VENDORED.md` — describe the CURRENT (old) harness's deploy targets and layout; will be entirely superseded, not something the new harness repo touches.
- `image/harness/setup.sh`, `claude/setup.sh`, `antigravity/setup.sh` — old dispatcher + per-vendor deploy scripts (rsync-based, `merge-settings.py`, `derive-agy-agent.py`, backs up existing files with `.bak.$(date)` timestamps, retires named agents/commands explicitly). New `sh-agent install`/`update` replaces all of this logic wholesale.
- `internal/httpapi/setup.go:230-253` (`toolDetails`) — **hardcodes old harness paths** for the settings-page UI: `.claude/skills`, `.claude/agents`, `.claude/commands`, `.gemini/config/skills`, and specifically `.gemini/config/plugins/harness/agents` (line 248) for agy's agent list. The new harness has no `plugins/harness/` wrapper — `sh-agent install` writes `~/.gemini/config/{skills,agents,commands,workflows,rules}` directly (per the dispatch's own description). This function will silently show an empty/wrong agent list for agy until updated.
- `internal/orchestrator/orchestrator.go:251-256` — comment: per-project home is "seeded from the image (dotfiles + harness)"; created before the mount so the entrypoint can chown it. No path-specific coupling here beyond the comment.
- `.agents/docs/architecture/DECISIONS.md` ADR-030 (per-project homes + broker), ADR-031 (clean-cut per-project homes, image seeds harness from `image/harness/`), ADR-046 (harness is a verbatim mirror; `STYRMAN_VERSION` bump is the ONLY delivery path — no live sync channel to already-running homes), ADR-047 (styrman-side workarounds for vendored-script quirks live in the entrypoint invocation, never inside `image/harness/` itself — this precedent likely still applies to `sh-agent`-specific quirks).
- `.agents/docs/testing/styrman/README.md:293-366` (Tier 5) — **entirely manual, "KNOWN GAP: not automated."** Asserts today's exact roster: `diff -rq image/harness ~/workspace/devshell_prompt/harness` (mirror fidelity — meaningless once the source is a Go binary, not a file tree to diff), line counts of `CLAUDE.md`/`GEMINI.md`, skill counts under `~/.claude/skills/*/` and `~/.gemini/config/skills/*/`, agent roster under `~/.claude/agents/`, both shell gates under `~/.agents/bin/` (the new harness ships **no scripts/hooks at all** — this check becomes N/A), valid JSON in `~/.claude/settings.json` (new harness writes no settings.json — also N/A), and the **latency assertion (3a)** guarding the ADR-047 PATH-trim regression (`~1s` not `~60s`) — this specific check is the one most likely to catch a `sh-agent`-equivalent blocking call if one exists.
- `.agents/docs/testing/styrman/README.md:270-289` (Tier 4, e2e) — documents that a first attempt to e2e-test cloning the **private** `kesokaj/styrman-harness` repo failed correctly with `fatal: could not read Username for 'https://github.com'`, because Tier 4's e2e server runs in HOST MODE (`STYRMAN_SELF_CONTAINER` unset) where `EnsureSelfAttached` no-ops and `waitForBroker` returns false immediately (`internal/httpapi/provision.go:136,204`) — **no credential broker in that test mode**. This is explicitly called a hard limit of Tier 4 only, not of the platform: "only Tier 3 (real Kata, real broker) or manual testing against a containerized server can exercise" credentialed clones. In a real deployed project VM (broker attached), the system-level git credential helper (`styrman-git-credential`, wired via `git config --system credential.helper` in `image/Dockerfile`) should make `git clone` of a private GitHub repo work — but this recon did not find a positive, executed test confirming that end-to-end for a private repo (only the negative host-mode case is evidenced).
- `.agents/docs/specs/styrman/versioning.md` — exists but the harness-relevant sections were not read in full during this pass (recon time-boxed); worth a follow-up read before designing the version-pin policy for the new harness's git-tag/commit pin.

## Flows
1. **Build time:** `image/Dockerfile` `COPY harness/ /styrman/harness/`, stamps `/styrman/VERSION` from `ARG STYRMAN_VERSION`.
2. **Boot time (`image/entrypoint.sh`):** on every container start, compare `/styrman/VERSION` to the per-home stamp `~/.styrman/.harness-version`. On mismatch: copy the harness tree to a user-owned tmp dir (needed because the image path is root-owned and the vendored `setup.sh` also refreshes files inside its own tree), run `setup.sh` as the project user with a deliberately trimmed `PATH`, then write the new version stamp. Non-fatal — a harness failure logs a WARN but never blocks `/run/styrman/ready`.
3. **Settings UI:** `internal/httpapi/setup.go`'s `toolDetails` reads straight off the project home filesystem (not through any harness API) to populate the per-tool cards shown in the app — this is a live, ungated dependency on exact harness output paths.
4. **Version delivery:** ADR-046 — no live-sync channel; a harness change only reaches a project when `STYRMAN_VERSION` bumps AND that project's container restarts. A project that never restarts never upgrades.

## Conventions
- Every ADR follows a strict Context/Decision/Consequences template with a `Source:`/`Verification:` footer pointing at a `changes/` entry.
- Styrman-side workarounds for vendored-tool quirks belong at the *call site* (`entrypoint.sh`), never inside the vendored tree itself (ADR-047) — this pattern will likely need to repeat for any `sh-agent`-specific timing or path quirks discovered.
- Non-fatal, loudly-logged failure is the house style for anything in the boot path that isn't core to R1/R2 readiness (see the harness block's own comment: "Non-fatal: a harness hiccup must never block the project from booting").

## Risks (ranked)
1. **R1 boot-latency regression** — the single most concrete, previously-hit failure mode (ADR-047: 60s vs 0.4s, from one blocking CLI call gated only by `command -v`). Any `sh-agent install` invocation that can reach network-touching binaries (`agy`, `claude`) on a freshly-created project (no OAuth token materialized yet, since that happens via a login shell that hasn't run at entrypoint time) needs the same scrutiny — confirm `sh-agent install` makes no such calls, or replicate the PATH-trim pattern.
2. **`internal/httpapi/setup.go:248` hardcoded path** (`.gemini/config/plugins/harness/agents`) will break the agy tool card silently (empty list, not an error) under the new layout — needs an explicit code update, not just an image swap.
3. **Re-seeding an existing home without clobbering user files** — old harness backs up (`.bak.<timestamp>`) before overwrite and explicitly retires named files (`testing.md`, migrated commands); `sh-agent update`'s "no clobber" behavior for already-customized homes (e.g. a user's own `~/.claude/skills/`) was not verified in this recon — the dispatch's own framing says skills sync `rsync --delete`-style today, which is a known accepted data-loss risk (ADR-046 consequences) for hand-added skills.
4. **Private-repo git access from inside a project VM was not positively evidenced** in this recon (only the Tier 4 host-mode negative case). If `sh-agent update` needs to `git pull` from a private `styrman-harness` repo *from inside project VMs themselves* (as opposed to being baked into the image at build time), that path needs Tier 3/manual verification against the real broker before relying on it.
5. **Tier 5 test rewrite required** — every assertion in `.agents/docs/testing/styrman/README.md` Tier 5 (mirror-diff, line counts, `~/.agents/bin/` gates, `settings.json` JSON validity) is specific to the old harness's shape and will need to be replaced, not just re-pointed, since the new harness ships no scripts/hooks/settings.json at all.
6. **ADR-046's "verbatim mirror" precedent doesn't map cleanly** — the old harness is a file-tree mirror diffed with `diff -rq`; the new harness is a Go binary from a separate git repo. The version-pin/delivery-path story (STYRMAN_VERSION bump = only delivery path) needs a fresh ADR, not a reused one, since "rebuild image to update" may or may not still be the right model for a `git fetch && sh-agent update`-capable tool.

## Open questions
- Does `sh-agent install` (or anything it calls) make any network or CLI-shellout calls (e.g. probing `agy`/`claude` availability) that could block on a home with no credentials yet? Not determined from styrman-crew code — needs checking against the `styrman-harness` repo itself (out of scope for this read-only recon of styrman-crew).
- Is `sh-agent` intended to be baked into the image at build time (`COPY`'d binary + `install --home` at boot, mirroring today's model) or invoked fresh via `git clone`/`go install` at each boot? This changes whether private-repo network access from inside the VM is even needed at seed time.
- Does the credential broker's git helper actually support cloning a *private* repo from inside a real (non-host-mode) project VM today? This recon found strong indirect evidence (system-wide `credential.helper`, ADR-030/032 broker design) but no executed positive test in the trail — worth a quick manual Tier-3-style check before depending on it.
- `specs/styrman/versioning.md` was not read in full — check it for an existing version-pin policy that should extend to (or explicitly exclude) the harness binary/repo.
