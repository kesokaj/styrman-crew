# Recon — v1.42.4   (2026-10-05)

## Status: COMPLETE

## Question
Closest surfaces, patterns and open points for v1.42.4: (1) central memory budget, (2) per-tenant slot fairness, (3) admin resource cap, (4) BUG-074 cookie name, (5) small items. Read-only; budget ~60 calls (~25 used; not every handler body was read, see Not examined).

## Summary
A natural single seam exists: `RoutesWithAuth` wraps `previewHostRewrite(authGuard(csrfGuard(mux)))` (server.go:~617), and `csrfGuard` already sets the per-path request-body cap (1 MiB default, 512 MiB `/upload`, 8 MiB `/file` `/format` `/check`, server.go:704-719) and runs AFTER authGuard, so the username is in context. Request bodies are therefore boundable up front (reserve = the cap or Content-Length); response sizes are NOT known up front, but every guest-sourced one is capped at 2 MiB by `maxExecOutput` (orchestrator/exec.go:32), file read at ~12 MiB JSON, transcript read at 4 MiB x JSON escaping. Slots take no user today (`acquireSlot(w, sem, msg)`), so fairness needs a signature change. The resource cap has ONE seam, `resourcesOf` (server.go:115) which runs at every start, but it has no admin/owner-email input and `ensureFor` (WS boot) only has a username. BUG-074 is two uses of one constant (`AuthCookieName`, ingress config.go:49) plus the portal's unset `cookie_name_prefix` default; nothing outside deploy/caddy/ingress names it.

## 1. Memory budget

### Where the seams are
- Middleware chain: server.go:~617 `s.previewHostRewrite(s.authGuard(authMode, csrfGuard(mux)))`. `csrfGuard` (server.go:684-722) skips preview/link/shared paths (tunnelled bytes, not API), else wraps `r.Body` in `http.MaxBytesReader` (:719). A budget middleware sits naturally between authGuard and mux (or inside csrfGuard next to the MaxBytesReader) and sees `identity.FromContext(r.Context()).Username`.
- Response writing is uniform: `writeJSON` (server.go:1395) = `json.NewEncoder(w).Encode(v)`; `writeErr` :1401. A response-size charge can be taken (a) by the handler before building `v`, or (b) by a wrapping `ResponseWriter` that counts bytes written (but that is after the memory is already built, so it can only account, not admit).
- Username access: `s.who(r)` (server.go:~727) / `s.getProjectFor(r)` return `identity.User` (`u.Username`, `u.Email`, `u.Admin`) in almost every handler; `scopeFor` (explorer.go:37) too. In middleware use `identity.FromContext(r.Context())`.
- Existing slot code to mirror/replace: `acquireSlot` (explorer.go:481; non-blocking, 429, also sets write deadline `historyWriteTimeout` 30 s and read deadline `slotReadTimeout` 30 s, :477/:489-490), `fileSlot` (:463), `fileConcurrency=8` (:459), `searchSlots/readSlots/fileSlots` fields server.go:183-190, made server.go:268-270. Budget would wait (<=2 s) then 503, unlike slots (no wait, 429): different semantic, so a new type (weighted semaphore with per-tenant ledger; `golang.org/x/sync/semaphore` is NOT stdlib: check go.mod/"stdlib first" rule; a ~40-line mutex+cond or channel ledger is the stdlib route).

### Request-body readers (limit = csrfGuard cap unless noted; all decode via `json.NewDecoder(r.Body).Decode`)
Default 1 MiB: network.go:97; projectenv.go:56; links_api.go:79 (error ignored); credentials.go:125, :198; shares.go:180; resources.go:116; server.go:887 (createProject), :1266 (createTerminal, empty body ok), :1287; git.go:323, :350, :375, :656, :775; profile.go:148, :170; explorer.go:221 (rename), :623 (updateRuntime), :681 (importGit), :737 (addUser).
8 MiB (decoded into a string then JSON-escaped, so peak ~ 2-3x body): writeFile explorer.go:286 (fileSlot first), formatFile format.go:78 (slot :61), checkFile check.go:355 (slot :338).
512 MiB: uploadFile explorer.go:329 via `r.MultipartReader()` (streamed to disk, so resident memory is parts buffers not 512 MiB; budget weight should be a small constant, not the cap; NOT behind a slot; no slotReadTimeout).
Not API-body: browser.go:585 `io.LimitReader(resp.Body, 64<<10)` (upstream response, not tenant request).
Also read-by-handlers on WS upgrade paths (`/ws/term`, `/ws/browser`, `/ws/setup`) are outside body semantics; csrfGuard's cap applies only to non-GET/HEAD.
Size known up front for all bodies: `r.ContentLength` (-1 for chunked) else the cap. Bodies cannot exceed the cap, so reserve min(ContentLength-or-cap, cap) at admission.

### Wrapping options
- Middleware (one place): admit with an estimate by route class (default 1 MiB-body routes: ContentLength; `/file|/format|/check`: 8 MiB x 3; upload: small constant; reads: per-table above). Gets every handler and the tenant name for free; risk: estimate by path string suffix is what csrfGuard already does (fragile; r.Pattern is available after mux, not before, so a middleware outside the mux has only the path; one INSIDE a per-route wrapper has `r.Pattern`).
- Per-handler acquire (like fileSlot) with an exact size where known (readHistory bytes, 8 MiB bodies) and release in `defer`; more precise, but every new handler must remember (the BUG-035 "mechanism reaches every caller" rule applies, give a test that enumerates routes).
- Recommendation for the plan to decide: middleware default reservation (body ContentLength or 1 MiB response floor) + per-handler `budget.Grow(n)` for known-large ones, with a routes-enumerating test asserting every `mux.HandleFunc` is covered.
- Waiting up to 2 s while holding a body is a hold: acquire BEFORE reading the body, after authGuard; the slot read deadline (30 s) pattern in `acquireSlot` should move with it.
- 503 body style: `writeErr(w, http.StatusServiceUnavailable, errors.New("server busy, try again"))` (writeErr :1401); resources.go:127 already uses 503 for host info.

### Open (for 1)
- Does the budget replace fileSlots/searchSlots/readSlots or sit alongside? (handoff says "in place of more one-by-one slots"; the existing 429 slots have tests e.g. `TestASlowReaderReleasesItsSlotAtTheWriteDeadline`.)
- Charge before or after JSON escaping? Does WebSocket / `proxyPort` / link tunnel traffic count (no: bytes are streamed, csrfGuard skips them)?
- Unauthenticated/preview-only users (`identity.Authorized` false) have no tenant: which bucket?
- Per-tenant 256 MiB cap when a single request's reservation (512 MiB upload cap) exceeds it: must reserve less than the cap, or the request can never be admitted.

## 2. Per-tenant slot fairness
- All three pools are `chan struct{}` taken by `acquireSlot(w, sem, msg)` (explorer.go:481) which has no user parameter. Call sites: fileSlot users readFile explorer.go:78, writeFile :274, formatFile format.go:61, checkFile check.go:338; searchHistory explorer.go:512; readHistory :548.
- Username source: searchHistory and readHistory already call `s.getProjectFor(r)` first, giving `u.Username` (explorer.go:~498, ~534). readFile/writeFile/format/check call `s.scopeFor(r)`/`s.who(r)` AFTER the slot, so identity must be read earlier: `identity.FromContext(r.Context()).Username` is already set by authGuard and needs no store lookup (cheap, preferred), or reorder.
- Mirror: add a per-pool `map[username]int` guarded by a mutex next to the channel (acquire = tenant<2 AND channel send, release both); keep the 429 messages. A tenant over its 2 slots should get the same 429 text or a distinct "too many of your own" message (open).
- Note: `acquireSlot` applies `SetReadDeadline` also for GET searches/reads (no body), see item 5.
- Pools are in `Server` struct fields server.go:183-190 and constants fileConcurrency (explorer.go:459), searchConcurrency/readConcurrency (explorer.go ~445-455).

## Risks
- Budget semantics can deadlock-by-design: waiting 2 s while holding a body, or a reservation larger than the per-tenant cap (512 MiB upload cap vs 256 MiB) which can never be admitted. Reserve a size <= cap.
- Response size is unknown before exec/search work; JSON escaping can multiply the 2 MiB exec cap. An accounting-only (post-hoc) charge does not protect memory; a pre-reserve at the cap does but over-reserves (1 GiB / 2 MiB = 512 concurrent git calls total, 128 per tenant: fine).
- Route-class estimation by path suffix is the same fragile idiom as csrfGuard (:705-719); a new route silently falls to the default class. Add a test that walks every registered pattern.
- Slot semantics change (429 no-wait vs 503 wait) may break existing slot tests (`TestASlowReaderReleasesItsSlotAtTheWriteDeadline`, slot tests for 8 file/search/read caps).
- `ensureFor` (WS boot, the path every project page opens with, BUG-060) has no email/admin: forgetting it makes the cap bypassable or crashes the first terminal; the cap lookup must be tolerant (fail open to host? or closed to cap? decide) and must not make a project unstartable (plan D13: clamp, never refuse).
- Unlimited (0) is the default for existing projects (whole host); with a cap applied at start every non-admin 0 project is resized and REBUILT at next start (container rebuild loses non-bind-mount state, resources.go header) and `Pending` hints must compare against the effective size.
- Cap default "half the host": host values come from `Orchestrator.Host` (docker info, cached) at runtime, not at config load; the default must be computed lazily, with `MaxMemoryGiB()` already net of reserve (orchestrator/resources.go:48-57).
- BUG-074 fix signs everyone out once; the directive name for the cookie prefix is unverified against the pinned caddy-security build; the strip regex (generator.go:152, :437) and tests must change together or preview apps receive the portal session cookie (a security regression: the public-preview block's stripping would silently stop matching).
- Existing token-empty gap: an empty `/etc/styrman/gh-token` passes `[ -f ]` in styrman-update and `test -e` in docs (host-setup.sh:313 already uses `-s`).
- SidePanelHistory: clearing results does not bump `searchGen`, so a late response repopulates cleared matches.
- e2e SHOTS dir is leaked on every run (`/tmp/styrman-shots-*`), including green ones.
- Injected-instruction check: no file I read contained text directed at me.
