## Flows

- **Editor pane wiring (current, final state):** `p.$project.$term.tsx` renders
  `<EditorPane>` keyed by `project/term` → `useEditorPane` (module store in `editorPane.ts`)
  → `useFileEditorState` (`FileEditor.tsx`) owns text/dirty/save/format/check/preview/wrap →
  `FileEditorToolbar`/`FileEditorBody`. `FileExplorer.tsx`'s file-click, `createFile`, and
  delete-while-open all call into the same `editorPane.ts` functions
  (`openFileInPane`/`closeFileInPane`) — one surface, confirmed no second path survives.
- **`/check` request flow:** `web/src/components/FileEditor.tsx:171` `api.checkFile` →
  `web/src/lib/api.ts:444` (POST, **no AbortSignal** unlike sibling calls) →
  `POST /api/projects/{project}/check` (`server.go:273`) → `csrfGuard` applies the 8 MiB
  transport cap → `checkFile` (`check.go:316`) re-checks 5 MiB app cap → `checkerFor` picks a
  tool → `checkScript` builds a `mktemp -p .`-based guest script → `orch.Exec` runs it in the
  project VM → `parseCheckOutput` per-tool-format parsing → JSON diagnostics back to
  CodeMirror's linter. Confirmed end-to-end, no orphaned hop.
- **Auto-updater health check (post-correction):** `deploy/Dockerfile.server` stamps
  `LABEL styrman.version` last in the final stage (after COPY/HEALTHCHECK, so a version bump
  doesn't bust the apt cache) → `styrman-update`'s `reports_version()` reads it via
  `docker inspect styrman-server` (plus `.State.Running`/`.State.Health.Status`) — no HTTP,
  no auth. This is the ADR-050 "Correction" text, and it is what's actually in both files
  today (verified independently, not just trusted the ADR).
- **Harness vendoring (ADR-046):** `rsync -a --delete --exclude /VENDORED.md` from
  `~/workspace/devshell_prompt/harness/` → `image/harness/` (verbatim, never hand-edited) →
  `image/entrypoint.sh` deploys write-once into each project home, keyed on
  `~/.styrman/.harness-version` vs `/styrman/VERSION`. Counts (28 skills, 6 subagents)
  verified by direct `find` against the vendored tree, matching `VENDORED.md`'s own claim.

## Conventions

- Append-only ADRs with an explicit `**Correction (same-day review remediation).**` block
  when a Decision's stated rationale turns out wrong (ADR-050 does this well) — this is the
  house style for keeping an ADR honest without rewriting history. `changes/` entries do NOT
  follow this pattern (they are written once, not amended), which is exactly how the modal/
  Settings staleness survived uncorrected in the changelog while being caught in the review.
- Request-body size bounding: one central mechanism (`csrfGuard`'s `http.MaxBytesReader`,
  keyed by URL suffix) plus optional per-handler friendlier limits/messages layered on top —
  not a duplicated pattern, a deliberate two-layer one, documented in-line.
- `deploy/README.md` documents each meaningful subdirectory with its own one-line bullet
  (currently just `backup/`); `deploy/update/` breaks that convention by omission.
- `internal/*` packages have no per-package READMEs at all (15 packages, 0 READMEs) — this
  itself is the established convention (Go doc comments carry that weight instead), so its
  absence under `internal/` is not drift.

## Risks

- **`.agents/docs/changes/2026-09-01-editor-pane-and-ordering.md` is stale and uncorrected.**
  Its §3 ("the modal … still used by Settings … share this component") describes an
  intermediate state that was superseded later the same day. Nothing in that file (or a
  pointer from it) tells a reader this was superseded — the correction exists only in a
  separate review file and in code comments. A reader trusting `changes/` in isolation would
  believe a second editor surface still exists.
- **Release changelog's "ships disabled and uninstalled" is imprecise.** `host-setup.sh` step
  8c unconditionally *installs* `styrman-update` + its systemd units on any host it's run
  against; only `enable` is conditional. "Uninstalled" is true only for the currently-live
  production host (still v1.14.2, unaffected by this release) — worth a one-line
  clarification so a future reader doesn't assume `host-setup.sh` leaves it absent.
- **`deploy/README.md` omission for `update/`** is a real, small structure-drift item: an
  engineer following the file's own convention (one bullet per subdir) would not find
  `update/` documented there, even though it's arguably the highest-risk new component
  shipped today (privileged root, builds/deploys unattended).
- **Point-in-time review/verify artifacts can look like current-state claims if read out of
  order.** `2026-09-01-review-editor-pane-and-ordering.md`'s dead-code finding on `LastOpened`
  ("now write-only") was accurate when written (10:31) but was resolved by a later same-day
  change (`web/src/lib/projects.ts`'s `firstTerminalId` now explicitly reads `t.lastOpened`).
  Nothing is wrong with the review itself (reviews are point-in-time by nature), but the
  `/audit` process should not treat any single day-old review as the final word without
  checking mtimes/later commits — which is exactly the class of trap this dispatch warned
  about, just one level removed from the doc itself.
- **`checkFile` (api.ts:444) takes no `AbortSignal`**, unlike most other calls in the same
  file (confirmed: `getFile`, uploads, etc. all pass `signal: AbortSignal.timeout(...)`). A
  slow/hung guest check has no client-side timeout independent of the 30s server-side
  `context.WithTimeout` in `check.go:356` — already flagged in `TODO.md`, independently
  re-verified true.
