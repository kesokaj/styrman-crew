# Recon — project-resources   (2026-10-05)

## Status: COMPLETE

## Question
Per-project CPU/RAM/Docker-disk settings: where create/rebuild/store/API/UI/disk/host-config live, what to mirror, what breaks.

## Summary
The network-mode toggle (`internal/httpapi/network.go` `setProjectNetwork`, orchestrator `WithProject`/`lockedProject`, `ensureRunningLocked` mismatch-recreate) is the template: under the project lock, inspect, stop, persist the record, `EnsureRunning`. The container's Resources come from global `cfg.VCPUs/MemoryMB` at `orchestrator.go:1081-1087`, so they must come from a per-project value passed through `RunOpts`/`createSpec`. The record (`project.Project`, one JSON file per user, absent fields = zero) needs new fields, and zero = unlimited gives a free migration. Biggest findings: (a) `deploy/host-setup.sh` does NOT create the clh shim wrapper (it symlinks the default shim, which resolves to the qemu config); the NUC's `/usr/local/bin/containerd-shim-mvm-v2` is a hand-made wrapper with `KATA_CONF_FILE=...configuration-clh.toml` and no repo file/doc reproduces it, and `host_converge` only manages the firewall files, so there is no existing config-sync path; (b) there is no admin-for-any-project path today (stores are per-user, `getProjectFor` uses the caller's own space); (c) `STYRMAN_DOCKER_DISK_GB` is baked into the container ENV at create time, so it cannot change on a live container without a recreate.

## Flows
- Toggle today: PUT /network -> `getProjectFor` -> `WithProject(lock)` -> `Status`/`ModeMismatch` -> `Stop` -> `projects.SetLanAccess` (inner `netMu`) -> `pr.EnsureRunning(RunOpts{Lan: lanOf})` -> `ensureRunningLocked` creates network (bridge name from mode) + container -> background `EnsureSelfAttached`. A not-running project only writes the record; the next start applies it through the in-`ensureRunningLocked` mismatch recreate.
- For resources the equivalent is "sizing mismatch": compare record (cpus/mem/disk) with `insp.HostConfig`/Env, stopped container -> remove and recreate (existing pattern); running container -> handler does stop + persist + start, like the toggle. Disk grow is NOT a rebuild: online exec path, with a stopped project grown at the next boot via the entrypoint.

## Conventions
- Handlers: 404 before authz; reply decided under lock, written after; failure messages say what state the project is in; slog Info with `by`, `project`, `projectName`.
- Store setters: mutex, copy-on-write, rollback on failed `save()` (M20), no-op on equal.
- A value read at start must be re-read under the project's lock (RunOpts closure).
- Comments say why; behavioural text changes must update every restating comment/doc/test (STYRMAN_VCPUS prose in `config.go:106-107`, `orchestrator.go:1079-1083`, api.md, deploy.md).
- Tests: orchestrator via fake docker; handlers via `fakeMode`; new tests in new files (writing-files rule); Tier 2/4 counts in `testing/styrman/README.md` in the same commit.

## Risks
- Unlimited semantics: Kata's unset = 1 vCPU/2 GB, not "all host". Must be a concrete value computed on the host (cores via `runtime.NumCPU`, RAM from `/proc/meminfo`; inside the server CONTAINER these may not match the host: check `NumCPU` honours cgroup limits and where the server container is run) or a Kata config change. Unprobed.
- Env-baked disk size: a stopped container created before this change carries the OLD operator disk env; the rebuild-on-start check needs a defined "sizing signature" including env; `ContainerUpdate` cannot change env.
- A rebuild kills live terminals (existing UX for the toggle; `lanRebuildTimeout` 3 min; client timeout 210 s) and anything living only in the container filesystem (documented in AGENTS.md for the toggle) is lost; now a mere CPU edit does it. Dockerd inside the guest restarts with it.
- "Existing projects rebuilt on next start": the rebuild branch only handles stopped containers (a running one is deliberately skipped to protect sessions), and every old container has Resources of 0/0 (or env-set values) vs a new "unlimited = concrete number" default, so every existing project would rebuild once on its next start (a fleet-wide, one-time cost; confirm that is intended).
- Rebuilding on mismatch must also resolve a "cannot read record" case fail-safe (BUG-031/032 shape) and never retry-loop if Docker/Kata rejects an oversize Memory/NanoCPUs request; a project that cannot start because the number exceeds the host needs a clear error path (host-limit validation).
- host-setup edits Kata's packaged toml: overwritten on a Kata upgrade; the wrapper script is outside the repo today (drift between NUC and fresh hosts: BUG-070 family).
- `reclaim_guest_freed_memory` ("Enabling this feature may sometimes reduce the speed of memory access in the VM", toml comment) only takes effect on next sandbox start.
- Admin-on-any-project requires cross-user project lookup that does not exist; a naive version would leak cross-tenant existence (404 rule) or lock-key (`key(user,project)`) under the wrong user.
- Online resize in a Kata guest unverified: `losetup -c` + `resize2fs` on a mounted loop ext4 over virtiofs; grow-only (5-500, never shrink) needs a server-side check against the image's current size; if resize fails the record must not claim the larger size (record-vs-in-force again).
- Stale statements in tests/docs: `config.DockerDiskGB()` doc ("NEWLY created") and `settings.tsx` row label will mislead once per-project disk exists.
