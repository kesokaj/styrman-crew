# Recon — updater-status   (2026-10-02)

## Status: COMPLETE (budget-limited; see Not examined)

## Question
Show admins on Settings when the host auto-updater (`deploy/update/styrman-update`) is failing, and why. Root-written status file, server reads read-only, settings API exposes to admins, UI renders.

## Summary
The updater has exactly one trap (EXIT, DOCKER_CONFIG cleanup, line 307) and every failure funnels through `fail()` (line 61, `exit 1`), so a status write fits best in an EXIT trap chained to that cleanup, keyed on a script-level `RESULT`/`REASON` pair set before each `fail`/`exit 0`. The server container mounts only `/var/lib/styrman` (rw, plain bind, `docker-compose.yml:125`); `/etc/styrman` is root 0700 and unmounted (`host-setup.sh:406`), so the server cannot read the status where the updater state lives. Recommended: root writes `/var/lib/styrman/updater-status.json` (a file directly under the mount, server-only area, NOT under `users/`/`homes/`/`projects/`) via atomic temp+rename, mode 0644; server reads it with a bounded, fail-soft read and adds `updater` to `/api/settings` for admins only. The updater STATE_DIR must stay `/etc/styrman/update` (ADR-052 forbids it inside `/var/lib/styrman`, line 261-264), so the status file is a separate path, not STATE_DIR.

## 1. Updater shape (deploy/update/styrman-update, 835 lines)
- `fail()` line 61 prints to stderr, `exit 1`. Call sites by cause:
  - Config/arg: 218 and 230 (test hooks usage), 256 (STATE_DIR unset), 259 (canonicalize), 264 (inside /var/lib/styrman), 274-277 (bad state dir shape). Unknown flag: `exit 2` at 246. Not root: 251.
  - Environment/trust: 310 (no deploy clone), 314 (.env missing), 328, 332, 334 (state dir create/owner/mode), 352, 354, 359 (clone ownership), 364, 368 (.env owner/mode), 391, 393 (gh-token owner/mode), 435/438 (update.env owner/mode).
  - Network/auth: 409 `git fetch failed` (the BUG-084 case; message is generic, git's own stderr goes to the journal only because `2>&1` is inside the `if`, not captured — capture needed for "authentication" vs "network").
  - Tags: 416 (no stable tags), 450 (`verify_tag` refused LATEST).
  - Deploy: 815 (no previous version, LATEST latched failed), 833 (rolled back, LATEST latched), 835 (rollback also failed). Deploy-internal `return 1` paths (676, 692 no token, 694, 706) land on 809 `ERROR: did not come up healthy` -> latch at 813.
- `exit 0` paths: 336 lock busy (another run; must NOT overwrite status); 769 latched failed tag skipped (LATEST == `failed-version`, no `--force`; this is still a failure state and should report failing, since nothing is being deployed); 777 already up to date (success/ok); 782 `--check` with an update available (must write nothing, `--check` promises to change nothing); 805 deployed (success).
- Traps: one EXIT trap at 307 only when DOCKER_CONFIG is not `/run/*` (under the unit it is `/run/...`, so NO trap is set in production); a RETURN trap inside verify_tag at 159. Comment at 305-306 says any new EXIT trap must chain the cleanup. A new status trap must be installed unconditionally and call the DOCKER_CONFIG cleanup only in the mktemp case.
- Non-tick modes: `__verify-tag` (216-223, gated; exits via `exit 0/1` before arg parsing), `__retire-harness-units` (228-232, gated by `STYRMAN_UPDATE_TEST=1`), `--check` (CHECK_ONLY, 244), `--force` (245). The status trap must be installed only after the test hooks (after line ~248) and skipped when `CHECK_ONLY=true`. The pre-root-check failures (251) and STATE_DIR failures (256-277) occur before any trustworthy path exists; decide whether those write (they cannot know the status path unless it is env-pinned like STATE_DIR).
- STATE_DIR (ADR-052): `STYRMAN_UPDATE_STATE_DIR` has no default (42, 256); canonicalized 259; refuses `/var/lib/styrman` and below (261-264), `/`, and any single-component path (273-278); must be root-owned, not group/world-writable (331-334). Created 0700 with parent (326-328).
- Self-install: `self_install` (503) runs after a health-checked deploy at 801 and rollback at 830 only; installs the verified checkout's copy via atomic rename (493-499); the running bash keeps the old inode, so the NEW script first runs on the NEXT tick (comment 480). A new release's status-writing code therefore first executes on the tick after the one that deploys it. Consequence: until then the old updater writes no status; the first status appears one tick (5 min) after deploy. And a host whose updater is stuck failing (BUG-084 case: fetch fails so no release is ever taken) will never receive the status code via self-install: it must be hand-installed once (`styrman-ctl update`/host-setup or by hand) - a fundamental limit of the feature on the very host that motivated it.
- Unit: `deploy/update/styrman-update.service` pins `STYRMAN_UPDATE_STATE_DIR=/etc/styrman/update` (line 10) and the other targets as Environment=; no ProtectSystem/ReadWritePaths seen (only ProtectHome=yes, ProtectKernel*, NoNewPrivileges), so writing under /var/lib/styrman is not blocked by the sandbox. A new `STYRMAN_UPDATE_STATUS_FILE` pin follows the ADR-052 "no in-script default" shape: unset = no status written (tests and hand-runs safe).

## 2. Where a status file could live
- `/etc/styrman`: root:root 0700 (`host-setup.sh:406-407`, also `styrman-ctl:611`); holds `gh-token` (600), `allowed_signers` (644), `update.env`, `update/` state dir (0700). Not mounted into the server. `deploy/.env` mode 600 (`host-setup.sh:226`).
- Compose server mounts (`deploy/docker-compose.yml`): `/var/run/docker.sock` (122, rw), `/var/lib/styrman:/var/lib/styrman` (125, rw, default rprivate, no `:ro`). The ingress service has `:ro` Caddyfile.base at 29. Server runs `user: '${STYRMAN_UID}:${STYRMAN_GID}'` (75) = the operator's uid, plus docker group; Dockerfile.server not read (not examined).
- Options: (a) bind `/etc/styrman/update-status:ro` - needs a compose change, a root-owned dir that is 0755 inside a 0700 parent (server uid cannot traverse `/etc/styrman`, so mount a dedicated dir like `/var/lib/...` instead) and bind-propagation question (BUG-016). (b) file under the existing `/var/lib/styrman` mount: no compose change (a release adds nothing the server needs mounted, which matters because a mount change needs the stack rebuilt), works the same on NUC and GCP. Server is operator-uid and can already write that tree, so a hostile project cannot reach it (ADR-064 keeps `homes/<u>` server-only; guests only see their own bind). Trust: the file is informational only, never an input to a privileged action, so the lower trust of a server-writable path is acceptable; the server must not treat content as trusted (see risks).
- Recommendation: (b) `/var/lib/styrman/updater-status.json`, written by root with temp file in the same dir + `mv -fT` (atomic; mirrors `atomic_install` 493), mode 0644, never via `mkdir -p`/chown through a path (BUG-009): the directory exists and is server-owned, so root only does `[ -d dir ] && [ ! -L file ]` checks and `mv -fT` onto a regular file or absent target; if the target is a symlink or dir, skip with a log line. Note `mv -fT` over a symlink replaces the symlink itself (safe), but the temp file creation inside an operator-owned dir lets that user race-plant a link at the temp name; use `mktemp` in that dir with `umask 022` or write to the root-owned STATE_DIR and `cp`... simplest safe option: root creates the temp in `/run` (tmpfs, root) then `install -m 644` onto the target; open question below.
- Precedents (all in `.agents/docs/bugs/INDEX.md`):
  - BUG-009 (INDEX:15): root `mkdir -p`+chown followed a guest-plantable symlink; `install -d` re-moded an existing dir. Forbids `-p`/chown through a lower-privileged owner's path; assert non-symlink+owner first.
  - BUG-014 (INDEX:20): root's LAN status file unreadable -> UI showed "off". Advises: an unreadable/absent status reads "cannot confirm", never "ok/off"; derive state from root's last confirmed word. Directly applies to the unreadable-file case.
  - BUG-016 (INDEX:22): rw bind used rprivate propagation, a host tmpfs mount under it was not seen. Advises `:rslave` if root mounts something under a bound path; irrelevant if the file is a plain file on the existing mount.
  - ADR-052 (DECISIONS.md:1948): privileged code has no production-path default; tests use a scratch prefix. Updater STATE_DIR may not be under /var/lib/styrman, so the status file is separate from STATE_DIR.
  - ADR-065 (DECISIONS.md:2403) / ADR-067 (2468): the root-mediated per-project netpolicy status/spool design was deleted; ADR-065 note in guest-writable-paths rule says the server-written, root-read `netpolicy/lan/<uuid>` sat beside `users/`/`projects/`, never under a mounted home (so no guest could plant links), and root read by NAME only, refusing symlinks. ADR-067 deleted it because "root side per-project state" was too costly: a lesson to keep this a single small file with no root-side parsing of server input (the data flows only root -> server here).

## Flows
Timer -> `styrman-update.service` -> script: guards -> fetch (409) -> verify (450) -> latch/up-to-date/check exits (766-783) -> deploy+health (790) -> OK exit (805) or rollback (813-835). Proposed: each exit sets `RESULT`/`REASON`; EXIT trap writes the file once (skipped under `--check`, test hooks, and lock-busy). Server: `GET /api/settings` -> `settings()` -> read file -> `updater` key for admins -> `SettingsPage` banner.

## Conventions
Atomic temp+rename (`atomic_install` 493); `log()` lines for every skip; root asserts owner/mode before trusting input; no in-script production defaults (ADR-052); fail-soft server reads with a stderr WARN; writeErr/writeJSON; colour tokens; tests name BUG/ADR in comments; docs/README count lines updated in the same commit.

## Risks
1. Self-install lag/bootstrapping: the code that writes status only runs after a successful deploy plus one tick; a host stuck on a failing fetch (the BUG-084 host itself, still 1.38.0) will never receive it and needs a manual `install -m 755` of the new script. The UI shows nothing exactly where it is most needed. Needs the operator's call.
2. Staleness: "ok at T" persists forever if the timer is disabled/host down. Include `checkedAt` and have the server flag `stale` when older than e.g. 3 timer intervals (timer interval not read; check `deploy/update/styrman-update.timer`) - not "ok".
3. Missing file must say nothing (never set up), but a file that exists and is unreadable/unparseable/oversized is "cannot confirm" (BUG-014), distinct from missing. For a host whose updater was never self-updated, absence is also indistinguishable from "failing with the old script".
4. Remote text on the page: git stderr and tag names reach the file. Write only a closed reason code (`auth`, `network`, `no-tags`, `signature`, `deploy-failed-rolled-back`, `config`) plus optional tag matched against `^v[0-9]+\.[0-9]+\.[0-9]+$`; never raw git output (could contain the token URL or control chars). Server re-validates the code against the allowlist; React escapes text, but keep it plain.
5. The file sits in a server-writable tree: the server (and any code in it) could forge it; acceptable for info, but do not treat it as authoritative.
6. Trap interaction: under the unit no EXIT trap exists today; an `exit 1` from `fail()` inside a command substitution/subshell does not trigger the parent's EXIT trap with the right RESULT. `set -e`/`ERR` not examined. Failures before line ~248 and lock-busy must not write.
7. Latched-failed (769) exits 0 and repeats every tick forever: the status must stay "failing" there (reason: release latched), and `--force` clearing resets it.
8. Writing into the operator-owned `/var/lib/styrman` as root: temp-file symlink race by that user; use root-owned temp + rename, no chown through the path (BUG-009).
9. Documentation duty: new env pin, status file schema, and settings JSON key need specs in `.agents/docs/specs/styrman/deploy.md`, `versioning.md`; ADR required for the structural choice (global rule 4). `REQUIREMENTS.md` not checked for conflicts (not read).
