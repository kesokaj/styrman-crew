## Proposals

### Proposal 1: A second target exercises the shared path — learnings go back in the same change, and the fresh-host path is exercised deliberately
Scope: project — Target: `.agents/rules/shared-path-learnings.md` — Status: applied 2026-09-22 (the v1.37.0 release commit)
Scope rule: target-in-project
Trigger: findings 2 and 4. Current behavior: the plan froze `host-setup.sh`/`styrman-ctl` as Out; the NUC never re-runs steps guarded by "already installed", so a dead download URL survived every green gate since the first bring-up. Expected behavior: any defect or simplification a second target exposes in the shared path is fixed there in the same change (D14); a change to `host-setup.sh`'s provisioning steps, or a release that carries one, names how the FRESH-host path was exercised (`deploy/gcp/vm.sh create` + `install.sh` against a new VM, or "unexercised" in the gate report).
diff (new file):
```markdown
# A second target exercises the shared path (BUG-070, operator 2026-09-21)

The first GCP bring-up found that `host-setup.sh` could not install Kata on
any fresh host: the download URL had been dead upstream for months, hidden by
`[[ ! -x /opt/kata/bin/kata-runtime ]]` on the NUC, which never re-runs the
step. The operator: "take your learnings back to local if any".

- What a second target (GCP, a fresh VM, a new machine) teaches about the
  SHARED path — `host-setup.sh`, `styrman-ctl`, the updater, the image — is
  fixed in the shared path in the same change, never kept target-specific.
  The change entry carries a "Learnings for the local host" section, with
  "none" written deliberately when there are none.
- A step guarded by "already installed" is verified only by a host that has
  not installed it. A change to such a step, or a release carrying one,
  states how the fresh-host path was exercised: `deploy/gcp/vm.sh create`
  + `deploy/gcp/install.sh` against a new VM, or "fresh-host path
  unexercised" in the gate report — never a green re-run on the NUC.
- A download's checksum comes from something the publisher still publishes
  (GitHub's release-asset digest), never a sidecar file assumed to exist.

Same family as BUG-035 (a mechanism must reach every caller — here the
fresh-host caller) and BUG-056 (an external publisher changing under a green gate).
```
Rationale: the rule recurs by construction — every provisioning step is guarded this way — and the GCP scripts now make the fresh-host exercise cheap.

### Proposal 2: A remote check names the transport's failure before the condition's
Scope: project — Target: `.agents/rules/remote-check-names-transport-first.md` — Status: applied 2026-09-22 (the v1.37.0 release commit)
Scope rule: target-in-project
Trigger: finding 3. Current behavior: `status` and `install.sh` attributed an unreachable VM to "not installed" / "no /dev/kvm" (fixed in `lib.sh` `ssh_reachable`). Expected behavior: every script that diagnoses over ssh/HTTP starts with a reachability probe and refuses with the transport's own message; a management port is not exposed publicly when the platform offers a tunnel.
diff (new file):
```markdown
# A remote check names the transport's failure first (BUG-069)

The first GCP install died with "no /dev/kvm on styrman" while the VM had
KVM: the operator's own network had started dropping port 22, and both
`vm.sh status` ("styrman not installed") and `install.sh` diagnosed a
condition through an ssh they had not checked. Scanners reached the VM's
public 22 within four minutes of boot.

- A check made over a transport (ssh, HTTP, a broker) probes the transport
  first — one `true` over ssh, one `/healthz` — and a transport failure is
  reported as exactly that, with the tool's own troubleshooting command,
  never as the condition the check was about. `deploy/gcp/lib.sh`
  `ssh_reachable`/`ssh_hint` is the model; a new remote check reuses it.
- A test of such a check plants a transport failure (`FAKE_SSH_RC=255`) and
  asserts the message names the transport and NOT the condition
  (`TestGCPSSHUnreachableIsNamed`).
- A management port (ssh) is not exposed publicly when the platform offers
  a tunnel (IAP here); the public path stays as an explicit opt-in.

Same family as BUG-034 (silence from your own instrumentation) and BUG-040
(a green run against the wrong server): a signal read as the wrong thing.
```
Rationale: one line of `lib.sh` prevents the class; the rule keeps the next script from re-deriving it.
